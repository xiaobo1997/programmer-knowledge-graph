# 从零开始认识 CI/CD 系列导读

> 本系列共 10 篇（0 导读 + 6 入门正文 + 3 实践篇），覆盖持续集成/持续部署整个知识面：流水线设计、构建提速、测试门禁、制品管理、部署策略与回滚，以及 GitHub Actions 的三篇可复制实战。
> 本篇是导读：先建立「CI 管质量反馈速度、CD 管发布可控性」的心智模型，再决定从哪读起。

## 一、为什么需要这套系列

「代码写完」和「代码在线上创造价值」之间隔着一条完整链路：构建、测试、打包、部署、验证、（出问题时）回滚。CI/CD 把这条链路自动化，它的价值常被误解为「省人力」——真正的价值是**反馈速度与发布确定性**：一次提交 10 分钟内知道能不能上线，一次发布 5 分钟内能回到上一个版本。发布不可控的团队，功能迭代速度迟早被发布恐惧拖住。

学 CI/CD 常见两种卡法：**工具视角**——只会写某个平台的 YAML，换平台归零，也回答不了「这个阶段为什么存在」；**链路盲区**——构建会跑了，但制品怎么管理、数据库变更怎么跟代码一起发布、回滚怎么设计没有概念。这套系列按「链路环节」组织，每个环节讲机制与取舍，工具只是载体。

## 二、全局心智模型

```mermaid
flowchart LR
    C[代码提交] --> CI[CI: 构建与验证<br/>反馈速度是生命线]
    CI --> ART[制品: 不可变的版本化产物]
    ART --> CD[CD: 部署与验证<br/>可控性是生命线]
    CD -.指标异常.-> RB[回滚: 分钟级回到上一个制品]
    CI -.质量门禁不过.-> C
    CD -.发布策略.--> P[生产: 滚动/蓝绿/金丝雀]
```

三个要点：

1. **CI 的生命线是反馈速度**：构建超过 15 分钟，开发者就会批量提交、并行开发，集成的「持续」名存实亡——所以缓存、并行、测试分层都是 CI 的核心课题而非优化点缀。
2. **制品是 CI 与 CD 的契约**：CI 产出不可变制品（镜像/包），CD 只负责把这个制品部署到各环境。「同一个制品走到生产」是发布确定性的基石（镜像构建细节归[Docker 系列](../../../docker/入门层/从零开始认识Docker系列/0_系列导读-全景.md)）。
3. **回滚是设计出来的，不是运气**：能回滚的前提是制品可追溯、配置可回退、数据库变更可兼容——这些都要在流水线设计时预留。把 CI/CD 放进交付架构看，它处在「代码世界」与「运行世界」交界的上下游——架构上把这条边界设计清楚（构建产物即契约），两个世界才能各自演进互不拖累。

## 四、入门者最容易踩的 3 个认知误区

### 误区 1：CI/CD 等于「会写 YAML」

流水线文件只是载体，核心是链路设计：阶段怎么分才能快速反馈、制品怎么管才能确定性发布、门禁怎么设才能不形同虚设。工具从 Jenkins 换到 GitHub Actions 的团队很多，链路没设计对，换什么工具都是「更快的垃圾」。

### 误区 2：「部署成功 = 发布完成」

部署是把制品放到生产环境，发布是让流量看到新版本——两者解耦（金丝雀/特性开关）才有「部署高频、发布从容」。把两者焊死的团队，每次发布都是一次全量赌博。

### 误区 3：「回滚是失败才需要的东西」

回滚能力是发布频率的前提：敢频繁发布，是因为知道 5 分钟内能回来。没有演练过回滚的流水线，发布频率上不去——这不是胆量问题，是工程问题。
