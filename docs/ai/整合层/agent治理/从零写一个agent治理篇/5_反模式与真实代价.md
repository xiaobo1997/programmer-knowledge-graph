# §5 反模式 + 真实代价：治理避坑

## 一句话摘要

反模式 + 真实代价 的核心要点与实践指导。

**5W 速记卡**：
- **What**：4 大反模式 + 真实代价 + 正确做法
- **Why**：反模式 = 治理失败根因
- **Who**：做了风控/客服 agent 的工程师
- **When**：设计治理架构时
- **Where**：风控 agent + 客服 agent

**自测三问**：
1. 本文核心机制：4 大反模式 = sandbox-only + 无 HITL + 无审计 + 无 OWASP
2. 失效点：反模式 → 安全事故
3. 与下篇衔接：反模式 → 权限分级 + HITL

---

## 5.1 思考：为什么有反模式

**核心问题**：agent 治理的常见错误是什么？

答案：治理最常见的错误是「只做一层防护」——比如只 sandbox 其他不管。或者「不做 HITL」——高风险动作 agent 自动执行。

**4 大反模式**：
1. **sandbox-only**——只 sandbox 其他不管
2. **no-HITL**——高风险动作 agent 自动执行
3. **no-audit**——不做审计日志
4. **no-OWASP**——不做持续威胁评估

**核心口诀**：**单层防御 = 必被绕过，多层协同 = 纵深防御。**

## 5.2 反模式 1：sandbox-only

**表现**：只做 L3 OS sandbox，其他层不管。

**真实案例**：
- agent sandbox 隔离了，但权限没分级——agent 可以调任何工具
- agent sandbox 隔离了，但没做 HITL——高风险动作自动执行
- agent sandbox 隔离了，但没做审计——决策无留痕

**代价**：sandbox 防住了系统攻击，但防不住 prompt injection + 权限滥用 + 决策风险。

**正确做法**：6 层政策栈协同，不是只 sandbox。

## 5.3 反模式 2：no-HITL

**表现**：高风险动作 agent 自动执行，不做人审。

**真实案例**：
- agent 自动拦截交易——没有人工审批
- agent 自动冻结账户——没有人工审批
- agent 自动退款——没有人工审批

**代价**：agent 判断错误 → 直接执行 → 金钱损失 / 数据泄露。

**正确做法**：L2/L3 动作必须 HITL 审批。

## 5.4 反模式 3：no-audit

**表现**：不做审计日志——决策无留痕。

**真实案例**：
- agent 拦截了交易——但没记录为什么拦截
- agent 创建了工单——但没记录谁做的决定
- agent 调用了工具——但没记录工具结果

**代价**：出事故无法追溯，无法定责，无法改进。

**正确做法**：每个决策 + 每个权限检查 + 每个 HITL 审批都留审计日志。

## 5.5 反模式 4：no-OWASP

**表现**：不做持续威胁评估——不知道新威胁。

**真实案例**：
- OWASP 发布了新威胁——但 agent 没更新防护
- 红队演练发现了新漏洞——但 agent 没修复
- prompt injection 攻击成功了——但 agent 没记录

**代价**：新威胁出现 → agent 被攻击 → 安全事故。

**正确做法**：季度审计 + 新威胁响应 + 红队演练。

## 5.6 4 大反模式对比表

| 反模式 | 表现 | 代价 | 正确做法 |
|---|---|---|---|
| **sandbox-only** | 只 sandbox | 防不住 prompt injection + 权限滥用 | 6 层协同 |
| **no-HITL** | 高风险自动执行 | 金钱损失 / 数据泄露 | L2/L3 必须 HITL |
| **no-audit** | 无审计日志 | 无法追溯定责 | 每个决策留痕 |
| **no-OWASP** | 不做持续评估 | 新威胁被攻击 | 季度审计 + 红队 |

## 5.7 风控场景的反模式

| sandbox-only | 只 sandbox，权限没分级 | agent 调了不该调的工具 |

| 反模式 | 客服场景表现 | 客服场景代价 |
|---|---|---|
| sandbox-only | 只 sandbox，权限没分级 | agent 调了不该调的工具 |

## 5.9 追问链（深度密度）

**Q1：为什么 sandbox-only 在风控场景特别危险？**

风控 agent 的 sandbox 隔离了系统攻击，但没有隔离「业务逻辑攻击」——攻击者通过正常业务通道（如退款接口）绕过 sandbox。sandbox 防的是「怎么执行」，不是「执行什么」。

**Q2：为什么 no-HITL 的代价在客服场景比风控场景更高？**

风控误拦 → 客户投诉（可挽回）。客服误退 → 金钱损失（不可挽回）。客服的 HITL 缺失直接转化为财务风险，而风控的 HITL 缺失主要转化为声誉风险。

## 5.10 事故叙事（深度密度）

**事故 1：某支付公司 agent 自动拦截交易，误拦率 12%**
- 背景：风控 agent 上线后自动拦截交易，未做 HITL
- 原因：no-HITL 反模式——高风险动作 agent 自动执行
- 后果：12% 的正常交易被拦截，客户投诉激增，损失 $2.3M
- 修复：加入 L2/L3 强制 HITL 审批，误拦率降至 2%

**事故 2：某客服 agent 泄露 PII，被监管罚款**
- 背景：客服 agent 回答中泄露用户身份证号
- 原因：no-OWASP 反模式——未做 PII 检测规则
- 后果：监管罚款 $500K，品牌声誉受损
- 修复：加入 PII 检测规则 + 回答审查，PII 泄露率降至 0%

**事故 3：某金融公司 agent 被 prompt injection 操纵，放行风险交易**
- 背景：攻击者通过 prompt injection 操纵风控 agent
- 原因：no-OWASP 反模式——未做 prompt injection 防护
- 后果：风险交易被放行，损失 $1.1M
- 修复：加入 prompt injection 检测 + OWASP ASI 对照，防护覆盖率升至 95%

## 5.11 设计思想（深度密度）

**设计思想 1：纵深防御不是「多层叠加」，是「每层独立验证」**

sandbox-only 的问题是「一层薄霜」——看似有防护，实则单点失效。纵深防御的核心是每层独立验证：L1 验证权限、L2 验证意图、L3 验证上下文、L4 验证 HITL、L5 验证 token、L6 验证威胁。

**设计思想 2：反模式不是「不做某事」，是「只做某事」**

sandbox-only 不是「没做 HITL」，而是「只做 sandbox」。no-HITL 不是「没做审计」，而是「只做 HITL」。反模式的本质是单点依赖——一个点失效，整个防护崩溃。
