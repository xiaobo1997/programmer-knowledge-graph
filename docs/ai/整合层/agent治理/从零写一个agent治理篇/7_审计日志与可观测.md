# §7 审计日志 + 可观测：治理落地

## 一句话摘要

审计日志 + 可观测 的核心要点与实践指导。

**5W 速记卡**：
- **What**：审计日志 + 可观测体系
- **Why**：治理需要可观测才能发现问题
- **Who**：做了风控/客服 agent 的工程师
- **When**：设计审计日志时
- **Where**：风控 agent + 客服 agent

**自测三问**：
1. 本文核心机制：审计 = Trace + 日志 + 指标
2. 失效点：无审计 → 无法追溯
3. 与下篇衔接：审计日志 → 评估 + 演练

---

## 7.1 思考：审计为什么重要

**核心问题**：agent 审计为什么重要？

答案：agent 自主决策——决策可能有误，误决策需要追溯。不做审计，出事故无法定责，无法改进。

**审计的三个层次**：
1. **Trace**——每个决策的完整链路
2. **日志**——每个操作的记录
3. **指标**——安全指标的度量

**审计日志的 6 个字段**：
| 字段 | 说明 |
|---|---|
| timestamp | 决策时间 |
| agent_id | agent ID |
| action | 动作（查/标记/拦截/退款） |
| risk_level | 风险等级 |
| decision | 决策结果（放行/拦截/人工审核） |
| reason | 决策依据 |

## 7.3 风控 agent 审计日志

风控 agent 的审计日志：

```python
audit_log = {
    "timestamp": "2026-09-21T10:00:00Z",
    "agent_id": "risk-agent-001",
    "action": "block_transaction",
    "risk_level": "high",
    "decision": "block",
    "reason": "规则 rule_001 命中：金额 > 10000",
    "h_itl": "auto",
    "user_id": "user_123",
    "transaction_id": "txn_456"
}
```

**风控场景的审计重点**：
- 拦截决策：为什么拦截？
- 规则命中：哪条规则命中？
- LLM 判断：LLM 为什么这样判断？
- HITL 审批：谁审批的？什么时候？

## 7.4 客服 agent 审计日志

客服 agent 的审计日志：

```python
audit_log = {
    "timestamp": "2026-09-21T10:00:00Z",
    "agent_id": "service-agent-001",
    "action": "create_ticket",
    "risk_level": "low",
    "decision": "create",
    "reason": "用户咨询退款政策",
    "h_itl": "auto",
    "user_id": "user_123",
    "query": "如何退款？"
}
```

**客服场景的审计重点**：
- 回答内容：为什么这样回答？
- PII 泄露：是否泄露了敏感信息？
- HITL 审批：谁审批的？什么时候？
- 工具调用：调了什么工具？结果是什么？

## 7.7 追问链（深度密度）

**Q1：为什么 Trace 比日志更重要？**

日志记录「发生了什么」，Trace 记录「为什么发生」。日志是事后追溯，Trace 是事前预防。风控 agent 拦截交易——日志只能看到「拦截了」，Trace 能看到「为什么拦截、哪条规则命中、LLM 怎么判断的」。Trace 是可观测的核心。

**Q2：为什么安全指标要分风控和客服两套？**

风控关心「拦截准确率/误拦率/漏拦率」——钱有没有被骗。客服关心「回答准确率/误答率/PII 泄露率」——用户有没有被骗。两套指标对应两类风险——金融风险 vs 用户风险。不能一套指标打天下。

## 7.8 事故叙事（深度密度）

**事故 1：某风控 agent 拦截交易，但审计日志没记录原因**
- 背景：风控 agent 拦截交易，团队无法追溯为什么拦截
- 原因：no-audit 反模式——审计日志缺字段
- 后果：无法定责，无法改进，误拦率居高不下
- 修复：补齐审计日志 6 字段 + Trace 全链路，误拦率从 12% 降至 2%

**事故 2：某客服 agent 泄露 PII，审计日志无记录**
- 背景：客服 agent 回答中泄露用户身份证号
- 原因：no-audit 反模式——审计日志不记录 PII
- 后果：监管罚款 $500K，品牌声誉受损
- 修复：审计日志 + PII 检测 + 回答审查，PII 泄露率降至 0%

**事故 3：某金融公司 agent 被攻击，无法追溯攻击路径**
- 背景：agent 被 prompt injection 攻击，但无 Trace
- 原因：无 Trace + 无审计——无法追溯攻击路径
- 后果：攻击路径不明，防护无效
- 修复：Trace + 审计日志 + 安全指标，防护覆盖率升至 95%

## 7.9 设计思想（深度密度）

**设计思想 1：可观测不是「有日志」，是「有链路」**

日志记录单点操作，Trace 记录全链路。可观测的核心不是「记录了什么」，是「能把一件事从头到尾 trace 清楚」。日志是点，Trace 是线。线比点重要。

**设计思想 2：安全指标不是「度量」，是「决策依据」**

安全指标（准确率/误拦率/漏拦率）不是摆设，是治理决策的依据。指标差 → 调整策略。指标好 → 保持策略。指标是「治理是否有效」的衡量标准。没有指标，治理就是盲治。
