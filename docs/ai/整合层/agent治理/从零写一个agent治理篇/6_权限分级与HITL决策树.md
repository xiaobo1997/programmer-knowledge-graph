# §6 权限分级 + HITL 决策树：风控 + 客服

## 一句话摘要

权限分级 + HITL 决策树 的核心要点与实践指导。

**5W 速记卡**：
- **What**：L0-L3 权限分级 + HITL 决策树
- **Why**：风控和客服都需要权限控制
- **Who**：做了风控/客服 agent 的工程师
- **When**：设计权限体系时
- **Where**：风控 agent + 客服 agent

**自测三问**：
1. 本文核心机制：L0-L3 + HITL 矩阵
2. 失效点：权限过宽 → 安全事故
3. 与下篇衔接：权限分级 → 审计日志

## 6.1 思考：权限分级为什么重要

**核心问题**：agent 权限为什么需要分级？

答案：agent 能调工具 = 能调 API = 能改数据 = 能删记录。不做权限分级，agent 可以做任何事——包括删数据库、改规则、冻结账户。

**权限分级的核心思想**：
- L0 只读（查数据）
- L1 写业务数据（标记/创建）
- L2 外部副作用（拦截/退款）
- L3 系统级（删除/改配置）

**核心口诀**：**agent 默认 L0，L1+ 必须显式授权，任何授权可立即撤销。**

## 6.2 风控 agent L0-L3 映射

| 级别 | 风控场景 | 风险 | 授权方式 |
|---|---|---|---|
| **L0 只读** | 查交易 / 查规则 / 查黑名单 | 低 | 默认允许 |
| **L1 写业务数据** | 标记风险 / 记录日志 | 中 | 显式授权 |
| **L2 外部副作用** | 拦截交易 / 冻结账户 | 高 | 强制 HITL |
| **L3 系统级** | 删交易 / 改规则 / shell | 极高 | 强制 HITL + 多重审计 |

## 6.3 客服 agent L0-L3 映射

| 级别 | 客服场景 | 风险 | 授权方式 |
|---|---|---|---|
| **L0 只读** | 查订单 / 查费率 / 查结算 | 低 | 默认允许 |
| **L1 写业务数据** | 创建工单 / 标记用户 | 中 | 显式授权 |
| **L2 外部副作用** | 退款 / 转账 / 发通知 | 高 | 强制 HITL |
| **L3 系统级** | 删订单 / 改规则 / shell | 极高 | 强制 HITL + 多重审计 |

**HITL 矩阵**：

| 风险等级 | HITL 必要性 | 风控审批人 | 客服审批人 | 决策权 |
|---|---|---|---|---|
| L0 只读 | ❌ 不需要 | - | - | agent 自动 |
| L1 业务 | ⚠️ 抽样（10%）| 业务 owner | 业务 owner | agent 自动 + 事后审计 |
| L2 外部 | ✅ 必审批（实时）| 业务 owner | 业务 owner | 人工实时审批 |
| L3 系统 | ✅✅ 双人审批（实时）| 业务 + 技术 owner | 业务 + 技术 owner | 人工双人审批 |

## 6.5 权限分级的 5 个设计原则

1. **最小权限**——agent 默认只能做 L0
2. **显式授权**——L1+ 必须显式授权
3. **可撤销**——任何授权可立即撤销
4. **审计留痕**——每个权限检查留审计日志
5. **定期审查**——定期审查权限分配

## 6.6 降级方法（4 种）

| 降级方法 | 适用场景 | 示例 |
|---|---|---|
| 批量审批 | L1 抽样 | 10% 抽样批量审批 |
| 异步审批 | L2/L3 | 人工审批队列 |
| 自动审批 + 事后审计 | L1 | 自动审批 + 事后审计 |
| 智能审批 | L1/L2 | AI 辅助决策 |

## 6.7 风控 vs 客服权限对比

| 维度 | 风控 agent | 客服 agent |
|---|---|---|
| L0 | 查交易 / 查规则 | 查订单 / 查费率 |
| L1 | 标记风险 / 记录日志 | 创建工单 / 标记用户 |
| L2 | 拦截交易 / 冻结账户 | 退款 / 转账 |
| L3 | 删交易 / 改规则 | 删订单 / 改规则 |
| HITL 核心 | 拦截/冻结必须审批 | 退款/删除必须审批 |
| PII 风险 | 卡号/身份证 | 姓名/地址/电话 |

## 6.8 追问链（深度密度）

**Q1：为什么 L2 外部副作用必须 HITL，而 L1 写业务数据可以抽样？**

L2 的「外部副作用」意味着动作已经超出系统边界——拦截交易是调外部接口，退款是调支付通道。一旦 AI 判断错误，动作已不可逆。L1 的「写业务数据」只是标记/创建，还在系统内部，可以回滚。所以 L2 必须实时人工审批，L1 可以抽样。

**Q2：为什么 HITL 审批人分「业务 owner」和「技术 owner」两类？**

业务 owner 知道业务上下文（这笔交易是否合理），技术 owner 知道系统上下文（这个接口能调吗）。单一审批人只能看到一面——业务 owner 可能忽略技术风险，技术 owner 可能忽略业务风险。双人审批 = 两面验证。

## 6.9 事故叙事（深度密度）

**事故 1：某风控 agent 自动冻结账户，误冻 500+ 正常账户**
- 背景：风控 agent 上线后自动执行冻结，未做 HITL
- 原因：L2 外部副作用无 HITL——拦截/冻结必须人工审批
- 后果：500+ 正常账户被冻结，客户投诉，损失 $800K
- 修复：L2 强制 HITL + 降级方法（批量审批），误冻率降至 0.1%

**事故 2：某客服 agent 自动退款 $50K，账户被盗**
- 背景：攻击者通过 social engineering 获取客服 agent 权限
- 原因：L2 外部副作用无 HITL——退款必须人工审批
- 后果：$50K 被退款，账户被盗
- 修复：L2 强制 HITL + 权限分级（最小权限），退款需双人审批

**事故 3：某金融公司 agent 删数据库，权限过宽**
- 背景：agent 被赋予 L3 权限，可以删交易/改规则
- 原因：权限过宽——agent 默认 L0，L3 需多重审计
- 后果：数据库被删，业务中断 4 小时
- 修复：权限分级 + L3 强制 HITL + 多重审计

## 6.10 设计思想（深度密度）

**设计思想 1：权限分级不是「给权限」，是「控动作」**

L0-L3 不是权限等级，是动作风险等级。L0 是查（无副作用），L1 是标记（低副作用），L2 是外部动作（高副作用），L3 是系统动作（极高副作用）。权限分级的核心是「动作风险分级」，不是「权限大小分级」。

**设计思想 2：HITL 不是「人审」，是「风险决策」**

HITL 的本质不是让人看一遍，而是让人在风险决策点介入。L0 风险低，不需要人审；L1 风险中，抽样审；L2 风险高，实时审；L3 风险极高，双人审。HITL 的粒度由风险决定，不是由习惯决定。
