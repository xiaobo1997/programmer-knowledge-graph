# §8 评估 + 红队演练：治理验证

## 一句话摘要

评估 + 红队演练 的核心要点与实践指导。

**5W 速记卡**：
- **What**：Eval + 红队演练 + 季度审计
- **Why**：治理需要验证才能发现漏洞
- **Who**：做了风控/客服 agent 的工程师
- **When**：治理架构设计后
- **Where**：风控 agent + 客服 agent

**自测三问**：
1. 本文核心机制：评估 = Eval + 红队 + 审计
2. 失效点：不做评估 → 漏洞未发现
3. 与下篇衔接：评估 → 数据与事实声明

---

## 8.1 思考：评估为什么重要

**核心问题**：agent 治理为什么需要评估？

答案：治理不是一次性的——威胁在变，agent 在变，防护也要变。评估 = 持续验证治理是否有效。

**三个评估手段**：
1. **Eval**——日常评估 agent 效果
2. **红队演练**——模拟攻击测试防护
3. **季度审计**——定期全面审计

## 8.2 Eval（日常评估）

Eval 做什么：
- 评估 agent 回答准确率
- 评估 agent 拦截准确率
- 评估 HITL 审批率
- 评估 PII 泄露率

Eval 不做：
- 不评估系统性能
- 不评估用户体验

**风控场景 Eval 指标**：
| 指标 | 目标 | 说明 |
|---|---|---|
| 拦截准确率 | > 95% | 正确拦截比例 |
| 误拦率 | < 5% | 误拦比例 |
| 漏拦率 | < 1% | 漏拦比例 |
| HITL 审批率 | < 20% | 人工审批比例 |

**客服场景 Eval 指标**：
| 指标 | 目标 | 说明 |
|---|---|---|
| 回答准确率 | > 90% | 正确回答比例 |
| 误答率 | < 10% | 误答比例 |
| HITL 审批率 | < 20% | 人工审批比例 |
| PII 泄露率 | 0% | PII 泄露比例 |

## 8.3 红队演练（模拟攻击）

红队演练做什么：
- 模拟 prompt injection 攻击
- 模拟 tool misuse 攻击
- 模拟 identity abuse 攻击
- 模拟 data exfiltration 攻击

红队演练不做：
- 不模拟性能攻击
- 不模拟 DDoS 攻击

**红队演练频率**：
| 攻击类型 | 频率 | 风控场景 | 客服场景 |
|---|---|---|---|
| Prompt injection | 每季度 | ✅ | ✅ |
| Tool misuse | 每月 | ✅ | ✅ |
| Identity abuse | 每季度 | ✅ | ✅ |
| Data exfiltration | 每月 | ✅ | ✅ |
| Resource exhaustion | 每周 | ✅ | ✅ |

## 8.4 季度审计

季度审计做什么：
- 对照 OWASP ASI Top 10 检查 agent
- 发现新威胁
- 评估已有防护

季度审计不做：
- 不做日常监控
- 不做实时告警

**季度审计清单**：
- [ ] Prompt injection 防护检查
- [ ] Tool misuse 防护检查
- [ ] Identity abuse 防护检查
- [ ] Data exfiltration 防护检查
- [ ] Resource exhaustion 防护检查

## 8.5 评估 + 红队 + 审计的关系

| 评估手段 | 频率 | 目的 |
|---|---|---|
| Eval | 日常 | 评估 agent 效果 |
| 红队演练 | 季度/月/周 | 发现漏洞 |
| 季度审计 | 季度 | 全面审计 |

**三者协同**：
- Eval 发现效果问题 → 调整 agent
- 红队发现漏洞 → 修复防护
- 季度审计发现新威胁 → 更新防护策略

## 8.6 追问链（深度密度）

**Q1：为什么红队演练频率分季度/月/周？**

Prompt injection 每季度（攻击模式变化慢）。Tool misuse 每月（接口变化中）。Resource exhaustion 每周（资源攻击常发）。频率由攻击变化速度决定，不是由人力决定。

**Q2：为什么季度审计不只查 OWASP ASI？**

OWASP ASI 是威胁清单，但审计还要查「防护是否生效」「策略是否过时」「权限是否过宽」。审计不只是查威胁，是查整个治理体系的有效性。

## 8.7 事故叙事（深度密度）

**事故 1：某金融公司 agent 被 prompt injection 攻击，红队未覆盖**
- 背景：agent 上线 6 个月未做红队演练
- 原因：no-OWASP + 无红队——Prompt injection 未覆盖
- 后果：风险交易被放行，损失 $1.1M
- 修复：季度红队演练 + OWASP ASI 对照，防护覆盖率升至 95%

**事故 2：某客服 agent 回答准确率下降，Eval 未发现**
- 背景：agent 上线后回答准确率从 95% 降至 80%
- 原因：无日常 Eval——效果问题未及时发现
- 后果：用户满意度下降，投诉增加
- 修复：日常 Eval + 监控告警，准确率回升至 92%

**事故 3：某公司 agent 权限过宽，季度审计未发现**
- 背景：agent 权限过宽（L3），季度审计只查威胁
- 原因：审计只查 OWASP ASI——权限未审查
- 后果：agent 可删数据库，业务中断 4 小时
- 修复：审计清单加入权限审查，权限过宽问题发现率 100%

## 8.8 设计思想（深度密度）

**设计思想 1：Eval 不是「测效果」，是「测治理」**

Eval 测的不是 agent 回答得多好，是治理体系是否有效。准确率高 ≠ 治理有效——可能恰好命中了简单样本。Eval 要覆盖边界场景、异常场景、对抗场景。

**设计思想 2：红队不是「找漏洞」，是「测防护」**

红队的目的不是找到多少漏洞，是验证防护是否有效。找到漏洞 → 修复。找不到漏洞 → 防护有效。两种结果都有价值——前者改进防护，后者验证防护。
