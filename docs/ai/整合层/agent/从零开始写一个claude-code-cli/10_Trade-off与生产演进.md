# §10 Trade-off 与生产演进

> **系列**：从零开始写一个 claude-code-cli（整合层 demo 工程）
> **模板**：project-demo-template.md v3.1（§10 = Trade-off 5 维度）
> **核心原则**：每个关键决策都要讲"为什么这样选"——哪怕答案只是"因为 demo 简单"。学习型 demo 的 trade-off 与生产型不同。

---

## 10.1 为什么这样实现（关键决策的理由）

| 决策 | 为什么这样实现 |
|---|---|
| **Python 主版本** | AI 生态绝对主流（openai-python 31k⭐）；脚本式开发快；聚焦 agent 逻辑不被语言特性分散 |
| **不用 LangChain 等框架** | 学习目的——手写才能理解核心机制（框架是黑盒，手写是透明）|
| **requests 直调 API** | 理解"LLM = HTTP POST"的本质；不引入 SDK 依赖 |
| **6 工具用注册表** | 开闭原则——加工具不改核心；生产级 agent 的扩展基础 |
| **权限 5 层** | 纵深防御——单层必被绕过（LLM 不可信任）|
| **JSON 会话存储** | demo 简单可读；生产用 SQLite（并发安全）|
| **argparse** | 标准库零依赖；够用即可（生产用 typer 更友好）|

## 10.2 原理（底层机制）

**核心原理：为什么 agent 要循环？**

传统 LLM 调用 = 一次问答（输入 → 输出）。但真实任务（读文件 → 分析 → 修改 → 验证）需要**多步推理 + 工具调用**——所以 agent 用 **ReAct 循环**：

```
Reason（思考：我该做什么）→ Act（行动：调用工具）→ Observe（观察：工具结果）→ 循环
```

**为什么循环不能无限**：LLM 可能陷入死循环（反复调同一工具）——所以 `max_steps` 限制。

**为什么权限必须绕开 LLM**：LLM 是 pattern matching，没有真正理解"不能做 X"——prompt injection 可以操纵它。所以权限检查是**代码层强制**（hook 在工具调用前），不依赖 LLM 自觉。

## 10.3 实现（代码层面的选择）

| 实现点 | 选择 | 为什么 |
|---|---|---|
| **工具 Schema** | JSON Schema | LLM 函数调用的标准描述格式 |
| **工具结果回传** | 追加到 messages（role=tool）| LLM 需要"观察"才能继续思考 |
| **tool_call 解析** | LLM 输出 JSON → 解析 | demo 简化；生产用官方 function calling |
| **token 计数** | 字符数 // 4 | 简单近似；生产用 tiktoken 精确 |
| **目录边界** | 绝对路径前缀匹配 | demo 够用；生产用真实路径解析（防 ../ 绕过）|
| **危险命令** | 字符串包含匹配 | demo 够用；生产用正则 + 沙箱 |

## 10.4 替代方案（有没有更好的）

| 我们的选择 | 替代方案 | 为什么不选 | 什么场景该用替代 |
|---|---|---|---|
| Python | Node.js（官方同款）| 学习成本高；生态差异 | 想做官方同栈 / 前端集成 |
| 手写（无框架）| LangChain / LangGraph | 学习目的（手写才懂）| 快速生产 / 复杂编排 |
| requests 直调 | openai SDK / anthropic SDK | 减少依赖 + 看本质 | 生产（SDK 处理重试/流式）|
| argparse | typer / click | 零依赖 | 生产 CLI（更友好）|
| JSON 会话 | SQLite / Redis | 简单 | 生产（并发安全）|
| 字符串匹配权限 | 正则 / 沙箱 / 企业策略 | demo 够用 | 生产（安全关键）|

## 10.5 生产路径（demo → 生产怎么演进）

**目前是哪一步**：纯学习 demo——能跑、能理解核心，但不适合生产（无 MCP / 无并发 / 权限简单）。

**演进到生产的路径**（参考官方能力，见 §6）：

```
Step 1：核心夯实（已完成）
  → 6 工具 + ReAct Loop + 5 层权限 + 会话 ✅

Step 2：生态扩展
  → 接 MCP（工具任意扩展）→ 插件系统
  → SubAgent（子任务并行）→ 上下文自动管理

Step 3：企业化
  → 多提供商认证（Bedrock/Vertex）→ 企业 SSO
  → 遥测 + 调试 + 升级通道
  → 企业网关 + MDM → 分发（brew/npm）

Step 4：安全增强
  → 权限从字符串匹配 → 正则 + 沙箱
  → 会话从 JSON → SQLite + 加密
  → 加审计日志（合规）
```

**学习型 demo 的定位**：**停留在 Step 1**——因为目标不是做产品，是理解核心。生产路径写清楚 = 读者知道"如果我要做产品，下一步是什么"。

---

## 小结

**Trade-off 总结**：每个决策都是"**学习优先**"——用最简单方案讲清楚核心机制（手写 + 标准库 + 零依赖），生产化的复杂（MCP / 并发 / 安全 / 企业）**刻意留给 §6 差距分析**。这就是学习型 demo 的 trade-off：**用 2-3 周换核心认知，不为生产化买单。**
