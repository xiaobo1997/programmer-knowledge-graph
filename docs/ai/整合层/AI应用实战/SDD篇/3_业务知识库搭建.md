# §3 业务知识库搭建：团队共享

## 一句话摘要

业务知识库搭建 的核心要点与实践指导。

**5W 速记卡**：
- **What**：业务知识库 = 业务规则 + 领域模型 + 决策记录
- **Why**：团队共享知识，避免知识断层
- **Who**：团队leader + 开发工程师
- **When**：项目启动时 + 迭代中
- **Where**：团队共享

**自测三问**：
1. 本文核心机制：业务知识库 = 规则 + 模型 + 决策 + 经验
2. 失效点：知识库腐化 → 无人维护
3. 与下篇衔接：业务知识库 → 个人知识库

---

## 3.1 思考：为什么需要业务知识库

**核心问题**：团队怎么共享 AI 生成代码的知识？

答案：AI 生成代码的速度很快，但团队没人知道「为什么这样生成」。业务知识库 = 把业务规则 + 领域模型 + 决策记录沉淀下来，让团队共享。

## 3.3 业务规则

**业务规则是什么？**——业务逻辑的正式描述。

业务规则包含：
- 业务流程（交易→清分→结算→对账）
- 业务规则（风控规则 + 合规规则）
- 业务术语（统一语言）

## 3.4 领域模型

**领域模型是什么？**——业务实体的抽象描述。

领域模型包含：
- 实体（交易/账户/订单）
- 关系（交易→账户→订单）
- 约束（金额>0 / 状态合法）

## 3.5 决策记录

**决策记录是什么？**——记录「为什么这样选」。

决策记录包含：
- 为什么选这个方案
- 为什么不选那个方案
- 代价是什么

## 3.6 经验知识

**经验知识是什么？**——踩坑 + 最佳实践。

经验知识包含：
- 踩坑记录（坑 + 解决方案）
- 最佳实践（已验证的方法）
- 反模式（避免的陷阱）

## 3.7 搭建步骤

| 步骤 | 做什么 | 产出 | 优先级 |
|---|---|---|---|
| ① 梳理业务规则 | 业务流程 + 规则 + 术语 | 业务规则文档 | P0 |
| ② 建立领域模型 | 实体 + 关系 + 约束 | 领域模型图 | P0 |
| ③ 记录决策 | 为什么这样选 | 决策记录 | P1 |
| ④ 沉淀经验 | 踩坑 + 最佳实践 | 经验知识库 | P1 |
| ⑤ 维护机制 | 谁来维护 + 怎么更新 | 维护机制 | P0 |

## 3.8 与 AI 辅助的关系

| AI 辅助环节 | 知识库作用 |
|---|---|
| 代码生成 | 按业务规则生成 |
| 代码审查 | 按领域模型审查 |
| 重构建议 | 按决策记录建议 |
| 文档生成 | 按经验知识生成 |

**核心原则**：AI 辅助需要知识库支撑——没有知识库，AI 生成 = 无源之水。

## 3.9 维护机制

**维护机制是什么？**——知识库持续更新的机制。

维护机制包含：
- 负责人（谁负责）
- 更新时机（代码变更 → 文档同步）
- 审查机制（谁审查）

## 3.10 常见反模式

| 反模式 | 表现 | 代价 | 正确做法 |
|---|---|---|---|
| 知识库无人维护 | 知识库腐化 | 无人使用 | 明确负责人 |
| 知识库与代码脱节 | 文档过时 | 误导开发者 | 代码变更 → 文档同步 |
| 知识库过于详细 | 信息过载 | 无人阅读 | 精简 + 索引 |
| 知识库过于简单 | 信息不足 | 不够用 | 分层 + 深度 |
