# 深入理解多级缓存一致性协议

> 本篇是「多级缓存架构」特性层第 1 篇，深入缓存一致性协议的源码级机制、边界条件与生产级参数调优。

## 一、一致性协议的数学模型

### 1.1 CAP 在缓存场景的映射

```
缓存系统的 CAP 三角：

          C (一致性)
         / \
        /   \
       /     \
      /       \
     A -------- P (分区容错)

缓存系统的取舍：
  - L1 本地缓存：AP（可用性优先，短暂不一致可接受）
  - L2 Redis：CP（一致性优先，失效传播保证）
  - L3 DB：CA（单库强一致）
```

### 1.2 不一致窗口量化

```
不一致窗口 = T_写DB + T_失效传播 + T_客户端重试

各阶段耗时：
  T_写DB      = 1-10ms（取决于 DB 延迟）
  T_失效传播  = 1-100ms（取决于传播机制：
                      主动失效=1ms, Pub/Sub=5ms, Binlog=50-500ms）
  T_客户端重试= 0-100ms（客户端重试间隔）

总不一致窗口：
  主动失效：1-20ms
  Pub/Sub：5-100ms
  Binlog：50-500ms
```

## 二、失效传播的源码级分析

### 2.1 Redis Pub/Sub 模式

```
Redis Pub/Sub 源码逻辑（简化）：

PUBLISH channel message
  → 遍历 channel 的订阅者列表
  → 将 message 放入每个订阅者的输出缓冲区
  → 订阅者客户端读取缓冲区

问题：
  - 订阅者离线 → 消息丢失（Pub/Sub 不持久化）
  - 订阅者慢消费 → 输出缓冲区溢出 → 连接断开
  - 无 ACK 机制 → 无法确认送达
```

**生产建议**：Pub/Sub 仅适用于「可丢消息」场景（如缓存失效），不可用于「必须送达」场景。

### 2.2 Redis Streams 模式（推荐）

```
Redis Streams 源码逻辑（简化）：

XADD stream * event_type invalidate key=xxx
  → 追加到 stream 末尾
  → 生成唯一 ID (timestamp-sequence)
  → 消费者组消费：
      XREADGROUP GROUP mygroup consumer1 COUNT 1 STREAMS stream >
  → 消息持久化到 AOF
  → 消费者 ACK 后消息标记为已处理

优势：
  - 消息持久化（AOF + RDB）→ 不丢失
  - 消费者组 → 负载均衡 + 失败重试
  - ACK 机制 → 可确认送达
  - 支持多个消费者组 → 多服务独立消费
```

### 2.3 Canal 订阅 Binlog 模式

```
Canal 工作流程（简化）：

1. Canal Server 连接 MySQL Master
   → 发送 dump 协议
   → MySQL 返回 binlog event

2. Canal 解析 binlog event
   → TableMeta: 表结构信息
   → RowChange: 行变更数据
   → EventType: INSERT/UPDATE/DELETE

3. Canal Client 订阅解析后的事件
   → 根据配置规则过滤（哪些表/哪些操作）
   → 生成失效消息

4. 消息发送到 MQ
   → Kafka / RocketMQ / RabbitMQ

5. Consumer 消费消息
   → 执行失效操作（del L1/L2 key）
```

**Canal 关键配置**：

```yaml
canal.instance.master.address=mysql_host:3306
canal.instance.dbUsername=canal
canal.instance.dbPassword=canal_password
canal.instance.connectionCharset=UTF-8

# 过滤规则：只监听需要失效缓存的表
canal.instance.filter.regex=.*\.(user_info|product_info|order_info).*

# 批次大小
canal.instance.batch.size=1000

# 事务提交间隔
canal.instance.transaction.size=1000
```

## 三、L1/L2 数据不一致的根因分析

### 3.1 根因分类

| 根因 | 发生概率 | 影响范围 | 检测难度 | 修复成本 |
|---|---|---|---|---|
| **失效传播失败** | 中 | 局部 | 高 | 中 |
| **双写顺序错误** | 低 | 局部 | 中 | 低 |
| **网络分区** | 低 | 全局 | 高 | 高 |
| **客户端并发** | 高 | 局部 | 高 | 中 |
| **缓存过期** | 高 | 局部 | 低 | 低 |

### 3.2 失效传播失败

```
场景：
  写 DB 成功 → 失效 L2 成功 → 失效 L1 失败

原因：
  - L1 广播消息丢失（Pub/Sub 不持久化）
  - L1 客户端离线
  - L1 客户端处理超时

检测：
  - 对账脚本定期扫描 L1/L2/DB 的差异
  - 监控「L1/L2 值不一致」的事件数

修复：
  - 对账发现不一致 → 重写 L1
  - 升级为 Binlog 订阅 + MQ 重试
```

### 3.3 双写顺序错误

```
错误顺序：先写缓存 → 后写 DB
  写缓存成功 → 写 DB 失败 → 缓存是脏数据

正确顺序：先写 DB → 后失效缓存
  写 DB 成功 → 失效缓存 → 下次读自然回填

为什么先写 DB：
  - DB 是权威数据源
  - 缓存失效后，下次读一定是从 DB 读最新数据
  - 短暂不一致窗口内，读请求读到的是旧缓存（可接受）
```

## 四、亿级流量下的一致性参数调优

### 4.1 失效传播延迟优化

```
优化目标：减少不一致窗口

优化手段：
  1. 失效消息本地化（同机房部署 Canal + Consumer）
     → 跨机房 RTT 1-5ms → 同机房 RTT 0.1-0.5ms
     → 不一致窗口减少 10-50 倍

  2. 批量失效合并（100 个 Key 合并为 1 条消息）
     → 减少 MQ 消息数量
     → 减少 Consumer 处理次数
     → 延迟从 10ms → 2ms

  3. 管道化失效（Pipeline）
     → Redis Pipeline 一次发送多个 del 命令
     → 延迟从 5ms → 1ms（100 个 Key）
```

### 4.2 缓存预热参数

```yaml
预热策略参数:
  # 预热 Key 数量
  warmup_key_count: 100000  # 10w
  
  # 预热 Batch Size
  warmup_batch_size: 1000   # 每批 1000 个
  
  # 预热 Pipeline 大小
  warmup_pipeline_size: 100 # Pipeline 一次 100 个
  
  # 预热并发度
  warmup_concurrency: 10    # 10 个并发线程
  
  # 预热耗时估算:
  # 10w Key / (1000 Batch × 100 Pipeline × 10 并发)
  # = 10w / 100w = 0.1s (理论)
  # 实际 5-30min (取决于 DB 查询延迟 + 网络延迟)
```

## 五、生产级一致性方案对比

| 方案 | 一致性级别 | 延迟 | 可靠性 | 复杂度 | 适用场景 |
|---|---|---|---|---|---|
| **主动失效** | 强一致 | 1-20ms | 中 | 低 | 单体应用 |
| **Pub/Sub** | 最终一致 | 5-100ms | 中 | 低 | 分布式应用 |
| **Canal + MQ** | 最终一致 | 50-500ms | 高 | 中 | 多服务/跨语言 |
| **Binlog + 事务消息** | 强一致 | 100-1000ms | 极高 | 高 | 金融/账务 |

## 六、核心带走

- **核心一句话**：缓存一致性 = 写 DB 后失效缓存 + 失效传播 + 定时对账
- **策略选择**：金融选 Write-through / 电商选 Invalidate / 社交选 Write-behind
- **失效传播**：Binlog 订阅（Canal）是生产环境推荐方案
- **亿级保障**：预热 + 动态 TTL + 双写补偿 + 定时对账
- **哪里会坏**：网络分区导致失效堆积、消费失败无限重试、双写顺序错误
