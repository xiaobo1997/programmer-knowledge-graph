# 为什么需要分布式任务调度

> 单机 `@Scheduled` 的三堵墙：多实例重复执行、节点挂了任务就丢、几百个任务没人管得了。

## 一句话摘要

> 分布式调度 = 调度中心（谁来触发）+ 执行分片（谁来干）+ 容错补偿（干砸了怎么办）三问题。

## 起步门槛

- 量级分档意识：10w 档任务量 Spring Task+锁即可，千万级任务量需要分片广播与水平扩容，亿级任务量需要秒级调度+工作流编排

## 调度三问题

|| 问题 | 含义 | 典型场景 |
|---|---|---|---|
| 触发 | 谁来触发、什么时候触发 | cron / 固定频率 / 依赖触发 |
| 分片 | 谁来干、怎么分 | 分片广播 / 负载均衡 / 手动指定 |
| 容错 | 干砸了怎么办 | 重试 / 告警 / 补偿 / 降级 |

## 量级三档

|| 量级 | 方案 | 工具 |
|---|---|---|---|
| 10w 档 | 日均 10w 次任务 | cron + 分布式锁 | Spring @Scheduled + Redis 锁 |
| 千万级 | 日均千万次任务 | 分片广播 + 失败重试 | XXL-Job / ElasticJob |
| 亿级 | 日均亿次 + 秒级 | 秒级调度 + 工作流编排 | PowerJob / 自研平台 |

## 误区

- ❌ 延迟一次执行找任务调度——延迟一次用 RocketMQ 定时消息，周期性任务才用调度中心
- ❌ 以为分片=负载均衡——分片是「数据分片」，负载均衡是「请求分片」，两码事

## 与相邻系列的关系

- **Spring Boot 系列**：单机 @Scheduled 在那边正式讲——本篇只讲「单机局限」
- **RocketMQ 系列**：延迟消息（单次延迟执行）正式定义篇在那边，本系列管周期与编排
- **K8s 系列**：CronJob 深挖在那边，本系列云原生篇只做定位与边界

> 金句：单机 cron 不是不行，行了就撞墙——三堵墙是分布式调度的起点。
