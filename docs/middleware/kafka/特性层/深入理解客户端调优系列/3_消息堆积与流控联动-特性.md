# Kafka 消息堆积与流控联动机制

> 本篇深入消息堆积的根因分析、流控联动机制、亿级流量下的自动降级与恢复策略。

## 一、本文核心

消息堆积 = 生产速度 > 消费速度

流控 = 降级 + 限速 + 优先级

## 二、核心机制原理穿透

### 2.1 消息堆积本质

```
消息堆积 = 消费速度 < 生产速度

堆积增长公式：
  堆积量(t) = ∫(生产速率 - 消费速率)dt
  
  生产速率 > 消费速率 → 堆积增长
  生产速率 < 消费速率 → 堆积消减
  生产速率 = 消费速率 → 堆积稳定
```

### 2.2 堆积根因分析

**生产侧**：
- 流量突增：大促/营销活动/热点事件
- Producer 阻塞：缓冲区满/网络延迟/Broker 不可用
- 消息体积过大：单条消息超过 fetch.max.bytes
- 分区不均：某些分区流量远大于其他分区

**消费侧**：
- 消费逻辑阻塞：外部调用超时/数据库慢查询
- 消费者数量不足：Partition 数 > 消费者数
- 再平衡：再平衡期间消费暂停
- 位移提交失败：提交延迟导致重复消费
- GC 停顿：Full GC 导致消费线程暂停

**Broker 侧**：
- 磁盘 IO 瓶颈：消息写入速度超过磁盘能力
- 网络带宽瓶颈：消息传输速度超过网络能力
- Partition 过多：元数据管理开销过大
- ISR 同步延迟：Follower 同步慢于 Leader

## 三、流控联动机制

### 3.1 生产者流控

```
生产者流控策略：

  1. 背压机制
     → 缓冲区满时，阻塞或降级
     → 缓冲区使用率 > 80% → 启用背压
     → 背压模式：丢弃/降级/排队

  2. 限流
     → 限制 Producer 发送速率
     → 令牌桶/漏桶算法
     → 限流阈值 = Broker 吞吐量 / Producer 数量

  3. 降级
     → 流量超过阈值时，丢弃非核心消息
     → 核心消息：订单/支付/库存
     → 非核心消息：日志/统计/通知
```

### 3.2 消费者流控

```
消费者流控策略：

  1. 限速消费
     → 限制 Consumer 处理速率
     → max.poll.records 控制每次处理数量
     → 处理间隔控制（sleep/限流器）

  2. 批量处理
     → 批量消费 vs 单条消费
     → 批量处理吞吐量更高，但延迟增加
     → 批量大小 = 消费速率 / 处理延迟容忍

  3. 优先级消费
     → 核心消息优先消费
     → 按消息优先级分流到不同消费者组
     → 核心消费者组：高优先级 + 高并发
     → 非核心消费者组：低优先级 + 低并发
```

### 3.3 自动降级

```
自动降级策略：

  1. 堆积检测
     → 位移 lag > 阈值 → 触发降级
     → lag 增长率 > 阈值 → 触发紧急降级

  2. 降级执行
     → 丢弃非核心消息
     → 核心消息进入死信队列
     → 通知运维/触发告警

  3. 恢复策略
     → 堆积消减到阈值以下 → 恢复正常
     → 逐步增加消费速率（退避算法）
     → 监控恢复期间的消息处理质量
```

## 四、亿级流量下参数调优

| 量级 | 生产者流控 | 消费者流控 | 降级阈值 |
|---|---|---|---|
| 十万 QPS | 缓冲区 32MB | max.poll.records=500 | lag > 10w |
| 百万 QPS | 缓冲区 64MB | max.poll.records=2000 | lag > 50w |
| 千万 QPS | 缓冲区 128MB | max.poll.records=5000 | lag > 100w |
| 亿级 QPS | 缓冲区 256MB | max.poll.records=10000 | lag > 500w |

## 五、生产事故与排查

### 事故 1：大促消息堆积

**场景**：某电商大促，消息队列堆积超过 1000 万条。

**现象**：
- Consumer lag 持续增加
- 消费延迟从秒级增加到小时级
- 下游服务数据不一致

**根因**：
- 大促流量是日常 10 倍
- Consumer 数量未弹性扩容
- 消费逻辑包含外部调用，延迟高

**修复**：
1. 大促前预热：增加 Consumer 实例
2. 消费逻辑优化：异步化外部调用
3. 启用降级：非核心消息丢弃
4. 积压处理：积压消息优先处理

### 事故 2：Producer 阻塞导致堆积

**场景**：Broker 集群扩容，Producer 缓冲区满。

**现象**：
- Producer 阻塞在 `send()` 方法
- 应用线程池耗尽
- 上游请求超时

**根因**：
- `buffer.memory` 默认 32MB，不足以缓冲瞬时流量
- `max.block.ms` 默认 60s，阻塞时间过长

**修复**：
1. 增大 `buffer.memory` 到 128MB
2. 设置 `max.block.ms=10000`，超时后降级
3. 启用背压：缓冲区满时丢弃非核心消息

## 六、业内惯例

- 消息堆积检测：Consumer lag 监控 + 告警
- 降级策略：非核心丢弃 + 核心进死信 + 逐步恢复
- 流控参数：buffer.memory + max.poll.records + lag 阈值
- 积压处理：积压消息优先处理 + 批量补偿

## 七、核心带走

- **核心一句话**：消息堆积 = 生产 > 消费，流控 = 降级 + 限速 + 优先级
- **降级策略**：非核心丢弃 + 核心进死信 + 逐步恢复
- **流控参数**：buffer.memory + max.poll.records + lag 阈值
- **哪里会坏**：再平衡期间堆积、Producer 阻塞、消费逻辑阻塞
