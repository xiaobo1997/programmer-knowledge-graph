# 文章验证流程（先想再做）

> 写完一篇文章，**不要急着 commit**。先经过 6 维度验证循环，确保「写得对、写得好、写得安全」。
> 这是「先想再做」原则的执行流程。

## 核心理念

> **写完一篇文章 ≠ 完成。** 写完 + 通过验证 = 完成。

很多人写完博客直接 commit，结果：

- ❌ 留了敏感数据（公司名 / 内部接口 / 业务数据）
- ❌ 错误信息没纠正（链接 404 / 事实错误 / 代码跑不通）
- ❌ 写得不全（漏了关键章节 / 漏了反模式）
- ❌ 内容过时（API 改了 / 库废弃了 / 最佳实践变了）
- ❌ 表达不好（结构乱 / 重复 / 难以理解）

**验证循环 = 在 commit 前发现问题，避免「写到一半就沉淀」污染知识库。**

## 6 维度验证循环

每篇文章 commit 前，按顺序跑这 6 个检查：

```
┌─────────────────────────────────────────────────┐
│  Loop 1: 完整性检查                              │
│  - 6 章节齐全？ 5W 卡有吗？                       │
│  - 代码能跑？截图能看？                            │
│  - 关键概念都覆盖？                                │
└─────────────────────────────────────────────────┘
                     ↓ 通过？
┌─────────────────────────────────────────────────┐
│  Loop 2: 准确性检查                                │
│  - 技术/业务事实正确？（术语/费率/流程）            │
│  - 代码可运行？                                    │
│  - 链接能打开？                                    │
│  - 引用来源真实？                                  │
│  - **Mermaid 语法正确？**（全角括号/特殊字符）     │
│    检查项：grep -n '（\|）' *.md → 排查全角括号    │
│           grep -n 'subgraph.*\[' *.md → 节点命名    │
└─────────────────────────────────────────────────┘
                     ↓ 通过？
┌─────────────────────────────────────────────────┐
│  Loop 3: 隐私 / 安全性检查                          │
│  - 无公司名 / 业务专属词？                          │
│  - 无真实接口 / 域名 / 凭证？                      │
│  - 无真实用户数据 / 业务数据？                      │
│  - 无内部敏感信息？                                │
└─────────────────────────────────────────────────┘
                     ↓ 通过？
┌─────────────────────────────────────────────────┐
│  Loop 4: 时效性检查                                │
│  - API / 库版本是否过时？                          │
│  - 链接是否还能访问？                              │
│  - 「业界现状」是否还准确？                       │
│  - 标注了「最后更新」时间？                       │
└─────────────────────────────────────────────────┘
                     ↓ 通过？
┌─────────────────────────────────────────────────┐
│  Loop 5: 结构 / 表达检查                            │
│  - 章节顺序合理？                                  │
│  - 标题层级清晰？（## / ### 不乱跳）               │
│  - 代码块有语言标记？                              │
│  - 表格 / 列表 / 引用用得对？                     │
│  - 没有重复内容？                                  │
└─────────────────────────────────────────────────┘
                     ↓ 通过？
┌─────────────────────────────────────────────────┐
│  Loop 6: 价值 / 影响检查                            │
│  - 这篇文章解决了什么问题？                        │
│  - 读者看完能「学以致用」吗？                     │
│  - 与同类文章有差异化价值吗？                     │
│  - 配得上「沉淀进仓库」吗？                       │
└─────────────────────────────────────────────────┘
                     ↓ 通过 → commit
```

## 详细检查项

### Loop 1：完整性检查

**章节结构（按 article-format.md）：**

- [ ] concept 类：背景 / 是什么 / 怎么做 / 5W 卡 / 反模式 / 总结
- [ ] problem 类：现象 / 原因 / 排查 / 解决 / 验证 / 反模式
- [ ] deep-dive 类：背景 / 原理 / 实战 / trade-off / 反模式 / 反思

**必备元素：**

- [ ] 一句话摘要（blockquote 开头）
- [ ] 关键词标签（frontmatter tags）
- [ ] 5W 速记卡（concept 类必填）
- [ ] trade-off 对比表（deep-dive 类必填）
- [ ] 反模式 / 踩坑章节（任何类）
- [ ] 参考资料 / 相关链接（最后）

**代码 / 图片：**

- [ ] 代码块标了语言（```typescript 不是 ```plain）
- [ ] 代码能 copy-paste 跑通
- [ ] 图片能正常显示（路径正确）
- [ ] Mermaid 流程图能渲染

### Loop 2：准确性检查

**技术事实：**

- [ ] API / 方法签名正确
- [ ] 库版本号正确（不写即将废弃的版本）
- [ ] 配置参数与默认值正确
- [ ] 命令行示例可执行
- [ ] 「业界现状」陈述准确

**代码：**

- [ ] 语法正确（TypeScript / Go / Python 等）
- [ ] 逻辑可运行（不是伪代码）
- [ ] 没有死循环 / 内存泄漏
- [ ] 命名规范

**链接 / 引用：**

- [ ] 所有外部链接能打开（用 curl 验证）
- [ ] 内部链接指向正确路径
- [ ] 引用来源真实可查（不要编造）
- [ ] 「据某某说」必须有出处

### Loop 3：隐私 / 安全性检查（公开仓库必查）

**禁止出现：**

- [ ] ❌ 公司名（满帮 / 阿里 / 字节 / 腾讯 ...）
- [ ] ❌ 业务专属词（信贷 / 放款 / 借款单 / 风控审核 ...）
- [ ] ❌ 真实接口地址（`https://api.xxx.com/v1/...`）
- [ ] ❌ 真实域名 / IP / 端口
- [ ] ❌ 真实凭证（密钥 / token / 密码）
- [ ] ❌ 真实用户数据（姓名 / 手机 / 邮箱）
- [ ] ❌ 真实业务数据（金额 / 订单号 / 流水号）
- [ ] ❌ 内部工具名（lion / Lancet / Pigeon 等代号）

**泛化处理：**

- [ ] 公司 → 「某互联网公司」/ 「某金融科技公司」
- [ ] 业务 → 「核心业务」/ 「订单场景」/ 「支付场景」
- [ ] 接口 → 「`/api/users/{id}`」
- [ ] 数据 → 「XX 公司」「用户 123」
- [ ] 金额 → 「峰值 QPS 800」/ 「金额 XX 元」

**完整规则：** 见 [`docs/conventions/article-format.md`](./article-format.md)

### Loop 4：时效性检查

**API / 库版本：**

- [ ] 不引用已废弃的 API
- [ ] 标注「截至 XXXX 年 XX 月」
- [ ] 提供「升级到新版本」指引

**链接：**

- [ ] 所有外部链接仍能访问（用 `curl -I` 检查 200/301）
- [ ] 如果链接失效，在文中标注「链接已失效」
- [ ] 内部链接全部能打开

**业界现状：**

- [ ] 「业界主流」的陈述准确（搜索确认）
- [ ] 不夸大 / 不过时
- [ ] 标注数据来源 / 报告时间

**时间标注：**

- [ ] frontmatter 有 `date` 字段
- [ ] 文末有「最后更新」时间
- [ ] 重要更新用 changes/ 记录

### Loop 5：结构 / 表达检查

**章节顺序：**

- [ ] 从背景 → 原理 → 实践 → 反模式 → 总结（递进）
- [ ] 不跳级（## 直接到 #### 不合理）
- [ ] 不重复说同一件事

**标题层级：**

- [ ] `##` 一级（文章 3-7 个）
- [ ] `###` 二级（章节内分组）
- [ ] `####` 三级（少用，超过 3 层考虑拆文章）

**代码块：**

- [ ] 标语言（```typescript / ```go / ```bash ...）
- [ ] 关键参数加注释
- [ ] 不超过 50 行（链接到示例仓库）

**表格 / 列表：**

- [ ] 表格不超过 7 列（太宽难读）
- [ ] 列表用 `-` 要点 / `1.` 步骤分明
- [ ] 关键术语加粗（`**QPS 800**`）

**引用：**

- [ ] 关键结论用 `>` blockquote
- [ ] 引用 block 标明出处
- [ ] 不滥用（不是每个句子都加引用）

### Loop 6：价值 / 影响检查

**解决问题：**

- [ ] 这篇文章解决什么具体问题？
- [ ] 「学完能用」还是「学完没用」？

**差异化价值：**

- [ ] 与同类文章 / 官方文档有什么不同？
- [ ] 提供了官方没有的「踩坑经验」？
- [ ] 提供了个人实战视角？

**沉淀价值：**

- [ ] 未来自己 / 别人会查吗？
- [ ] 配得上「沉淀进仓库」吗？
- [ ] 还是只适合写一次性分享？

## 验证执行方式

### 手动验证（适合个人）

```
写完文章
    ↓
对照本文件的 6 个 Loop 检查项逐个跑
    ↓
有任何 Loop 不通过 → 修改 → 重新跑那个 Loop
    ↓
全部通过 → commit
```

### AI 自动验证（适合 Cursor / Claude Code）

让 AI 按以下 prompt 跑验证循环：

```markdown
请按 `docs/conventions/article-verification.md` 的 6 个 Loop 验证这篇文章：

文件路径：docs/xxx/yyy.md

验证要求：
1. Loop 1 完整性：检查 6 章节齐全 / 必备元素 / 代码图片
2. Loop 2 准确性：检查技术事实 / 代码 / 链接 / 引用
3. Loop 3 隐私安全：检查禁止词（公司 / 业务 / 接口 / 数据）
4. Loop 4 时效性：检查 API 版本 / 链接 / 业界现状 / 时间标注
5. Loop 5 结构表达：检查章节顺序 / 标题层级 / 代码格式 / 表格
6. Loop 6 价值影响：检查解决问题 / 差异化 / 沉淀价值

输出格式：
- 每个 Loop 单独报告
- 列出问题（具体到行号）
- 给出修改建议
- 总分（6/6 通过才能 commit）
```

### Hook 自动化（适合 CI / pre-commit）

可以在 `npm run x -- check` 里加一个验证步骤：

```bash
# scripts/verify-articles.mjs（待实现）
# 自动跑 6 个 Loop 的基础检查：
# - 检查 frontmatter 必填字段
# - 扫描禁止词
# - 检查死链
# - 检查 frontmatter date 距今超过 1 年（提醒复查）
```

**高级**：可在 GitHub Actions 跑 review bot（每次 PR 自动跑）。

## 验证 checklist 速查卡

**commit 前 30 秒检查：**

```
□ 文章有完整 frontmatter（title / type / tags）？
□ 一句话摘要清晰？
□ 6 章节齐全？
□ 代码块标语言 + 能跑？
□ 没有公司名 / 真实数据 / 内部接口？
□ 链接都能打开？
□ 一句话总结在最后？
□ 反思 / 反模式 / 踩坑章节有？
```

**任一不通过 → 不 commit，先修。**

## 验证失败处理

| Loop 失败 | 处理 |
|---|---|
| **Loop 1 完整性** | 补章节 / 补 5W / 补反模式 |
| **Loop 2 准确性** | 改技术细节 / 改代码 / 改链接 |
| **Loop 3 隐私安全** | 立刻脱敏（公司名 / 业务数据） |
| **Loop 4 时效性** | 更新 API 版本 / 替换失效链接 |
| **Loop 5 结构表达** | 重写章节 / 调整顺序 / 修正格式 |
| **Loop 6 价值影响** | 删掉 / 合并 / 重新定位 |

**严重问题（Loop 2/3）必须修完才能 commit。其他 Loop 可以 commit 后单独 fix。**

## 持续验证（不只是 commit 前）

**commit 后也要定期验证：**

| 频率 | 验证什么 |
|---|---|
| **每季度** | 跑一次全文章 Loop 1-4 检查 |
| **半年** | 检查业界现状是否还准确（Loop 4） |
| **1 年** | 检查 API 是否过时 / 库是否废弃 |
| **2 年** | 考虑文章是否需要重写或归档 |

**自动化建议：**

- GitHub Actions 每月跑一次 `npm run x -- check`
- 跑 markdown-link-check（死链检测）
- 跑敏感词扫描（Loop 3）
- 通知 owner 复查超过 1 年的文章

## 与现有流程的关系

**之前：** 写完 → commit → push

**现在：** 写完 → **6 Loop 验证** → commit → push

**验证不是「阻塞」，是「质量保证」。**

**目标：** 让每一篇沉淀到仓库的文章都是「值得未来查阅」的，而不是「写到一半就废弃」的。

## AI 协作流程

**推荐流程：**

```
1. AI 写初稿（按 article-format.md 模板）
    ↓
2. AI 自动跑 Loop 1-3 检查
    ↓
3. 人类 review Loop 4-6（时效 + 价值需要人判断）
    ↓
4. AI 修改不通过的部分
    ↓
5. 全部通过 → commit
```

**人机分工：**

- **AI 做**：章节完整性 / 代码能跑 / 死链 / 敏感词扫描 / 格式
- **人做**：业界现状是否准确 / 文章是否值得沉淀 / 反思是否深刻
