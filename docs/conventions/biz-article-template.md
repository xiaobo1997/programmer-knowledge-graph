# 业务知识文章模板

> **AI 和人都能读懂的写作方法论——每篇业务文章都按这个骨架来。**

---

## 核心理念

> **主题驱动，不是维度驱动。** 文章聚焦一个具体业务 topic，自然覆盖相关维度。19 维是思考清单，不是强制 checklist。

---

## 写作前：AI 先和用户确认 3 件事

每篇业务文章开始前，AI 必须先输出以下确认清单，等用户点头再写：

```markdown
## 📋 写作确认清单

**文章主题：** [具体 topic，如「国内支付清结算体系」]

**所属分类：** [业务域，如「国内支付」]

**这篇文章要讲清楚什么：**
1. [核心问题 1]
2. [核心问题 2]
3. [核心问题 3]

**需要哪些图：**
- [ ] 业务流程图（Mermaid flowchart）
- [ ] 时序图（Mermaid sequence）
- [ ] 数据模型图（Mermaid ER）
- [ ] 架构图（Mermaid graph）
- [ ] 状态机图（Mermaid state）
- [ ] 产品形态图

**预计篇幅：** [2k-5k 字]

**关联文章：** [已有 / 计划中的关联文章]
```

---

## 文章骨架

每篇文章按以下结构写，选填——不是每篇都要所有 section：

```
1. 一句话定义          ← 必选：用一句话讲清这是什么
2. 业务背景与价值       ← 必选：为什么需要这个东西
3. 业务术语表           ← 必选：核心术语中英对照
4. 业务形态与模式       ← 这个业务的玩法、参与方、盈利模式
5. 业务流程图           ← Mermaid flowchart / sequence
6. 产品形态            ← 用户看到什么、交互是什么
7. 用户角色与操作       ← 谁、做什么、权限矩阵
8. 数据模型            ← Mermaid ER 图 + 关键表说明
9. 系统架构            ← Mermaid graph：系统拓扑、模块关系
10. 服务模型           ← 服务边界、接口、RPC 调用链
11. 核心功能用例        ← 最重要的 3-5 个场景
12. 业务打法与策略      ← 怎么做能赢、竞争优势
13. Trade-off 分析     ← 方案对比表（维度×选项）
14. 业务前景与趋势      ← 市场规模、技术演进方向
15. 一句话总结          ← 必选：看完这篇文章记住什么
```

## 配图规范

| 场景 | 用什么图 | Mermaid 类型 | 示例 |
|---|---|---|---|
| 业务流程 | 泳道/流程图 | `flowchart LR` | 支付→清算→结算 |
| 交互时序 | 时序图 | `sequenceDiagram` | 用户→收银台→网关→银行 |
| 数据模型 | ER 图 | `erDiagram` 或 `flowchart` | 订单表→流水表→账户表 |
| 系统架构 | 架构拓扑图 | `graph TD` | 接入层→服务层→数据层 |
| 状态流转 | 状态机图 | `stateDiagram-v2` | 待支付→支付中→已支付→已退款 |
| 决策逻辑 | 决策树 | `flowchart TD` | 路由规则、风控决策 |

**图的要求：**
- 每张图配一句说明文字（「上图展示了 xxx 的核心流程」）
- 节点用中文命名
- 复杂流程用 `alt` 分支展示异常路径
- 颜色区分不同系统/角色（Mermaid 支持 `style` 和 `classDef`）

## 质量检查清单

写完必跑的 6 个检查项：

| # | 检查项 | 标准 |
|---|---|---|
| 1 | **讲清楚了吗** | 一个完全不懂这个业务的人看完能复述核心流程 |
| 2 | **有图吗** | 至少 2 张 Mermaid 图（流程 + 架构/数据/时序） |
| 3 | **术语准吗** | 术语表里每个词都有中英对照 + 一句话解释 |
| 4 | **有 trade-off 吗** | 至少列出 2 个关键决策的利弊对比 |
| 5 | **能索引吗** | 标题和 section 锚点清晰，sidebar 里能快速定位 |
| 6 | **脱敏了吗** | 不出现公司名、具体项目名、真实交易金额 |

## 与通用文章模板的关系

| | 通用技术文章 | 业务知识文章 |
|---|---|---|
| 模板 | `article-format.md`（6 步方法论） | `biz-article-template.md`（本文件，15 section 骨架） |
| 焦点 | 技术/工具/框架 | 业务/产品/领域 |
| 配图 | 代码块为主 | Mermaid 图为主（流程/架构/数据/时序） |
| 目标 | 学会怎么用 | 理解为什么这样做 |

**两者互补：技术文章讲 How，业务文章讲 Why + What。** 同一个人既要有技术深度也要有业务厚度。

---

## 沉淀原则

- 每篇文章是一个独立的知识单元——不依赖其他文章也能读懂
- 先盖楼（建 topic 框架），再装修（逐篇填充深度内容）
- 写完一篇 = 这个 topic 的「速查手册」+「深度解读」
- 面试时可以拿出来讲：「你看，我在业务沉淀上有自己的方法论」
