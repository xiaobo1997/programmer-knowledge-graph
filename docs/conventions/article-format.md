# 文章内容格式规范

> 知识图谱的文章按什么结构写。所有 AI 写文章时遵循这个模板。

## 🧭 元方法论（最重要的部分）

### 核心信念

> **学习一个东西 = 写一个东西 = 沉淀一个东西 = 三者是一回事。**

不管你是学技术（TypeScript / K8s）、学业务（跨境支付 / 信贷）、学软实力（沟通 / 决策）——

**唯一正确的方法：**

```
1. 为什么学 / 为什么做？           ← 动机 + 价值
2. 生态定位（在哪里 / 跟谁配套）   ← 全景图
3. 是什么 / 怎么定义？             ← 核心概念
4. 怎么做 / 怎么实现？             ← 步骤 + 代码 + Demo
5. 为什么这样做？                  ← trade-off + 决策
6. 踩过什么坑？                   ← 反模式 + 真实经验
    ↓
按这个 6 步写一篇博客 → commit 到仓库 → 未来查阅
```

### 为什么这套方法论有效？

| 错误做法 | 正确做法 |
|---|---|
| 学完就忘 | 学完写一篇博客沉淀 |
| 看懂不会用 | 「用自己的理解讲一遍 + 实践一遍」（费曼学习法） |
| 学错方向 | **第二步生态定位**告诉你全景图和同类方案 |
| 学完不知道值不值 | **第一步为什么学**给你价值定位 |
| 学完不知道避坑 | **第六步踩坑**给你反模式 |

### 适用所有学习

✅ **硬实力**：编程语言 / 框架 / 算法 / 系统设计 / 架构
✅ **软实力**：沟通 / 决策 / 时间管理 / Code Review / 技术领导力
✅ **业务**：跨境支付 / 信贷 / 电商 / 任何业务领域
✅ **方法论**：稳定性 / 性能优化 / 任何「如何做」的方法
✅ **解决方案**：对账 / 幂等 / 限流 / 任何具体问题的解法

### AI 写文章必须遵循

**任何 AI 接到「写一篇博客」任务时：**

1. **先问「为什么写」**——动机 + 价值定位
2. **先问「这文章在哪个生态位置」**——同类文章 / 上下游
3. **再写 6 章节**（按下方骨架）
4. **必须有 5W 速记卡**（concept 类）
5. **必须有 trade-off**（deep-dive 类）
6. **必须有反模式 / 踩坑**（任何类）
7. **写到代码必须能跑**（A/B/C 类）
8. **必须沉淀到仓库**（commit + push）

### 沉淀的意义

> **学完不写 = 没学。** 写完不沉淀 = 白写。

**这个仓库的每一篇博客 = 一次学习 = 一份沉淀 = 未来的参考。**

## 三种文章类型 + 统一骨架

| 类型 | 场景 | 长度 | 深度 |
|---|---|---|---|
| **概念科普**（concept） | 第一次学一个技术 | 3-5 分钟 | 浅（原理 + 示例） |
| **问题排查**（problem） | 遇到具体问题来查 | 5-15 分钟 | 中等（根因 + 方案 + 验证） |
| **实战深挖**（deep-dive） | 面试 / 复杂场景 / 架构选型 | 15-60 分钟 | 深（生产数字 + trade-off + 反思） |

**frontmatter 标记：**

```yaml
---
title: RocketMQ 事务消息在信贷场景的应用
type: deep-dive     # concept / problem / deep-dive
tags: [后端, 分布式事务, RocketMQ, 信贷]
---

```

## 统一骨架（每种类型都遵循）

```
# 标题（一句话点题）

> 一句话摘要：解决什么问题 / 学完能会什么 / 适用边界

## 1. 背景（Why 这个问题存在）
- 实际场景 / 不这么做会怎样
- 关键约束（性能、一致性、成本）

## 2. 核心内容（What & How）
- 原理 / 关键概念 / 最小可运行示例
- 关键参数 + 默认值

## 3. 实战 / 线上案例（deep-dive 必有，其他类型可省略）
- 我们系统怎么用的（带数据）
- 踩过的坑 + 怎么排查
- 线上配置（QPS / 线程数 / 超时）

## 4. Trade-off（为什么选 A 不选 B）
- 至少 2-3 个备选方案对比表
- 选择理由 + 代价

## 5. 反模式 / 常见误区
- ❌ 错误做法 + 后果
- ✅ 正确做法 + 为什么

## 6. 一句话总结
> 30 秒能讲完的核心

## 参考
- 官方文档
- 相关 ADR / 内部文档 / 推荐阅读
```

## 5W 原则速记卡（concept 类必备）

deep-dive 类不需要（已经在正文展开了）。**concept 类必须在文章末尾有 5W 表：**

| 维度 | 答案 |
|---|---|
| **What** | 一句话定义 |
| **Why** | 为什么需要 / 解决什么问题 |
| **When** | 何时用 / 何时不用 |
| **Where** | 适用场景 / 不适用场景 |
| **How** | 怎么做（链接正文详细步骤） |

**5W 是文章的「电梯版」**——读者扫一眼就能复述给别人。

## 类型专属规则

### concept（概念科普）

- ✅ **必须有 5W 表**
- ✅ 一个最小可运行代码示例
- ✅ 一张原理图或流程图（Mermaid 优先）
- ❌ 不要堆砌生产数字（不真实）
- ❌ 不要列 trade-off（读者还没学会不需要纠结选型）

### problem（问题排查）

- ✅ **标题用「问题描述」格式**（如「RocketMQ 消息积压如何排查」）
- ✅ 步骤清晰：**现象 → 原因 → 排查 → 解决 → 验证**
- ✅ 包含至少一个**真实报错信息 / 日志片段**
- ❌ 不要罗列所有可能原因（聚焦最常见的 2-3 个）

### deep-dive（实战深挖）

- ✅ **必须穿透八层**（是什么/为什么/怎么做/trade-off/坑/更好/生产画像/深度机制）
- ✅ 必须有生产数字（QPS/TPS/P99/线程数/连接池）
- ✅ 必须有 trade-off 章节
- ✅ 至少 2 个备选方案对比
- ✅ 结尾必须有**反思/回头看**（P7 杀手锏）
- ❌ 不要「忘了」「不清楚」（基础题没借口）

## 排版规则

### 标题层级

- `##` 一级章节（一个文章 3-7 个）
- `###` 二级章节
- `####` 三级章节（少用，超过 3 层考虑拆文章）

### 列表

- **要点列表**：用 `-` 不用 `1.`
- **步骤列表**：用 `1.` 标明顺序
- **避免**：超过 7 项的长列表（拆成多个段落或表格）

### 表格

- **对比/参数** → 表格
- **3 列以内** → 列表
- **表头要清晰**，**第一列** 总是「比较项」或「维度」

### 代码

- **必须可运行**：能 copy-paste 跑起来
- **加注释**：关键参数用 `// 为什么这么设` 说明
- **避免**：超过 50 行的代码块（链接到示例代码仓库）

### 引用

- **关键结论**：用 `>` blockquote
- **面试官原话 / 反问**：用 `> 你：「为什么不用 X」`
- **数据/数字**：用粗体 `**QPS 1200**` 不用引用块

## 篇幅指南

| 类型 | 字数 | 阅读时间 |
|---|---|---|
| concept | 800-2000 字 | 3-5 分钟 |
| problem | 2000-5000 字 | 5-15 分钟 |
| deep-dive | 5000-20000 字 | 15-60 分钟 |

**超过 2 万字 = 该拆成系列文章了**。

## 学习方法论（所有学习的通用模板）

> **核心观点：学任何东西都是方法论。** 学一门新技术是方法论，学一个业务是方法论，学一个体系也是方法论。
> 区别不在「有没有方法论」，而在于「侧重什么维度」。

### 为什么方法论是通用的？

不管你学什么——K8s、跨境支付收单、稳定性建设、Code Review——都需要回答这 5 个问题：

| 问题 | 含义 | 示例（学 K8s） | 示例（学跨境支付） |
|---|---|---|---|
| **1. 为什么** | 解决什么问题 / 为什么要学 | 为什么需要 K8s？单体不够用？ | 为什么做跨境支付？市场机会？ |
| **2. 是什么** | 全景地图 / 核心组件 | K8s 有什么？Master / Node / Pod | 跨境支付链路有什么？收单 / 清结算 / 风控 |
| **3. 怎么做** | 流程 / 步骤 / 关键设计 | K8s 怎么部署集群？怎么调度？ | 支付链路怎么流转？怎么清算？ |
| **4. 为什么这样做** | 决策依据 / trade-off | 为什么用 etcd？不用 Zookeeper？ | 为什么 T+1 对账？不用实时？ |
| **5. 踩过什么坑** | 真实经验 / 反模式 | K8s 网络坑？存储坑？ | 跨境支付的汇率坑？时区坑？ |

**任何学习都可以套这 5 个问题。** 具体到每种学习对象，只是「侧重点」和「代码量」不同。

### 学习对象分类（按方法论侧重）

| 学习对象 | 例子 | 侧重维度 | 代码密度 |
|---|---|---|---|
| **A. 编程语言 / 框架** | TypeScript / Vue / Go | 怎么用（API + 例子） | ⭐⭐⭐⭐⭐ |
| **B. 新技术 / 概念** | LLM Agent / WebAssembly / WASI | 是什么 + 为什么 | ⭐⭐⭐ |
| **C. 工程实践** | 微信小程序从 0 到 1 上线 | 怎么做（流程 + 决策） | ⭐⭐⭐ |
| **D. 体系技术** | K8s / 微服务 / 数据中台 | 是什么 + 怎么做（全景 + 演进） | ⭐⭐⭐ |
| **E. 业务领域** | 跨境支付收单 / 信贷风控 / 电商订单 | 为什么 + 是什么（业务 + 数据结构） | ⭐⭐ |
| **F. 方法论** | 稳定性建设 / 性能优化 / Code Review | 为什么 + 怎么做（原则 + 步骤） | ⭐ |
| **G. 解决方案** | 对账体系 / 幂等设计 / 限流方案 | 为什么 + 怎么做（方案对比 + 选型） | ⭐⭐ |

**关键洞察：**

- **A / B / C / D** 都是「技术向」，需要代码
- **E / F / G** 都是「业务/方法论向」，**代码很少，重点是知识本身**
- 同一个学习方法论，只是「代码示例比例」不同

### 通用学习路径（5 步方法论）

任何学习都按这 5 步推进：

```
1. 为什么（Why）      ← 动机 + 价值定位（1 篇）
2. 是什么（What）      ← 全景 + 核心概念（1-3 篇）
3. 怎么做（How）       ← 流程 / 步骤 / 实现（2-10 篇，A 类最多）
4. 为什么这样做（Why2）← trade-off / 选型 / 决策依据（1-3 篇）
5. 踩过什么坑（Trap）  ← 反模式 / 真实经验（1-2 篇）
```

**总文章数：6-19 篇**，根据学习对象的复杂度递增。

### 实战示例

│   ├── 高可用设计/
│   ├── 调度算法/
│   └── 存储设计/
├── 04_可观测性/                      ← 监控 / 日志 / 链路追踪

## 学习方法论补充：生态定位维度

> **学一个东西不只是学怎么用，还要学它在「整个技术生态 / 业务生态」里的位置。**
> 这样才能真正「融会贯通」——从「会用」升级到「懂」。

### 为什么需要生态定位？

很多人学完一个技术只会「怎么用」，但回答不了这些问题：

- ❌ **K8s 在架构的哪一层？**（基础设施 / 中间件 / 应用？）
- ❌ **现在 K8s 在行业里处于什么地位？**（主流 / 衰退 / 新兴？）
- ❌ **业界用 K8s 通常干什么？**（微服务？大数据？AI？）
- ❌ **K8s 能和什么配合？**（Service Mesh？Serverless？GitOps？）
- ❌ **类似 K8s 的方案有哪些？**（Docker Swarm？Mesos？）
- ❌ **未来 K8s 会怎么演进？**（边缘计算？AI workload？）

**没有生态定位 = 操作工 / 有生态定位 = 架构师。**

### 生态定位 6 问（每个学习对象都问）

每个学习对象（技术 / 框架 / 业务 / 解决方案）都按这 6 问组织「生态定位」章节：

| 问题 | 含义 | 学 K8s 时回答 | 学跨境支付时回答 |
|---|---|---|---|
| **1. 在哪里？** | 在技术栈 / 业务链路的哪一层 | 基础设施层（IaaS / 容器编排） | 支付链路（收单 → 清结算） |
| **2. 现在怎么样？** | 当前行业地位 / 趋势 | 主流 / 标准化 / 大厂标配 | 蓝海 / 增长快 / 监管变化 |
| **3. 能干什么？** | 核心能力 / 典型场景 | 微服务 / 大数据 / AI | 跨境收款 / 多币种结算 |
| **4. 怎么配合？** | 上下游 / 替代 / 互补方案 | Service Mesh / Helm / ArgoCD | 与 Stripe / Adyen / Worldpay 区别 |
| **5. 类似什么？** | 同类方案 / 竞品 | Docker Swarm / Mesos / Nomad | 国内 PingPong / Airwallex |
| **6. 怎么演进？** | 历史 / 未来趋势 | 从 Borg → K8s → Serverless K8s | 从 SWIFT → 卡组织 → 区块链结算 |

### 生态定位章节骨架（每篇学习对象至少一篇）

### 现在怎么样（行业地位）

- **2014 年**：Google 开源，业界观望
- **2017 年**：CNCF 成立，K8s 成为事实标准
- **2020 年**：大厂全面拥抱（阿里 / 腾讯 / 字节）
- **2024 年**：K8s 统治容器编排，80% 企业生产环境在用

**当前状态：**
- ✅ 云原生时代的事实标准
- ✅ 所有云厂商都提供托管 K8s 服务（EKS / AKS / GKE / ACK）
- ⚠️ 学习曲线陡峭，运维成本高
- ⚠️ 在小项目可能过度设计

### 能干什么（典型场景）

| 场景 | K8s 适合度 | 替代方案 |
|---|---|---|
| 微服务编排 | ⭐⭐⭐⭐⭐ | Docker Compose（单机） |
| 大数据 / AI 训练 | ⭐⭐⭐⭐ | YARN / Mesos |
| Serverless 平台 | ⭐⭐⭐⭐ | Knative / OpenFaaS |
| 传统应用容器化 | ⭐⭐⭐⭐ | Docker Swarm |
| 边缘计算 | ⭐⭐⭐ | K3s / MicroK8s |

### 怎么配合（上下游生态）

**上游（被 K8s 编排）：**
- Docker / Containerd / CRI-O（容器运行时）
- Helm（包管理）
- Operators（CRD 扩展机制）

**下游（基于 K8s 构建）：**
- Service Mesh（Istio / Linkerd）
- Serverless（Knative / OpenFaaS）
- GitOps（ArgoCD / Flux）
- 监控（Prometheus + Grafana）

### 类似什么（同类方案）

| 方案 | 类型 | 优势 | 劣势 |
|---|---|---|---|
| K8s | 容器编排 | 生态最丰富 | 学习曲线陡 |
| Docker Swarm | 容器编排 | 简单 | 生态弱 |
| Mesos | 资源调度 | 大数据成熟 | 学习曲线陡 / 社区萎缩 |
| Nomad | 资源调度 | 简单 / 多 workload | 生态较弱 |
| K3s | 轻量 K8s | 适合边缘 | 仍依赖 K8s 生态 |

### 怎么演进（历史 + 未来）

**过去：**
- Borg（Google 内部）→ K8s（Google 开源）→ CNCF 毕业

**现在：**
- K8s 已成为容器编排标准
- 云原生生态围绕 K8s 展开

**未来 5 年：**
- **Serverless K8s**：不用管节点，只写 Pod Spec
- **AI/ML Workload**：K8s 成为 AI 训练平台标准
- **边缘 K8s**：K3s / KubeEdge 在 IoT / CDN 场景普及
- **WebAssembly + K8s**：Wasm 运行时的容器化

## 总结

> K8s 是云原生时代的「操作系统」，不是简单的容器编排工具。
> 它的生态地位类似 Linux 内核——所有上层应用（微服务 / Serverless / AI）都构建在它之上。

## 成长方法论（不只是学技术）

> 上面的「学习方法论」不只是学技术 / 学业务用的——**它是通用的成长方法论**。
> 硬实力（编程 / 算法 / 系统设计）和软实力（沟通 / 管理 / 决策）都适用。
> 核心：为什么 → 生态定位 → 是什么 → 怎么做 → 为什么这样做 → 踩过什么坑

### 软实力也用同一套方法论

很多人学软实力是「看鸡汤文」「听大道理」「记笔记」，但没真正内化。

**用同一套方法论学软实力：**

| 学习对象 | 类型 | 用方法论的哪个部分 |
|---|---|---|
| **沟通能力** | F 方法论 | 为什么 → 是什么原则 → 怎么做（练习） → 为什么这样做 → 踩过的坑 |
| **技术管理** | F 方法论 | 为什么需要 → 生态定位（个人贡献者 vs Lead） → 是什么角色 → 怎么做 → 决策 trade-off |
| **决策能力** | F 方法论 | 为什么 → 决策框架（生态） → 是什么（原则） → 怎么做 → 反模式 |
| **Code Review** | F 方法论 | 为什么 → 生态（PR / CI） → 是什么原则 → 怎么做 → 反模式 |
| **时间管理** | F 方法论 | 为什么 → 生态（GTD / Pomodoro） → 是什么 → 怎么做 → 踩坑 |
| **写作能力** | F 方法论 | 为什么 → 生态（读者视角） → 是什么原则 → 怎么做 → 反模式 |

**软实力学习的关键：**
- 不是「读懂」而是「会用」
- 不是「知道」而是「做到」
- 不是「理论」而是「实践 + 反思」

### 「为什么学」是学习的发动机

很多文章 / 书的开头上来就讲「是什么」「怎么做」，但**漏掉了「为什么学」**。

**没有「为什么」的学习：**
- 看完就忘（动力不足）
- 学不下去（没有耐心）
- 学完不会用（没真正理解价值）

**有「为什么」的学习：**
- 知道这个知识点的「位置」和「价值」
- 学不下去时知道「值得学」
- 学完能用上（因为知道适用场景）

**学习模板第一步永远是「为什么」**，不管是：
- 学 TypeScript：为什么 TS？大型项目团队需要类型系统
- 学跨境支付：为什么做？中国出海企业需要
- 学沟通：为什么？团队协作效率
- 学 Code Review：为什么？提升代码质量 + 知识共享

### 看书也是一样：快速看懂一本书

**很多人看书的方法错了：**从头到尾一字不漏 → 看完就忘。

**正确的看书方法（套用学习方法论）：**

```
1. 为什么看这本书？                    ← 1 分钟（看前言 / 序）
2. 这本书在领域的什么位置？             ← 5 分钟（看目录 + 序言）
3. 这本书讲了什么？                     ← 30 分钟（快速翻全书）
4. 核心方法论是什么？                    ← 30 分钟（重点章节细看）
5. 哪些方法我会用？ 哪些不会？           ← 10 分钟（思考应用场景）
6. 我要怎么用？                        ← 10 分钟（计划实践）
```

**这就是费曼学习法 + 我们的方法论：**

| 阶段 | 费曼学习法 | 我们的方法论 |
|---|---|---|
| **第一步** | 选择概念 | 1. 为什么学 |
| **第二步** | 教给别人 | 3. 是什么 + 4. 怎么做（讲出来） |
| **第三步** | 查漏补缺 | 5. 为什么这样做 |
| **第四步** | 简化语言 | 8. 一句话总结 |

**核心：用「自己的理解讲一遍」+「实践一遍」。**

### 「用自己的理解讲一遍」

读完 / 学完一个东西，**强制自己讲给别人听**：

- 写一篇博客（这个仓库！）
- 给同事 / 朋友讲
- 在团队内部分享
- 教一个新同事

**为什么有效：**
- 暴露自己没真正懂的部分
- 加深记忆（教是最好的学）
- 沉淀成可复用的知识
- 收到反馈纠正错误

### 「实践一遍」

学完一个东西，**必须做 1-2 个真实项目或练习**：

| 学习内容 | 实践方式 |
|---|---|
| TypeScript | 用 TS 重构一个已有 JS 项目 |
| K8s | 在本地 minikube 部署一个真实应用 |
| 跨境支付 | 读一遍 Stripe / Adyen 文档，写一个 demo |
| 沟通 | 下次会议主动应用学到的技巧 |
| Code Review | 实际 review 10 个 PR，总结反馈 |
| 时间管理 | 用番茄钟法 1 周，记录效果 |

**没有实践 = 没有真正学会。**

### 沉淀到仓库（最重要的一步）

**学习 → 写作 → 沉淀** 是完整的闭环：

```
学完一个东西
    ↓
按方法论写一篇博客（这个仓库的某篇文章）
    ↓
沉淀进仓库（commit + push）
    ↓
未来忘了回来查（搜索 / 侧栏 / 知识图谱）
    ↓
下次再用（学以致用）
```

**这个 programmer-knowledge-graph 仓库就是这个过程的产物**——

- 学 TypeScript → 写「TS 基础语法」文章 → 沉淀到仓库
- 学跨境支付 → 写「跨境支付收单」系列 → 沉淀到仓库
- 学沟通技巧 → 写「沟通方法论」文章 → 沉淀到仓库

**你学习了什么，沉淀下来，未来你自己 + 别人都能复用。**

### 持续进步的飞轮

```
沉淀知识到仓库
    ↓
未来遇到问题快速查阅（不重新学）
    ↓
节省时间 → 学更多新东西
    ↓
沉淀更多知识
    ↓
（飞轮转起来）
```

**为什么很多人学了很多但感觉没进步？**
- 没沉淀 → 学完就忘 → 下次重新学 → 时间浪费
- 没实践 → 学了不会用 → 知识没内化
- 没反思 → 学了不知道哪里没懂 → 重复犯错

**本仓库的作用就是「让学习有积累」——每学一个东西，就沉淀一篇博客。**

### 学习方法论 = 成长方法论 = 沉淀方法论

**三者是一回事：**

| 维度 | 学习 | 成长 | 沉淀 |
|---|---|---|---|
| 输入 | 学技术 / 学业务 / 学软实力 | 实践经验 / 项目复盘 / 读书 | 自己理解的笔记 |
| 处理 | 按 6 步方法论消化 | 反思 / 总结 / 改进 | 按文章模板组织 |
| 输出 | 会用 | 进步 | 仓库里的文章 |
| 沉淀 | 仓库 | 仓库 | 仓库 |

**核心：持续输入 → 处理 → 输出 → 沉淀 → 形成个人知识资产。**

### 「积累书里面的精华，就是用自己的理解讲一遍，实践一遍」

这句话是核心。拆解来看：

- **积累精华** = 提取最有价值的部分（不是全部）
- **自己的理解** = 不是抄写，是消化 + 重组
- **讲一遍** = 写作 / 分享 / 教（费曼学习法）
- **实践一遍** = 用到工作 / 项目 / Demo

**这个仓库就是「积累书里的精华」+「讲一遍」+「实践一遍」三者的产物。**

### 持续进步的具体方法

| 频率 | 动作 |
|---|---|
| **每天** | 学一个知识，写 30 分钟短博客 |
| **每周** | 整理本周博客，找共通点 |
| **每月** | 写一篇月度总结（学了什么、踩了什么坑） |
| **每季** | 复盘学习方法论是否有效，调整模板 |
| **每年** | 整体回顾知识图谱，清理过时内容 |

### 软实力 + 硬实力 = 完整工程师

**硬实力（技术）：**
- 编程语言 / 框架 / 工具
- 系统设计 / 架构
- 算法 / 数据结构

**软实力（沟通 / 决策 / 管理）：**
- 沟通能力
- 时间管理
- 决策能力
- 团队协作
- 技术领导力

**两者都用同一套方法论：**

6. 踩过什么坑

**把学习当成习惯，把沉淀当成投资——这就是持续进步。**
