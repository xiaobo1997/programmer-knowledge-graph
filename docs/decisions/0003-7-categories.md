# ADR-0003: 用 9 大类分类（按工程师工作场景）

## 状态

已采用（2025-07-20）

## 背景

最初用 6 大类（读书笔记 / 全栈 / DevOps / Agent / 成长 / 技术地图），发现粒度不均：

- DevOps 占 9 篇（含子目录）
- 全栈只 2 篇
- 路线图 2 篇、技术地图 2 篇和 DevOps / 全栈内容重叠
- 个人成长只放职业相关，没有工程实践（Git/测试/Review）

## 决定

按工程师工作场景分 9 大类：

1. 后端开发
2. 前端开发
3. 数据 & 中间件
4. DevOps & 云原生
5. AI & 大模型
6. 架构 & 性能
7. 工程实践
8. 读书笔记
9. 个人成长

## 评估过的方案

### 方案 A：保持 6 类

- 优点：导航简单
- 缺点：粒度太粗，前端后端混在「全栈」里
- 结论：否决

### 方案 B：拆成 10+ 类

- 优点：粒度细
- 缺点：导航难用；类太多读者记不住
- 结论：否决

### 方案 C：不分类，按时间倒序

- 优点：实现简单
- 缺点：找特定领域内容难
- 结论：否决

### 方案 D：9 类按工作场景（采用）

- 优点：粒度均衡；语义清晰（按「做什么」分而不是「用什么技术」分）
- 缺点：3 类（前端 / 数据 / 工程实践）暂时空
- 结论：✅ 选用

## 关键决策点

### 为什么拆出「数据 & 中间件」？

- MySQL / Redis / ES / MQ / 缓存是后端必备独立技能
- 13 篇大厂后端面试常考，独立成类便于沉淀
- 跟「后端开发」不重叠（一个是语言/框架，一个是数据层）

### 为什么拆出「工程实践」？

- Git / 测试 / Code Review / 调试 / 编码规范
- 跟 DevOps 不重叠（DevOps 是部署运维，工程实践是日常编码）
- 软技能但偏技术

### 为什么不用「全栈」？

- 「全栈」是工作场景的描述，不是技术分类
- 工程师实际上是「后端 + 前端」或「后端 + 数据」组合
- 「全栈」反而模糊了主技能

## 分类与子目录

- 9 大类用一级目录：英文小写（`backend/`, `frontend/`, ...）
- 一级分类下可以建子目录（如 `devops/cicd/`, `devops/cicd/advanced/`）
- 子目录名也要进 `titleMap`（用 `utils.ts` + `sync-toc.cjs`）
