# 大数据链路：从 binlog 到数仓分层的全量数据体系

> 业务库里的每一条变更，如何在分钟级出现在数仓、报表与算法特征里？大数据链路 = **采集（binlog/CDC）→ 传输（MQ）→ 落地（ODS）→ 加工（分层建模）→ 消费（报表/算法/画像）**——它是数据面与治理面的地基：没有可靠的采集链路，大盘、报表、AI 全是空中楼阁。

## 一句话摘要

大数据链路的标准形态：**binlog 订阅（Canal/Flink CDC）捕获业务库变更 → MQ 缓冲与分区 → ODS 贴源落地 → DWD/DWS/ADS 分层加工 → 上游消费（报表/画像/特征）**；纪律三条：ODS 保真不改原数据、下游消费幂等（可重跑）、口径在 DWD 统一定义——链路的可靠性决定整个数据面的可信度。

## 本文核心

**核心机制一句话**：binlog 是业务库变更的「天生事件流」——订阅它比业务代码发消息更可靠（不侵入业务、不遗漏变更），CDC 工具把它变成结构化数据流，喂给数仓与实时计算。

**机制链**：MySQL binlog → Canal/Flink CDC 解析 → Kafka 分区（按表/主键）→ ODS 落地（Hive/HDFS）→ 每日/小时调度加工（DWD 清洗 → DWS 聚合 → ADS 报表）→ 下游消费（BI/算法/画像/风控特征）。

**失效点/边界**：binlog 解析要处理 DDL 变更（表结构变了链路要跟）；全量+增量的一致性衔接（初始化快照 + 增量拼接的断点管理）；数仓跑批延迟（上游依赖链长，一处延迟全链顺延）。

## 一、背景：为什么采集走 binlog 而不是业务发消息

业务代码发消息（双写）有三个先天缺陷：**侵入业务**（每个写操作都要埋消息代码）、**会遗漏**（直接 UPDATE 数据库的运营操作、历史脚本不发消息）、**语义不完整**（消息只有「发生了什么」，binlog 有「数据变成了什么」——before/after 镜像）。

binlog 订阅（CDC，Change Data Capture）的三个优势：**零侵入**（业务代码无感知）、**无遗漏**（数据库所有变更必然写 binlog）、**带前后镜像**（字段级变更可感知）。代价：binlog 解析的工程复杂度（DDL 处理/大事务/格式版本）——Canal/Flink CDC 把复杂度封装了。

> 💡 实战提示：CDC 工具选型看两点——DDL 变更的自动适配能力（加字段链路不断）与断点续传的可靠性（宕机后从位点恢复不丢不重）。这两点决定 CDC 链路的运维成本。

## 二、核心：链路全景与分区设计

```mermaid
flowchart LR
    DB["业务库<br/>MySQL 分片集群"] -->|"binlog"| CDC["Canal / Flink CDC<br/>解析为结构化变更流"]
    CDC --> K["Kafka<br/>按 库.表 分区"]
    K --> ODS["ODS 贴源层<br/>Hive/HDFS 原样落地"]
    K --> RT["实时消费者<br/>Flink: 大盘/特征"]
    ODS --> DW["每日调度<br/>DWD→DWS→ADS"]
    DW --> BI["BI 报表/画像/风控特征"]

```

**分区设计**：Kafka 按「库.表」分区保证单表变更有序（同一行按主键再分区更细）——订单表变更的顺序性是下游状态机正确消费的前提。**ODS 保真原则**：贴源层原样存储（含 before/after 镜像），不做任何清洗——清洗错了可以重跑，原始数据丢了就没了。

**调度加工（分层）**：调度系统（DolphinScheduler/Airflow）按依赖编排每日/小时任务：DWD 清洗（去重/补维度/口径统一）→ DWS 按主题聚合（人/商品/商户日粒度）→ ADS 应用层供报表。**分层复用是效率核心**：下游报表消费 DWS 而不是各自重扫 ODS——聚合算一次，处处使用。

```mermaid
flowchart TB
    RT["数据时效光谱"] --> R1["秒级: Flink 实时消费<br/>大盘/风控特征"]
    RT --> R2["小时级: CDC 准实时入仓<br/>准实时报表"]
    RT --> R3["T+1: 调度批量加工<br/>BI/画像/全量重跑"]

```

## 三、机制：可靠性三支柱

**① 不丢：断点与重放**。CDC 位点（binlog offset）定期持久化，宕机后从位点恢复；ODS 层保留原始事件，**任何下游加工错误都可以从 ODS 重跑**——「可重跑」是数据链路可靠性的核心语义（对比业务 MQ：消息消费确认后即删，重放成本高）。

**② 不重：幂等消费**。重跑必然产生重复数据——下游表用「主键覆盖」语义（insert overwrite 按分区覆盖）或去重窗口处理。**幂等不是可选是必须**：数据链路的重跑是常态（口径变更/历史修复都靠重跑）。

**③ 可校验：链路对账**。源库行数 vs ODS 行数（按表按天比对）、关键字段 checksum 比对——**采集链路自己也要被对账**（它是对账体系的数据供给方，自己错了全链错）。

链路的量级形态：万级表变更/秒的峰值（大促下单洪峰）由 Kafka 缓冲削峰，ODS 按天落地的数据量达 TB 级——**量级决定链路的分区数与集群容量，量级翻倍前要先扩链路**。

## 四、实践：典型场景与消费矩阵

| 消费方 | 数据需求 | 时效 | 从哪取 |
|---|---|---|---|
| 实时大盘 | 订单事件流 | 秒级 | Kafka 直接消费（Flink） |
| BI 报表 | 全量明细+聚合 | T+1 | ADS/DWS |
| 推荐画像 | 用户行为明细 | 小时级 | DWD |
| 风控特征 | 实时行为+历史统计 | 秒+T+1 混合 | Kafka + DWS |
| 机器学习 | 全量历史特征 | 离线批量 | 数仓全层 |

**一份数据多种消费**是链路的建设目标——ODS/DWD 建好后，新需求（新报表/新特征）只是「多一个下游消费者」，不再需要新建采集链路。**数据链路的边际成本递减，是它区别于烟囱式建设的核心价值**。

## 与实时大盘的关系

实时大盘（第 9 篇）是本链路的「实时消费者」分支：Flink 既做实时聚合也做 CDC 入仓（Flink CDC 一体化）。两者的分工：大盘要秒级（Kafka 直消）、数仓要全量准确（ODS 重放）——**同一份 binlog，按时效要求分流到不同消费形态**。

## 你们可能会问

**Q1：实时链路（Flink）和离线数仓数据不一致怎么办？**
Lambda 架构的老问题——主流做法：以离线为准做最终口径，实时层标注「近似」；Kappa 架构（纯流式重算）是演进方向但重算成本高。两条腿走路时，**指标口径登记表必须区分「实时口径」与「离线口径」**。

**Q2：新表接入链路要多久？**
标准化流程：binlog 白名单开通 → Kafka topic 创建 → ODS 落地 → DWD 建模——工具化成熟后半天级；没有工具链的团队会拖一周，这是数据平台建设的投资点。

## 追问链与我的判断

**追问链 1**：「binlog 直接进数仓不就行，为什么要 Kafka 中转？」→ Kafka 是「削峰+重放+多消费者」的缓冲层——直连意味着 CDC 工具故障直接影响数仓 → 中转层的成本换的是链路解耦 → **我的判断：数据链路的每一跳都要问「这一跳解耦了什么」，答不出就合并**。

**追问链 2**：「数仓分层这么多层，小团队也要分吗？」→ 分层的本质是「口径治理+复用」，不是层数仪式——两层（ODS+应用层）起步完全可行，报表过 10 张出现重复计算时再引入中间层 → **按痛点加层，不按教科书加层**。

**追问链 3**：「CDC 断了一天，数据怎么补？」→ 位点还在就能重放（ODS 按天分区重跑）→ 位点丢了呢？→ 全量快照重新初始化 + 增量拼接 → **断点管理是 CDC 运维的命门，位点监控要进告警体系**。

## 常见误区

- **误区一：binlog 采集侵入业务需要改代码**。恰恰相反，CDC 的核心价值是零侵入——业务团队无感知
- **误区二：ODS 要清洗后再落地**。ODS 的定义就是贴源保真——清洗在 DWD 做，ODS 脏了无法重跑
- **误区三：数据链路建好就完了**。表结构变更/新增表/下线表都要同步链路变更——链路的运维（DDL 适配/位点管理/延迟监控）是长期工作，监控盲区是链路故障的常见根因

## 工程级深化：链路参数、接入步骤与量级分档

> 数仓链路的参数是「时间刻度」：位点保留多久、分层保留几份、调度窗口多密。这一节给出从 binlog 到报表的参数表与新表接入 runbook。

### 参数级配置清单（数仓链路）

| 配置项 | 默认值 | 10w 级推荐 | 千万级推荐 | 亿级推荐 | 为什么 |
|---|---|---|---|---|---|
| binlog 位点保留 | 7 天 | 7 天 | 3-7 天 | 3 天+监控 | 位点是增量同步的生命线，保留期短于「最长故障修复时间」等于裸奔 |
| ODS 保留 | 30 天 | 30 天 | 90 天 | 180 天+归档 | 贴源层是重算一切的基础，保留期按「回溯重算需求」定 |

| 敏感字段策略 | 无 | 掩码 | 分级+掩码 | 分级+掩码+审计 | 数仓是敏感数据汇聚地，分级策略必须在第一张表就定 |

### 步骤级操作：新表接入数仓

前置条件：源表 binlog 开启、字段字典（含敏感等级）评审通过、下游消费方确认。

- Step 1 登记：新表进数据资产目录，标注 owner、敏感等级、更新频率。验证点：无 owner 的表不允许接入——孤儿表是数仓腐化的起点。
- Step 2 ODS 接入：配置 binlog 到 ODS 的实时同步 + 每日快照。验证点：实时流与快照对账一致，分区完整。
- Step 3 DWD 加工：按业务过程写明细宽表模型，清洗规则可回溯。验证点：清洗掉的数据有「脏数据留存区」，可审计清洗了什么。
- Step 4 下游联调：DWS/ADS 层按需求加工，报表接线。验证点：报表口径与模型文档一致，指标含义无双解。
- Step 5 SLA 挂网：任务挂上调度依赖图，配置延迟告警。验证点：人为延迟上游任务，告警链路按预期通知 owner。
- 回退：模型错误回退到「上游分区重跑」，禁止原地 UPDATE 修正历史——数仓的回退单位是分区，任何「就地修数」都会制造不可信的历史。

### 量级分档下的数仓取舍

10w 级（一张大宽表时代）：这个量级别分层，直接「业务库只读从库 + 每日同步 + 一层宽表」，报表够用。该档位的 Trade-off：模型演进性换建设速度，等查询模式稳定后再谈分层。

千万级（标准三层起步）：ODS-DWD-DWS 三层成为刚需，ETL 调度依赖图开始复杂，需要调度平台。该档位的 Trade-off：接受 20-30% 的存储冗余（各层重复存储），换每层独立演进与重算能力。

亿级（分层+实时化+治理）：离线三层之上叠加实时层（Kappa 或 Lambda），数据治理（血缘、质量、成本）从人肉升级为平台。该档位的 Trade-off：数仓团队一半人力花在「治数据」而不是「出报表」——这是规模化的必然成本，越晚投入越贵。

「挂起」是值班最需要关注的状态：重试耗尽意味着自动机制失效，人工介入的 MTTR（平均修复时间）直接决定下游报表能不能赶上 SLA——所以挂起告警的升级链必须比普通失败更急。

### 边界与反方案深推

数仓链路最深的边界是「历史的不可变性」：业务库的数据会被更新与删除，但数仓的报表一旦发出就被引用、被截图、被作为决策依据。所以 ODS 层必须保留变更前像（拉链或日快照），任何「直接覆盖历史」的做法都会让三个月前的报表无法复现——数仓的可信度建立在「历史可回放」上，这是它与业务库最本质的区别。

反方案推演：「不做分层，ODS 直出报表」——小规模时确实更快，被推迟分层的原因在亿级暴露：同一份订单明细被二十张报表各自清洗一遍，口径漂移悄悄发生，两张报表的同名指标对不上，排查成本远高于当年省下的分层建设。分层的本质是「清洗逻辑只写一次」，复用防止漂移。另一个反复出现的选项是「全面实时化，废弃 T+1」：被否的理由是成本与价值不匹配——绝大多数经营分析对时效的真实要求是小时级而非秒级，只有作战类指标值得实时链路，全面实时化等于为最后一个 5% 的场景支付 50% 的基建成本。

还有一条工程边界值得写进基因：binlog 的语义陷阱。业务侧一个 UPDATE 会产生一行 binlog，但批量任务的全表更新会产生百万行事件，同步链路如果没有批处理识别与限流，一次深夜的全表刷数就能把下游消费打挂——上游业务行为会以数据事件的形式攻击数据链路，同步层必须有背压与突发识别，这是很多链路第一次雪崩的原因。

### 多视角圆桌：一条报表口径的部门之争

**业务方**：订单量报表和支付成功率报表对不上，GMV 口径里到底算不算退款？**数据团队**：GMV 有两个口径（支付口径与履约口径），两个报表取了不同口径，文档里写了。**业务方回应**：没人看文档，报表名字一样就该是同一个数。**架构结论**：同名指标必须单源——指标字典平台化，每张报表的指标绑定字典 ID，字典改动强制通知所有引用方。口径之争的本质不是技术问题，是「指标的命名权与定义权归谁」的治理问题，答案只能是集中登记、变更广播。

### 深层追问链

追问一：为什么 binlog 同步会乱序，顺序不是有保障的吗？——单表单行的顺序在 binlog 流里确实有序，但同步链路为了吞吐并行消费，跨表、跨分片的并行打散了全局顺序；同一行多次变更如果被并行处理，旧值可能后到覆盖新值。所以宽表写入必须带版本仲裁（更新时间戳或 binlog 位点），乱序到达时旧版本被丢弃——并行度是吞吐与顺序的交易，版本号是这场交易的仲裁者。

追问二：数仓为什么强调「可重跑」？任务失败重跑不就行了？——重跑的前提是「重跑结果幂等」：同一分区重跑三次结果一致。要幂等就必须「先删后写」且范围严格限定在分区边界，任何跨分区写、任何「增量追加」式加工都可能在重跑后产生重复数据。可重跑性是设计出来的：加工任务只碰自己的分区，是数仓最重要的一条工程纪律。

追问三：实时链路和离线链路会不会算出不一样的数？——必然会有差异（延迟、乱序、重算策略不同），Lambda 架构的双链路差异是常态而不是异常。工程上的做法是「以离线为权威、实时为准实时」：实时数字用于作战监控，日切后以离线重算结果覆盖，且差异率本身被监控——差异率突增说明实时链路有 bug，这个「监控差异的监控」是 Lambda 架构的自我校验层。

### 一次调度风暴的复盘式推演

月末零点，财务出报表的批量任务触发，恰好与某业务线的存量迁移任务重叠，集群 IO 打满，上百个任务排队，核心报表 T+1 延迟四小时才出。事后复盘发现两个问题：调度平台没有「优先级」概念，财务核心任务与普通任务平等排队；任务提交没有容量审批，业务线的大任务可以随意挤占共享集群。改造动作：任务分三级优先队列，核心报表任务独占资源池；大任务提交走容量评估（预估数据量、预估运行时长），超阈值自动要求拆分或错峰。风暴之后的集群规则变了：共享集群的每一次「大动作」都要先回答「你占多少、占多久、别人会怎样」——调度风暴不是算力问题，是资源治理缺位问题。

### 你们可能会问

问：数仓分层会不会过度设计？小团队要不要简化？——简化的是层数不是原则。小团队可以 DWD 与 DWS 合并、ADS 轻量化，但「清洗逻辑只写一次」「分区可重跑」「口径单源」三条原则无论规模都不能让步——层是形式，原则是本质。

问：binlog 直接进数仓，为什么还要过消息队列？——削峰、多订阅方解耦、以及位点管理的职责分离。binlog 流直接灌下游，任何一个订阅方消费慢都会反压整个同步；过一层队列后，每个下游独立消费自己的分区，慢消费不影响别人——队列在这里买的是「订阅方之间的隔离性」。

## 自测三问

1. **为什么采集走 binlog 而不是业务双写？**
   - 零侵入、无遗漏、带前后镜像——双写会漏（直改库的操作）且侵入业务；binlog 是数据库变更的完整事件流。

2. **数仓为什么要分层（ODS/DWD/DWS/ADS）？**
   - 分层治理口径与复用：清洗规则在 DWD 唯一、聚合在 DWS 复用、ADS 只做应用——没有分层就是每张报表各自算一遍。

3. **数据链路怎么保证「可重跑」？**
   - ODS 保真存储（原样事件可重放）+ 下游幂等（分区覆盖语义）+ 调度支持断点重跑——任何加工错误都能从 ODS 重来。

## 开放问题

- **湖仓一体的落地**：数仓（Hive）与数据湖（Iceberg/Hudi/Paimon）的选型之争仍在演进——湖的灵活性（schema evolution/实时 upsert）与仓的成熟治理各有优势
- **实时数仓的口径一致性**：Flink 实时口径与离线口径的天然漂移（Lambda 架构老问题），流批一体的完全统一仍在路上

## 核心带走

**30 秒复述**：大数据链路 = binlog CDC 零侵入采集 → Kafka 分区有序 → ODS 保真落地 → 分层加工（DWD 口径统一/DWS 复用聚合/ADS 应用）→ 多消费（报表/画像/风控/大盘）；可靠性三支柱：不丢（断点重放）/不重（幂等）/可校验（链路对账）。**失效边界**：ODS 清洗后无法重跑、DDL 未适配断链、链路无延迟监控三处盲区。
