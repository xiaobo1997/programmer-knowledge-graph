# 存储架构亿级选型全景

> 本篇是存储架构的整合层收束篇，提供 MySQL/Redis/Kafka/ES 在千万/亿级下的分层选型与 Trade-off 评估。

## 一、本文核心

存储选型 = 量级定形态 + 红线定时机 + Trade-off 评估

核心产出：选型决策树 + Trade-off 对照表 + 演进路线图

## 二、核心机制原理穿透

### 2.1 组件角色判定

```
组件角色判定口诀：

  换语言还用得上吗？
    ├─ 是 → architecture（通用机制）
    └─ 否 → ecosystem/middleware（组件层）

  选型判定：
    数据量 < 100GB → MySQL 为主
    数据量 100GB - 1TB → MySQL + Redis
    数据量 > 1TB → MySQL + Redis + ES/Kafka
```

### 2.2 量级红线对照表

| 量级 | MySQL | Redis | Kafka | ES |
|---|---|---|---|---|
| **十万** | 单库单表 | 单机 | 单集群 | 单节点 |
| **百万** | 读写分离 | 集群 | 多分区 | 2-3 节点 |
| **千万** | 分库分表 | 集群 + 哨兵 | 多集群 | 3-5 节点 |
| **亿级** | 分库分表 + 中间件 | 集群 + 读写分离 | 多集群 + 跨机房 | 5+ 节点 |

## 三、关键参数与边界条件

### 3.1 混合部署 Trade-off

| 决策 | 选 A | 选 B | Trade-off |
|---|---|---|---|
| 主存 | MySQL | PolarDB-X | MySQL 灵活，PolarDB-X 运维省心 |
| 缓存 | Redis 单机 | Redis 集群 | 单机简单，集群高可用 |
| 消息 | Kafka | RocketMQ | Kafka 高吞吐，RocketMQ 事务消息 |
| 检索 | ES | MySQL 全文索引 | ES 强大，MySQL 简单 |
| 缓存一致性 | Write-through | Invalidate | Write-through 强一致，Invalidate 最终一致 |
| 分片数 | 64 片 | 1024 逻辑槽 | 64 片简单，1024 槽灵活 |
| 中间件 | 客户端 SDK | 代理层 | SDK 延迟低，代理层语言无关 |
| 一致性 | 强一致 | 最终一致 | 强一致吞吐低，最终一致需要补偿 |
| 部署 | 单机房 | 多机房 | 单机房简单，多机房高可用 |

### 3.2 演进路线图

```
演进路线图：

  十万 QPS ────→ 百万 QPS ──────→ 千万 QPS ─────────→ 亿级 QPS
     │                │                 │                  │
     ▼                ▼                 ▼                  ▼
  MySQL           MySQL +           MySQL +            MySQL +
  单库单表         Redis            Redis 集群 +        Redis 集群 +
  单体应用         读写分离          分库分表            分库分表 +
                                                     异步削峰
                                                     单元化
```

## 四、业内惯例

- 量级判断：先看当前量级，再看增长斜率
- 选型原则：金融强一致、电商最终一致、社交高吞吐
- 演进路径：先优化再拆分，先读写分离再分库分表
- 混合部署：核心数据 MySQL + 热数据 Redis + 日志 Kafka + 检索 ES

## 五、核心带走

- **核心一句话**：存储选型 = 量级定形态 + 红线定时机 + Trade-off 评估
- **量级红线**：十万 MySQL 单库、百万读写分离、千万分库分表、亿级分布式架构
- **选型原则**：金融强一致、电商最终一致、社交高吞吐
- **Trade-off**：没有银弹，每一步都是代价换收益
- **哪里会坏**：选型不当、量级估计错误、扩展性不足
