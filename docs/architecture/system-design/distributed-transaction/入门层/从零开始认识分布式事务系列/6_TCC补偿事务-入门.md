# TCC 补偿事务

> Try-Confirm-Cancel——资源预留式柔性事务，幂等/空回滚/悬挂三坑拆解。
>
> 本文为系列规划大纲页：篇目结构已定，正文按下方骨架落盘。

## TCC 的本质：资源预留

- Try：冻结/预留资源（冻结额度，不是真扣）
- Confirm：用预留资源完成业务（冻结转实扣）
- Cancel：释放预留（解冻）——不是「写回」而是「解冻」

## 为什么不是业务操作拆三份

- Try 就真扣 → Cancel 无法补偿只能反向写 → 并发下必然错账
- 正确姿势：账户表设计「可用额度 + 冻结额度」两列
- 反例教学：把 update 拆成 tryUpdate/confirmUpdate 的实现事故

## 三个经典坑

- 幂等：Confirm/Cancel 都可能重试，必须幂等（回指分布式理论幂等篇）
- 空回滚：Try 没到达（超时）但 Cancel 先到——Cancel 要识别「没预留过」直接返回成功
- 悬挂：Cancel 执行后 Try 才到——Try 要识别「事务已回滚」拒绝执行；解法套路：事务状态表 + 状态检查
