# 高并发架构决策树：从十万 QPS 到亿级

> 本篇是高并发架构的专题层收束篇，提供从十万 QPS 到亿级请求的统一决策树与 Trade-off 评估。

## 一、本文核心

高并发架构 = 量级定形态 + 红线定时机 + 决策树定路径

核心产出：决策树 + Trade-off 表 + 三类演进事故

## 二、量级分档全景

```
量级分档决策：

  十万 QPS ──── 百万 QPS ───── 千万 QPS ────────── 亿级 QPS
     │              │                 │                  │
     ▼              ▼                 ▼                  ▼
  单级缓存       多级缓存         多级缓存+       全链路缓存+

  单库单表       读写分离         分库分表          分布式架构
  单机部署       集群部署         单元化部署        多地多活
```

## 四、三类演进事故

### 4.1 事故 1：为想象中的量级预支复杂度

**场景**：系统当前 100 万 QPS，提前按亿级架构设计。

**现象**：
- 架构过度复杂
- 运维成本高
- 性能反而下降

**根因**：
- 过度设计
- 为未来量级预支复杂度
- 忽略当前量级的最优解

**修复**：
1. 按当前量级设计
2. 预留扩展点（不预支实现）
3. 量级到了再升级

### 4.2 事故 2：分片键选错导致数据倾斜

**场景**：按低基数列分片，热点数据集中。

**现象**：
- 某些分片数据量远超其他
- 热点实例压力过大
- 扩容再平衡困难

**根因**：
- 分片键选择不当
- 数据分布不均匀
- 未考虑业务特性

**修复**：
1. 分片键满足"数据均匀 + 查询对齐"
2. 提前验证数据分布
3. 使用逻辑分片 + 映射表

### 4.3 事故 3：跨分片事务丢失一致性

**场景**：分库后，本地事务变成跨分片事务。

**现象**：
- 数据不一致
- 事务失败
- 资金损失

**根因**：
- 未使用分布式事务
- 跨分片操作无协调
- 补偿机制缺失

**修复**：
1. 使用 SAGA/TCC 分布式事务
2. 补偿机制完善
3. 对账体系建立

## 五、决策树

```
量级判断：
  < 10w QPS → 单体 + 单级缓存 + 单库
  10w - 100w → 集群 + 多级缓存 + 读写分离
  100w - 1000w → 分片 + 异步削峰 + 单元化
  > 1000w → 分布式架构 + 全链路缓存 + 多地多活

分片决策：
  能分片？ → 水平分片
    分片键可选？ → 按分片键分片
    分片键不可选？ → 先加缓存/ES 兜底
  不能分片？ → 垂直分片（按业务边界）

缓存决策：
  读多写少？ → 缓存
  读少写多？ → 不缓存
  一致性要求高？ → Write-through
  一致性要求低？ → Invalidate
```

## 六、Trade-off 评估

| 决策 | 选 A | 选 B | Trade-off |
|---|---|---|---|
| 分片数 | 64 片 | 1024 逻辑槽 | 64 片简单但再平衡难；1024 槽灵活但路由复杂 |
| 缓存 | 单级 Redis | 多级缓存 | 单级简单，多级一致性强 |
| 数据库 | MySQL | PolarDB-X | MySQL 灵活，PolarDB-X 运维省心 |
| 消息队列 | Kafka | RocketMQ | Kafka 高吞吐，RocketMQ 事务消息 |
| 注册中心 | Nacos | Eureka | Nacos 强一致，Eureka 高可用 |
| 网关 | Nginx | Envoy | Nginx 成熟，Envoy 动态配置 |
| 一致性 | 强一致 | 最终一致 | 强一致吞吐低，最终一致需要补偿 |
| 部署 | 单机房 | 多机房 | 单机房简单，多机房高可用 |

## 七、业内惯例

- 按当前量级设计，不为未来预支复杂度
- 分片键必须满足"数据均匀 + 查询对齐"
- 缓存是读多写少场景的首选
- 分布式事务是最后手段，不是标配

## 八、核心带走

- **核心一句话**：高并发架构 = 量级定形态 + 红线定时机 + 决策树定路径
- **量级分档**：十万 → 百万 → 千万 → 亿级，每档有最优解
- **红线校准**：单机/单库/单集群红线是决策依据
- **决策树**：按量级 → 分片 → 缓存 → 数据库 → 消息 → 注册 → 网关 → 一致性 → 部署
- **Trade-off**：没有银弹，每一步都是代价换收益
- **哪里会坏**：预支复杂度、分片键选错、跨分片事务



**追问与质疑**：高并发架构决策树 的方案在更极端条件下是否成立？——生产环境的复杂性常超设计假设，每个结论都需在实战中验证。反直觉的是，最简方案往往比复杂方案更稳定。
