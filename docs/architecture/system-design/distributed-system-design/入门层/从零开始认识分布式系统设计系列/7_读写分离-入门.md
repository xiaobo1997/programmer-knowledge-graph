# 读写分离

> 主从复制 / 读写分离 / 复制延迟下的一致性权衡。
>
> 本文为系列规划大纲页：篇目结构已定，正文按下方骨架落盘。

## 读写分离的动机与架构

- 读多写少是多数业务形态；主写从读分摊压力
- 主从复制：binlog → 从库重放（异步复制为默认）
- 读写路由：SDK 层 / 中间件层 / 数据库代理

## 复制延迟的应对

- 延迟根因：从库单线程回放（老版本）/ 大事务 / 从库负载高
- 强制读主：关键路径（下单后查订单）走主库，代价是主库压力
- 会话内读己之写：写后短时间读主（回指分布式理论一致性模型）

## 读写分离的边界

- 主从只是「读扩展」，写瓶颈靠分库分表（归 MySQL 系列深挖）
- 主从切换的数据丢失窗口（异步复制）与半同步权衡
- 读写分离是演进中间态：流量再涨进分库分表
