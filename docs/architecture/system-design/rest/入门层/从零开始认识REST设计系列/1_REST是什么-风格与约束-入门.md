# REST 是什么：风格与约束

> **一句话摘要**：REST 是一种**架构风格**而不是协议或标准——Fielding（2000 博士论文）把 Web 为什么能扩展到全球的原因提炼成六条约束，满足约束的 API 才叫 RESTful；它回答的不是「接口怎么写」，是「接口如何在互联网规模上独立演进」。

> **本文核心**：机制链 = **Web 规模的两大敌人（不可预知的负载变化 + 客户端服务端独立演进）→ 六约束逐条对抗（无状态抗扩容、统一接口抗演进、缓存抗延迟…）→ HATEOAS 是约束的完全体（工程上常降级）**——REST 的每条约束都有明确的「对抗对象」，理解约束先看它防什么。

前置阅读：[系列导读](./0_系列导读-全景.md)。HTTP 语义细节见下一篇[HTTP 语义用对](./2_HTTP语义用对-入门.md)。

## 1. 背景：Fielding 在回答什么问题

Roy Fielding 是 HTTP/1.1 的主要作者，2000 年博士论文《Architectural Styles and the Design of Network-based Software Architectures》里问了一个问题：**Web 为什么能长到全球规模，而大多数企业系统做不到？** 答案是一组架构约束——把它们用在 API 设计上，接口就能获得 Web 同款的可扩展性与演进能力。

这个定位解释了三个常见误解：REST 不是「JSON 接口的别称」（协议无关，HTTP 只是 Web 的现实载体）；不是「URL 好看一点」的风格滤镜；也不是「RPC 的反面」（RPC 与 REST 是两种架构风格的取舍，见第 7 节）。

## 2. 核心机制：六约束与各自的对抗对象

```mermaid
flowchart TD
    W[Web 规模的敌人] --> E1[负载不可预知: 突发流量]
    W --> E2[客户端服务端必须独立演进]
    E1 --> C1[客户-服务器分离: 职责解耦才能各自扩展]
    E1 --> C2[无状态: 请求自带全部上下文 -> 任意实例可服务 -> 水平扩展]
    E1 --> C3[缓存: 响应声明可缓存性 -> 中间层卸载重复请求]
    E2 --> C4[统一接口: 资源识别/表述/操作分离 -> 双方只认契约不认实现]
    E2 --> C5[分层系统: 客户端不知也不必知中间层(代理/网关/负载均衡)]
    E2 --> C6[按需代码(可选): 服务端下发代码扩展客户端能力]
    C1 & C2 & C3 & C4 & C5 & C6 --> R[满足约束 = RESTful]
```

逐条的核心（追问链式预判）：

- **无状态**——为什么是 REST 最值钱的约束？请求携带全部上下文（认证令牌/参数），服务端不存会话 → 任意实例可服务任何请求 → 负载均衡与水平扩展零特殊设计；代价是每次请求重复携带（令牌体积/带宽）与「服务端无法记忆」的业务设计调整。**它也是工程上最常被违反的约束**（服务端 session、顺序依赖）。
- **统一接口**——为什么敢让客户端和服务端独立升级？接口固定为「资源识别（URI）、表述（格式）、操作（HTTP 方法）」三分离——服务端内部实现随便换，只要资源与语义不变，客户端无感。这是演进能力的来源，也是 REST 与 RPC 的根本分野（RPC 每加一个功能就多一个接口方法，客户端必须跟着升级）。
- **分层系统**——客户端不需要知道请求到达的是真服务还是缓存/网关/代理——这是 CDN、网关、负载均衡能无缝插进 Web 的原因。
- **缓存、客户-服务器、按需代码**——分别对抗延迟、耦合、客户端能力固化；按需代码（JavaScript）在 Web 是现实，在 API 设计里常不适用（可选约束）。

## 3. 落地实践：用约束自检你的 API

1. **无状态自检**：把任一实例重启，正在进行的客户端会话会断吗？（会 → 有状态残留）；同一请求发两次到不同实例，结果一致吗？（不一致 → 实例内有状态）。
2. **统一接口自检**：新增一个查询维度需要客户端升级吗？——需要 → 接口绑死了实现（如 URL 带 `/getOrderByIdAndDateV2` 这类动作式命名）；资源式设计（`/orders?date=...`）让新维度只是新参数。
3. **分层自检**：在服务前插一个缓存/网关，API 会坏吗？——会（比如响应带实例本地状态）→ 分层约束被违反。
4. **HATEOAS（超媒体即应用状态引擎）自检**：客户端的下一步操作由响应里的链接引导吗？——多数工程答案是否（HATEOAS 是六约束中最少被完整实现的），**显式承认降级**比假装 RESTful 诚实：约束达成度是谱系（Richardson 成熟度模型：0 级 RPC 式 → 1 资源化 → 2 方法语义 → 3 HATEOAS），业内主流在 2 级。

## 4. 生产视角：违反约束的代价形态

- **有状态接口的扩容失败**：大促扩容后流量仍集中（负载均衡按会话粘住旧实例）——粘性会话是「无状态被破坏」的止血带，代价是扩容不均与故障爆炸半径集中（呼应[高扩展设计](../../../distributed-system-design/入门层/从零开始认识分布式系统设计系列/8_高扩展设计-入门.md)的无状态纪律）。
- **动作式 URL 的演进税**：`/getUserInfoV1`、`/getUserInfoV2`——每加一个字段出一个新接口，客户端矩阵爆炸；「V2 地狱」是统一接口缺失的复利债。
- **响应不可缓存的连锁**：全接口 no-store——网关/CDN 全部失效，所有流量直达源站。缓存约束的违反让「分层卸载」这张王牌作废。
- **「RESTful 之名行 RPC 之实」**：URL 全是动词（`/createOrder`）、POST 一招走天下——Richardson 0 级。能用，但放弃了 HTTP 语义给的缓存/幂等/工具链红利（下一篇展开方法语义）。

## 5. 主流方案怎么做：约束达成度的生态现实

| 生态 | RESTful 程度 | 机制选择 |
|---|---|---|
| 公共开放 API（GitHub/Stripe 等） | 高（2-3 级） | 资源建模严格 + 版本化 + 分页/过滤约定统一——演进能力是卖点 |
| 国内大厂开放平台 | 中（2 级为主） | 资源化 + 动作资源折中（如 POST /orders/123/cancel） |
| 企业内部微服务 | 2 级常见，0 级不少 | 团队规范驱动；内部 RPC 场景常直接选 gRPC/Dubbo（机制不同不打 REST 旗号） |
| GraphQL/WebSocket 场景 | 另立风格 | 查询复杂/推送场景，REST 的统一接口不占优——按场景选型 |

规律：**「完全 RESTful」在工业界是少数派，2 级是主流平衡点**——方法语义与资源建模的红利最大、代价最低；HATEOAS 的收益（客户端零升级）在前后端同发版的组织里折旧。

## 6. 典型场景

- **开放平台**（对外级）：第三方千千万万不能强求同步升级——REST 约束的价值最大化场景。
- **前后端分离**（协作级）：契约（OpenAPI）+ 资源式接口——独立演进的红利内化。
- **内部高帧率调用**（例外级）：微服务间每秒万次调用、字段级强耦合——gRPC（RPC 风格）效率更优；**REST 不是普适答案，是「边界与演进」场景的答案**。

## 7. 与相邻概念的区别

- **REST vs RPC**：统一接口（资源+方法固定）vs 自由接口（动作即方法）——REST 买演进与缓存，RPC 买直白与效率；同一家公司常两者并用（对外 REST、对内 RPC）。
- **REST vs RESTful vs Richardson 分级**：REST 是约束全集；RESTful 是「满足度较高」的口语；分级模型（0-3）给满足度刻度——讨论时先对齐「第几级」。
- **REST vs GraphQL**：统一接口的「资源粒度」之争——GraphQL 让客户端自选字段（解决过度获取），代价是缓存语义与网关生态重造；查询复杂的场景值得，简单 CRUD 是过度设计。
- **架构风格 vs 协议**：REST 可跑在 HTTP/1.1、HTTP/2、甚至其他协议上——HTTP 是事实载体不是定义的一部分。

## 8. 常见误区与不适用

- **「用 JSON + HTTP 就是 RESTful」**： Richardson 0 级的 RPC 只是恰好住在 HTTP 里——约束达成度才是判据。
- **「HATEOAS 不实现就不是 REST」**：约束达成是谱系；显式声明降级（2 级）比嘴上全须全尾诚实——关键是知道放弃了什么收益。
- **「无状态 = 服务端不存任何数据」**：不存「会话状态」（请求上下文），缓存、数据库照存——约束管的是「请求可被任意实例处理」，不是失忆。
- **「POST 一招鲜最灵活」**：绕过方法语义 = 放弃缓存判定、幂等语义、重试安全（下一篇的主题）——灵活的代价是全部语义红利归零。
- **不适用**：强实时推送（WebSocket/流式）、字段级灵活查询且规模大（GraphQL）、内部极致性能调用（RPC/二进制协议）——REST 的强项是边界与演进，不是全部场景。

## 9. 你们可能会问

- **2 级够用，为什么要知道 3 级？** 知道全貌才知道放弃了什么——HATEOAS 的收益（客户端跟随链接发现能力）在「API 消费方不受你控制」的开放场景是真需求；内部系统可放弃，但应是决策不是默认。
- **REST 约束和微服务的「无状态」是一回事吗？** 同源同义——REST 的无状态约束是微服务水平扩展纪律的理论出处之一（设计系列的高扩展篇与它互为表里）。
- **内部服务要不要也 RESTful？** 按交互形态：边界类（跨团队、演进频繁）值得；内部高频性能敏感类 RPC 更优——「对外 REST、对内 RPC」是主流双轨。
- **怎么向团队推行约束自检？** 把第 3 节四个自检题进 code review checklist + Richardson 分级写进 API 规范——约束变检查项，风格变纪律。
- **REST 会过时吗？** 资源+统一接口的边界设计思想不过时；协议载体与补充风格（GraphQL/gRPC）持续演进——学约束（为什么），别绑协议（是什么）。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：REST = 用六条架构约束对抗 Web 规模的两大敌人（负载不可知 + 独立演进）——每条约束防一个敌人，满足度是谱系。
- **链条复述**：两大敌人 → 六约束（无状态/统一接口/缓存/分层/分离/按需代码）→ 各自的对抗对象 → Richardson 分级自评 → 按场景取舍。
- **失效点与边界**：推送/极致性能/字段灵活查询场景非其主场；0 级 API 不应自称 RESTful。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 六约束架构风格 + Richardson 分级 |
| Why | Web 全球规模的可扩展性与演进能力的经验提炼 |
| When | 开放平台、前后端契约、边界 API 设计 |
| Where | HTTP 之上的资源式接口（协议无关） |
| How | 约束自检四题 → 分级自评 → 显式取舍 |

💡 **实战提示**：无状态与统一接口是两大主约束（先保这两个）；分级自评写进 API 规范；对外场景 HATEOAS 的放弃要显式决策。

**开放问题**：如果客户端生态（App 版本碎片化）继续恶化，HATEOAS 的「服务端引导」会不会回归主流——还是被 GraphQL 式的「客户端自选」取代？

**决策（何时用）**：边界与演进敏感的接口推荐 REST（至少 2 级）；内部高频调用推荐 RPC 双轨；推荐把「Richardson 目标级」写进 API 设计规范。

**Trade-off（代价与反方案）**：REST 约束用「设计纪律 + 显式建模成本」换「演进能力 + 缓存与扩展红利」；反方案——RPC（直白高效，代价是演进耦合）、GraphQL（灵活查询，代价是缓存与生态重造）、全 POST 的 0 级（零纪律，代价是语义红利归零）。

**演进视角**：2000 年的约束体系在 HTTP/2、HTTP/3 时代依然适用——约束定义在「架构层」而非「协议层」，这是它比任何具体技术长寿的原因；演进的是载体，不变的是对抗对象。
