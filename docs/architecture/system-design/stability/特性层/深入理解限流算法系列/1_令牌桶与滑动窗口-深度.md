# 深入理解限流算法：令牌桶/滑动窗口/漏桶源码级

> 入门层讲了「限流是什么」，本篇讲「限流算法底层怎么实现」——从计数器到令牌桶的演进，为什么 Go-zero/Spring Cloud Gateway 选择令牌桶，Redis+Lua 限流的原子操作设计。

## 一句话摘要

限流算法的本质是**控制请求进入系统的速率**。三种主流算法（计数器/滑动窗口/令牌桶/漏桶）各有取舍：计数器简单但临界突发，滑动窗口精确但内存开销大，令牌桶允许突发但实现简单。金融场景选令牌桶——突发可控 + 实现简单 + 易于限流降级联动。

## 🎯 本文核心

**核心机制一句话**：限流 = 按算法（令牌桶/漏桶/滑动窗口）在阈值处快速拒绝超额请求，让系统在超载时「有损但可用」而不是雪崩。

**机制链（4 个节点）**：

计数器（固定窗口）→ 滑动窗口（精确计数）→ 漏桶（匀速排出）→ 令牌桶（允许突发）

## 为什么不用计数器做生产限流

计数器最简单，但存在**临界突发**问题：

```
窗口1: [0-59s]  100 请求 → 窗口重置瞬间 0
窗口2: [60-119s] 100 请求 → 允许
→ 60s 瞬间涌入 200 请求（两窗口叠加）
```

**解决方案**：滑动窗口（精确但内存开销大）或令牌桶（允许突发但可控）。

## 四种算法对比

| 算法 | 允许突发 | 实现复杂度 | 精确度 | 适用场景 |
|---|---|---|---|---|
| 固定窗口计数器 | ❌ 有临界突发 | ⭐ | 窗口内精确 | 入门理解 |
| 滑动窗口 | ✅ | ⭐⭐ | 精确 | 需要精确限流 |
| 漏桶 | ❌ | ⭐⭐ | 匀速流出 | 流量整形 |
| **令牌桶** | ✅ 可配置 | ⭐ | 允许突发 | **生产首选** |

## 令牌桶源码级解析

### 核心数据结构

```java
// 令牌桶核心变量
class TokenBucket {
    double maxTokens;      // 桶容量（最大突发）
    double tokens;         // 当前令牌数
    double refillRate;     // 每秒生成令牌数（QPS）
    long lastRefillTime;   // 上次填充时间戳
}
```

### 核心逻辑

```java
// 1. 计算应补充的令牌数
double now = System.currentTimeMillis();
double elapsed = (now - lastRefillTime) / 1000.0;
double tokensToAdd = elapsed * refillRate;
tokens = Math.min(maxTokens, tokens + tokensToAdd);
lastRefillTime = now;

// 2. 尝试获取令牌
if (tokens >= 1) {
    tokens -= 1;
    return true;  // 允许通过
} else {
    return false; // 限流拒绝
}
```

### 关键参数设计

| 参数 | 含义 | 金融场景取值 | 为什么 |
|---|---|---|---|
| maxTokens | 桶容量 | QPS 的 1.5-2 倍 | 允许短时突发，不浪费带宽 |
| refillRate | 生成速率 | 核心链路 P99 QPS | 平滑请求速率 |
| 预热时间 | 桶从空到满的时间 | 1-2 秒 | 防止刚启动就限流 |

## 为什么令牌桶比漏桶更适合金融场景

- **漏桶**：严格匀速流出，突发直接拒绝——适合流量整形（网络设备），不适合业务
- **令牌桶**：允许突发（令牌积累），平滑消费——业务突发是正常现象，不应该被拒绝
- **金融场景**：大促/秒杀是合法突发，令牌桶允许「攒令牌→瞬间通过」，漏桶会误杀

## 分布式限流：Redis + Lua

单机限流不够——多实例需要共享计数。Redis + Lua 保证原子性：

```lua
-- Redis Lua 限流脚本
local tokens = redis.call('get', KEYS[1])
local now = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local max_tokens = tonumber(ARGV[3])
local last_time = tonumber(ARGV[4])

-- 计算应补充令牌
local elapsed = now - last_time
local new_tokens = math.min(max_tokens, tokens + elapsed * refill_rate)

if new_tokens >= 1 then
    redis.call('set', KEYS[1], new_tokens - 1, 'PX', 1000/refill_rate)
    return 1  -- 允许
else
    redis.call('set', KEYS[1], new_tokens, 'PX', 1000/refill_rate)
    return 0  -- 限流
end
```

> 💡 **tips**：Lua 脚本在 Redis 单线程执行，保证原子性——不需要额外的分布式锁。

## 与熔断/降级的联动

限流不是孤立的——与熔断、降级构成三层防线：

1. **限流**：入口控制，QPS 超阈值拒绝
2. **熔断**：下游故障，快速失败 + 自动恢复
3. **降级**：核心链路保护，非核心功能主动放弃

```
请求 → 限流（QPS 控制）→ 熔断（下游健康）→ 降级（核心保护）→ 服务
```

## Trade-off

| 选项 | 结论 |
|---|---|
| 令牌桶 vs 滑动窗口 | 令牌桶实现简单 + 允许突发 → 生产首选 |
| 本地限流 vs 分布式限流 | 单机用本地（Guava RateLimiter），多实例用 Redis+Lua |
| 限流阈值设多少 | P95 × 0.8 起步 + 20% 余量 + 动态调整 |

## 常见误区

1. **"限流阈值 = 峰值 QPS"** —— 峰值是理想状态，应按 P95 设阈值
2. **"令牌桶满了就不限流"** —— 桶满后仍然限流，只是允许短时突发
3. **"限流后就丢弃"** —— 可以排队等待（令牌桶支持排队模式），不是必须丢弃

## 你们可能会问

**Q1：Guava RateLimiter 和 Redis 限流怎么选？**
单机用 Guava（进程内，零网络开销），多实例用 Redis+Lua（共享计数，分布式一致）。

**Q2：限流被拒的请求怎么处理？**
返回 429 Too Many Requests + Retry-After 头，客户端指数退避重试。

**Q3：限流和熔断的区别？**
限流控制入口速率（预防），熔断处理下游故障（止损）——两者互补，不是替代。

**Q4：为什么不用滑动窗口？**
滑动窗口精确但实现复杂（需要维护时间槽数组），令牌桶实现简单 + 允许突发 → 生产首选。

**Q5：限流阈值怎么动态调整？**
监控实时 QPS + 错误率 → 告警触发 → 人工/自动调阈值。不要静态设置。
