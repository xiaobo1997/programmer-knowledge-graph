# 深入理解混沌工程：主动暴露弱点

> 入门层讲了「混沌工程是什么」，本篇讲「混沌工程怎么设计实验」——实验设计原则（Formulate/Hypothesize/Execute/Observe），注入层次（进程/Pod/机房），以及如何避免「实验引入真实故障」。

## 一句话摘要

混沌工程不是「搞破坏」，是**主动暴露弱点**——通过注入可控故障，验证系统在异常条件下的韧性。核心原则：在非高峰期 + 影响范围可控 + 有回滚方案的前提下，从小到大逐步注入。

## 🎯 本文核心

**核心机制一句话**：混沌工程 = 实验设计（假设→注入→观察→结论）——主动暴露弱点，验证韧性。

**机制链（4 个节点）**：

假设 → 注入故障 → 观察系统反应 → 得出结论（弱点/韧性）

## 混沌工程 vs 故障演练

| 维度 | 混沌工程 | 故障演练 |
|---|---|---|
| 范围 | 主动注入故障 | 模拟真实场景 |
| 自动化 | 高度自动化 | 半自动化 |
| 覆盖 | 未知弱点 | 已知场景 |
| 目的 | 暴露未知弱点 | 验证已知预案 |
| 工具 | Litmus/Chaos Mesh | 人工触发 |

> 💡 **tips**：混沌工程的价值在于发现**未知的弱点**——预案覆盖不到的地方。

## 实验设计原则

### 四步法

1. **Formulate（假设）**：系统在什么条件下应该仍然可用？
   - "如果数据库主库挂了，从库应该 30 秒内接管"
2. **Hypothesize（预期）**：注入故障后系统应该表现如何？
   - "注入网络延迟后，服务降级但不崩溃"
3. **Execute（执行）**：注入故障，观察
   - "使用 Chaos Mesh 注入 5 秒网络延迟"
4. **Observe（观察）**：对比预期和实际
   - "实际 28 秒接管，符合预期 ✅"

### 安全原则

- **非高峰期**：不在业务高峰期注入故障
- **影响范围可控**：从单个 Pod 开始，逐步扩大
- **有回滚方案**：实验失败时能快速恢复
- **有监控**：实验期间 100% 监控
- **有审批**：生产环境实验需审批流程

## 注入层次

| 层次 | 工具 | 风险 | 适用 |
|---|---|---|---|
| 进程级 | Chaos Monkey | 低 | 单机测试 |
| Pod 级 | LitmusChaos | 中 | K8s 集群 |
| 虚拟机级 | Chaos Mesh | 中高 | 混合云 |
| 机房级 | 人工断网 | 高 | 大促前全链路 |

## 常用实验类型

| 类型 | 注入内容 | 验证目标 |
|---|---|---|
| Pod 杀死 | 删除随机 Pod | 副本自动恢复 |
| 网络延迟 | 注入 100-500ms 延迟 | 超时/重试是否有效 |
| 网络丢包 | 丢包率 10-30% | 降级/熔断是否触发 |
| CPU/内存压力 | 占满资源 | 资源隔离是否有效 |
| 主库故障 | 主库切换 | 从库接管 + 数据一致性 |
| 配置变更 | 修改配置 | 动态刷新是否生效 |

## 常态化实践

- **月度实验**：每月至少一次混沌实验，纳入发布流程
- **每次发布前**：核心链路做一次小型实验（杀死一个 Pod）
- **大促前**：全链路混沌实验（网络延迟 + 主库切换）
- **复盘反哺**：实验发现的弱点 → 补充预案 → 下次实验验证

## 常见误区

1. **"混沌工程 = 搞破坏"** —— 混沌工程是验证韧性，不是搞破坏
2. **"一次实验就够了"** —— 系统在变，需要常态化实验
3. **"生产环境不能做实验"** —— 在可控前提下生产环境更有价值
4. **"实验失败了就是事故"** —— 实验本身就是要暴露弱点，不是事故

## 你们可能会问

**Q1：混沌工程会不会引入真实故障？**
实验设计原则：非高峰期 + 影响范围可控 + 有回滚方案——先小后大，先非核心后核心。

**Q2：LitmusChaos 和 Chaos Mesh 怎么选？**
K8s 环境选 LitmusChaos（社区活跃 + ChaosHub 预设），非 K8s 选 Chaos Mesh。

**Q3：实验怎么设计才安全？**
四步法（假设→注入→观察→结论）+ 安全原则（非高峰期/影响可控/有回滚/有监控/有审批）。

**Q4：混沌工程和故障演练的区别？**
混沌工程暴露未知弱点，故障演练验证已知预案——两者互补。

**Q5：金融场景能做混沌工程吗？**
可以，但需更严格：审批流程 + 非高峰期 + 核心链路保护 + 有回滚方案。
