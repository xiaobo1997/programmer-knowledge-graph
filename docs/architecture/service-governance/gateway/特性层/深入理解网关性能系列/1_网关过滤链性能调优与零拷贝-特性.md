# 网关过滤链性能调优与零拷贝机制

> 本篇深入网关过滤链的性能瓶颈、零拷贝原理、千万级 QPS 下的参数调优。

## 一、网关架构全景

```
┌─────────────────────────────────────────────────┐
│                   网关架构                           │
│                                                       │
│  客户端 → 负载均衡 → 网关 → 过滤链 → 后端服务      │
│               ↑                                    │
│         路由/鉴权/限流/熔断                           │
│                                                       │
│  过滤链执行顺序：                                        │
│  1. 路由匹配 → 2. 鉴权 → 3. 限流 → 4. 熔断          │
│  5. 协议转换 → 6. 请求转换 → 7. 响应转换              │
└─────────────────────────────────────────────────┘
```

## 二、过滤链性能瓶颈

### 2.1 瓶颈分析

```
过滤链每个阶段的开销：

  阶段           单次开销    千万QPS累计
  ──────────────────────────────────
  路由匹配       0.1ms      1000s/天
  鉴权           0.5ms      5000s/天
  限流           0.05ms     500s/天
  熔断           0.05ms     500s/天
  协议转换       1ms        10000s/天
  请求/响应转换  2ms        20000s/天
  ──────────────────────────────────
  总计           ~3.7ms     ~37000s/天
```

### 2.2 零拷贝原理

```
传统拷贝：
  磁盘 → 内核缓冲区 → 用户缓冲区 → 内核缓冲区 → 网络
  4 次上下文切换 + 4 次数据拷贝

零拷贝：
  磁盘 → 内核缓冲区 → 网络
  2 次上下文切换 + 2 次数据拷贝

零拷贝实现：
  - sendfile()：文件 → socket 直接传输
  - mmap()：内存映射文件
  - splice()：管道间数据传输
```

## 三、Nginx 过滤链优化

### 3.1 Nginx 配置优化

```nginx
http {
    # 连接层
    worker_processes auto;           # CPU 核数
    worker_connections 65535;        # 每 worker 连接数
    multi_accept on;                 # 一次性接受所有连接
    use epoll;                       # epoll 模型
    
    # 缓冲区
    client_body_buffer_size 16k;     # 请求体缓冲区
    client_header_buffer_size 1k;    # 头缓冲区
    large_client_header_buffers 4 8k; # 大头缓冲区
    
    # 零拷贝
    sendfile on;                     # 开启零拷贝
    tcp_nopush on;                   # 减少小包
    tcp_nodelay on;                  # 禁用 Nagle
    
    # 缓存
    proxy_cache_path /tmp/cache levels=1:2 keys_zone=my_cache:10m;
    proxy_cache_key "$uri$is_args$args";
    
    # 超时
    proxy_connect_timeout 1s;
    proxy_send_timeout 1s;
    proxy_read_timeout 1s;
}
```

### 3.2 过滤链执行顺序优化

```
优化前：
  路由匹配 → 鉴权 → 限流 → 熔断 → 协议转换 → 请求转换 → 响应转换

优化后：
  路由匹配 → 限流 → 鉴权 → 熔断 → 协议转换 → 请求转换 → 响应转换
  
  调整理由：
    - 限流先执行：减少后续处理的无用请求
    - 鉴权次之：认证失败直接拒绝
    - 熔断最后：只有通过前两关才检查熔断
```

### 4.2 Envoy 性能优化

```yaml
# Envoy 配置优化
static_resources:
  listeners:
  - name: listener_0
    address:
      socket_address: { address: 0.0.0.0, port_value: 10000 }
    filter_chains:
    - filters:
      - name: envoy.filters.network.http_connection_manager
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
          stat_prefix: ingress_http
          route_config:
            name: local_route
            virtual_hosts:
            - name: backend
              domains: ["*"]
              routes:
              - match: { prefix: "/" }
                route: { cluster: service_backend }
          http_filters:
          - name: envoy.filters.http.router
            typed_config:
              "@type": type.googleapis.com/envoy.extensions.filters.http.router.v3.Router
          
          # 性能优化
          upgrade_configs:
          - upgrade_type: websocket
          use_remote_address: true
          xff_num_trusted_hops: 1
          server_name: envoy
          
  clusters:
  - name: service_backend
    type: STRICT_DNS
    lb_policy: ROUND_ROBIN
    load_assignment:
      cluster_name: service_backend
      endpoints:
      - lb_endpoints:
        - endpoint:
            address:
              socket_address:
                address: backend
                port_value: 8080
```

## 五、千万级 QPS 下的参数调优

| 量级 |  worker_processes | worker_connections | buffer_size | 零拷贝 |
|---|---|---|---|---|
| 十万 QPS | 4 | 10240 | 16k | sendfile |
| 百万 QPS | 8 | 65535 | 32k | sendfile + tcp_nopush |
| 千万 QPS | 16 | 65535 | 64k | sendfile + mmap |
| 亿级 QPS | 32+ | 65535 | 128k | sendfile + splice |

## 六、生产事故案例

### 事故 1：过滤链顺序不当

**场景**：某系统鉴权过滤链在限流之后，大促期间大量非法请求消耗限流配额。

**现象**：
- 限流配额被非法请求耗尽
- 合法请求被限流
- 用户投诉增加

**根因**：
- 过滤链顺序：路由 → 鉴权 → 限流
- 非法请求也消耗限流配额

**修复**：
1. 调整顺序：路由 → 限流 → 鉴权
2. 限流只针对合法请求
3. 非法请求直接拒绝，不消耗配额

## 七、核心带走

- **核心一句话**：网关性能 = 零拷贝 + 过滤链优化 + 参数调优
- **调优顺序**：开启零拷贝 → 优化过滤链顺序 → 调整缓冲区大小 → 增加 worker
- **亿级参数**：worker 32+、buffer 128k、零拷贝开启、连接数 65535
- **哪里会坏**：过滤链顺序不当、缓冲区过小、未开启零拷贝
