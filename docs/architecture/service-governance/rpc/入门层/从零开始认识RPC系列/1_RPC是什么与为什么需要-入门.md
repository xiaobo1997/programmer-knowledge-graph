# RPC 是什么：从本地调用到远程调用的抽象

> **本文核心**：RPC 的本质是**把远程调用伪装成本地调用**——屏蔽网络通信/序列化/寻址的复杂度，让开发者像调本地方法一样调远程服务。**机制链**：本地调用（进程内方法栈）→ 远程调用需要（寻址+连接+序列化+网络传输+反序列化+执行）→ RPC 框架将以上封装为透明代理。

## 一句话摘要

RPC（Remote Procedure Call）解决的核心问题：**进程间边界**——本地调用是同一进程内存栈上的方法跳转，远程调用要跨网络到另一台机器的进程。RPC 框架把「寻址、建连、序列化、传输、反序列化、异常映射」封装为透明层，让开发者只需要写接口+实现，调用感受与本地一致。从演进看：RMI（Java 原生，1997）→ Thrift（Facebook，跨语言）→ gRPC（Google，HTTP/2+Protobuf）→ Dubbo（阿里，微服务生态）——**每一代都在解决上一代的跨语言性、性能或生态瓶颈**。

## 一、为什么不能只用 HTTP + JSON

裸 HTTP 调用的问题不在「能不能」，在**治理能力**：① 手动解析 URL 与 JSON——没有接口契约（IDL）约束；② 没有负载均衡（每次直连固定地址）；③ 没有服务发现（实例变更需人工干预）；④ 没有超时/重试/容错的统一治理——**RPC 框架 = 通信协议 + 服务治理的全家桶**，HTTP+JSON 只是它的传输底座之一。

## 二、RPC 调用与本地调用的区别


**远比本地的代价**：序列化/反序列化 CPU 开销 + 网络 RTT + 对端处理时间 + 失败概率从零变为非零——RPC 的设计目标就是**最小化这些代价、最大化治理能力**。

### 一次完整 RPC 调用的时序分解

把「透明封装」拆开看，一次调用在 consumer 侧要穿过四层，每层只解决一个问题——这就是 RPC 框架的分层设计思想：

```mermaid
sequenceDiagram
    participant App as 业务代码
    participant Proxy as 代理层
    participant Cluster as 集群治理层
    participant Proto as 协议+序列化层
    participant Net as 传输层
    App->>Proxy: interface.method(args)
    Proxy->>Cluster: Invocation(方法+参数)
    Cluster->>Cluster: 服务发现+路由+负载均衡选实例
    Cluster->>Proto: 选定 invoker
    Proto->>Proto: 序列化+协议编码
    Proto->>Net: 字节流
    Net->>Net: 长连接发送(或建连)
    Note over Net: 网络传输 RTT
    Net-->>Proto: 响应字节流
    Proto-->>Cluster: 反序列化结果(或异常)
    Cluster-->>App: 结果(异常已映射)
```

**分层为什么重要**：故障定位时能按层归因——超时多半在网络/下游处理（传输层+业务层），连接拒绝在传输层，序列化异常在协议层，找不到实例在集群治理层。**不掌握分层，排障就只能靠猜**。Dubbo 的 `Protocol/Cluster/Directory/LoadBalance` 分层接口、gRPC 的 `Channel/Stub` 抽象，都是这套思想的落地。

**设计思想**：代理（动态代理/Stub）是 RPC 的第一抽象——它把「跨网络」这件事从业务代码里完全挪走，让治理逻辑有了一个统一的拦截点。没有代理，限流/熔断/路由这些治理能力就必须侵入每个业务方法——**治理能力的非侵入式挂载点，就是代理层存在的根本原因**。

## 三、与 HTTP API 的区别：语义与治理对照

| 维度 | RPC 框架 | HTTP REST API |
|---|---|---|
| 契约 | IDL 强类型（Protobuf/Thrift IDL） | OpenAPI（弱约束） |
| 序列化 | Protobuf/Hessian（二进制高效） | JSON（文本可读但低效） |
| 服务发现 | 框架内置（注册中心联动） | 需外部 DNS/网关 |
| 负载均衡 | 客户端内置策略 | 需 LB 设备/网关 |
| 容错 | failover/failfast 内置 | 应用层自行处理 |
| 适用 | 内部服务间高频调用 | 对外 API/跨语言轻量场景 |

**选型直觉**：内部高频调用用 RPC（性能+治理），对外或跨语言轻量场景用 HTTP——**两者不是竞争关系**，同一家公司内部 RPC + 对外 REST 是常态。

## 三·五、RPC 框架的技术要素拆解

一个能上生产的 RPC 框架 = **7 个技术要素**的组合，每个要素都有独立选型空间：

| 要素 | 解决什么 | 代表实现 |
|---|---|---|
| 动态代理 | 拦截调用、挂载治理 | JDK Proxy / ByteBuddy / Stub 生成 |
| 序列化 | 对象↔字节流 | Protobuf / Hessian / Kryo |
| 协议编码 | 消息边界与元数据承载 | Dubbo 协议 / gRPC(HTTP/2) / 自定义 header |
| 传输 | 字节流的收发 | Netty(NIO) / 长连接复用 |
| 服务发现 | 找到可用实例 | 注册中心联动（Nacos/ZK） |
| 负载均衡+路由 | 选哪个实例 | 随机/一致性哈希 + 标签路由 |
| 容错治错 | 失败了怎么办 | failover/failfast + 熔断降级 |

**为什么要拆要素看**：框架对比（篇 12）不是比「谁好」，而是比**每个要素的取舍点**——gRPC 强在序列化与跨语言（Protobuf+多语言 Stub 一等公民），Dubbo 强在治理生态（路由/容错/与 Spring 无缝）。**拆开看要素，对比才有判断依据**。



## 四、典型场景与误区

**典型场景**：订单服务调库存服务扣减（同步 RPC，需要返回值）、用户服务查询（读多写少，RPC + 负载均衡）、微服务内部链路（全链路 RPC 编排）。共同特征：**调用方需要立刻拿到结果才能继续业务逻辑**——下单要确认库存够、支付要确认账户有效，这类「结果决定分支」的调用是 RPC 的主战场；而「通知类」调用（发短信、记审计日志）结果不影响主流程，应改走 MQ 异步化，别让非关键路径的故障拖垮主流程。

**误区与不适用**（**量级演进视角**：千级 QPS 单服务 HTTP+JSON 够用；万级 QPS 微服务集群 RPC 的性能优势显现（Protobuf 体积小+长连接复用）；十万级 QPS+多机房 RPC 的连接复用与服务发现成为刚需——**RPC 的治理价值随服务数量与调用量增长而放大**。）：① 什么场景都用 RPC——异步消息（不需要返回值）用 MQ 更合适（互指 MQ 系列）；② RPC 调用不做超时——默认无超时等于调用方线程可能永远阻塞；③ RPC 当作数据库直连——跨服务调用本质是「跨数据所有权边界」，不是绕过服务直接查别人的表。

**三态结果：远程调用与本地调用最本质的语义差异**。本地调用只有成功/抛异常两种结果；远程调用有三种——成功、明确失败、**未知**（超时后你不知道请求到底执行没执行：可能是请求没到达，可能是执行了但响应没回来）。**「未知」态是所有分布式一致性问题的根源**：扣款调用超时了，要不要重试？重试了怕双扣，不重试怕漏扣——于是必须配套幂等设计（去重表/唯一键/状态机）。理解三态，才能理解为什么 RPC 篇章反复强调「超时+幂等是配套设计」，也是后续分布式事务系列（互指）的第一性原理。

## 五、💡 实战提示

- 💡 RPC 调用必配超时（默认值不是安全值——按下游 P99 × 2 设定）
- 💡 接口先行（IDL）优于代码先行——IDL 是跨团队契约的载体
- 💡 决策口径：同步需返回值 → RPC；异步无需返回值 → MQ；对外跨语言 → REST

## 六、你们可能会问

**Q1：RPC 和微服务什么关系？**
RPC 是微服务间通信的**技术手段**，微服务是**架构理念**——没有 RPC 微服务无法互调，但 RPC 也可以用于非微服务场景（单体内部的模块通信）。

**Q2：为什么不用消息队列代替 RPC？**
消息队列是异步解耦（发送方不需要立刻知道结果），RPC 是同步调用（调用方需要立刻拿到返回值）——语义不同，不可互替；两者在微服务架构中互补共存。

**Q3：RPC 框架和 HTTP 客户端（如 Feign）什么关系？**
Feign 是「声明式 HTTP 客户端」（HTTP 协议 + 声明式接口），本质仍是 HTTP 调用——RPC 框架通常自带更高效的二进制协议 + 更完整的治理能力。边界在模糊化（gRPC 也是 HTTP/2）。

**Q4：RPC 只能同步调用吗？**
不是。框架普遍提供异步形态：Future/CompletableFuture 返回（发请求先返回，结果后取）、回调注册（结果到了触发 callback）、以及 gRPC 的流式接口（服务端流/客户端流/双向流）。**异步调用的价值**：调用方线程不被阻塞，百级并发下线程数可控——但异步代码的可读性与排障成本更高（回调地狱/链路上下文传递），同步仍是默认选择、异步按需引入。

## 七、反思与追问

**质疑者视角**：RPC 解决的是「调远端像调本地」——但「像本地」本身就是一个危险的抽象：网络不可靠、远端可能超时、部分失败无法回滚。**伪装越彻底，开发者越容易忘记网络的存在**。Martin Kleppmann 在 DDIA 中指出：RPC 的透明性是一个「有用的假象」——你可以在语法上让远程调用看起来像本地调用，但你无法在语义上让网络具备本地调用的可靠性。这不是 RPC 框架的问题，是分布式系统的本质约束——框架做得再好，你仍然需要考虑超时、重试、幂等、降级。

**实践视角**：某团队在 RPC 调用中未设超时（使用框架默认 0 = 无超时），下游服务因 Full GC 卡顿 5 分钟——上游所有线程阻塞等待，线程池耗尽，上游也挂——**故障顺着调用链反向传播**。修复：全链路设置合理超时 + 熔断降级。

**追问链**：为什么「像本地一样」的目标反而要靠「记住网络不可靠」来实现？——因为透明性只封装**机制**（序列化/传输/寻址），不封装**语义**（可靠性/幂等/一致性）；机制可以自动化，语义必须业务自己声明。追问：那幂等声明放在哪？——接口契约层（IDL 注解或文档约定），超时重试的调用方按契约决定是否重试——这就是为什么成熟团队的 IDL 里会标注方法幂等性，重试策略与幂等声明是配套设计。

**演进视角**：RPC 的透明边界还在被重新协商——Service Mesh 把治理能力从 SDK 挪到 sidecar（业务进程外的代理），「透明」从框架层下沉到基础设施层；gRPC 走 HTTP/2 让 RPC 与 HTTP 生态重新合流。**每 3-5 年，RPC 的边界划分就会随基础设施演进重构一次**——理解机制而非绑定某个框架，才是可迁移的认知。

## 八、自测三问

1. RPC 框架相比裸 HTTP+JSON 多了哪些治理能力？（答：IDL 契约、服务发现、客户端负载均衡、超时/重试/容错统一治理——对照第三节表格自查）
2. 远程调用比本地调用多了哪些代价？（答：序列化 CPU、网络 RTT、对端处理时间、失败概率非零，以及超时后的「未知」三态）
3. RPC/MQ/REST 三者的选型边界是什么？（答：同步要返回值用 RPC、异步解耦用 MQ、对外跨语言轻量用 REST）

## 📎 核心带走

- **核心一句话**：RPC = 远程调用的透明封装 + 服务治理全家桶——「像调本地一样调远程」是体验，「治理」是价值
- **机制链**：接口声明 → 代理拦截 → 序列化 → 寻址+传输 → 反序列化 → 执行 → 结果返回
- **失效点/边界**：RPC 不替代 MQ（异步场景）；RPC 不等于 HTTP（治理能力差异）；跨服务调用不等于跨数据所有权
