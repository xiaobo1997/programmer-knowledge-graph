# RPC 的限流熔断降级：调用链上的稳定性三件套

> **本文核心**：RPC 场景下的稳定性三件套——**限流**（provider 侧自保：本机容量超限时快速拒绝）、**熔断**（consumer 侧自保：下游持续失败时停止调用走降级）、**降级**（业务侧兜底：返回默认值/缓存/简化逻辑）。**机制链**：调用 → 限流判定（provider 保护自身）→ 业务执行 → 失败率统计（consumer 熔断判定）→ 熔断打开 → 走降级 → 半开试探恢复。稳定性机制全景互指 stability 系列。

> **本文核心**：RPC 调用链上的三道稳定性防线——**限流**（保护 provider 不被过载打垮）、**熔断**（保护 consumer 不被故障下游拖死）、**降级**（兜底用户体验不降为零）。**机制链**：consumer 调用 → 限流判定 → 业务执行 → 失败统计 → 熔断阈值判定 → 熔断打开走降级 → 半开试探 → 恢复关闭。

## 一句话摘要

RPC 的稳定性三件套各管一段：**限流**（provider 视角：进来的流量我扛不住就拒）、**熔断**（consumer 视角：下游不可靠我先停）、**降级**（用户视角：功能降级但不停）——三件的正交组合构成调用链的完整韧性，机制原理深挖互指 stability 系列的限流算法/熔断器/降级策略篇。

**量级演进视角**：千级 QPS 的服务 RPC 配置默认够用；万级需要全链路参数调优（超时/重试/限流/序列化协议全配）；十万级必须关注序列化效率与连接池容量——治理强度随调用量级升级。

## 💡 实战提示

- 💡 限流在 provider 侧、熔断在 consumer 侧——两层各自独立配置
- 💡 降级预案必须提前编写并演练——线上现场写降级逻辑为时已晚
- 💡 决策口径：限流保护容量、熔断保护调用方、降级保护用户体验——三者按业务重要性分级

**Trade-off 视角**：性能与治理能力的权衡——治理面越完善框架越重，性能极致则治理面弱。团队需按实际需求对齐，不为用不到的能力买单。

## 📎 核心带走

- **核心一句话**：RPC 稳定性三件套 = 限流（provider 自保）+ 熔断（consumer 自保）+ 降级（用户兜底）——三层上下游正交组合
- **机制链**：限流判定 → 业务执行 → 失败统计 → 熔断判定 → 降级走兜底 → 半开试探恢复
- **失效点/边界**：限流不防下游故障（那是熔断的活）；熔断不解决容量不足（那是限流/扩容的活）
