# RPC 的服务路由与灰度：定向分发的调用方语义

> **本文核心**：RPC 的路由 = 调用方按规则**过滤地址列表的子集**（在负载均衡之前缩小候选集）——条件路由（按调用方/参数/标签匹配）与标签路由（实例打标 + 按标筛选）。**机制链**：请求 → 路由规则匹配 → 筛选后子集 → 负载均衡选实例。治理机制深挖互指 service-routing 系列（条件路由/标签路由/泳道）。

> **本文核心**：RPC 调用方的路由语义——**在候选集中做子集筛选**：标签路由（实例版本/环境标签 + 规则匹配）与条件路由（调用方/方法/参数表达式）。路由的结果是「缩小的候选集」，交给负载均衡做最终选择——**路由管定向、均衡管摊匀**（视角型边界，互指 service-routing 系列）。

## 一句话摘要

RPC 客户端路由 = 在负载均衡**之前**按规则筛选地址子集——灰度发布（新版本实例打标 + 规则引流）、多环境隔离（测试标签封闭）、故障切流（异常机房规则摘除）——三种场景共用「标签匹配 + 子集筛选」的机制。灰度机制（泳道/染色）深挖互指 service-routing 系列。

**量级演进视角**：千级 QPS 的服务 RPC 配置默认够用；万级需要全链路参数调优（超时/重试/限流/序列化协议全配）；十万级必须关注序列化效率与连接池容量——治理强度随调用量级升级。

## 💡 实战提示

- 💡 路由规则必须有默认兜底（无匹配走全量），防「规则打空」服务不可用
- 💡 路由条件引用的标签必须与注册中心元数据对齐（互指 metadata-center）
- 💡 决策口径：临时引流用条件路由、常态治理用标签路由、跨服务链路用泳道

**Trade-off 视角**：性能与治理能力的权衡——治理面越完善框架越重，性能极致则治理面弱。团队需按实际需求对齐，不为用不到的能力买单。

## 📎 核心带走

- **核心一句话**：RPC 路由 = 在负载均衡之前按规则筛选地址子集——条件/标签/泳道三形态递进
- **机制链**：请求特征 → 规则匹配 → 子集筛选 → 负载均衡 → 目标实例
- **失效点/边界**：规则必须带兜底默认；标签对齐注册元数据；路由失效比均衡失效更危险
