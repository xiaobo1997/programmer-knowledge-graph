# RPC 的可观测与链路追踪：调用链的透明化

> **本文核心**：RPC 调用的三根可观测支柱——**指标**（QPS/RT/错误率的 Red 方法）、**日志**（traceId 串联跨服务日志）、**链路追踪**（Span 树形结构可视化调用拓扑与耗时分解）。**机制链**：traceId 入口生成 → MDC 注入 → 跨服务 Header 透传 → 每跳 Span 上报 → 追踪平台聚合瀑布图。

## 一句话摘要

RPC 的可观测 = 指标（Red：Rate/Errors/Duration）+ 日志（traceId 串联）+ 追踪（Span 树形分解）——三根支柱联合回答「延迟高吗？错在哪一段？调用链路径是什么？」——观测体系机制深挖互指 stability 系列的监控与追踪篇。

**量级演进视角**：千级 QPS 的服务 RPC 配置默认够用；万级需要全链路参数调优（超时/重试/限流/序列化协议全配）；十万级必须关注序列化效率与连接池容量——治理强度随调用量级升级。

## 💡 实战提示

- 💡 traceId 用 W3C Trace Context 标准头（traceparent）——与 OTel 生态兼容
- 💡 Red 三指标（Rate/Errors/Duration）进基础大盘——RPC 健康的心电图
- 💡 决策口径：有观测平台走 OTel，无平台先手工 traceId——先有链路再谈体系

**Trade-off 视角**：性能与治理能力的权衡——治理面越完善框架越重，性能极致则治理面弱。团队需按实际需求对齐，不为用不到的能力买单。

## 📎 核心带走

- **核心一句话**：RPC 可观测 = 指标（Red 三元组）+ 日志（traceId 串联）+ 追踪（Span 瀑布图）三根支柱
- **机制链**：入口生成 traceId → MDC 注入 → Header 透传 → 每跳 Span 上报 → 平台聚合
- **失效点/边界**：三根支柱正交互补——指标发现异常、日志归因细节、追踪定位路径
