# 深入理解注册中心亿级选型

> 本篇深入注册中心的核心机制、CP/AP 选型、千万级客户端连接管理、亿级推送延迟优化。

## 一、注册中心架构全景

```
┌─────────────────────────────────────────────────┐
│                   注册中心架构                        │
│                                                       │
│  服务提供者 ──→ 注册中心 ←── 服务消费者                │
│      │                │                │             │
│      ↓                ↓                ↓             │
│   注册/心跳      订阅/推送       发现/查询             │
│                                                       │
│  核心功能：                                              │
│  ├── 服务注册：实例上线注册                          │
│  ├── 服务发现：消费者查询提供者                        │
│  ├── 健康检查：心跳检测 + 故障剔除                   │
│  └── 配置推送：配置变更推送给消费者                   │
└─────────────────────────────────────────────────┘
```

## 二、CP/AP 选型

### 2.1 CP 注册中心（强一致）

```
CP 注册中心：
  ┌──────────────────────────────────────┐
  │ Nacos (CP 模式)                      │
  │  → Raft 一致性协议                    │
  │  → 数据强一致                          │
  │  → 分区容错                            │
  │  → 可用性降低（分区时不可写）              │
  └──────────────────────────────────────┘

  适用场景：
    - 服务注册/发现（需要强一致）
    - 配置管理（需要强一致）
    - 金融/账务场景
```

### 2.2 AP 注册中心（高可用）

```
AP 注册中心：
  ┌──────────────────────────────────────┐
  │ Eureka (AP 模式)                     │
  │  → 无强一致协议                        │
  │  → 数据最终一致                        │
  │  → 分区时仍可用                        │
  │  → 可能数据不一致                      │
  └──────────────────────────────────────┘

  适用场景：
    - 服务发现（短暂不一致可接受）
    - 非金融场景
    - 高可用优先场景
```

### 2.3 选型决策

```
选型决策树：

  需要强一致？
    ├─ 是 → CP 注册中心（Nacos/Raft/ZooKeeper）
    └─ 否 → AP 注册中心（Eureka/Consul）
    
  金融/账务场景？
    ├─ 是 → CP + 强一致协议
    └─ 否 → AP + 最终一致
    
  分区容错要求？
    ├─ 高 → AP（分区时仍可用）
    └─ 低 → CP（分区时不可写）
```

## 三、千万级客户端连接管理

### 3.1 连接模型

```
注册中心连接模型：

  短连接：
    ├── 优点：实现简单
    └── 缺点：频繁建连/断连，开销大
    
  长连接：
    ├── 优点：减少建连开销
    └── 缺点：连接数多，资源消耗大
    
  连接池：
    ├── 优点：复用连接，资源可控
    └── 缺点：实现复杂
```

### 3.2 千万级连接优化

| 优化项 | 优化前 | 优化后 | 效果 |
|---|---|---|---|
| 连接模型 | 短连接 | 长连接 + 心跳 | 减少 90% 建连开销 |
| 连接池 | 无 | 固定大小连接池 | 控制资源上限 |
| 心跳间隔 | 30s | 10s | 加速故障检测 |
| 心跳超时 | 90s | 30s | 加速剔除 |
| 推送模式 | 推送 | 推拉结合 | 减少推送压力 |

### 3.3 推送延迟优化

```
推送延迟优化：

  1. 增量推送
     → 只推送变更部分
     → 减少推送数据量
     → 延迟从 500ms → 50ms

  2. 批量推送
     → 多个变更合并推送
     → 减少推送次数
     → 延迟从 100ms → 20ms

  3. 优先级推送
     → 核心配置优先推送
     → 非核心配置延迟推送
     → 保证关键配置及时生效

  4. 推送流控
     → 推送速率限制
     → 避免推送风暴
     → 推送速率 = 客户端数 / 推送间隔
```

## 四、生产事故案例

### 事故 1：注册中心推送风暴

**场景**：某系统配置变更，1000 个客户端同时拉取。

**现象**：
- 注册中心 CPU 100%
- 客户端连接超时
- 服务发现失败

**根因**：
- 推送模式：配置变更 → 推送给所有客户端
- 1000 客户端同时拉取 → 推送风暴

**修复**：
1. 推拉结合：客户端定期拉取 + 变更推送
2. 推送流控：限制推送速率
3. 批量推送：多个变更合并推送

### 事故 2：连接数耗尽

**场景**：某系统客户端数从 1000 增长到 10000。

**现象**：
- 注册中心连接数耗尽
- 新客户端无法注册
- 服务发现失败

**根因**：
- 连接数限制：maxConnections = 5000
- 客户端数超过限制

**修复**：
1. 增大连接数限制
2. 连接池复用
3. 长连接 + 心跳

## 五、核心带走

- **核心一句话**：注册中心选型 = CP 强一致 vs AP 高可用，亿级连接 = 长连接 + 心跳 + 推送流控
- **选型原则**：金融选 CP、非金融选 AP、分区容错要求高选 AP
- **连接优化**：长连接 + 心跳 10s + 连接池 + 推拉结合
- **推送优化**：增量推送 + 批量推送 + 优先级推送 + 流控
- **哪里会坏**：推送风暴、连接数耗尽、心跳超时误剔除
