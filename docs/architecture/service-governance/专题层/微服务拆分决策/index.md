# 微服务拆分决策

> 「什么时候拆、按什么拆、拆到多细」——微服务拆分的三个决策问题，用决策树回答而不是用流行度回答。

```mermaid
graph TD
    S1[拆分三信号量化] --> S1a[变更冲突度: 发布互等次数/月]
    S1 --> S1b[扩展冲突度: 热点域拖全站的告警占比]
    S1 --> S1c[团队冲突度: 同仓并行人数]
    S1a & S1b & S1c --> GO{任一过红线?}
    GO -->|是| SPLIT[启动拆分评审]
    GO -->|否| WAIT[模块化单体继续]
```

```mermaid
graph LR
    T0[量级三档的拆分形态] --> T1[10w 档: 模块化单体<br/>代价=无独立扩展]

    T0 --> T3[亿级档: 域内二次拆<br/>代价=平台化投入]
    T1 -->|上下游| T2 -->|上下游| T3
```

## 一句话摘要

拆分决策 = 拆分信号（团队/变更/扩展的冲突度）× 拆分依据（限界上下文而非技术分层）× 粒度红线（拆到团队可独立交付为止）——10w 档单体+模块边界，千万档按上下文拆核心域，亿级档核心域再按读写/热点二次拆。

```mermaid
graph TD
    S[拆分信号] --> S1[变更冲突: 两域发布互相等]
    S --> S2[扩展冲突: 一域热点拖全站]
    S --> S3[团队冲突: 多队改一仓库]
    S1 & S2 & S3 --> D{按限界上下文切}
    D --> G[粒度红线: 可独立交付即止]
```

## 演进视角

微服务粒度的演变：单体 → 过度拆分（纳米服务反模式）→ 理性回归（单团队可交付为界）——演变教训是「拆分的成本在运维与一致性，收益在交付与扩展」，权衡随团队规模与量级漂移。
