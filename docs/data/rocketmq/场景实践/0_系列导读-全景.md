## 二、什么是"实战 SOP"（不是"概念文档"）

```
┌──────────────────────────────────────────────────────────────┐
│  文档类型       │  目的                  │  读者动作          │
├──────────────────────────────────────────────────────────────┤
│  概念文档       │  知道 X 是什么          │  "懂了"            │
│  原理文档       │  知道 X 怎么工作        │  "哦原来"            │
│  选型文档       │  知道选 X 还是 Y        │  "决定用 X"          │
│  ★ 实战 SOP ★   │  知道怎么用 X +能跑起来 │  "做完能上线"        │
└──────────────────────────────────────────────────────────────┘
```

**实战 SOP 的 5 个核心特征**：

1. **目的导向**——解决一个具体问题，不讲概念
2. **可复制**——给完整代码 / 命令 / 配置，直接粘能用
3. **可验证**——每步都有"怎么验证生效"
4. **避坑清单**——至少 5 个踩坑场景 + 解决
5. **时间预估**——告诉读者"这件事你做要多久"

**实战 SOP 与原 deep-dive 的关系**：

| 维度 | L1 特性层 deep-dive | L4 实践 SOP |
|---|---|---|
| **目的** | 讲透原理 | 解决问题 |
| **字数** | 5000-7000 字 | 3000-5000 字 |
| **代码** | 关键片段 | 完整可运行 |
| **结构** | 8 节 + 业内惯例 | 6 节（前置 / 步骤 / 验证 / 避坑 / 时间） |
| **读者** | 懂原理 | 照着做 |
| **可执行性** | 概念清晰 | 操作清晰 |

## 四、SOP 通用骨架（6 节结构）

每篇 SOP 按这个结构写：

```
┌──────────────────────────────────────────────────────────────┐
│  SOP 通用骨架（6 节）                                      │
├──────────────────────────────────────────────────────────────┤
│  0. 一句话目标                                             │
│     这篇解决什么问题 / 解决到什么程度                      │
│                                                              │
│  1. 前置依赖                                                │
│     环境 / 工具 / 权限 / 时间预估                          │
│                                                              │
│  2. 5 步接入（核心）                                       │
│     步骤 1：xxx — 操作 +验证（可复制命令）                │
│     步骤 2：xxx — 操作 +验证                              │
│     步骤 3：xxx                                              │
│     步骤 4：xxx                                              │
│     步骤 5：xxx                                              │
│                                                              │
│  3. 完整可复制代码 / 配置                                    │
│     一键复制即可使用                                         │
│                                                              │
│  4. 5 大踩坑清单                                            │
│     真实场景 + 触发条件 + 排查 + 解决                      │
│                                                              │
│  5. 时间预估 + 难度评级                                    │
│     新人 / 中级 / 高级 评级                                 │
│     30min / 2h / 1d 时间预估                              │
└──────────────────────────────────────────────────────────────┘
```

**为什么是 5 步**：
- 太少（3 步）→ 颗粒度太粗，验证点不够
- 太多（10 步）→ 读者负担重，跟不完
- **5 步 = 黄金数字**——"5 步接入"是行业惯例（5 Why / 5 Whys / 5W2H）

**为什么每步要"操作 +验证"**：
- 没有验证步骤 → 读者不知道做对没
- 有验证步骤 → 每步独立完成 / 独立验证 / 独立排查

## 五、5 步接入的设计原则

每篇 SOP 的 5 步不是"任意 5 步"，而是"**最小完整链路**"：

```
原则 1：从环境开始，到验证结束
  步骤 1：环境准备
  步骤 2：依赖引入
  步骤 3：配置接入
  步骤 4：代码实现
  步骤 5：运行验证

原则 2：每步独立可验证
  步骤 1 验证：环境是否就绪
  步骤 2 验证：依赖是否下载成功
  步骤 3 验证：配置是否生效（启动日志 / 配置中心可见）
  步骤 4 验证：代码是否编译 / 单测通过
  步骤 5 验证：端到端跑通（消息发出 / 收到 / DLQ 行为）

原则 3：步骤间依赖清晰
  步骤 N 失败 → 不进入步骤 N+1
  步骤 N 部分完成 → 必须回退或补全
```

## 六、5 大踩坑清单的设计原则

```
原则 1：真实踩坑（非理论）
  ❌ "理论上可能有问题"
  ✅ "某次某版本某配置导致某事故"

原则 2：可触发
  ❌ "可能会失败"
  ✅ "当 X 配置 + Y 流量时，100% 触发"

原则 3：可定位
  ❌ "问题难以排查"
  ✅ "看 /var/log/xxx 日志第 N 行 + grep xxx"

原则 4：可解决
  ❌ "可能需要重构"
  ✅ "改 application.yaml 第 X 行的 Y 字段从 A 到 B"

原则 5：可验证（修复后）
  ❌ "应该没问题了"
  ✅ "跑测试命令 xxx，期望输出 yyy"
```

## 附录 D：实战 SOP 的写作约束（来自真实项目经验）

### 约束 1：每个 SOP 必须有"前置依赖"

**反例**：直接讲代码不说环境要求，读者照做发现 JDK 版本不对，浪费 30 min。

**正解**：
- JDK / Maven / Spring Boot / RocketMQ 版本
- 时间预估（30 min / 2h / 1d）
- 难度评级（新人 / 中级 / 高级）
- 依赖服务（如 RocketMQ 服务端）

### 约束 2：每步必须有"验证"动作

**反例**：步骤 1 引入依赖 → 步骤 2 写代码 → 步骤 3 跑测试。

**正解**：
- 步骤 1 引入依赖 → 验证 `mvn compile` 通过
- 步骤 2 写代码 → 验证 单测通过
- 步骤 3 跑测试 → 验证 日志看到预期输出

**理由**：每步独立可验证，失败时能精确到具体步骤，排查时间从 30 min 降到 5 min。

### 约束 3：踩坑清单必须真实

**反例**：写"可能存在线程安全问题"（空话）。

**正解**：写"设了 consumeMessageBatchMaxSize=10，某条失败，整批 10 条都进重试"，附触发条件 + 解决方案 + 验证命令。

**理由**：实战 SOP 价值在于"替读者踩过坑"，空话没有价值。

### 约束 4：决策树比推荐值更重要

**反例**：直接给"线程数设 32"（不解释为什么）。

**正解**：决策树（流量级判断）+ 推荐值（每档具体值）+ 计算公式。

**理由**：决策树让读者自己也能推理到正确值，推荐值只是参考。

### 约束 5：时间预估不是装饰

**反例**：写"中等难度"。

**正解**：步骤级时间 + 总计时间 + 首次做 vs 熟练后时间差。

**理由**：时间预估让读者安排工作，例如只有 30 min 就先做核心 2 步。

## 附录 G：实战 SOP 写作 3 大反模式（最后提醒）

**反模式 1：抄官方文档当 SOP**——只翻译不增量，读者看完还得自己踩坑。正确做法是必须包含至少 5 个真实踩坑场景与解决。

**反模式 2：贴大段代码不讲决策**——把 GitHub README 复制过来，没有"为什么这么选"的决策树。正确做法是每个推荐值都要附决策树或公式。

**反模式 3：只有 happy path**——只讲成功路径，失败怎么办完全不提。正确做法是每个 SOP 必须有"失败场景验证"小节。

   ```
   ★ 贯穿维度 1：设计思想（Design Philosophy）
     - "为什么这么做"（不是"怎么做"）
     - 主导者：阿里"高可用优先" / 字节"极致性能" / 美团"业务连续性" / Netflix"故障优先"
     - 映射到具体参数 / 配置 / 代码

   ★ 贯穿维度 2：设计方案（Design Solution）
     - "有哪些具体方案"（方案 A / B / C）
     - 各自的架构图 / 数据流 / 控制流
     - 为什么选 A 不选 B（边界在哪）

   ★ 贯穿维度 3：互联网大厂取舍（Big-Tech Trade-off）
     - 阿里 / 字节 / 美团 / Netflix 实际怎么做的？
     - 公开资料 / 演讲 / 博客有什么证据？
     - 你的场景该学谁？
   ```

   **3 种落地方式**：

   | 方式 | 位置 | 体现形式 |
   |---|---|---|
   | 1. 每节末尾加 1 段 | 每个章节末尾 | 【设计思想】/【设计方案】/【大厂取舍】 |
   | 2. 第 6 节扩展为专章 | 第 6.1 + 6.2 | 大厂取舍 + Trade-off 矩阵 |
   | 3. 附录加对照表 | 附录 A | 4-5 行的"场景 → 思想 → 方案 → 取舍"对照表 |

   ## 十一、SOP 标准与模板的分类原则

   **对外公开**（commit 到 origin）：
   - 完成的 SOP 文章（如 `0/1/2_xxxSOP.md`）
   - SOP 系列的入口索引（`docs/practice/index.md`）

   **本地维护**（`_internal/` 在 .gitignore）：
   - 实战 SOP 颗粒度标准（`practice-sop-standard.md`）
   - 实战 SOP 完整模板（`sop-template.md`）

   **为什么这样分**：
   - 外部读者看到的是"可以照着做的实战文章"（公开）
   - 内部维护的是"如何写出这种文章的 SOP"（本地）
