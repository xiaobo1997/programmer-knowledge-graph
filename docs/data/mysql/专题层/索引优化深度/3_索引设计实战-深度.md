# 索引设计实战：从查询画像到联合索引的完整方法论

> 索引失效手册治「已有的病」，EXPLAIN 手册管「诊断」，这篇管「出生」：一张新表、一批新查询，索引应该怎么设计才能少走弯路——四步设计法 + 场景落地 + 评审清单，把索引设计从「经验手感」变成「可复制流程」。

## 一句话摘要

索引设计的本质是**用查询画像（高频查询的 WHERE / ORDER BY / SELECT 列）反推索引结构**：四步法——「筛高频 → 定列序（等值在前、范围/排序随后、覆盖殿后）→ 评代价（写放大/空间/维护）→ 建评审基线（计划 diff + 慢查询跟踪）」。单表索引个数收敛在个位数、每个索引能说清服务哪条查询，是业内最稳的两条底仓约束。

## 🎯 本文核心

**核心一句话：索引设计 = 查询画像反推索引结构——列序就是检索路径（等值 → 范围/排序 → 覆盖），每个索引都要付「写放大、空间、维护」三笔账，且必须有退出机制；「先加后删」是唯一安全的重构顺序。**

方法链：四步设计法（筛高频 → 定列序 → 评代价 → 建基线）→ 三类场景模板（列表页覆盖 / 账务幂等 / 多条件分层）→ 索引瘦身事故的完整剧本 → 十项评审清单。全文一句话可重构：「索引为高频查询而生、按检索路径排序列、为写放大付账、有生命周期地退出」。

## 一、四步设计法

```mermaid
flowchart LR
    S1["① 筛高频<br/>查询画像排序"] --> S2["② 定列序<br/>等值→范围/排序→覆盖"]
    S2 --> S3["③ 评代价<br/>写放大/空间/选择性"]
    S3 --> S4["④ 建基线<br/>计划diff+慢查询跟踪"]
    style S2 fill:#ffd3a5
    style S4 fill:#a8e6a3
```

**① 筛高频**：索引为高频查询而生。把候选查询按「频率 × 表量级 × 延迟要求」排序，Top 查询才值得独立索引，长尾靠联合索引顺带或系统自适应兜底。**量级视角**：十万行表怎么建都行，五千万行表每个索引都是真金白银的写放大——设计强度跟着量级走。

**② 定列序**：联合索引的列序就是检索路径。业内默认口诀：

```text
等值条件列（选择性高的在前）→ 范围/排序列 → 覆盖列（按需）
例：WHERE user_id=? AND status=? ORDER BY create_time
   →  (user_id, status, create_time)   -- 等值对齐后 create_time 有序
```

**③ 评代价**：每个索引都要付三笔账——**写放大**（每 INSERT/UPDATE 多维护一棵树 + 分裂概率，见特性层篇 1）、**空间**（叶子 + 主键复制）、**优化器选择成本**（索引越多计划空间越大）。估算口径：索引键宽 × 行数 × 树高扇出，粗算即可做取舍。

**④ 建基线**：索引上线不是终点——计划 diff 进发布流水线、慢查询周报跟踪该索引的使用率（`sys.schema_unused_indexes`），**长期没被用的索引按流程下线**。索引生命周期管理是「设计」的最后一环，也是多数团队缺的一环。

## 二、场景模板一：订单/流水类（列表页）

画像：`WHERE user_id=? AND status=? ORDER BY create_time DESC LIMIT 20`，展示列若干。

```sql
-- 列表页覆盖索引：等值在前、时间殿后、展示列跟进
ALTER TABLE orders
  ADD INDEX idx_user_status_time (user_id, status, create_time, amount, title);
```

设计拆解：user_id/status 等值对齐后，create_time 在索引内有序，`ORDER BY ... LIMIT 20` 免排序免临时表；展示列并入实现覆盖（`Using index`），列表查询零回表。**取舍**：展示列跟进让索引变宽、写放大上升——只并入「列表页真实展示」的窄列，大字段（详情 JSON）永不入索引。

## 三、场景模板二：账务/对账类（时间范围 + 幂等）

画像：`WHERE biz_no=?`（幂等检查）+ `WHERE account_id=? AND create_time BETWEEN ?`（对账区间）。

```sql
ALTER TABLE ledger
  ADD UNIQUE INDEX uk_biz_no (biz_no),                          -- 幂等：唯一索引兜底
  ADD INDEX idx_account_time (account_id, create_time);         -- 对账：等值 + 范围
```

设计拆解：**幂等用唯一索引而不是「先查后插」**——数据库层兜底并发重复，应用层省一次往返；对账索引等值在前范围在后，范围扫描沿叶子链表顺序走。业内惯例：账务表的唯一索引（业务幂等键）是数据正确性防线，宁可索引多不可防线少——这与「索引收敛」不矛盾：**正确性索引不参与收敛讨论**。

## 四、场景模板三：搜索/筛选类（多条件组合）

画像：商品表按类目 + 价格区间 + 状态自由组合筛选。

痛点：组合数爆炸，不可能为每种组合建索引。分层解法：

1. **高频固定组合建联合索引**（如 `(category_id, status, price)`），覆盖八成流量
2. **低选择性维度靠数据组织**：类目本身可做**分表/分区维度**（量级演进到亿级时的架构答案），让每片内的筛选范围天然缩小
3. **自由文本/多维度组合溢出到搜索引擎**（ES 互指本仓库 elasticsearch 系列）——「什么条件都索引」在 MySQL 里是死路，**把不适合的关系型查询送出去**是架构级取舍

**Trade-off 核心**：MySQL 索引擅长「前缀确定的多条件」，不擅长「任意组合」；识别查询形态属于哪类，比堆索引有效十倍。

## 五、事故推演：一次批量导入的索引瘦身

某上游系统年度数据迁移，目标表已积累 11 个索引，导入窗口预估 6 小时。第一批试跑百万行耗时远超线性预期——归因发现**每一行写入都要同步维护 11 棵 B+ 树**（写放大机制见特性层篇 1），其中 4 个索引经 `sys.schema_unused_indexes` 核实近半年零命中。低峰下线 4 个冗余索引后重跑，导入耗时接近减半，窗口稳稳保住。

这次事故的三条沉淀：

1. **索引是读的资产、写的负担**——评审不能只看「读会不会快」，还要看「写要付多少」；批量写入场景尤其要算这笔账
2. **未使用索引要有退出机制**——只进不出是索引数量的结构性膨胀来源，例行盘点是治理不是可选动作
3. **瘦身动作有安全顺序**——先加新、后删旧、观察完整业务周期再收尾：

    A["盘点冗余<br/>sys.schema_unused_indexes"] --> B["低峰在线加新索引"]
    B --> C["观察完整业务周期<br/>计划 diff + 慢查询跟踪"]
    C --> D["下线旧索引"]

## 六、评审清单：索引评审的十项快查

```text
□ 每个索引能说清服务哪条高频查询（说不清 = 候选删除）
□ 单表索引个数 ≤ 位数级（业内默认 5-7 个警戒线）
□ 最左前缀可覆盖：现有索引是否已被新索引包含（冗余检测）
□ 等值列在前、范围/排序列随后、覆盖列殿后
□ 唯一业务键有唯一索引兜底（幂等防线）
□ 键宽收敛：长字符串用前缀索引或哈希列
□ 大字段（TEXT/JSON）不入索引
□ 计划 diff 已接入发布流水线
□ 未使用索引有定期盘点机制
□ 量级评估：表达到预期规模后的写放大可接受
```

## 业内惯例

> 💡 **实战提示**
> - 何时建、何时不建的快速判定：高频 + 大表 + 选择性够 → 建；低频或小表 → 不建；「以后可能用到」→ 不建（加了没人用的索引只有成本没有收益）
> - 列表页索引模板直接套：`(等值1, 等值2, 排序列, 窄展示列…)`——订单/账单/消息列表八成场景一个索引全覆盖
> - 建索引动作自带变更纪律：低峰 + `INPLACE, LOCK=NONE` + 从库先行滚动 + 回滚脚本（DROP 秒级，但误删高频索引的复建以小时计）
> - 例行盘点两条 SQL 常备：`sys.schema_unused_indexes`（谁没被用）+ `sys.schema_redundant_indexes`（谁重复了）

- **冗余索引检测进例行巡检**：`sys.schema_redundant_indexes` 一查便知——先建 (a,b) 又建 (a) 是最常见的无意识冗余
- **加索引用 `ALGORITHM=INPLACE, LOCK=NONE`**：8.0 大部分索引操作在线完成，但仍有容量与主从延迟代价——**大表变更走低峰 + 从库先行滚动**是变更管理默认
- **「先 EXPLAIN 后建索引」反着来也成立**：设计阶段用假想索引（8.0 的 optimizer hint 或测试环境预演）验证收益，再上生产——降低「建了没用」的概率
- **索引变更视同代码变更**：走评审、走发布单、留回滚脚本——索引回滚（DROP）秒级完成，但「误删高频索引」的复建时间可能以小时计

## 你们可能会问

**Q1：联合索引 (a,b) 和两个单列 (a)(b)，为什么不都要？**
(a,b) 服务「a 等值 + b 条件/排序」，(a)(b) 两个索引各自服务单列查询且写放大翻倍。若查询真的只有 a= 或 b= 两种孤立形态，两个单列才成立——列序设计从查询形态反推，不从直觉。

**Q2：覆盖索引把展示列并进去，列一多索引巨宽怎么办？**
宽索引的本质问题是「每页容纳行数下降 + 写放大上升」（特性层篇 1 的扇出逻辑）。取舍线：并入的覆盖列控制在少量窄列；宽了就退回「主键定位 + 回表」，或讨论把列表页展示需求拆到缓存/搜索侧。

**Q3：存量表怎么无痛做索引重构？**
三步：`sys.schema_unused_indexes` 盘点冗余 → 新索引低峰在线加 → 观察一个完整业务周期后下线旧索引。**先加后删**（而不是先删后加）是安全顺序——误删的代价远大于冗余的代价。
