# 延迟诊断与一致性保障：主从复制的生产实践

> 复制链路「看起来正常」，但延迟在悄悄积累。一篇把延迟的诊断方法、一致性模型、常见不一致场景讲透——从「复制延迟是多少」到「什么时候数据真的可能不一致」，给出可落地的监控与治理手法。

## 一句话摘要

主从复制的核心问题是**延迟 + 不一致**：延迟看 IO 线程追 binlog 的速度 + SQL 线程重放的速度；不一致有「异步丢数据」「半同步降级」「大事务阻塞」三类来源。治理靠「监控秒级延迟 + 半同步 + GTID + 并行复制」四件套。

## 🎯 本文核心

**核心一句话：延迟 = 「IO 追 binlog」与「SQL 重放」两段各自的水位差，诊断先分清是哪段慢；一致性 = 「送达」与「重放完成」的差距——半同步只保送达，检查一致性永远看 Exec（已执行）位点而非 Read（已接收）位点。**

机制链：两段延迟的归因分叉 → 监控指标与陷阱（Seconds_Behind_Master 的时钟依赖）→ 一致性模型四级对照 → 三类不一致场景与排查 → 治理优先级（先大事务、再并行、后参数）。全文一句话可重构：「延迟看两段水位，一致性看执行位点，治理先杀大事务」。从架构上讲，延迟诊断本质是在主备链路的上下游各段找水位差：主库产出、网络传输、relay 中转、SQL 重放四个模块边界上各有一个进度坐标——任意两点的差值就是那一段的积压量，架构定了，诊断就是读坐标。

## 二、延迟诊断：秒级监控 + 定位

```mermaid
flowchart LR
    M["主库"] -->|"binlog"| IO["备库 IO 线程"]
    IO -->|"relay log"| SQL["备库 SQL 线程"]
    SQL -->|"重放"| D["备库数据"]
    style M fill:#ffd3a5
    style D fill:#a8e6a3
```

延迟分两类：

| 类型 | 定义 | 原因 |
|---|---|---|
| **IO 延迟** | relay log 落后主库 binlog | 网络慢、主库 binlog 写入快 |
| **SQL 延迟** | SQL 线程落后 relay log | 重放慢、单线程瓶颈、大事务 |

**监控指标**：

```sql
-- 秒级延迟（推荐）
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: 0 = 追上
-- Master_Log_File / Read_Master_Log_Pos: IO 进度
-- Relay_Master_Log_File / Exec_Master_Log_Pos: SQL 进度

-- GTID 一致性检查（8.0+）
SELECT * FROM performance_schema.replication_applier_status_by_worker;
```

**诊断链路**：

```
1. Seconds_Behind_Master > 0 → 有延迟
2. IO 进度 vs SQL 进度 → 判断是 IO 慢还是 SQL 慢
3. SQL 慢 → 看最近重放的事务（大事务？锁等待？）
4. IO 慢 → 看网络 + 主库写入压力
```

## 三、一致性模型：异步、半同步、组提交的边界

| 模型 | 主库提交 | 备库状态 | 数据一致性 |
|---|---|---|---|
| **异步** | 立即返回 | 可能没收到 | 可能丢数据 |
| **半同步** | 等 N 个备库 ACK | 已收到 relay log | 不丢（已送达） |
| **无损半同步** | 等备库 relay log 落盘 + ACK | 已落盘 | 崩溃零丢失 |
| **组提交并行** | 批量 ACK | 批量送达 | 取决于组内顺序 |

**关键认知**：半同步「送达」不等于「重放完成」——备库收到 relay log 但还没执行完，数据仍不一致。**一致性检查要看 Exec_Master_Log_Pos，不是 Read_Master_Log_Pos**。

四个模型的一致性强弱与代价放一张图上看：

```mermaid
flowchart LR
    A["异步<br/>最快 / 可丢"] --> B["半同步<br/>多一跳ACK / 不丢送达"]
    B --> C["无损半同步<br/>commit前等 / 崩溃零丢失"]
    C --> D["组提交并行<br/>送达+重放并行 / 吞吐最大化"]
    style A fill:#ffaaa5
    style C fill:#a8e6a3
    style D fill:#ffd3a5
```

## 源码关键路径

以 8.0 主线口径（sql/、plugin/semisync/）：

- 延迟水位：`rpl_replica.cc` 的 Coordinator 循环——`Seconds_Behind_Master` 的计算逻辑（事件时间戳与系统时钟差）在此，理解它才能理解这个指标的陷阱
- 降级计数：`plugin/semisync/` 的 `ReplSemiSyncMaster`——`no_times` 递增与超时降级的判定点
- worker 分发状态：`replication_applier_status_by_worker` 表是 Coordinator/Worker 结构的对外投影，延迟归因「哪个 worker 慢」直接查它

阅读建议：把「一个延迟告警」拆成 IO/SQL 两段，各自对照源码里的进度推进点——两段水位在代码里各有一个明确的推进变量，机制与观测一一对应。

## 四、不一致场景与排查

### 4.1 异步复制丢数据

主库崩溃 + binlog 未送达备库 → 切换后备库缺少事务。**排查**：对比主备 GTID 集合 `SELECT * FROM performance_schema.replication_connection_status`。

### 4.2 半同步降级导致丢数据

半同步超时降级为异步 → 主库继续提交不等待 ACK → 崩溃时同样丢数据。**排查**：`SHOW STATUS LIKE 'Rpl_semi_sync_master_no_times'`（降级次数）。

### 4.3 并行复制的边界（不是不一致，是退化）

WRITESET 并行下，冲突判定保证「碰同一行的事务串行、不碰的并行」——**最终结果与主库一致**，这点与异步/半同步无差。它真正的边界是：无主键/唯一键的表无法计算行冲突集，**退化为单线程重放**——「并行复制不生效导致延迟」，而不是「并行导致不一致」。把这两件事分开，归因才不会跑偏。

### 4.4 大事务阻塞 SQL 线程

一个 `DELETE FROM big_table` 事务在备库执行时，SQL 线程被占满 → 其他事务积压在 relay log → 延迟飙升。**排查**：`SHOW PROCESSLIST` 看 SQL 线程状态。

## 五、治理手法：监控 + 延迟治理

| 手法 | 动作 | 代价 |
|---|---|---|
| **秒级延迟监控** | `Seconds_Behind_Master` + 自定义脚本 | 无 |
| **半同步降级告警** | `Rpl_semi_sync_master_no_times` | 无 |
| **GTID 一致性检查** | 主备 GTID 集合对比 | 每日 |
| **大事务治理** | `information_schema.innodb_trx` 查运行时长 | 每日 |
| **并行复制状态** | `performance_schema.replication_applier_status_by_worker` | 每周 |

**延迟治理的优先级**：

1. 先消灭大事务（单事务阻塞是最大延迟源）
2. 再开并行复制（WRITESET 模式，要求全表有主键）
3. 最后调半同步参数（`rpl_semi_sync_master_timeout` 适当调大，避免频繁降级）

## 业内惯例

> 💡 **实战提示**
> - 延迟告警配「位点差」而不是只配秒数：对比 Retrieved_Gtid_Set 与 Executed_Gtid_Set 的事务数差——时钟漂移骗得过秒表，骗不过事务号
> - 延迟突增排查口诀「先看 SQL 线程状态」：`SHOW PROCESSLIST` 里重放线程在读 relay 还是卡在某条语句——卡语句 = 大事务/锁等待，在读 = 产出过快
> - 半同步降级次数（`Rpl_semi_sync_master_no_times`）非零即查：降级窗口 = 容灾静默掉档，恢复后要复盘超时原因
> - 云厂商「强一致读」宣传的验真方法：问清是「等 GTID 重放完成」还是「仅半同步送达」——前者才配叫读一致性，后者只是不丢

1. **延迟监控**：`Seconds_Behind_Master` 是秒级指标，建议配合 `Exec_Master_Log_Pos` 做位点比对——时钟不同步时 Seconds_Behind_Master 可能不准。
2. **半同步降级告警**：监控 `Rpl_semi_sync_master_no_times`，> 0 即触发告警。
3. **GTID 一致性检查**：每日对比主备 GTID 集合，`SELECT * FROM performance_schema.replication_connection_status`。
4. **大事务治理**：`information_schema.innodb_trx` 查运行时长，超过 60s 的大事务优先拆分。
5. **并行复制**：MySQL 8.0 默认 WRITESET 模式，要求表有主键或唯一键——无主键的表退化为串行。
6. **网络延迟**：ping 主库 + traceroute，网络延迟 > 1ms 时 IO 延迟成为瓶颈。
7. **云数据库「强一致性」**：部分云厂商提供「强一致性复制」，但底层仍是半同步的变种——理解机制才能判断厂商宣传是否属实。

## 跨周期经验

1. **异步复制丢数据是常态**：主库崩溃 + binlog 未送达 → 数据丢失。金融场景必须用半同步或无损半同步。
2. **并行复制从库级到 WRITESET**：三代演进主线是「并行度判定从粗到细」，WRITESET 打破「主库串行 → 备库也无法并行」的传导。
3. **Seconds_Behind_Master 有陷阱**：主库静默时该值可能为 0 但实际未追上——需结合位点比对。

## 常见误区

- **「Seconds_Behind_Master = 0 就是追上了」**：主库静默时该值可能为 0 但实际未追上——需结合位点比对。
- **「并行复制能解决所有延迟」**：WRITESET 要求表有主键/唯一键，无主键的表退化为串行。
- **「半同步送达 = 一致性」**：半同步「送达」不等于「重放完成」——备库收到 relay log 但还没执行完，数据仍可能读旧。
- **「并行复制会导致主备结果不一致」**：冲突判定保证结果一致，它退化的是「并行度」不是「正确性」——归因错位会引向错误的治理。

## 你们可能会问

**Q1：监控延迟应该看哪个数字最可靠？**
事务级位点差最可靠：`Retrieved_Gtid_Set` 与 `Executed_Gtid_Set` 的事务数差。Seconds_Behind_Master 受时钟与「主库静默」双重干扰，只当趋势参考不当精度依据。

**Q2：写后读一致性在复制体系里怎么落地？**
三层递进：读主库（最简单、代价最高）→ GTID 等待（`WAIT_FOR_EXECUTED_GTID_SET` 确认备库重放完成再读，精确且均衡）→ 会话粘性（粗粒度兜底）。选型按读放大的代价与一致性窗口要求定。

**Q3：延迟与不一致，先治哪个？**
延迟是持续损耗（读旧数据、切换窗口长），不一致窗口是切换时刻的集中风险。常态治理盯延迟（大事务/并行度），切换设计盯一致（半同步 + GTID 校验 + 校验工具对账）——两套预案都要有。

## 开放问题

- 云托管数据库把复制监控产品化后，「延迟水位」的观测粒度正下沉到平台层，用户侧诊断套路如何与平台指标体系衔接，仍在摸索。
- 一致性读的 GTID 等待模式在跨机房场景的等待成本如何优化（读写分离中间件内置 GTID 路由等），各家实现成熟度不一，值得跟踪。
- 「延迟多大算不可接受」本质是业务定价问题：把一致性窗口翻译成业务 SLA 的方法论，比任何固定阈值都更值得沉淀。

## 🎯 核心带走

- **核心一句话**：延迟分两段水位（IO 追 / SQL 放）各自诊断，一致性看执行位点不看到达位点——治理顺序：先杀大事务、再开并行、最后动参数
- **机制链**：两段延迟 → 监控陷阱 → 一致性四级 → 三类不一致场景 → 治理优先级
- **哪里会坏**：SBM 假零、半同步降级窗口、大事务堵重放、误把并行退化当不一致
