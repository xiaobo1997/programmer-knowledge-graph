# B+ 树与页存储：索引为什么长这样

> 入门层讲过「索引是排好序的数据结构」。但为什么偏偏是 B+ 树？为什么主键乱序写入会变慢？「三层 B+ 树存两千万行」这句话到底怎么来的？这篇下到页与分裂的层面，把索引的存储机制讲透。并补上跨库对照（其他数据库用什么索引结构）、生产事故、代价量化三个深度维度。

## 一句话摘要

InnoDB 把整张表组织成一棵**按主键排序的 B+ 树**，树的最小物理单位是 16KB 的**页**：非叶子节点页存「路标」，叶子节点页存完整行数据。索引的所有性能特征——范围扫描快、随机主键写慢、自增主键吃香——全部能从「树 + 页」这两个结构推演出来。

跨库对照：PG 用 B+ 树 + FSM（空闲空间映射），Oracle 用 B+ 树 + 位图索引，SQL Server 用 B+ 树 + 列存储索引，MongoDB 用 B+ 树，WiredTiger 用 LSM + B+ 树混合——索引结构服从存取介质与工作负载。

## 🎯 本文核心

**核心一句话：InnoDB 索引 = B+ 树 × 页的两层结构——树决定「多少次 I/O 定位」（树高即 I/O 次数），页决定「每次 I/O 之后多快找到」（页目录二分），写入性能则由「插入位置是否顺序」决定页分裂频率。**

机制链（本篇全部内容挂在这条链上）：数据结构演进（为什么 B+ 树）→ 页结构（I/O 单位）→ 树高与页内二分（查询代价 = 树高 × 页内查找）→ 页分裂与合并（写入放大的来源）→ 主键设计结论（自增快、随机慢的因果闭合）→ 跨库对照 → 生产事故 → 代价量化。记住「树管定位、页管落盘、顺序管写入」这一句话，全篇可重构。

## 二、从二叉树到 B+ 树：一场围绕 I/O 次数的演进

数据库索引的历史，本质是一部「**如何减少磁盘 I/O 次数**」的演进史。

**二叉搜索树 / AVL / 红黑树**：每节点最多 2 个分叉，千万行数据树高 20+ 层，每层一次 I/O——磁盘时代这是灾难。它们是为内存设计的结构。

**哈希表**：等值查询 O(1)，但完全不支持范围扫描与排序，做不了「WHERE create_time >」这类高频需求。

**B 树**：多叉，一个节点放几十上百个键，树高骤降到 3-5 层。但 B 树的节点里「键 + 数据」混存，非叶子节点也占大量空间，导致每个节点能放的键变少、扇出变小；且范围查询要在树上反复回溯。

**B+ 树**：两处关键改良——非叶子节点**只存键不存数据**（扇出大幅提高），叶子节点之间**用双向链表串起来**（范围扫描变成沿链表顺序走，不再回溯父节点）。这两点让 B+ 树在「磁盘块尺寸」的约束下碾压其他结构，成为 InnoDB 与多数 OLTP 数据库的统一选择。

```mermaid
flowchart LR
    A["二叉/红黑树<br/>树高 O(logN) 层"] -->|多叉增扇出| B["B 树<br/>键+数据混存"]
    B -->|非叶子去数据<br/>叶子加链表| C["B+ 树<br/>矮胖 + 叶子成环链"]
    C --> D["InnoDB 聚簇索引"]
    style C fill:#a8e6a3
    style D fill:#ffd3a5
```

顺带回应一个高频疑问：Redis 的 ZSet 用跳表，MySQL 为什么不用？跳表是内存结构，实现简单且支持并发更新；B+ 树的矮胖形态是为**按页 I/O 的磁盘**量身定制的。介质不同，最优结构不同——底层机制服从存取介质，这是数据结构选型不变的取舍逻辑。

## 三、页：InnoDB 一切 I/O 的最小单位

InnoDB 不按「行」读写磁盘，按**页**读写——默认每页 16KB，这是整个存储引擎最底层的常量。一次哪怕只更新一行，落盘的也是整页。

一个索引页从上到下大致是：

```text
┌─────────────────────────────┐
│ File Header（页号/前后页指针/LSN）│
│ Page Header（记录数/层级/槽位信息）│
│左侧: Infimum + Supremum 虚拟记录 │
│ User Records（真实行,头部带 next 指针) │
│ Free Space（未分配空间）          │
│ Page Directory（记录槽:二分查找用） │
│ File Trailer（校验和,崩溃恢复用）  │
└─────────────────────────────┘
```

两个设计值得展开：

**记录区里的行不是物理连续的，是「逻辑有序、物理松散」**。每行记录头带一个指向下一行的 next 指针，行与行之间按主键用指针串联。这样新行可以插进页内任意空位，只需调整指针，不需要搬移数据。

**页目录是为二分查找服务的**。如果没有目录，页内查找只能沿 next 指针逐条走（O(n)）。InnoDB 每若干条记录设一个「槽」，槽里存记录的页内偏移，查找时先对槽二分定位到小区间，再在小区间内顺序扫描——这就是「页内二分」的**关键路径**。树高决定 I/O 次数，页内目录决定每次 I/O 之后的内存查找速度，两者相乘才是索引的查询代价。

B+ 树的每个节点就是一个页：非叶子节点页里存「键 + 子页号」，叶子节点页里存完整行（聚簇索引）或「键 + 主键」（二级索引）。**树高即 I/O 次数**：根页常驻内存，两千万行的表按经验估算树高 3 层，即一次主键点查约 1-2 次真实 I/O——这就是那句「三层 B+ 树存两千万」的来历，注意它是按行大小做的**估算**，不是保证值。

## 四、跨库对照：其他数据库用什么索引结构

| 数据库 | 索引结构 | 备注 |
|---|---|---|
| **MySQL InnoDB** | B+ 树（聚簇） | 叶子存完整行，主键即索引 |
| **PostgreSQL** | B+ 树 + FSM + GiST/GIN | 主索引用 B+ 树，GiST 支持空间/GIN 支持全文 |
| **Oracle** | B+ 树 + 位图索引 + 反转键索引 | 位图索引适合低基数列，反转键防索引热点 |
| **SQL Server** | B+ 树 + 列存储索引 + 哈希索引 | 列存储索引用于分析型查询 |
| **MongoDB** | B+ 树（ WiredTiger 引擎） | 默认索引结构，支持复合索引 |
| **RocksDB / LevelDB** | LSM 树 + SSTable | 写优化，读需合并多层 |
| **TiDB** | B+ 树（Raft 分布式） | 分片内 B+ 树，全局有序靠 Raft 共识 |
| **OceanBase** | LSM + B+ 树混合 | 写路径 LSM，读路径 B+ 树 |

**关键洞察**：MySQL 的聚簇索引（叶子存完整行）是 InnoDB 的独特设计——PG 叶子只存行指针，Oracle 同理。聚簇索引省一次回表但写入成本更高（叶子更新=整行移动），是「读优化」的典型取舍。

**选型对照**：写密集选 LSM（RocksDB），读密集选 B+ 树（InnoDB），混合选 WiredTiger（LSM + B+ 树），分析型选列存储（SQL Server / Oracle）。没有银弹，只有场景适配。

## 五、页分裂与页合并：写入放大从哪来

页是定长的 16KB。当新行要插入的页已满，就会发生**页分裂**：InnoDB 申请一个新页，把原页约一半的行搬过去，父节点里新增一个「键 + 新页号」的路标。反向地，删除使相邻两页合计利用率低于阈值（`MERGE_THRESHOLD`，默认 50%）时触发**页合并**，两页并一页、父节点删路标。

```mermaid
flowchart LR
    A["插入新行<br/>目标页已满"] --> B["申请新页"]
    B --> C["原页后半段行<br/>搬移到新页"]
    C --> D["父节点新增路标<br/>键 + 新页号"]
    D --> E["一次插入放大为<br/>搬移 + 多页写盘"]
    style A fill:#ffd3a5
    style E fill:#ff8b94
```

由此可以推演出入库设计里最重要的几条结论：

1. **自增主键快，是因为它把插入变成「永远往最后一页追加」**。顺序追加几乎不触发分裂（页满了直接开新页，原页保持满），随机主键（如无序 UUID）则每行都可能命中页中间，频繁搬移——这就是「随机主键写入慢」的底层机制，和「UUID 索引膨胀」一起构成主键设计的核心 Trade-off。
2. **乱序删除与插入交替，会让页利用率持续走低**（碎片化），表「删了很多行但空间不还」，`OPTIMIZE TABLE` 重建的本质就是重排页。
3. **大批量导入先按主键排序**，把随机写变顺序写，是导入提速的通用手法。

## 六、代价量化：页分裂的真实成本

**量化口径**（行业经验，非官方数字）：

| 场景 | 页分裂频率 | I/O 放大倍数 | 写入吞吐影响 |
|---|---|---|---|
| 自增主键顺序插入 | 极低（页满才开新页） | ~1x | 几乎无影响 |
| 随机 UUID 主键插入 | 高（每行可能命中页中间） | 2-5x | 写入吞吐下降 50%+ |
| 高频删除+插入交替 | 中（碎片化触发合并） | 1.5-3x | 写入吞吐下降 20-40% |
| 大批量导入（未排序） | 高 | 3-5x | 导入时间延长数倍 |

**量化逻辑**：一次页分裂 = 申请新页 + 搬移约一半行 + 父节点新增路标 → 一次插入放大为多次磁盘写。写密集场景下，分裂频率随插入乱序度非线性增长——这是「随机主键写入慢」不仅是理论而是可测量的代价。

**Benchmark 边界**：TPC-C 类标准测试通常用自增主键，互联网业务实际负载更乱——测试环境必须用线上真实主键分布，否则量化结果不可外推。

## 七、源码关键路径

以 MySQL 8.0 源码（storage/innobase）为准，三条路径对应本文三个机制（函数名为 8.0 主线口径，小版本可能微调）：

- **树搜索**：`btr_cur_search_to_nth_level()` 自根向下逐层定位；页内经 `page_cur_search_with_match()` 走页目录二分 + 线性扫描
- **页分裂**：`btr_page_split_and_insert()`（btr0btr.cc）——先尝试在插入点附近分裂以减少搬移，失败退回 50/50
- **页合并**：`btr_merge_page_and_update()` 一族函数，删除后由 `btr_cur_may_adopt_...` 路径检查 `MERGE_THRESHOLD` 触发

读源码时建议顺着「一次 INSERT 的调用栈」往下走：`row_insert_for_mysql → btr_cur_optimistic_insert（乐观插入,页内有空间直接放）→ 失败则悲观路径 btr_page_split_and_insert`。「乐观插入失败才分裂」这个两层设计，正是多数插入其实很快的原因。

## 八、生产事故推演：页分裂导致主库 CPU 毛刺

**场景**：某日志表使用无序 UUID 做主键，白天流量高峰期 CPU 飙到 90%+，慢查询激增。

**根因链路**：

1. UUID 主键随机写入 → 每次插入可能命中页中间 → 触发页分裂
2. 页分裂 = 申请新页 + 搬移约一半行 + 父节点新增路标 → 一次插入放大为多次磁盘写
3. 高峰期大量并发插入 → 大量页分裂同时发生 → Buffer Pool 被 dirty page 挤占
4. 后台刷脏页线程被唤醒 → 与业务线程抢 I/O → CPU 毛刺

**排查 SOP**：

```sql
-- 查碎片率（信息_schema）
SELECT table_name, data_free, avg_row_length
FROM information_schema.tables
WHERE table_schema = 'your_db' AND table_name = 'your_table';

-- 查页分裂频率（performance_schema）
SELECT * FROM performance_schema.events_waits_summary_global_by_event_name
WHERE EVENT_NAME LIKE '%innodb/buf_page_size%';
```

**止血三步**：
1. 紧急：`OPTIMIZE TABLE` 重建表（锁表，低峰做）
2. 短期：换趋势递增主键（雪花/号段），杜绝随机 UUID 做聚簇索引
3. 长期：监控 `DATA_FREE` + `innodb_page_size` 利用率

**Trade-off**：`OPTIMIZE TABLE` 重建期间业务不可用（大表锁表数分钟），所以**碎片治理要定期做**，不能等满了再救。

## 九、典型场景

- **日志/流水表**：写多读少、按时间范围查——自增主键 + 时间索引，追加写不打架，范围扫沿叶子链表
- **账务/订单表**：业务要求全局唯一且不泄露量级，业务 ID 多为雪花类——趋势递增可接受，注意时钟回拨造成的局部乱序仍会引发零星分裂
- **老表重建**：碎片率高（信息表中 `DATA_FREE` 异常大）时 `OPTIMIZE TABLE` 或 `ALTER ... ENGINE=InnoDB` 重建聚簇，恢复页利用率
- **跨库对照**：从 Oracle 切 MySQL 时，Oracle 的反转键索引（Reverse Key Index）专门防 B+ 树热点——MySQL 无等价机制，必须用雪花/号段分散写入——迁移时索引策略要重新评审

## 十、业内惯例

> 💡 **实战提示**
> - 大批量导入先按主键排序再灌入：随机写变顺序写，页分裂几乎归零，导入提速一个量级起步
> - 监控碎片率用 `information_schema.tables` 的 `DATA_FREE`：持续走高就该安排低峰重建，别等写入抖动报警
> - 「自增主键 + 隐藏风险」：自增在单机安全、在分库分表会冲突——全局唯一需求出现时换号段/雪花，别等到撞了才改
> - 二级索引键要短：主键会被每个二级索引叶子复制，主键与索引键的长度一起收敛才有扇出收益
> - 高峰期不做大批量删除：合并伴随搬移与父节点修改，与刷脏叠加就是抖动——低峰作业是业内不成文默认
> - 页分裂排查看 `information_schema.innodb_ftables` 的 `DATA_FREE` 和 `frag_ratio`：碎片率 > 30% 安排低峰重建

- **主键用自增 BIGINT 是默认起点**：无特殊诉求不引入无序 ID；必须用分布式 ID 时选趋势递增实现（号段/雪花），避免纯随机 UUID 做聚簇主键——业内默认，官方文档不会替你做这个决定
- **显式主键**：不建主键时 InnoDB 会选唯一非空索引充当，没有则生成隐藏行号聚簇——隐式行为不可控，业内一律显式声明主键
- **索引键长度收敛**：8.0 单列上限 3072 字节，但实际惯例是索引键远短于上限——键越长每页容纳的路标越少，扇出下降树高上升，代价在 I/O 次数上体现
- **`MERGE_THRESHOLD` 少动**：默认 50% 覆盖绝大多数场景，个别高频插入删除交替的索引会按页配置到 40% 推迟合并，属于「先测量再调优」项

## 十一、常见误区

- **「三层 B+ 树 = 2000 万行」当铁律**：它是按每页扇出与行数做的估算。行宽大、键长，同样的表树高就可能是 4 层。正确的用法是把它当「量级感」，真正的树高用 `information_schema` 或 perf 工具实测
- **以为分裂总是 50/50**：InnoDB 会优先尝试在插入点附近分裂（保留原页前段空间给后续顺序插入），50/50 是兜底。所以「自增插入几乎不分裂」与「随机插入分裂频繁」并存
- **把页合并当免费**：合并伴随搬移与父节点修改，高峰期大量删除同样造成抖动——批量删除选低峰，是业内不成文的默认
- **主键越短越好 ≠ 一味换短类型**：主键长度会被二级索引的每个叶子复制一遍，短主键省的是全索引的空间，但前提是满足业务唯一性与趋势递增——先满足正确性再谈优化
- **「PG 的索引和 MySQL 一样」**：PG 的 B+ 树叶子只存行指针（堆表），InnoDB 叶子存完整行（聚簇）——写入放大和回表代价差异大，跨库迁移必须重新评审
- **「LSM 树一定比 B+ 树快」**：LSM 写优化但读要合并多层，B+ 树读稳定但写可能分裂——选结构看读写比例，不是听说

## 你们可能会问

**Q1：把页调大到 32KB/64KB 能不能提速？**
`innodb_page_size` 建库时确定且影响深远：大页扇出高、树更矮，但单页写放大与缓存粒度变粗，OLTP 默认 16KB 是大量权衡后的业界默认。改它是建库级决策，不是调优手段。

**Q2：为什么删除大量数据后表文件不变小？**
删行只打删除标记并让页走向合并，但已分配的页不会主动归还操作系统。空间回到「可用但不还」状态，重建表才能真正收缩。

**Q3：二级索引的叶子为什么存主键而不是行地址？**
存主键让行移动（页分裂）时二级索引完全不用改——代价是回表要多一次树查找。这是「稳定」与「少一次查找」之间的经典折中，InnoDB 选了前者。

**Q4：MongoDB 用什么索引？**
MongoDB WiredTiger 引擎默认 B+ 树索引，稀疏索引支持缺失字段——与 MySQL InnoDB 的聚簇索引不同，MongoDB 是堆表 + B+ 树索引，回表是常态而非例外。

**Q5：Redis ZSet 为什么用跳表不用 B+ 树？**
ZSet 在内存中，跳表实现简单且支持并发更新（无锁 CAS），B+ 树的磁盘 I/O 优化在内存中反而多此一举。介质不同，最优结构不同。

## 开放问题

- 分布式数据库（分片 + 各分片本地 B+ 树）时代，「全局有序」被切成了「分片内有序」，页分裂理论在多写多活下要怎么重新推导，业内尚无统一答案
- LSM 树（写优化）与 B+ 树（读优化）长期并存，**融合结构**（如 bLSM 类设想）能否在通用 OLTP 里落地，取决于硬件演进与工作负载的漂移
- NVMe 延迟下降后，B+ 树的 I/O 优化是否正在贬值——业内暂无定论

## 🎯 核心带走

- **核心一句话**：InnoDB 索引 = B+ 树 × 页——树高定 I/O 次数，页内目录定查找速度，插入顺序定页分裂频率
- **机制链**：结构演进（扇出 + 叶子链表）→ 页结构（逻辑有序物理松散）→ 查询代价（树高 × 页内二分）→ 写入放大（分裂/合并）→ 主键结论（自增快随机慢）→ 跨库对照 → 生产事故 → 代价量化
- **哪里会坏**：随机主键高峰页分裂风暴、碎片堆积（DATA_FREE 走高）、误把「三层两千万」当保证值
- **边界**：本篇讲「存成什么样」；「查一次要几跳、回表代价多少」在本系列篇 2《聚簇索引与回表》正式展开
