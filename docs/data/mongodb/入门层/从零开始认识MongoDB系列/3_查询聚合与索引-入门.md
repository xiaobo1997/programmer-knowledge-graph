# 查询聚合与索引：find 直觉、管道五阶段与 explain

> 一句话：find 的嵌套条件文档对应 SQL 的 WHERE 子句直觉可译，聚合管道把「一条复杂 SQL 的执行顺序」显式化成一串阶段；索引类型对齐数据形态（数组走多键、地理走 2dsphere），explain 用「扫描比」判断好坏——这套能力与 MySQL EXPLAIN 一一对应，换的是语法不是心智。

## 🎯 本文核心

**核心一句话：MongoDB 的查询体系 = find（简单条件）+ aggregation pipeline（把 SELECT/WHERE/GROUP BY/ORDER BY/LIMIT 翻译成 $match/$group/$sort/$project/$limit 等阶段串联）+ 索引家族（单字段/复合/多键/文本/地理）——性能判断的铁律两边同源：扫描的索引键数与文档数越接近返回数越好（IXSCAN 优于 COLLSCAN），复合索引按 ESR（等值-排序-范围）排列字段，排序内存放不下就报错——所有优化问题回到「减少扫描量」这一条底层原理。**

本篇按「写得出（语法直觉）→ 算得动（索引对齐）→ 看得懂（explain）」三步展开，全程对照 MySQL 语法与 EXPLAIN 心智。

## 一句话摘要

**find** 用嵌套文档表达条件：`db.orders.find({status: "paid", amount: {$gt: 100}})` 对应 `WHERE status='paid' AND amount>100`，操作符族（$gt/$in/$exists/$elemMatch…）覆盖 SQL 比较与集合判断；**聚合管道**用阶段数组表达复杂计算——$match（过滤，对应 WHERE）→ $group（分组聚合，对应 GROUP BY）→ $sort（排序）→ $project（字段裁剪与变形，对应 SELECT 列）→ $limit（对应 LIMIT），阶段顺序即执行顺序，可读性上比 SQL 的执行顺序隐式化更直白。**索引**与数据形态对齐：单字段/复合对应常规 B+tree；**多键索引**（multikey）给数组每个元素建项（服务「数组包含某值」查询）；文本索引服务关键词检索；地理索引（2d/2dsphere）服务近邻与围栏。复合索引的字段序遵循 **ESR 原则**（等值字段在前、排序字段居中、范围字段在后）。**explain("executionStats")** 输出三层数据：queryPlanner（计划）→ executionStats（真实执行统计）→ 关键比值 totalKeysExamined / totalDocsExamined / nReturned——扫描越接近返回数越健康，COLLSCAN（全集合扫描）是第一告警信号，内存排序超限（默认 100MB 量级，业内认知）直接报错。

## 一、find 语法直觉：从 SQL 到条件文档

四组最常用的翻译，先建立「条件文档 = WHERE」的直觉：

```javascript
// 1. 等值 + AND: 隐式并列即 AND
db.orders.find({ status: "paid", channel: "app" })
// SQL: WHERE status='paid' AND channel='app'

// 2. 范围与集合: $gt/$gte/$lt/$lte/$in/$nin
db.orders.find({ amount: { $gte: 100, $lt: 5000 }, channel: { $in: ["app", "web"] } })
// SQL: WHERE amount>=100 AND amount<5000 AND channel IN ('app','web')

// 3. OR 与嵌套字段
db.orders.find({ $or: [{ status: "paid" }, { amount: { $gt: 10000 } }] })
db.users.find({ "address.city": "Beijing" })   // 嵌套文档点路径

// 4. 数组元素匹配: $elemMatch (同元素同时满足多条件)
db.students.find({ scores: { $elemMatch: { subject: "math", score: { $gte: 90 } } } })
```

投影（projection）对应 SELECT 列裁剪：`find({...}, {name: 1, amount: 1, _id: 0})`——还有一类 SQL 没有的形态：数组投影 `$slice` 只取数组前 N 个元素，正好接住第 1 篇「最近 N 条内嵌」的建模惯例。

**追问：find 能表达的边界在哪？为什么要另学一套管道？**
反方案分析：为什么不用 find 加函数硬扛所有查询？因为 find 的输出是「文档子集」，而复杂计算（分组聚合、多阶段变形、关联）需要「数据流的中间形态」——管道把每一步的输入输出显式化，阶段可组合可推理。这与「SQL 一句话 vs 关系代数展开」是同一个 trade-off：SQL 更紧凑，管道更透明。

## 二、聚合管道五阶段：SQL 执行顺序的显式化

```javascript
// 语义: 各渠道近 7 天成交金额 TOP 排名 (mongosh 真实形态)
db.orders.aggregate([
  { $match: { status: "paid", created_at: { $gte: ISODate("2026-09-18") } } }, // WHERE
  { $group: {                                                                  // GROUP BY
      _id: "$channel",
      total: { $sum: "$amount" },
      cnt:   { $sum: 1 }
  } },
  { $sort: { total: -1 } },                                                    // ORDER BY
  { $project: { _id: 0, channel: "$_id", total: 1, cnt: 1 } },                 // SELECT 列
  { $limit: 10 }                                                               // LIMIT
])
```

```mermaid
flowchart LR
    A["全量文档"] --> M["$match<br/>先过滤 减少下游"]
    M --> G["$group<br/>分组聚合"]
    G --> S["$sort<br/>排序"]
    S --> P["$project<br/>字段裁剪变形"]
    P --> L["$limit<br/>截断"]
    style M fill:#a8e6a3
    style S fill:#ffd3a5
```

**设计思想**：管道的哲学是「越早过滤越好」——$match 放最前是惯例而非风格偏好：下游阶段处理的数据量决定整体耗时，且前置的 $match 能走索引（形态与 find 等价时）。这条原理与 SQL 优化器「谓词下推」完全同源——SQL 里优化器替你做，MongoDB 里管道顺序由你写，**优化责任从优化器转移到了作者**，这是文档查询体系最重要的心智差异。

**再追问：管道里能 JOIN 吗？**
打破砂锅说透：$lookup 是管道内的左外连接（同库集合间，跨分片有限制，机制以官方文档为准）——能做，但它的执行代价是嵌套扫描形态（业内认知），没有关系型优化器对 JOIN 的重排与算法选择能力。生产惯例：$lookup 用于低频管理查询与轻度关联；高频路径的关联优先在建模层内嵌解决（第 1 篇的三问），重分析场景卸载到专用系统（第 4 篇的接力线）。

## 三、索引家族：类型对齐数据形态

| 索引类型 | 机制一句话 | 典型 DDL | MySQL 对应 |
|---|---|---|---|
| 单字段 | 标准 B 树 | `db.orders.createIndex({created_at: 1})` | 一致 |
| 复合 | 多字段有序结构，遵循 ESR | `createIndex({status: 1, created_at: -1})` | 一致（最左前缀同理） |
| 多键 multikey | 数组每个元素建索引项 | 对 tags 数组建索引自动成为多键 | 无直接对应（JSON 多值索引近似） |
| 文本 text | 分词倒排 | `createIndex({content: "text"})` | FULLTEXT（分词器生态不同） |
| 地理 2dsphere | GeoJSON 球面索引 | `createIndex({loc: "2dsphere"})` | SPATIAL（能力子集） |
| TTL | 到期自动删除 | `createIndex({expire_at: 1}, {expireAfterSeconds: 0})` | 无（靠定时任务清理） |

**ESR 原则**（复合索引字段序）：Equality（等值条件字段）→ Sort（排序字段）→ Range（范围条件字段）。原理：等值字段把候选集切到最小，排序字段让索引序即结果序（省掉内存排序），范围字段放最后避免它打断排序连续性。与 MySQL 复合索引「等值列在前 + 排序列跟随」的原理一致——**这是同一套 B 树机制推出来的同一结论，换个词表而已**。

**追问：TTL 索引能当定时任务替代品吗？**
不能全信：TTL 由后台任务周期扫描删除（删除有滞后，业内认知分钟级），不适合「精确到期即删」的语义，适合「过期数据最终会被清掉」的运维语义（会话、临时令牌、日志留存）。精确时效业务逻辑要靠应用层判断字段值，TTL 只做兜底清理。

## 四、explain 怎么看：三层输出与一个铁律

```javascript
db.orders.find({ status: "paid", created_at: { $gte: ISODate("2026-09-18") } })
         .explain("executionStats")
```

输出三层，重点看第二层的四个数：

| 输出项 | 含义 | 健康线（业内认知） |
|---|---|---|
| winningPlan.stage | IXSCAN / COLLSCAN / FETCH | 见 COLLSCAN 即告警 |
| totalKeysExamined | 索引键扫描数 | 趋近 nReturned |
| totalDocsExamined | 文档扫描数 | 趋近 nReturned |
| executionTimeMillis | 真实耗时 | 结合业务 SLO |

**铁律一句话：扫描比（examined / returned）越接近 1 越健康**——keys 扫了 10 万、只返回 100 条，说明索引选择性与查询形态不匹配；docs 扫描远大于 keys 扫描，说明大量时间在回表取文档。与 MySQL EXPLAIN 的 rows 估算 + type=ref/range/ALL 的判断哲学完全同构，区别是 MongoDB 给的是**真实执行统计**（executionStats 模式会真跑），MySQL 默认给估算——MongoDB 这点反而更诚实。

线上排查过一则公开社区高频同款案例：订单列表页偶发超时，explain 一看 winningPlan 是 COLLSCAN——原因是查询条件里对时间字段包了格式转换（把字段转换后比较），索引完全用不上；复盘把比较条件改回裸字段形式（转换挪到参数侧），IXSCAN 回归。**「函数包列索引失效」这个 MySQL 经典坑，在 MongoDB 同样存在**——条件文档里对字段做表达式计算，索引就瞎了。

**内存排序红线**：$sort / find 的 sort 在无索引支撑时走内存排序，超过限额（默认 100MB 量级，业内认知，允许 allowDiskUse 临时落盘）直接报错 QueryExceededMemoryLimitNoDiskUseAllowed——生产上排序字段必须进复合索引（ESR 的 S 位），而不是靠 allowDiskUse 硬扛。

> 💡 **实战提示**
> - 💡 慢查询排查固定三步：explain("executionStats") → 看扫描比与 stage → 缺索引补索引/ESR 重排序——不要跳过 explain 凭感觉加索引（加错索引的写入代价是永久的）
> - 💡 $match 提前 + $project 减列是管道优化的零成本习惯：管道里每个阶段处理的文档大小都乘一遍，早减字段是全程省
> - 💡 索引不是越多越好：每个索引都是一份有序副本，写入时同步维护——用 $indexStats 找出访问量为零的索引下线，对应 MySQL 的 sys.schema_unused_indexes 习惯

## 五、与 MySQL 查询体系的能力区别

| 维度 | MongoDB | MySQL |
|---|---|---|
| 即席条件 | find 条件文档 | SELECT ... WHERE |
| 复杂计算 | 聚合管道（阶段显式） | SQL 一句话（优化器隐式） |
| JOIN | $lookup（管道内左外连接，代价高） | 优化器重排的 JOIN 家族 |
| 数组/嵌套查询 | 原生（$elemMatch/点路径/多键索引） | JSON 函数 + 多值索引（补丁式） |
| 执行计划 | executionStats 真实统计 | 默认估算（ANALYZE 后仍非真跑） |
| 排序兜底 | 内存限额报错 / allowDiskUse | filesort 内存/磁盘自动 |

**「与 MySQL 的区别」核心一条**：MySQL 的查询能力重心在**优化器自动决策**（JOIN 重排、谓词下推、访问路径成本估算），MongoDB 的重心在**作者显式编排**（管道顺序、字段序、索引对齐）——前者的上限高（复杂查询自动找路），下限也低（优化器选错时排查成本高）；后者把控制权交给你，写好很快，写差也很稳地差。放到整体架构上看：优化器架构与作者编排架构的分工差异，决定了两边团队的能力建设方向不同。团队选型时评估的其实是「查询侧的心智归谁管」。

## 六、常见误区与代价

- **误区一：把 $lookup 当 JOIN 常规武器**。代价：高频路径的关联查询在数据量上涨后延迟失控（嵌套扫描形态），回头再改建模要动数据——关联优先建模层解决，管道层 $lookup 只做低频。
- **误区二：正则查询随手写 `/^abc/` 变 `abc` 包含**。前缀锚定的正则可走索引，包含式（非前缀）退化全扫——与 MySQL LIKE 'abc%' 才走索引完全同理。
- **误区三：排序不进索引靠 allowDiskUse 硬扛**。落盘排序是性能悬崖不是功能开关——排序字段进复合索引（ESR 的 S 位）才是正路。
- **误区四：多键索引滥用在超大数组**。每个元素一个索引项，数组越长索引越肥、更新越贵——与第 1 篇「无界数组反模式」同源，规模先评估再建。
- **误区五：explain 只看 queryPlanner 就下结论**。计划是「打算怎么走」，executionStats 才是「实际走了多贵」——估算与真实的偏差正是慢查询的常见藏身处。

## 七、你们可能会问

**Q1：聚合管道和 SQL 哪个更好学？**
写简单查询 SQL 更紧凑；写多阶段计算时管道更直白（执行顺序即书写顺序，没有 SQL 的「书写顺序 ≠ 执行顺序」陷阱）。MySQL 背景的迁移路径：先把 WHERE/GROUP BY/ORDER BY 翻译成 $match/$group/$sort 建立映射，再把「优化器隐式做的事」内化成「管道编排的责任」。

**Q2：管道阶段顺序影响正确性还是只影响性能？**
两者都影响。$project 在 $group 前裁掉了分组需要的字段会直接算错；$match 放 $group 后语义就变了（对聚合结果过滤）——管道的每一步都是对数据流的实际变换，顺序即语义。性能差异只是这条正确性规则的自然推论。

**Q3：explain 的 allPlansExecution 模式什么时候用？**
它会把落选计划也试跑一遍（代价高），用于「为什么优化器不选我预期的索引」这类计划选择争议的取证——日常排查 executionStats 够用，计划仲裁才动用它（业内认知）。

## 八、什么时候用/不用与 Trade-off

| 场景 | 推荐 | 不推荐 |
|---|---|---|
| 高频条件查询 | 复合索引（ESR）+ find | $lookup 现场拼关联 |
| 即席统计报表 | 聚合管道（$match 前置） | 全量拉到应用层算 |
| 数组/嵌套检索 | 多键索引 + $elemMatch | 应用层过滤 |
| 大结果集排序 | 排序字段进索引 | allowDiskUse 当常态 |
| 关键词/地理/到期清理 | text / 2dsphere / TTL 各归其位 | 用 B 树硬模拟 |

Trade-off 的锚点是**显式编排与自动优化的分工**：管道把控制权交给作者——收益是行为可预测、性能问题可定位（每个阶段的责任清晰），代价是优化责任上移（作者不优化就没人优化）；SQL 把控制权交给优化器——收益是作者门槛低、复杂查询自动找路，代价是黑盒时刻的排查成本。两边的索引铁律（减少扫描量）完全一致，差异只在「谁来保证这条铁律被执行」。量级分界一句话：十万级文档随手查；千万级起扫描比与索引覆盖是必修课；亿级管道聚合要考虑预聚合（定时物化中间结果）或卸载专用分析系统——查询优化的尽头是「让高频问题在写入时就准备好答案」。

## 开放问题

- 查询优化器的自动化程度在两边持续演进（MongoDB 在补计划选择智能，MySQL 在补执行统计真实性），「心智归属」这条分界线十年后还在不在，值得跟踪
- 预聚合/物化视图能力（$merge 等管道输出能力）会不会把「实时管道」与「离线预计算」的边界重画，决定中等量级报表的默认形态

## 🎯 核心带走

- **核心一句话**：find 表达条件、管道表达计算（$match/$group/$sort/$project/$limit 五阶段 + $match 前置铁律）、索引对齐形态（复合按 ESR、数组走多键）——explain 用扫描比验证，examined 趋近 returned 即健康
- **心智迁移**：SQL 的优化由优化器隐式做，MongoDB 由作者显式做——管道顺序、字段序、索引对齐都是作者的责任
- **哪里会破**：$lookup 当常规 JOIN、函数包列失效索引、排序不进索引硬扛落盘、超大数组多键索引
- **取舍锚点**：显式编排（可预测/责任上移）vs 自动优化（低门槛/黑盒排查）

## 自测三问

1. ESR 原则的三段各指什么？为什么范围字段要放最后？——答出「等值切集/排序借索引序/范围不打断排序」算过。
2. explain 的健康线是什么？COLLSCAN 意味着什么？——答出「扫描比趋近 1 / 全集合扫描即告警」算过。
3. $match 放管道最前为什么是铁律？涉及正确性还是性能？——答出「下游数据量与索引可用性，两者都是」算过。
