# Lucene 与倒排索引：为什么快的地基

> ES 的快不是玄学，地基是 Lucene 的倒排索引。这篇讲清「从文档找词」到「从词找文档」的结构反转，以及词典、 postings list 这两个配套部件——理解了它们，ES 的大部分行为都能推演。

## 一句话摘要

倒排索引把文本拆成**词项（term）**，维护「**词项 → 包含它的文档列表（postings list）**」的映射：检索时先在**词典**里定位词项，再取 postings list 做交并运算出结果。**不可变的段（segment）+ 倒排结构**让检索路径几乎全是顺序内存访问——这是「快」的结构性来源，也是 ES「近实时、段合并」等一系列行为的根源。

## 一、为什么需要倒排索引

正排（数据库行存）回答「文档 100 有哪些词」要逐字段解析；检索的真实问题是反向的「哪些文档包含『手机壳』」——倒排索引把答案预先组织好：词项有序排列（词典可二分/跳步定位），每个词项挂着的文档 ID 列表按序存储（求交集是高效归并）。**空间换时间的极致形态：把「检索时的计算」提前到「写入时的组织」**。

## 5W 速记卡

| 维度 | 一句话 |
|---|---|
| What | 词项 → 文档列表的逆向映射结构（词典 + postings list） |
| Why | 亿级文档的按词检索要毫秒级，正排做不到 |
| When | 一切全文检索、过滤条件、聚合的底层承载 |
| Where | Lucene 段（segment）内，每个段自带完整倒排 |
| How | 分词 → 词典定位 term → postings 归并 → 打分排序 |

## 二、三个核心部件

```mermaid
flowchart LR
    Q["查询『手机壳』"] --> T["词典 Term Dictionary<br/>词项有序,可二分/跳步"]
    T -->|"定位 term"| P["Postings List<br/>文档ID列表(压缩+跳表)"]
    P --> M["多词求交/并<br/>按 docID 归并"]
    M --> S["相关性打分排序<br/>BM25"]
    style T fill:#ffd3a5
    style P fill:#a8e6a3
```

- **词典（Term Dictionary）**：段内所有词项的有序表，查找靠二分；为避免词典常驻内存的开销，Lucene 还建**术语索引（term index，FST 前缀树）**把「词项前缀 → 词典块」的映射压进内存
- **Postings List**：文档 ID 列表以**增量编码 + 变长压缩**存储（存差值而不是原值），并附**跳表**支持快速跳跃——亿级文档的一个词项列表也能压缩到很小且可快速定位
- **打分器**：BM25 按「词频 × 逆文档频率 × 文档长度归一」给每个命中文档算相关性——检索结果不只是「有没有」更是「哪个更相关」

## 三、不可变段：一切行为的根源

Lucene 的索引由一个个**不可变的段**组成，这条演进路线（从早期可变索引到全面段化）是 Lucene 性能的关键抉择。写到的段生命周期：

```mermaid
flowchart LR
    W["新文档写入"] --> B["内存 buffer<br/>不可检索"]
    B --> R["refresh 生成新段<br/>可检索"]
    R --> M["删除/更新打标记<br/>.del 文件"]
    M --> MG["段合并<br/>物理回收空间"]
    style R fill:#a8e6a3
    style MG fill:#ffd3a5
```

段化的结构：
写入生成新段（refresh 后可检索）、删除只打标记（.del 文件）、更新 = 删旧建新。不可变带来检索友好（无锁、缓存友好、可压缩），也带来两个必然后果——**删除是标记不是真删**（空间要等**段合并**回收）、**近实时**（段生成前不可检索）。不可变段是检索端架构的基石（无锁读、可压缩、缓存友好），理解了它，ES 的 refresh/merge/translog 三件套就都能推演出来——这个演进抉择解释了一切（写入链路细节留给特性层）。

## 四、与 MySQL B+ 树的区别

| 维度 | 倒排索引（Lucene 段） | B+ 树（InnoDB） |
|---|---|---|
| 回答的问题 | 哪些文档包含这些词 | 主键/索引值的精确定位 |
| 结构特征 | 不可变段 + 压缩 postings | 可变页 + 原位更新 |
| 更新代价 | 删旧建新（贵） | 原位更新（便宜） |
| 擅长 | 模糊、多词、相关性排序 | 精确、范围、事务 |

**介质与问题的分野**（Redis 跳表篇的同款结论）：检索问题是「批量按词找」用倒排，事务问题是「单点精确改」用 B+ 树——两个结构各自服务各自的问题域。

## 五、典型场景与误区

**典型场景**：商品标题搜索（分词 + 倒排 + BM25）、日志检索（时间过滤 + 关键词，倒排与列存协同）、标签圈人（term 查询本质就是 postings 交并）。

**误区与不适用**：① 把 ES 当 KV 用——点查走倒排反而绕路，_exact_ 精确值场景keyword 字段可但不是 ES 的主场；② 忽视分词对索引的影响——上下游分工不清：高频更新的活留给数据库，检索副本才进 ES，这不是 ES 的短处而是分工——**「搜不到」多数是分词问题不是索引问题**（中文没分好词，倒排里就没有那个 term）；③ 频繁更新文档——段模型的更新是删除重建，高频更新字段应考虑拆索引。

## 六、你们可能会问

**Q1：文档 ID 也是倒排的一部分吗？**
docID 是 postings 的主体——Lucene 内部把外部文档 ID 映射为段内自增 docID（0 起连续），压缩与跳表都建立在这个连续性上。

**Q2：过滤条件（term/range）也走倒排吗？**
keyword 精确值走倒排 postings，数值/日期范围走 **BKD 树**（另一类专用索引结构）——「倒排」是主角但不是唯一，Lucene 为不同数据类型配了不同的索引结构。

**Q3：为什么删除不直接物理删？**
段不可变是性能与复杂度之间演进出的取舍：物理删就要可变结构，Lucene 用「标记删除 + 段合并回收」换取检索端的极致稳定。
