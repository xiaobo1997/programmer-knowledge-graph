## 核心观点

作者用六个篇章把"大型软件系统"切成六层视角，越往后越靠近运维与基础设施：

1. **演进中的架构**——用原始分布式 → 单体 → SOA → 微服务 → 后微服务 → 无服务的整条历史，强调"架构没有银弹，是被业务量倒逼出来的"。
2. **架构师的视角**——远程调用（REST 设计）、事务处理（本地/全局/共享/分布式）、透明多级分流（缓存/CDN/负载均衡）、架构安全性（认证/授权/凭证/保密/传输/验证）。
3. **分布式的基石**——Paxos/Multi-Paxos/Gossip 共识、服务发现/网关/客户端 LB、流量治理（容错、限流）、可靠通讯（零信任）、可观测性（日志/链路追踪/聚合度量）。
4. **不可变基础设施**——以容器代替机器、CNI 网络、CSI 持久化、Kubernetes 调度、服务网格（Istio 落地）。
5. **技术方法论**——微服务的目的、前提、边界、治理。
6. **附录**——Docker CE、Kubernetes、Istio、Elastic Stack、Prometheus 的实操部署。

几个明确的主张：

- **没有完美的架构，只有权衡**。每一次架构演进都是解决上一阶段的痛点。
- **微服务是手段不是目的**。"微服务需要的条件"那一章几乎是必读——盲目拆服务只会把单体复杂度原样移植到分布式里。
- **透明多级分流**是性能与可用性的"免费午餐"，但要在客户端、CDN、网关、服务端**分层协作**，单点优化很容易被相邻层抵消。
- **可观测性是分布式系统的"内功"**——没有日志/Trace/Metrics 三件套就上线微服务，等于在黑屋子里开车。
- **云原生不是 Kubernetes**——Kubernetes 只是调度器，云原生还包含服务网格、不可变基础设施、可观测性、声明式 API 等整体理念。

作者配套写了若干 demo 工程（Spring Boot 单体、Spring Cloud 微服务、K8s 微服务、Istio 服务网格、AWS Lambda 无服务），同一业务需求对应多种架构实现，文档与代码互相印证。

## 个人思考

> 这里放的是**我对作者的认同/怀疑/补充**，不是书的观点复述。

- **认同"演进"叙事**——技术选型要看阶段。我服务过的支付业务，初期用 Spring Boot 单体撑起了 6 位数 TPS，后面才拆通道服务。**用未来 3 年的复杂度去设计当前 3 个月的项目，是最大的浪费**。
- **怀疑"全面拥抱云原生"**——作者强调云原生是趋势没错，但**没有给出小团队拒绝 K8s 的具体判据**。我更倾向把 K8s 当成"运维规模化"的答案，而不是"工程能力"的答案。一个 3 人小团队上 K8s，认知成本会比省下的运维成本还高。
- **补一笔"权衡"框架**——读完全书最缺的是一张判断表：什么时候不拆？什么时候非拆不可？我目前用的清单是"团队规模 > 单体认知负担 > 故障域隔离 > 团队协作成本"，四选二总比"全都要 K8s"更稳。
- **关于可观测性**——作者讲了"是什么"，但我工作中踩到的坑是**"日志和 Metrics 用一套思路"**——日志是叙事、Metrics 是探针，混着写会让告警系统变成废纸。这一点之后单独写一篇[可观测性的笔记](/)展开。
- **关于 Paxos**——这一章对没有分布式训练的人来说门槛较高。我自己读两遍才理顺"提案/接受/学习"三段，建议至少配合 Raft 算法动画一起看。
- **关于服务网格**——作者对 Istio 用了大量篇幅，但 Service Mesh 2024-2026 有新的方向（eBPF、Sidecarless），书的结论仍在主流，但具体实现已经走样。我会单独追一份 [Cilium/eBPF 的笔记](/)。

## 行动清单

接下来 30 天可以做的事，按 ROI 排序：

- [ ] **重读"透明多级分流"一章**，对照公司项目画一张端到端的请求链路图（用户 → 网关 → 风控 → 业务 → 收单通道 → 清算），标注每一层用的什么缓存、什么超时。这样下次线上出问题知道往哪里看。
- [ ] **把"事务处理"那一章翻译成项目内规**——本地事务、共享事务、分布式事务各自的适用场景，落到团队 wiki 里。和 [java-get-offer-interview](https://github.com/xiaobo1997/java-get-offer-interview) 的"交易状态码"那一节互补。
- [ ] **用作者的 demo 工程做基线对比**——Spring Boot 单体版和 Spring Cloud 微服务版同一个业务量级下资源占用差异。比听讲座有用。
- [ ] **跑通附录中的 K8s 部署脚本**——找一个开发测试集群，把 Prometheus + Elastic Stack + Istio 全链路装一遍，体会"不可变基础设施"的真实运维心流。
- [ ] **写下自己的"微服务判据"**，放进团队 ADR（Architecture Decision Record）：
  - 单体触达多少 LOC 启动考虑拆？
  - 团队规模几个人以上才值得拆？
  - 单次发布阻塞超过 X 分钟才值得拆？

## 工程实践连接

书中观点直接对应到日常工程的几个抓手：

- **kebab-case 命名 + cleanUrls**：VitePress 的文章 URL 设计本身就是"透明多级分流"的入口层实践。
- **首页 hero + features + 路线表**：信息架构的"分层"——首屏只放 1 个 CTA，其余卡片在不同入口被点击时浮现。
- **本地全文搜索（Pagefind/MiniSearch）**：把"LMS（Lightweight Minisearch）"换成本地搜索引擎，避免把搜索功能外包给第三方。
- **CI/CD 自动部署**：对应"不可变基础设施"——构建产物与运行环境分离，触发一次 push 就跑完 lint → test → build → deploy。
- **CI 失败自动回滚**：对应"可观测性"+"治理"——失败能 5 秒看见，5 分钟回滚。
