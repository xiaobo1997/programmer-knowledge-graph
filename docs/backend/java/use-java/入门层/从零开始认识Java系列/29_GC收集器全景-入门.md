# GC 收集器全景

> **一句话摘要**：收集器演进 = 停顿时间的四代压缩——**Serial（秒级全停）→ Parallel（吞吐优先多线程）→ CMS（并发标记但碎片致命，已死）→ G1（Region 化可预测停顿，JDK 9+ 默认）→ ZGC（着色指针并发整理，亚毫秒停顿）**；选型的分水岭是「堆大小 × 延迟要求」：小堆吞吐型选 Parallel、通用默认 G1、大堆低延迟选 ZGC。

> **本文核心**：机制链 = **停顿来源 = 根扫描 + 引用更新 + 搬移整理 → 历代收集器都在「并发化这些环节」：CMS 并发标记（但清除留碎片）→ G1 Region 化（把整堆整理拆成 Region 级增量复制）→ ZGC 着色指针（把「搬移时改引用」变成并发读屏障自愈）→ 选型决策树：堆 <4G Parallel 也行 / 通用 G1 / 大堆低延迟 ZGC**——收集器之争的本质是「停顿预算」之争。

前置阅读：[垃圾回收算法](./28_垃圾回收算法-入门.md)（三算法与分代组合）。参数与日志的落地见[JVM 调优与排查工具](./32_JVM调优与排查工具-入门.md)。

## 1. 背景：收集器演进的唯一主轴

业务对 GC 的诉求从「能回收」到「快回收」再到「不停顿」——**停顿（STW）时间从秒级压到亚毫秒**是四代收集器的唯一主轴。技术路线也随之进化：从「整堆 STW 串行回收」到「并发标记」到「Region 化增量」再到「并发整理（着色指针/读屏障）」。每个时代的旗舰收集器，都是当期「并发技术能力」对「停顿三角」的一次重新定价。

## 2. 核心机制：五代收集器的机制对比

```mermaid
flowchart LR
    S[Serial: 单线程 整堆STW<br/>小内存简单场景] --> P[Parallel: 多线程 STW<br/>吞吐优先 JDK8默认]
    P --> CMS[CMS: 并发标记清除<br/>低停顿先驱 碎片致命 已废]
    CMS --> G1[G1: Region化<br/>可预测停顿 JDK9+默认]
    G1 --> Z[ZGC: 着色指针<br/>并发整理 亚毫秒]
    style CMS fill:#ffcdd2
    style G1 fill:#c8e6c9
    style Z fill:#e3f2fd
```

- **Parallel（吞吐代）**：多线程并行回收，但全程 STW——「一次性把活干完」吞吐最高（STW 总时间占比最低）；适合批处理/后台计算（不在乎单次停顿）。JDK 8 默认。
- **CMS（并发先驱，已死）**：四阶段（初始标记 STW 短 → 并发标记 → 重新标记 STW 短 → **并发清除**）——标记与清除与业务并发，停顿显著降低；**致命伤**：标记-清除算法的碎片化 → 大对象分配失败 → 退化为 Serial Old 全停整理（Concurrent Mode Failure）——「低延迟先驱死于碎片」的历史教训（JDK 14 移除）。
- **G1（Region 代，JDK 9+ 默认）**：把堆切成等大 Region（1-32MB）——每个 Region 动态扮演 Eden/Survivor/Old/Humongous；回收以 **Region 为单位挑「垃圾最多的 Region」优先回收（Garbage First 之名由来）**——「整堆整理」变成「Region 级复制」（复制算法在 Region 尺度复活）。可预测停顿：`-XX:MaxGCPauseMillis=200` 设停顿目标，G1 按目标决定每次回收多少 Region。大对象（Humongous）跨 Region 是它的软肋之一。
- **ZGC（亚毫秒代）**：**着色指针**——64 位指针的几个 bit 存 GC 元数据（三色标记状态），读屏障在「读取引用时」自愈（对象被搬移则更新引用）——**搬移整理全程与业务并发**，STW 只剩极短的根扫描（<1ms 量级，与堆大小无关）。代价：吞吐略降（读屏障开销）与内存多占（着色视图）。JDK 21 引入分代 ZGC（JEP 439）补上吞吐短板。
- **Shenandoah**：与 ZGC 同代的低延迟路线（RedHat 主导）——转发指针（Brooks Pointer）实现并发整理；机制与 ZGC 异曲同工，生态在国内相对小众。

## 3. 落地实践：选型决策与参数基线

```text
选型决策树:
  堆 < 4G 且吞吐优先(批处理/后台)      -> Parallel
  通用 Web 服务 / JDK 9+              -> G1(默认, MaxGCPauseMillis 设目标)
  大堆(>16G) + 低延迟敏感(交易/网关)   -> ZGC(21+ 配分代)
  JDK 8 驻留                          -> Parallel(默认) 或 CMS(存量)
基线参数(G1 示例):
  -Xms=-Xmx 等值                      # 避免动态伸缩抖动
  -XX:MaxGCPauseMillis=100            # 停顿目标(默认200)
  -Xlog:gc*,gc+heap=debug             # 日志可观测
  -XX:+HeapDumpOnOutOfMemoryError     # 终局证据
```

三条纪律：① **先观测后换收集器**——GC 日志是唯一证据（停顿分布/频率/回收量），「听说 ZGC 快就换」是事故预备役；② **一变量原则**——换收集器时不动其他参数（归因清晰）；③ **升级 JDK 顺带升级收集器**（8 的默认是 Parallel、9+ 是 G1、21+ 可 ZGC）——「升级即换 GC」的行为差异要主动认知。

## 4. 生产视角：收集器事故的形态

- **CMS 的碎片死法**：运行数月后 Concurrent Mode Failure——碎片导致大对象放不下，退化为 Serial Old 全停整理（秒级到分钟级停顿）。历史事故的标本；G1 的 Region 化就是为它设计的解药。
- **G1 的 Humongous 大对象陷阱**：超大对象（>Region 一半）独占连续 Region 且晋升即入老年代——大对象风暴导致 Region 耗尽 / 停顿目标失效。整改：拆大对象 / 调大 Region（-XX:G1HeapRegionSize）/ 治理大对象的生成源头。
- **ZGC 换来的吞吐下降被忽视**：读屏障的代价让吞吐降几个百分点——低延迟不是免费的（延迟换吞吐的定价）；吞吐敏感场景对比压测后再定。
- **MaxGCPauseMillis 设得过小的反噬**：目标 20ms → G1 每次只回收极少 Region → 回收速度追不上分配速度 → 反而触发 Full GC。停顿目标是「与分配速率平衡的目标」，不是越小越好。

## 5. 主流系统怎么做：行业选型现状

| 业界形态 | 收集器选择 | 机制原因 |
|---|---|---|
| JDK 8 存量 | Parallel / CMS 存量 | 升级未至，默认即用 |
| 通用 Web（JDK 11/17） | G1 默认 | 通用平衡，停顿目标可调 |
| 交易/网关大堆 | ZGC（21+ 分代） | 亚毫秒停顿的价值 > 吞吐小幅损耗 |
| 大数据/批处理 | Parallel | 吞吐最大化，停顿无关业务 |

规律：**「JDK 版本决定可选集」是选型第一约束**（ZGC 需 13+/成熟建议 21+；G1 需 9+ 默认）——升级 JDK 的隐性收益之一就是收集器代际红利。

## 6. 典型场景

- **大促备战**（交易级）：交易核心堆大、延迟敏感——ZGC 分代 + 压测对齐停顿与吞吐。
- **批处理平台**（吞吐级）：Parallel + 大堆——单次停顿长但占比低。
- **存量 8 升级 17**（迁移级）：默认收集器 Parallel→G1 的行为变化纳入升级清单（第 2 篇的联动项）。

## 7. 与相邻概念的区别

- **收集器 vs 算法**：CMS/G1/ZGC 都是「标记-清除/整理」思想的产品化——算法稳定（28 篇），收集器轮替（本篇）。
- **G1 的 Region vs 传统分代**：Region 是「物理自由、逻辑分代」（Region 动态扮演代角色）——传统分代的物理固定布局被解耦。
- **ZGC vs Shenandoah**：着色指针 vs 转发指针——同为并发整理的两条技术路线（OpenJDK 双实现）；选型更多受发行版与支持生态影响。
- **本篇 vs 调优篇（32 篇）**：本篇是「选谁」；32 篇是「怎么调与怎么排障」——选型与调优的分工。

## 8. 常见误区与不适用

- **「新收集器全面优于旧收集器」**：ZGC 的吞吐损耗、G1 在小堆上的开销——「新」是能力扩展不是全面替代；按「堆大小 × 延迟预算」选。
- **「G1 参数 MinGCPauseMillis 越小越好」**：目标与分配速率失衡反而退化（第 4 节）——目标值要匹配业务的真实预算。
- **「换 ZGC 就不用管内存泄漏」**：收集器只管「不可达对象的回收」——可达的泄漏（27 篇）任何收集器都无能为力。
- **「CMS 还能用」**：JDK 9 废弃、14 移除——新版本无此选项；存量 8 的 CMS 是迁移的理由之一。
- **不适用**：微服务小堆（几百 MB 堆，G1/ZGC 优势不显，Serial/Parallel 也可）；离线分析（停顿无关）；非堆内存（本篇只管 GC 堆——元空间/直接内存 26 篇）。

## 9. 你们可能会问

- **G1 的「可预测停顿」怎么实现？** 回收成本模型：按历史数据估算每个 Region 的回收价值/成本，停顿目标反推本轮回收多少个 Region——「按预算做回收计划」的机制。
- **ZGC 的着色指针怎么做到并发搬移？** 指针本身带 GC 状态位——读到「已搬移」状态的引用时，读屏障自愈（取新地址并修正）——「改引用的成本分摊到每次读」的设计。
- **什么时候该从 G1 换 ZGC？** 三个信号：停顿目标压到百毫秒以下仍不达标、堆 16G+ 且停顿随堆增长失控、GC 抖动影响业务 SLO——换前拿 GC 日志量化「G1 的现实停顿分布」。
- **G1 的 Humongous 对象怎么治理？** 源头拆分（大集合/大数组化整为零）+ Region 尺寸调大（G1HeapRegionSize）+ 监控 Humongous 占用——三管齐下，源头第一。
- **怎么对比两个收集器？** 同压测模型下对比四指标：停顿分布（P99/P999）、吞吐、CPU 开销、尾延迟抖动——JMH 不适合（GC 是全进程行为），用全链路压测 + GC 日志分析（GCEasy 类工具）。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：收集器四代演进 = 停顿的四次重新定价——Parallel 吞吐、CMS 碎片死于己、G1 Region 化可预测（默认）、ZGC 着色指针亚毫秒；选型按「堆大小 × 延迟预算」决策树走。
- **链条复述**：STW 来源 → 各代并发化路线 → CMS 死于碎片的教训 → G1 的 Region/成本模型/停顿目标 → ZGC 着色指针并发整理 → 决策树 + 基线参数 + 三纪律。
- **失效点与边界**：小堆新收集器优势不显；换收集器不治泄漏；停顿目标失配会反噬。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 五代收集器机制对比 + 选型决策树 + 事故形态 |
| Why | 停顿预算是收集器选型的唯一主轴 |
| When | 新服务 GC 选型、停顿不达标治理、JDK 升级评估 |
| Where | 全堆（Region/着色指针） |
| How | GC 日志量化 → 决策树选型 → 一变量切换 → 压测验证 |

💡 **实战提示**：先观测后换器；停顿目标匹配分配速率；Humongous 治源头；升级 JDK 注意默认收集器变化。

**开放问题**：分代 ZGC（21）吸收了分代假设——低延迟与分代的合流是否意味着 G1 的中期使命完成，未来 LTS 默认会直接是分代 ZGC 吗？

**决策（何时用）**：默认跟随 JDK（9+ G1 / 21+ 评估 ZGC）；大堆低延迟推荐 ZGC 分代；推荐「GC 日志量化报告」作为任何收集器切换的前置交付物。

**Trade-off（代价与反方案）**：ZGC 用「吞吐小幅损耗 + 内存多占」换「亚毫秒停顿」；G1 用「Region 元数据与写屏障」换「可预测停顿」；Parallel 用「长停顿」换「最高吞吐」——收集器选型 = 「停顿预算」在产品货架上的采购决策，预算多少买什么。

**演进视角**：从 Serial 到 ZGC 的 25 年，是「STW 从秒到亚毫秒」的百倍压缩史；CMS 的死亡与 G1 的登基、ZGC 的分代化——每一次更替都由「并发技术突破 + 上一代的结构性死穴」共同推动；下一代的竞争点已在酝酿（分代成熟度/更低的屏障成本/AOT 协同），主轴仍是那一个词：停顿。
