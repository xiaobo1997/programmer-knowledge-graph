# 字符串与常量池

> **一句话摘要**：String 的不可变设计（final char/byte 数组 + 无暴露修改口）是字符串一切行为的根源——安全（作 Map 键/常量池复用）、性能（哈希缓存）、共享（常量池 intern）全由此来；拼接走 StringBuilder、常量池在堆上（7+）、intern 是双刃——本篇把「最熟悉的类型」的机制讲穿。

> **本文核心**：机制链 = **不可变（final 数组 + final 类 + 防御性设计）→ 三大红利（哈希缓存/线程安全/常量池共享）→ 拼接编译期常量折叠、运行期自动 StringBuilder、循环内必须手动 SB → 字面量进常量池（堆，JDK 7 起）、intern 返回池内引用**——字符串性能问题的 90% 是「循环拼接」与「大字符串驻留」两个坑。

前置阅读：[对象与类](./3_对象与类-入门.md)（final/不可变设计）。字符串驻留的内存代价在[运行时内存区域](./26_运行时内存区域-入门.md)展开。

## 1. 背景：String 为什么设计成不可变

String 是 Java 里少数「几乎全 final」的类（final 类不可继承 + 内部数组 final 私有 + 无修改方法）。这个设计的动机三连：

1. **安全**：String 是最通用的参数载体（文件路径、网络地址、数据库连接串、类名）——若可变，一个方法拿到引用后偷偷改内容，安全检查（路径校验）与实际使用（打开文件）之间出现 TOCTOU 漏洞；
2. **哈希缓存**：不可变 → hashCode 可算一次缓存（`hash` 字段懒计算）——String 作为 HashMap 键的高频使用因此高效；
3. **共享与常量池**：不可变才可安全共享——字符串常量池让相同字面量全 JVM 一份（内存经济 + 语义统一：`==` 可判等）。

代价是「每次修改都是新对象」——这换来 StringBuilder 这个配套生态。

## 2. 核心机制：拼接、常量池与 intern

```mermaid
flowchart TD
    CONCAT[三种拼接形态] --> A[编译期常量折叠<br/>'a'+'b' 直接合成 'ab' 进常量池]
    CONCAT --> B[普通运行期拼接<br/>编译器自动 StringBuilder.append]
    CONCAT --> C[循环内拼接<br/>每轮 new StringBuilder => O(n^2) 事故区]
    B --> SB[手动 StringBuilder: 同一实例追加 内部数组扩容]
    POOL[字符串常量池] --> P1[JDK 6: 永久代 -> 易 OOM]
    POOL --> P2[JDK 7+: 堆内 -> 可 GC 可调]
    POOL --> P3[字面量自动入池; new String 强制堆上新对象]
    INTERN[intern() ] --> I1[池里有: 返回池内引用]
    INTERN --> I2[池里没有: 入池并返回该引用]
```

- **三种拼接的性能差异**：编译期常量折叠零成本；运行期 `a + b` 编译器自动用 StringBuilder（单次拼接无所谓的）；**循环内拼接是事故区**——每轮循环编译器都新建一个 StringBuilder（编译器只对单表达式优化），n 轮 = O(n²) 的数组复制，百万级循环秒级卡顿。纪律：循环内拼接必须手动提 StringBuilder 到循环外。
- **常量池的演进**：JDK 6 在永久代（大小受限易 OOM）；**JDK 7 起移入堆**（可 GC、可调）——「String 占用永久代」的老知识要更新。
- **`==` vs equals**：字面量（编译期确定）进池后 `==` 可判等（同一池内引用）；`new String` 强制堆上新对象（`==` 为 false）——**工程铁律：字符串判等永远 equals**，`==` 只在「明确理解常量池语义」的场景（如与字面量比）可用。
- **intern 的价值与陷阱**：大量重复长字符串（如相同的状态描述、外部字典值）intern 后共享一份——省内存；但池查询有开销 + JDK 6 的池在永久代会 OOM（历史事故），现代用法是「量大且高度重复」才考虑，且依赖 G1 的字符串去重（`-XX:+UseStringDeduplication`，G1 专属）做自动版。

## 3. 落地实践：字符串的工程纪律

1. **循环拼接手动 StringBuilder**：预估容量更佳（`new StringBuilder(预估长度)` 免多次扩容复制）。
2. **判等永远 equals，比较前判空**（`Objects.equals(a, b)`）——NPE 免疫。
3. **比较内容排序用 compareTo**（字典序），大小写不敏感场景用 `CASE_INSENSITIVE_ORDER` 或统一转大写——locale 敏感场景（土耳其语 i 问题）用 `Locale.ROOT`。
4. **分隔拼接用 String.join / Stream joining**——比手工 append 可读且不易漏分隔符。
5. **格式化注意成本**：`String.format` 可读性好但慢（解析格式串）——日志占位符用 `{}`（SLF4J 懒求值），热路径拼接用 StringBuilder。

## 4. 生产视角：字符串事故的形态

- **循环拼接的接口超时**：导出功能拼万行 CSV 用 `+=`——O(n²) 卡死。整改：StringBuilder 提外 + 预估容量，或流式写出。
- **大字符串驻留堆压**：全量报文/大 JSON 存 String 长期持有（缓存里）——堆被大 char/byte 数组占据（String 内部数组，JDK 9 起是 byte[] 紧凑编码）。整改：短期化引用/分片/按需重取。
- **常量池引发的 == 假等**：两处代码一处字面量一处 `new String`，`==` 判等在测试环境碰巧真（都走池）生产环境假——判等纪律 equals 是唯一安全解。
- **split 的正则陷阱**：`split(".")` 按正则解释，`.` 匹配任意字符返回空数组——正则元字符要转义或用 `split("\\.")`/`StringUtils` 重载。
- **subString 的内存粘连（历史）**：JDK 6 的 subString 共享原数组——大串截小串导致大数组滞留；JDK 7u 起复制修复——老版本知识在阅读旧代码/旧文章时仍需辨识。

## 5. 主流系统怎么做：字符串的生态演进

| 机制 | 版本/载体 | 要点 |
|---|---|---|
| 紧凑字符串 | JDK 9（JEP 254） | 内部 char[] 改 byte[]（Latin-1 单字节省一半内存） |
| 字符串去重 | G1（JDK 8u20+） | GC 时自动去重相同内容，替代手工 intern 的主流方案 |
| 文本块 | JDK 15 正式 | 三引号多行字符串——JSON/SQL 模板可读性革命 |
| 字符串模板 | 预览阶段摇摆 | JDK 21 预览后撤回重设计——「未转正特性不进生产」的纪律案例 |

规律：**字符串的性能与表达力持续演进（紧凑/去重/文本块），不可变内核三十年不动**——这条「内核稳定 + 外围增强」的演进模式与 JVM 一致。

## 6. 典型场景

- **Map 键**（高频级）：String 作键——不可变保证哈希稳定 + 哈希缓存提速。
- **日志与报文拼接**（热路径级）：日志占位符懒求值 + StringBuilder 循环外提。
- **协议报文**（网络级）：报文解析注意新对象产生量——大流量网关用零拷贝/ByteBuf 类方案（Netty，第 34-35 篇的地基）替代频繁 String 化。

## 7. 与相邻概念的区别

- **String vs StringBuilder vs StringBuffer**：不可变 / 可变非线程安全（主流）/ 可变线程安全（synchronized，历史遗留——现代并发场景用别的同步策略，很少选它）。
- **== vs equals vs intern**：引用判等 / 内容判等 / 入池并返回池引用——三者是三个不同的语义层次，混用是 bug 之源。
- **String vs char[]（密码场景）**：String 不可变会驻留到 GC（密码长期滞留内存），char[] 用完可显式清零——密码载体选 char[] 的安全惯例。
- **本篇 vs JVM 篇**：常量池的运行时定位（元空间/堆）与字符串去重的 GC 联动在组 5 展开——本篇管类型语义，组 5 管运行时。

## 8. 常见误区与不适用

- **「字符串拼接一定要手动 StringBuilder」**：单次拼接编译器已优化——只有循环/超长链式拼接才必须手动；「一刀切手动」牺牲可读性。
- **「常量池在永久代」**：JDK 7 起在堆——老文章的知识时效要核对版本。
- **「intern 能省内存就多用」**：池管理有成本、字段分布不均时收益有限——现代优先 G1 去重，intern 退居特定场景。
- **「String 是 final 的所以线程安全没问题」**：String 自身线程安全正确；但「持有 String 的容器/字段」的并发安全是另一层——不要混淆对象与持有者。
- **不适用**：超高频修改场景（直接用 char[]/byte[] 或专用缓冲）；密码存储（char[]）；超大文本处理（流式，别整段 String 化）。

## 9. 你们可能会问

- **`new String("abc")` 创建几个对象？** 经典题的正确答案是「看情况」：字面量 "abc" 若池中已有则只 new 一个堆对象；池中没有则池内一个 + 堆一个——背「两个」不如理解「池与堆是两个空间」。
- **hashCode 缓存怎么验证？** 反射看 String 的 hash 字段（首次调用前为 0，调用后缓存）——机制可观测而非背诵。
- **为什么 JDK 9 改 byte[]？** Java 世界大量字符串是 Latin-1（单字节可表示）——char（2 字节）浪费一半内存；byte[] + 编码标记字段按内容自适应（Compact Strings，JEP 254）。
- **文本块与普通字符串的差异？** 内容语义相同（都编译成 String），文本块只改变「源码书写形态」（多行 + 缩进管理 + 转义减少）——编译期处理，运行时无区别。
- **字符串模板为什么被撤回？** JDK 21 预览的字符串模板在 23 被撤回重设计——新特性「预览 ≠ 可用」，生产紧跟 LTS 已正式特性是纪律（第 2 篇的版本纪律在此落点）。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：String 不可变（final 类 + final 数组）→ 安全/哈希缓存/常量池共享三大红利 → 拼接单次免费循环付费、判等永远 equals、intern 被 G1 去重取代为主流。
- **链条复述**：不可变设计 → 常量池（堆内，JDK 7+）→ 三种拼接形态 → 编译折叠/自动 SB/循环手动 SB → 紧凑字符串与去重的现代演进。
- **失效点与边界**：超高频修改不适用；密码用 char[]；超大文本流式处理。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 不可变机制 + 常量池 + 三种拼接 + 现代增强 |
| Why | 安全/共享/性能三大动机造就不可变设计 |
| When | 拼接性能、判等 bug、字符串内存治理 |
| Where | 堆与常量池（JDK 7+ 都在堆） |
| How | 循环 SB + equals 判等 + join/format 分场景 + 去重替代 intern |

💡 **实战提示**：循环拼接手动 SB 且预估容量；判等 Objects.equals；split 转义正则；密码用 char[]；G1 去重开起来。

**开放问题**：字符串模板撤回重设计说明「语言级模板」仍在寻找正确形态——未来会用什么形态回来，会不会直接吸收 Kotlin/Python 的经验？

**决策（何时用）**：拼接场景按「循环与否」选型；判等场景一律 equals；驻留场景优先 G1 去重；推荐「字符串纪律五条」进 code review 清单。

**Trade-off（代价与反方案）**：不可变用「修改即新对象」换「安全/共享/缓存」；反方案——可变缓冲（StringBuilder/char[]，管修改性能）、字符串池手工 intern（省内存，代价是池语义复杂度）——不可变内核 + 可变工具的搭配是权衡的最终答案。

**演进视角**：String 从 char[] 到 byte[]（JDK 9 紧凑化）、从永久代池到堆池（JDK 7）、从手工 intern 到 G1 自动去重——「不可变内核 + 运行时持续优化」的组合让最古老的类型保持现代性；字符串的演进史就是 JVM 演进的缩影。
