# 接口与抽象类

> **一句话摘要**：接口是「纯行为契约」（可多实现、无状态），抽象类是「半成品骨架」（单继承、带状态与实现）——Java 8 之后接口长出 default/static 方法、Java 9 长出 private 方法，两者的边界从「能力差异」收敛为「**契约 vs 骨架**」的语义差异；选型一句话：定义「能做什么」用接口，复用「怎么做的一半」用抽象类。

> **本文核心**：机制链 = **接口 = 契约（多实现 + default 进化能力）→ 抽象类 = 骨架（单继承 + 字段状态 + 构造器）→ default 方法解决「接口演进破坏实现类」→ 函数式接口（单抽象方法）是 Lambda 的类型载体**——三者的协作形态：接口定契约、抽象类给骨架、函数式接口接行为。

前置阅读：[继承与多态](./4_继承与多态-入门.md)（动态绑定/default 冲突仲裁的机制地基）。

## 1. 背景：接口为什么是 Java 解耦的主力

抽象类早于接口的「能力进化」存在——但行业实践持续投票给接口：JUC 全是接口+实现（Executor/ExecutorService）、JDBC 是接口体系、Spring 依赖注入面向接口。原因在耦合度：**接口实现只承诺行为（无实现耦合），抽象类继承连状态与实现一起继承**（上一篇的脆弱基类问题在抽象类上同样存在）。Java 8 给接口补上 default 方法后，「接口不能带实现」的最后劣势也消解了大半——抽象类的生存空间进一步收缩到「需要字段状态与构造逻辑」的骨架场景。

## 2. 核心机制：三者的能力矩阵与协作

```mermaid
flowchart TD
    I[接口 interface] --> I1[多实现: 一个类 implements N 个]
    I --> I2[成员: 抽象方法 + default + static + private(9+)<br/>无常量外状态 public static final 常量]
    I --> I3[演进: default 加方法不破坏实现类]
    AC[抽象类 abstract class] --> A1[单继承: 类层次占位]
    AC --> A2[成员: 一切皆可 含字段状态与构造器]
    AC --> A3[定位: 骨架复用 模板方法的载体]
    FI[函数式接口<br/>@FunctionalInterface] --> F1[恰好一个抽象方法]
    F1 --> F2[Lambda 的目标类型<br/>方法引用/行为参数化]
    I3 --> W[协作: 接口定契约 -> 抽象类给默认骨架 -> 实现类填空]
```

- **default 方法解决什么？** 接口演进困境——8 之前接口加方法 = 所有实现类编译爆炸；default 让接口「加方法带默认实现」而不破坏存量（`Collection.sort` 的默认实现、`Iterator.remove` 的默认抛异常都是这个机制）。多实现冲突时子类必须显式仲裁（`A.super.method()`）——冲突不自动解决，逼设计者表态。
- **接口的成员纪律**：字段全是 `public static final`（常量，无实例状态）——接口「无状态」的语法表达；Java 9+ 的 private 方法服务 default 之间的内部复用。
- **抽象类的不可替代点**：字段状态（模板流程中的中间状态）、构造器（骨架初始化）、protected 成员（受控的扩展面）——「需要在多个方法间共享演进状态」时接口无解，抽象类登场。
- **函数式接口**：恰好一个抽象方法的接口即函数式接口（`@FunctionalInterface` 校验）——它是 Lambda 的类型载体：`Comparator`/`Runnable`/自定义单方法接口都能接 Lambda。四大内建（Function/Consumer/Supplier/Predicate）覆盖绝大多数行为形状，先内建后自定义。

## 3. 落地实践：一次完整的协作设计

```java
// 1. 接口定契约(行为承诺)
public interface MessageSender {
    boolean send(Message msg);
    default boolean sendWithRetry(Message msg, int times) {   // default: 演进能力
        for (int i = 0; i < times; i++) {
            if (send(msg)) return true;
        }
        return false;
    }
    static MessageSender noop() {                             // static 工厂
        return msg -> true;
    }
}

// 2. 抽象类给骨架(共享状态与流程)
public abstract class AbstractBatchSender implements MessageSender {
    private final int batchSize;                              // 接口给不了的字段状态
    protected AbstractBatchSender(int batchSize) { this.batchSize = batchSize; }
    protected abstract boolean doSend(List<Message> batch);   // 受控扩展点
    @Override public boolean send(Message msg) {              // 骨架实现
        return doSend(List.of(msg));
    }
}

// 3. Lambda 接行为(轻量实现)
MessageSender urgent = msg -> channel.pushUrgent(msg);
```

分层清晰：**换实现频率高的行为放接口（多实现灵活）、跨实现共享的流程与状态放抽象类、简单行为直接 Lambda**。

## 4. 生产视角：选型失误的形态

- **常量接口反模式**：`interface Constants { int MAX = 100; }` 让实现类「继承」一堆常量污染 API 面——常量该放 final 工具类或枚举（Effective Java 第 22 条）。
- **该抽象类的地方硬上接口**：N 个实现各自复制一遍「批量拆分 + 重试 + 日志」流程——接口没有字段与构造器，流程复用无处安放，复制即漂移。
- **default 方法里藏业务状态依赖**：default 调用另一个抽象方法 A、假设 A 有某种语义——实现类重写 A 后 default 行为崩坏（default 与抽象方法的隐含契约）——default 内对「可能被重写的方法」的调用要按模板方法的脆弱性对待。
- **函数式接口过度抽象**：把 6 参数的巨型逻辑塞进自定义函数式接口——可读性归零；超过 2-3 个参数/复杂语义时回退普通接口 + 实现类。

## 5. 主流系统怎么做：生态用法对照

| 场景 | 生态选择 | 机制要点 |
|---|---|---|
| 行为契约 | JUC 的 Executor/Comparable | 接口 + 多实现 + Lambda 直接接入 |
| 骨架复用 | AbstractList/AbstractMap（JDK 集合骨架） | 抽象类实现接口的大部分，实现类只填空 |
| 接口演进 | Collection.sort/Iterable.forEach | default 加能力不破坏存量 |
| 行为参数化 | Function/Consumer/Predicate 四大件 | 函数式接口接 Lambda |

规律：**JDK 的「接口 + 抽象骨架实现类」双层结构（如 List 与 AbstractList）是教科书答案**——实现类继承骨架，绝大多数场景两层结构通吃。

## 6. 典型场景

- **服务扩展点**（框架级）：支付渠道/推送渠道多实现——接口 + Spring 注入。
- **算法骨架**（模板级）：导入导出/审批流固定流程——抽象类模板方法。
- **行为参数化**（函数级）：过滤条件/转换逻辑随调用变化——函数式接口 + Lambda。

## 7. 与相邻概念的区别

- **接口 vs 抽象类（语义层）**：能做什么（契约）vs 是什么（骨架）——is-a 的强类型归属用抽象类，can-do 的能力承诺用接口。
- **接口 vs 注解**：注解是元数据标记（无行为），接口是行为契约——注解常与接口配合（@Transactional 标记 + 接口代理）。
- **抽象类 vs 具体父类**：抽象类不可实例化（强制子类化）——「禁止直接使用的不完整骨架」语义；具体父类继承的风险（脆弱基类）上一篇已述。
- **本篇 vs SPI（Dubbo 特性层）**：接口是 SPI 的契约面（接口 + 实现 + 注册发现）——接口机制在生态扩展协议的应用。

## 8. 常见误区与不适用

- **「接口不能有实现」**：Java 8 起可以（default/static/9+ private）——这条老知识在代码评审里会误伤正确的演进设计。
- **「抽象类不能没有抽象方法」**：可以有全具体方法的抽象类（唯一作用 = 禁止直接实例化）——语义合法且有使用场景。
- **「一个类只能继承一个抽象类所以抽象类弱」**：单继承是语言决策（防菱形冲突），不是能力缺陷——能力的多样性由多接口承载，两者分工。
- **「接口字段能做实例状态」**：接口字段是 public static final 常量——想在「契约」里藏状态，是设计错位（状态归实现类）。
- **不适用**：无第二实现可能的私有工具（抽象是过度设计）；仅数据载体（record 优先）；单次使用的回调（Lambda 直接内联即可）。

## 9. 你们可能会问

- **default 方法能重写 Object 的方法吗？** 不能（toString/equals 不能以 default 形式出现在接口）——Object 是所有类的根，接口无法保证实现类的 Object 语义。
- **多接口 default 冲突怎么办？** 编译器拒绝，子类必须显式仲裁 `A.super.m()`——冲突不自动消解是刻意设计（设计者表态优于编译器猜测）。
- **抽象类可以没有抽象方法，接口可以有实现，那还分什么？** 分「单继承的骨架（带状态）」与「多实现的契约（无状态）」——能力趋同、语义与继承拓扑仍分明。
- **函数式接口必须有 @FunctionalInterface 吗？** 不必须（结构满足即 Lambda 目标），但注解强制编译器校验「恰好一个抽象方法」+ 文档表达——必写的低成本保险。
- **接口静态方法的作用？** 把「该接口的工具方法」收编进接口本身（`Comparator.comparing`/`MessageSender.noop`）——替代「XxxUtils 静态类」的散落，API 面更内聚。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：接口 = 无状态行为契约（多实现 + default 演进），抽象类 = 带状态骨架（单继承 + 模板方法），函数式接口 = Lambda 的类型载体——三者分工协作不竞争。
- **链条复述**：契约定能力 → 骨架给流程与状态 → default 保演进 → 函数式接口接行为 → 「接口 + 抽象骨架 + 实现填空」双层结构。
- **失效点与边界**：default 对「可能被重写方法」的调用仍是脆弱契约；接口字段只是常量；巨型函数式接口是反模式。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 能力矩阵（多实现/单继承/default/函数式）+ 协作形态 |
| Why | 解耦主力是接口；骨架复用靠抽象类；行为参数化靠函数式 |
| When | 扩展点设计、骨架流程复用、行为参数化 |
| Where | 框架 SPI、JDK 集合骨架、Lambda 目标类型 |
| How | 契约接口 → 骨架抽象类 → 填空实现 → 简单行为 Lambda |

💡 **实战提示**：四大函数式接口优先于自定义；default 与抽象方法的隐含契约要文档化；常量进 final 类或枚举不进接口；@FunctionalInterface 必写。

**开放问题**：接口能力持续增强（default/private/static）后，抽象类与接口的边界会不会彻底消失——「带构造器的接口」会是语言演进的下一站吗？

**决策（何时用）**：扩展点与跨实现契约推荐接口；共享流程与状态推荐抽象类骨架；推荐「JDK 双层结构」（接口 + AbstractXxx）作为团队 API 设计的默认模板。

**Trade-off（代价与反方案）**：接口抽象用「设计前置成本」换「解耦与演进能力」；反方案——直接具体类耦合（快，代价是替换困难）、继承复用（上一篇的脆弱基类）、全 default 接口（演进灵活，代价是契约语义稀释——接口该保持「最小承诺」）。

**演进视角**：接口从纯契约（1.0）到 default（8）到 private 方法（9）到 record 配套的密封契约（sealed 接口，17）——接口三十年从「薄」走向「有分寸的厚」；抽象类则从默认选择收缩为骨架专用，两个关键词的「势力范围」重新划界是 Java 设计演进最清晰的一条线。
