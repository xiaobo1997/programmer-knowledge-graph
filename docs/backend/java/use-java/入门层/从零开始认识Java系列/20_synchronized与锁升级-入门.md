# synchronized 与锁升级

> **一句话摘要**：synchronized 是 Java 内建的互斥原语——**基于对象头 Mark Word + Monitor（监视器）实现互斥与可见性双保证**；JDK 6 的锁升级把它的性能从「重量级」救回：无锁 → 偏向锁（单线程重复获取免同步）→ 轻量级锁（CAS 自旋）→ 重量级锁（内核互斥量），按竞争强度单向膨胀——本篇讲穿「对象的锁状态怎么存、怎么升级、什么时候直接用 ReentrantLock」。

> **本文核心**：机制链 = **synchronized 锁的是对象（不是代码）→ 锁状态存在对象头 Mark Word（无锁/偏向/轻量/重量 四态标记）→ 升级路径单向不可逆 → Monitor（monitorenter/exit + 等待队列）是重量级形态 → 兑现互斥 + happens-before（解锁-加锁可见性）双保证 → 高竞争/需要高级特性时换 ReentrantLock**——「锁」在 JVM 里是对象头里的几位状态位 + 一套膨胀协议。

前置阅读：[JMM 与 volatile](./19_JMM与volatile-入门.md)（解锁-加锁可见性规则）。ReentrantLock 的实现见[AQS 与 JUC 锁](./21_CAS与原子类-入门.md)与[22 篇](./22_AQS与JUC锁-入门.md)。

## 1. 背景：synchronized 的黑历史与翻身

JDK 1-5 时代的 synchronized 直接映射内核互斥量（重量级锁）——每次加锁/解锁都是系统调用，无竞争场景也付全价，「synchronized 慢」的印象由此而来。JDK 6 的锁升级改造（偏向/轻量级/自适应自旋）让它「无竞争时几乎免费、低竞争时自旋、真竞争才膨胀」——实测大幅回血，现代 Java 里 synchronized 是默认首选（Eff党也认可：能 synchronized 不用 Lock，除非需要高级特性）。

## 2. 核心机制：对象头、Monitor 与膨胀路径

```mermaid
flowchart TD
    OBJ[对象头 Mark Word<br/>64位: 锁状态位+hash+GC年龄+锁信息]
    OBJ --> S0[无锁: hash+分代年龄]
    S0 -->|首个线程进入| BIAS[偏向锁: 记录线程ID<br/>同线程再进只比对ID 零成本]
    BIAS -->|第二线程竞争| LW[轻量级锁: 栈上锁记录 CAS<br/>抢不到自旋一会儿]
    LW -->|自旋超限/第三线程| HW[重量级锁: Monitor<br/>mutex 内核互斥 阻塞挂起]
    S0 -->|直接多线程| LW
    NOTE[锁状态位: 每态的 Mark Word 布局不同<br/>升级单向不可逆(偏向撤销除外)]
```

- **锁的是对象不是代码**：`synchronized(obj)` / `synchronized` 方法（锁 this）/ static 方法（锁 Class 对象）——三把不同的锁；「锁错对象」是 synchronized 事故之王（想锁全局却 new 了对象、想锁实例却锁了 Class——粒度错配）。
- **偏向锁**：第一个获取的线程把「线程 ID」写进 Mark Word——之后同线程再进入只比对 ID（无 CAS 无同步）；第二线程竞争时偏向撤销（需要安全点，有成本）→ 升轻量级。**定位：无竞争的重复获取**（如单线程反复进 synchronized 块）。注：JDK 15 起偏向锁默认废弃（维护成本 > 收益，JEP 374）——现代版本直接走轻量级，学习它重在理解思想。
- **轻量级锁**：栈帧里造「锁记录」，CAS 把 Mark Word 换成指向锁记录的指针——成功即持有；失败则自旋一会儿（自适应自旋：上次成功就多转，失败率上就少转），自旋超限膨胀为重量级。定位：交替执行的低竞争场景。
- **重量级锁（Monitor）**：对象关联的 Monitor（C++ ObjectMonitor）——互斥量（mutex）+ 入队队列 + 等待队列；抢不到锁的线程内核挂起（不烧 CPU）——代价是挂起/唤醒的系统调用与切换。定位：真竞争长临界区。
- **双保证**：互斥（同一时刻一个线程）+ 可见性（解锁 happens-before 后续加锁，19 篇规则二）——synchronized 一揽子解决三难中的全部，代价是阻塞。

## 3. 落地实践：synchronized 的工程纪律

1. **锁对象固定且唯一**：常量对象 / this / Class——禁「锁新 new 的对象」（每次不同锁等于没锁）与「锁可变引用」（引用换向锁换向）。
2. **锁粒度最小化**：临界区只包共享状态操作——锁内调远程/IO 是性能事故之王（18 篇同源纪律）。
3. **锁选择与被保护资源一一对应**：多个无关资源用多把锁（或分桶锁）提高并发——「一把大锁」是并发度杀手。
4. **读写分离考虑 ReadWriteLock/StampedLock**：读多写少的共享结构（22 篇）。
5. **私有可能逃逸的对象作锁要谨慎**：锁对象被外部拿到 = 锁形同虚设；惯例 `private final Object lock = new Object()`。

## 4. 生产视角：锁的事故形态

- **锁错对象的假同步**：`synchronized (new Object())` 每次新锁——并发问题照旧发生且「代码看起来有锁」。评审铁律：锁对象必须 final 且语义唯一。
- **锁粒度过大的吞吐塌方**：整个方法 synchronized 而临界区只有一行共享操作——所有请求排队。整改：缩小临界区 + 分桶锁（按 key hash 分 N 把锁）或换 ConcurrentHashMap 思路。
- **锁内调远程服务的超时雪崩**：synchronized 块内调下游（正常 50ms，故障 5s）——所有线程堆积在锁上，上游线程池耗尽，故障放大三跳。锁内调远程是事故之王（18 篇纪律的锁版）。
- **死锁**：两个线程以相反顺序获取两把锁——jstack 直接报 Found one Java-level deadlock。预防：全局锁排序（按固定顺序获取）或 tryLock 带超时（ReentrantLock）。

## 5. 主流系统怎么做：锁的生态选型

| 场景 | 主流选择 | 机制要点 |
|---|---|---|
| 简单互斥 | synchronized | 默认首选（JIT 优化充分 + 语义清晰） |
| 高级特性 | ReentrantLock | 可中断/超时 tryLock/公平锁/多条件 Condition |
| 读多写少 | ReadWriteLock / StampedLock | 读写分离 / 乐观读（22 篇） |
| 计数 | AtomicLong/LongAdder | 无锁 CAS（21 篇） |
| 容器 | ConcurrentHashMap | 锁单桶（16 篇） |

规律：**synchronized 是默认，Lock 是「需要高级特性」时的升级选项**——可中断、超时、公平、多条件是 Lock 的四大独占能力。

## 6. 典型场景

- **单例懒加载**（模式级）：synchronized 方法或 DCL+volatile——锁的最小完整案例。
- **状态机流转**（业务级）：订单状态变更的临界区——锁 + 状态机校验的组合。
- **限流计数**（并发级）：简单场景 synchronized 计数，高并发换 LongAdder/Redis。

## 7. 与相邻概念的区别

- **synchronized vs ReentrantLock**：语法级（自动释放）vs API 级（手动释放必须 finally）；Lock 的四大高级能力（可中断/超时/公平/多条件）是选择依据；「忘了 unlock」是 Lock 的经典事故——简单场景 synchronized 更防呆。
- **偏向/轻量/重量 vs 公平/非公平**：前者是 JVM 内部膨胀阶段（对用户透明）；后者是 ReentrantLock 的语义选择（抢锁是否排队）——两个维度的概念，勿混。
- **锁升级 vs 锁粗化/锁消除**：升级是竞争膨胀；粗化（合并相邻锁块）与消除（逃逸分析证明无共享直接去锁）是 JIT 的另外两项锁优化（31 篇）。
- **本篇 vs AQS（22 篇）**：synchronized 是 JVM 内建（C++ ObjectMonitor）；ReentrantLock 是 Java 层 AQS 构建——两套实现，同一种语义（互斥+可见性）。

## 8. 常见误区与不适用

- **「synchronized 修饰方法锁的是方法」**：锁的是对象（this）或 Class（static）——「锁代码」的心智模型导致粒度误判。
- **「锁升级不可逆所以性能会持续下降」**：偏向锁的批量重偏向/撤销机制可部分恢复；且现代 JDK 已废弃偏向——「升级焦虑」不必有，按竞争现实评估。
- **「synchronized(this) 万无一失」**：this 锁对外可见（外部也可能 synchronized(this)）——私有锁对象更可控；「锁 this 被外人插队」是隐蔽的并发污染。
- **「volatile 可以替代 synchronized」**：volatile 无互斥——需要「检查再行动」的复合操作必须锁或 CAS（19 篇决策树的呼应）。
- **不适用**：锁内长 IO（先修结构再谈锁）；读多写少的共享结构（读写锁/不可变替换）；跨 JVM 互斥（分布式锁——单机锁管不了集群，见理论系列锁篇）。

## 9. 你们可能会问

- **为什么锁信息能存在对象头里？** Mark Word 的位布局按锁状态复用（无锁时存 hash+GC 年龄，偏向时存线程 ID，重量级时存 Monitor 指针）——「同一个字段多态复用」是空间设计的经典手笔。
- **自旋为什么比重挂起好？** 锁很快释放时，自旋（空转等）避免「挂起+唤醒」两次系统调用与切换——自适应自旋按历史成功率动态调整自旋次数。
- **偏向锁为什么被废弃（JEP 374）？** 现代应用的锁竞争模式变了（线程池多线程复用），偏向场景变少；而偏向撤销需要安全点（成本高）且代码维护复杂——「收益不抵维护」的理性退役。
- **怎么判断锁竞争是否激烈？** jstack 频繁 BLOCKED、JMC/JFR 的锁竞争事件（持锁时长/等待时长）、压测吞吐曲线拐点——「锁Monitor Enter 等待」指标是直接证据。
- **wait/notify 和锁的关系再确认？** wait/notify 挂在锁对象的 Monitor 上——必须在 synchronized 内调用（18 篇三铁律）；Monitor 的等待队列就是 wait 的栖身之所。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：synchronized 锁对象不锁代码——锁状态存在 Mark Word，按竞争单向膨胀（偏向→轻量自旋→重量 Monitor），互斥与可见性双保证；默认首选，高级特性换 ReentrantLock。
- **链条复述**：对象头 Mark Word 四态 → 升级路径 → Monitor 队列 → 双保证 → 锁对象纪律（final/唯一/粒度）→ 错锁与锁内 IO 两大事故。
- **失效点与边界**：偏向锁已废弃（JDK 15+）；锁内长 IO 是事故；跨 JVM 无效；final 类不可继承无关本题。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | Mark Word 四态 + 膨胀协议 + Monitor + 双保证 |
| Why | 互斥与可见性的内建一揽子方案 |
| When | 简单互斥、状态机临界区、单例 |
| Where | 对象头 Mark Word + Monitor（C++ 层） |
| How | 锁对象 final 唯一 → 粒度最小 → 锁内无 IO → 竞争激烈换 Lock |

💡 **实战提示**：锁对象 private final；锁内禁远程/IO；锁粒度最小化；死锁预防用全局锁排序。

**开放问题**：偏向锁退役、虚拟线程普及后，「锁」的未来形态是「单桶头 + CAS + 挂起队列」的合流——JVM 内建锁与 JUC 锁的边界会模糊到合并吗？

**决策（何时用）**：默认 synchronized；需可中断/超时/公平/多条件换 ReentrantLock；推荐「锁对象纪律 + 锁内无 IO」进评审红线。

**Trade-off（代价与反方案）**：synchronized 用「阻塞等待」换「简单与双保证」；轻量自旋用「烧 CPU」换「免挂起」；ReentrantLock 用「手动管理」换「高级特性」；大锁换小锁/分桶锁用「复杂度」换「并发度」——锁设计就是「正确性与并发度的持续交易」。

**演进视角**：synchronized 从「人人喊打」到锁升级翻身再到「默认首选」——性能演进改变了最佳实践（这是 Java 并发史最有教育意义的反转）；而 ReentrantLock 的价值从「更快」收缩为「更强」，也说明性能会过时、能力不会。

## 质疑者追问链

**质疑：synchronized 与锁升级 为什么设计成这样，不那样设计？**
synchronized 与锁升级 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——锁竞争 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。
