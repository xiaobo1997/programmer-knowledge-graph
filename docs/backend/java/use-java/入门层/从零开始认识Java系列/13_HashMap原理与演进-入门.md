# HashMap 原理与演进

> **一句话摘要**：HashMap = 「哈希定位 + 链地址法解决冲突 + 8 树化 6 退化 + 2 倍扩容重哈希」的工程杰作——**扰动函数让高位参与散列、容量恒为 2 的幂让取模变位运算、树化把最坏 O(n) 拉回 O(log n)**；本篇把面试高频题背后的机制链一次讲穿，Java 8 的树化与 Java 7 的死循环事故是演进的两大节点。

> **本文核心**：机制链 = **hash 扰动（高 16 位异或低位）→ (n-1) & hash 定桶（n=2 的幂）→ 冲突挂链 → 链长过阈值且表够大树化（红黑树 O(log n)）→ size 过阈值（容量×0.75）扩容 2 倍 → JDK 8 扩容优化（高低位拆分，免重哈希）→ 多线程 JDK 7 头插死循环事故是并发容器的动力案例**。

前置阅读：[集合框架总览](./11_集合框架总览-入门.md)（equals/hashCode 契约）。并发版本见[并发集合](./16_并发集合与线程安全容器-入门.md)。

## 1. 背景：HashMap 要同时解决什么

一个键值容器要同时做到：**快**（读写接近 O(1)）、**有序可预测**（不需要）、**省**（内存合理）、**稳**（最坏情况不失控）。哈希表用「数组 + 哈希定位」拿到均摊 O(1)，但引入两个新问题：**冲突**（不同键落同桶——链地址法解决）与**退化**（冲突链过长变 O(n)——树化解决）。Java 8 把「链表过长树化」引入后，HashMap 的最坏复杂度从 O(n) 改善到 O(log n)——这是 8 时代最重要的结构性演进。

## 2. 核心机制：定位、树化与扩容

```mermaid
flowchart TD
    PUT[put key value] --> H1[hash 扰动: key.hashCode 高16位异或低16位<br/>让高位参与散列 减少低位聚集]
    H1 --> H2[(n-1) & hash 定桶下标<br/>n 恒为 2 的幂: 取模变位运算]
    H2 --> H3{桶空?}
    H3 -->|空| NEW[新节点直接放入]
    H3 -->|冲突| H4[链表遍历: equals 相等则覆盖<br/>链长 >= 8 且 表容量 >= 64 则树化红黑树]
    H4 --> TREE[红黑树: 查询 O log n<br/>节点数退化到 6 转回链表]
    SIZE[size > 容量 x 0.75?] --> GROW[扩容 2 倍: JDK8 按高低位拆分两条链<br/>免重算 hash 只看新增位]
```

机制要点（追问链）：

- **扰动函数为什么「高 16 位异或低 16 位」？** 定桶用 `(n-1) & hash`，n 小于 65536 时只有低位参与——若 hashCode 只在高位有差异（如相近对象），低位全相同则全部撞同桶。扰动把高位信息混入低位，代价一次异或，收益散列均匀。
- **容量为什么恒为 2 的幂？** `hash % n` 换成 `(n-1) & hash`——位运算替代除法；且扩容翻倍时，元素要么留在原桶、要么去「原桶 + 旧容量」位置（只看新增的那一位）——**免重算哈希，拆分即可**（JDK 8 的扩容优化）。
- **为什么是 8 树化、6 退化？** 树化阈值 8 配合泊松分布（理想散列下单桶链长到 8 的概率约亿分之一）——树化是对「哈希质量差/攻击」的兜底而非常态；退化阈值 6（低于 8）留出差额防「8↔7 抖动反复树化/退化」。另有前置条件「表容量 ≥ 64」，小表先扩容不树化。
- **负载因子为什么 0.75？** 空间与时间的折中——过高（1.0）冲突链变长查询变慢，过低（0.5）空间浪费与扩容频繁；0.75 是泊松分布下的经验均衡点。
- **JDK 7 并发死循环事故**：JDK 7 头插法在并发扩容时可能形成环形链表——后续 get 落入死循环 CPU 100%（著名的线上事故案例）。JDK 8 改尾插修复此环，**但这不意味着 HashMap 变并发安全**——并发丢数据/不一致仍存在，并发场景的唯一正解是 ConcurrentHashMap（16 篇）。

## 3. 落地实践：HashMap 的工程纪律

1. **预估容量**：`new HashMap<>(expectedSize / 0.75 + 1)` 或 Guava `Maps.newHashMapWithExpectedSize`——免多次扩容重哈希（重哈希是 O(n) 全量搬迁）。
2. **键不可变 + 契约正确**：键的 equals/hashCode 契约一致（equals 相等必 hash 相等）；可变键入 map 后改字段 = 数据失踪（总览篇的事故在 HashMap 上最致命）。
3. **对象作键优先不可变类型**：String/枚举/record——哈希缓存与不变性双保险。
4. **get 语义用 getOrDefault/computeIfAbsent**：`map.computeIfAbsent(key, k -> new ArrayList<>()).add(x)`——多值 map 惯用法，免手写判空。
5. **遍历方式选 entrySet**：需要键值都用时 entrySet 一次取齐——keySet 后再 get 是二次哈希浪费。

## 4. 生产视角：HashMap 事故的形态

- **并发使用的数据丢失**：多线程 put 互相覆盖（无锁）——不报错但数据悄悄丢；JDK 7 还有死循环 CPU 100%。 HashMap 的并发使用是「静默故障」的典型——监控难发现，对账才暴露。
- **键可变导致缓存失踪**：缓存键对象被中途修改字段——命中失效且无法 remove（remove 也要算 hash，算出的已是新 hash）。此类「缓存幽灵条目」只有重启可清。
- **哈希质量差的性能塌方**：自定义键 hashCode 实现糟糕（全部返回常数或仅低位参与）——全表退化成一条链，接口 RT 随数据量线性劣化。树化兜底救了最坏情况，但常态性能已毁。
- **初始化容量错算的反向优化**：`new HashMap<>(1000)` 想存 1000 条——默认负载因子下 1000 条会触发扩容（1000 > 1024×0.75？不对，1024×0.75=768 < 1000 会扩）——正确算式 `1000/0.75+1`。

## 5. 主流系统怎么做：哈希表的家族演进

| 实现 | 机制选择 | 机制要点 |
|---|---|---|
| HashMap | 链地址 + 树化 + 2 倍扩容 | 单线程最优；null 键值允许 |
| LinkedHashMap | HashMap + 双向链表串节点 | 插入序/访问序 + removeEldestEntry 钩子（LRU 三行实现） |
| TreeMap | 红黑树 | 排序语义 O(log n)，range 查询 |
| ConcurrentHashMap | JDK 8 CAS+synchronized 桶头 | 并发分段思想演进（16 篇专讲） |
| Guava ImmutableMap | 构建期固定 | 不可变 + 紧凑布局 |

规律：**家族成员共享「哈希思想」，差异全在「冲突与并发策略」**——理解 HashMap 一家，整个哈希系（含 Redis 字典/各语言 map）的机制地图就打开了。

## 6. 典型场景

- **内存索引**（查找级）：ID → 对象的 O(1) 索引——业务代码最常见用法。
- **LRU 缓存**（缓存级）：LinkedHashMap accessOrder 三行实现——小规模本地缓存的快速方案。
- **分组统计**（聚合级）：`computeIfAbsent` 多值 map / merge 计数——流式统计的底层动作。

## 7. 与相邻概念的区别

- **HashMap vs Hashtable**：Hashtable 全 synchronized + 不允许 null（历史遗留类）——被 ConcurrentHashMap 全面取代，新代码禁用 Hashtable。
- **HashMap vs ConcurrentHashMap**：单线程性能 vs 并发安全——JDK 8 后者用「CAS + synchronized 锁单桶」做到并发且性能优秀；关键差异是「读要不要锁」（CHM 读无锁）。
- **哈希冲突 vs 哈希碰撞的术语**：同一含义（不同键同桶）；「哈希攻击」是恶意构造同桶键让退化为 O(n)——树化就是攻击防御。
- **本篇 vs Redis 字典**：Redis 渐进式 rehash（分两次搬迁）vs HashMap 一次性搬迁——内存数据库「停顿不可接受」的演进分支（Redis 系列可互参）。

## 8. 常见误区与不适用

- **「HashMap 线程安全，只是慢」**：完全不安全——丢数据/不一致/JDK 7 死循环都是它；「换 ConcurrentHashMap」是唯一并发正解，加锁包 HashMap 是下策。
- **「树化了就万事大吉」**：树化有前置（容量≥64）且树化本身有成本——它兜「最坏」，保不了「常态」；常态性能靠哈希质量与容量规划。
- **「负载因子可以随便调」**：调大省内存但冲突升、调小冲突降但扩容频繁——默认 0.75 是均衡解，调整要有基准依据。
- **「null 键能用就好」**：null 键只允许一个且语义模糊——业务上「无键」应该显式建模（Optional/默认对象），null 键是懒惰建模。
- **不适用**：需要排序遍历（TreeMap）；需要插入序（LinkedHashMap）；强一致并发（CHM/加锁）；持久化键值存储（Redis/LevelDB——内存 map 不是数据库）。

## 9. 你们可能会问

- **为什么树化阈值是 8 不是 16 或 4？** 理想散列下链长服从泊松分布，长度 8 的概率约亿分之一（源码注释给出）——8 意味着「几乎只有哈希劣化/攻击才会触发」，正常路径零树化成本。
- **扩容时元素怎么搬到新表？** JDK 8 按「新增高位位是 0 还是 1」拆两条链——index 不变或 index+旧容量，hash 不用重算（扰动值已存节点里）。
- **computeIfAbsent 的死循环风险？** JDK 9 前递归 compute 同 key 可能死循环（JDK-8071667）——mapping function 里不要再改同一个 map 的同 key；升级新版 + 规范规避。
- **为什么 0.75 不写成可调的默认更优值？** 它就是「可调的」（构造参数）——0.75 只是默认均衡；调整需要压测证据。
- **hashCode 相同 equals 不同的对象放 map 会怎样？** 都保留在同一条链/树里（冲突正常共存）——「覆盖」只发生在 equals 相等时；hashCode/equals 契约的完整理解在此落地。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：HashMap = 扰动散列 + 2 的幂位运算定桶 + 链地址（8 树化 6 退化）+ 2 倍扩容高低位拆分——单线程最优哈希表，并发唯一正解 ConcurrentHashMap。
- **链条复述**：hash 扰动混高位 → 位运算定桶 → 冲突挂链 → 8/6 树化与退化 → 0.75 触发 2 倍扩容（免重哈希拆分）→ JDK 7 死循环是并发事故史碑。
- **失效点与边界**：键契约必须正确且不可变；并发必须 CHM；排序需求去 TreeMap。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 定位/树化/扩容三机制 + JDK 7/8 演进节点 |
| Why | O(1) 键值访问是绝大多数查找场景的基座 |
| When | 索引构建、缓存实现、哈希相关故障排查 |
| Where | 堆（数组+链表/树节点） |
| How | 预估容量 → 不可变键 → computeIfAbsent 惯用法 → 并发换 CHM |

💡 **实战提示**：容量按 expectedSize/0.75+1；键不可变；entrySet 遍历；并发无脑 CHM；JDK 7 死循环故事当教训讲。

**开放问题**：HashMap 的树化解决了「最坏退化」，但「完美哈希/自适应结构」的研究会否让「冲突管理」从运行时策略变成编译期选择——map 的形态还会怎么演进？

**决策（何时用）**：无序键值默认 HashMap；并发默认 ConcurrentHashMap；排序 TreeMap、插入序 LinkedHashMap——推荐「按语义承诺选 map」与总览篇同一套方法论。

**Trade-off（代价与反方案）**：负载因子 0.75 的空间时间折中、树化的常态成本 vs 最坏兜底、扩容的吞吐抖动 vs 均摊效率——HashMap 内部全是微权衡；反方案是「不装了直接红黑树」（稳定但慢）或「不上哈希」（排序树）——工程哈希表的优雅恰在于用概率把坏情况推到几乎不可达。

**演进视角**：JDK 7 的头插死循环 → JDK 8 的尾插+树化+扩容优化 → ConcurrentHashMap 的 CAS 化——HashMap 的三次大演进对应「正确性、最坏情况、并发」三个时代命题；它既是数据结构课，也是一部并发事故史。
