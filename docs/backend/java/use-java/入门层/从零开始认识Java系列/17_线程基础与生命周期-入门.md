# 线程基础与生命周期

> **一句话摘要**：线程 = 调度与执行的独立单位——**创建四种方式（本质只有 Runnable/Callable 两种任务形态）+ 六状态机（NEW→RUNNABLE→BLOCKED/WAITING/TIMED_WAITING→TERMINATED）+ 上下文切换的代价（几微秒 + 缓存失效）**；「为什么并发难」的答案也在这篇确立：共享内存 + 调度不可控 + 编译器/CPU 优化重排——三重不确定叠加。

> **本文核心**：机制链 = **线程是内核调度的执行流 → Java 线程 1:1 映射内核线程（平台线程）→ 状态机由 JVM 与内核共同驱动 → 上下文切换 = 保存/恢复执行上下文 + 缓存失效 → 并发三难（原子性/可见性/有序性）在 19 篇 JMM 展开**——线程太贵（切换+内存），所以有线程池（25 篇）与虚拟线程（41 篇）两代解法。

前置阅读：[并发集合](./16_并发集合与线程安全容器-入门.md)。并发三难的内存模型解法见[JMM 与 volatile](./19_JMM与volatile-入门.md)。

## 1. 背景：为什么并发难

单线程的世界因果线性；多线程引入三重不确定：

1. **原子性被打破**：`count++` 是「读-加-写」三步，线程交错执行互相覆盖（丢失更新）；
2. **可见性被打破**：一个线程改了共享变量，另一个线程可能读到旧值（CPU 缓存/编译器优化的联合作用）；
3. **有序性被打破**：代码书写顺序 ≠ 执行顺序（编译器重排 + CPU 乱序执行 + 缓存刷新延迟）。

这三难不是 Java 的问题，是「共享内存多核」的物理现实——Java 的回答是 JMM（内存模型，19 篇）把「什么是合法行为」形式化，再提供 synchronized/volatile/原子类等机制按需兑换保证。理解「为什么难」才能理解「机制为什么这样设计」。

## 2. 核心机制：创建、状态机与切换代价

```mermaid
flowchart TD
    CREATE[创建方式四种] --> W1[new Thread 匿名/显式]
    CREATE --> W2[Runnable: 无返回值任务]
    CREATE --> W3[Callable + Future: 有返回值可抛异常]
    CREATE --> W4[线程池提交(25篇): 生产唯一正解]
    NEW --> NEW_STATE[NEW]
    NEW_STATE -->|start()| RUN[RUNNABLE: 可运行/运行中]
    RUN -->|等锁| BLK[BLOCKED: 等 synchronized]
    RUN -->|wait/join/park 无参| WAI[WAITING]
    RUN -->|wait t/sleep t/park t| TW[Timed_WAITING]
    BLK & WAI & TW -->|唤醒获得许可| RUN
    RUN -->|run 结束| TERM[TERMINATED]
```

- **创建方式的真相**：Runnable 与 Callable 是「任务」的两种形态（无返回值 vs 有返回值可抛异常）；`new Thread(task)` 是「手动为任务起一个线程」（生产禁用——线程创建销毁昂贵且无管理）；Lambda 让 Runnable/Callable 写法合一（`new Thread(() -> ...)`）——**「四种方式」是教学分类，工程只有一种：线程池提交任务**（25 篇）。
- **状态机的关键辨析**：BLOCKED（等 synchronized 锁）与 WAITING（主动等待 wait/join/park）是两条不同的挂起通道；RUNNABLE 包含「正在运行」与「就绪等调度」两种内核态（Java 层不区分）——`jstack` 里线程状态的解读依赖这张图（32 篇排障的地基）。
- **上下文切换的代价**：内核保存/恢复线程上下文（寄存器/程序计数器/内核栈）+ **缓存失效**（切走后 CPU 缓存被其他线程污染，切回要重新预热）——单次切换微秒量级，但缓存失效的隐性代价常数倍于此；高并发系统「线程数过多 → 切换风暴 → RT 上升」是经典劣化链。
- **平台线程的贵**：1:1 内核线程——每个线程约 1MB 栈内存（默认）+ 内核调度开销 → JVM 千级线程已重；万级线程切换风暴。这就是「线程池控制数量」（25 篇）与「虚拟线程极轻」（41 篇）两代方案的存在理由。

## 3. 落地实践：线程的正确起停

```java
// 任务的两种形态
Runnable task = () -> System.out.println("run");
Callable<Long> computing = () -> computeSomething();   // 有返回值 可抛异常

// 生产方式: 线程池(25篇详讲) -- 此处展示形态
executor.submit(task);
Future<Long> f = executor.submit(computing);

// 停止: 协作式中断(不是强杀)
Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {  // 响应中断
        doWork();
    }
});
t.start();
t.interrupt();   // 设置中断标志 -> 线程自检后退出
```

三条纪律：① **停止靠协作式中断**（interrupt 只是设置标志位，线程自己决定何时退出——强杀线程会破坏数据一致性，Thread.stop 早已废弃）；② **阻塞方法（sleep/wait/IO）收到中断会抛 InterruptedException**——catch 后要么恢复中断标志（`Thread.currentThread().interrupt()`）要么上抛，**吞掉中断 = 让线程失去停止能力**；③ **daemon 线程不阻止 JVM 退出**（后台线程语义：JVM 只等非守护线程结束）——守护线程里慎做「必须完成」的事。

## 4. 生产视角：线程问题的形态

- **线程数过多的高负载不降**：压测加线程反而 RT 上升——上下文切换风暴（调度开销 + 缓存失效吞掉并行收益），最佳线程数有拐点（CPU 密集 ≈ 核数、IO 密集按等待比放大，25 篇公式）。
- **吞掉中断的「停不下来」**：catch (InterruptedException e) {} 后循环继续——应用关停时线程永不退出（优雅停机失败的常见根因）。纪律：InterruptedException 要么抛要么恢复标志。
- **状态机误读的排障弯路**：jstack 大量 WAITING 线程误判「死锁」——WAITING 多数是正常挂起（等任务/等连接）；死锁的判据是「互相持有对方所需锁」（jstack 直接报 Found one Java-level deadlock）。
- **守护线程里的数据丢失**：JVM 退出不等守护线程——守护线程里的写操作被腰斩（数据没落盘）。生产写操作走非守护 + 优雅停机钩子。

## 5. 主流系统怎么做：线程的生态形态

| 形态 | 机制 | 要点 |
|---|---|---|
| 线程池 | ExecutorService + 工作队列 | 线程复用 + 数量管控（25 篇） |
| 虚拟线程 | JVM 调度的轻量线程（21 正式） | 挂起不占内核线程——万级并发成为可能（41 篇） |
| 定时调度 | ScheduledExecutorService | 延迟/周期任务的标准件 |
| 结构化并发 | StructuredTaskScope（预览） | 任务组生命周期管理——并发任务的「作用域化」演进 |

规律：**线程的「裸用」被逐代淘汰**（手动创建→池化→虚拟线程→结构化）——演进方向始终是「管理成本下沉、心智负担减轻」。

## 6. 典型场景

- **异步调用**（服务级）：线程池提交远程调用并行化——吞吐的核心手段。
- **后台任务**（常驻级）：非守护线程 + 优雅停机钩子——数据落盘类后台任务的标准形态。
- **CPU/IO 混合**（调优级）：按任务类型分池——隔离互不拖累（25 篇的池隔离纪律）。

## 7. 与相邻概念的区别

- **线程 vs 进程**：进程是资源分配单位（独立地址空间），线程是调度单位（共享进程内存）——共享内存既是并发的便利（通信快）也是灾难根源（互相踩踏）。
- **并发 vs 并行**：并发=交替执行（结构/能力），并行=同时执行（硬件/状态）——单核也有并发问题（交错），多核才有真并行。
- **BLOCKED vs WAITING**：被动等锁 vs 主动等待——恢复条件不同（锁释放自动恢复 vs 需要显式唤醒）。
- **平台线程 vs 虚拟线程**：1:1 内核映射 vs M:N JVM 调度——贵与轻的分野（41 篇），但共享同一套 Java 语义（Thread 类——虚拟线程是 Thread 的实现替换）。

## 事故叙事：一次线程泄漏引发的线上排查

当时某服务运行一周后接口越来越慢，线程数从 200 涨到 8000+（`jstack` 确认大量 WAITING 线程）。排查发现：每次 HTTP 请求创建一个新线程做异步通知，通知完成后线程应该结束——但通知逻辑里有 `while(true)` 等待外部回调，外部服务超时后回调永不到来，线程永远 WAITING。**线程泄漏 = 只创建不回收**。修复：改用线程池 + 超时机制。复盘沉淀：① 永远用线程池不要裸建线程；② 线程数是必监控指标；③ 异步任务的超时兜底不能省。


## 8. 常见误区与不适用

- **「线程安全 = 不用线程池也没事」**：裸线程的问题是「管理」（数量/生命周期/异常）——安全性与管理是两个维度，25 篇专治管理。
- **「interrupt 能强制停线程」**：它只设标志——不响应中断的线程 interrupt 无效；「强制」只有废弃的 Thread.stop（勿用）。
- **「线程越多越快」**：切换风暴与内存（1MB 栈/线程）的反噬——并行收益有拐点，线程数是调优参数不是越大越好。
- **「RUNNABLE = 正在 CPU 上跑」**：包含就绪等待调度——IO 阻塞在 Java 旧分类里也可能显示 RUNNABLE（IO 阻塞在 native 层不进 BLOCKED 状态）——jstack 解读的常见误区。
- **不适用**：极短任务的频繁起停（池化/虚拟线程替代）；单核强实时（切换代价敏感，考虑事件驱动单线程模型）。

## 9. 你们可能会问

- **run() 和 start() 的区别？** start 才会让 JVM 创建线程并调 run（新线程执行）；直接调 run 是普通方法调用（当前线程执行）——「多线程没生效」的经典原因。
- **sleep 和 wait 的区别？** sleep 是 Thread 静态方法（不释放锁、时间到自动醒）；wait 是 Object 方法（必须在 synchronized 内调用、释放锁、需 notify 唤醒）——「锁的所有权」是两者的本质分界。
- **上下文切换多久？** 微秒量级（含缓存失效的实际代价更高）——绝对值不大，但高频切换累积显著；观测手段：vmstat/mpstat 的 cs 指标。
- **Java 线程和内核线程怎么对应？** 平台线程 1:1（HotSpot 用内核 pthread）——这也是「线程贵」的原因；虚拟线程改为 M:N（41 篇）。
- **怎么给线程命名？** 构造器/setName——「线程名」是日志与 jstack 排障的导航地图，线程池默认命名的工厂方法（25 篇）是生产纪律。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：线程 = 贵的内核执行流（1:1 映射 + 1MB 栈 + 切换代价）——六状态机是排障地图，协作式中断是唯一停止方式，工程用法只有线程池一种。
- **链条复述**：并发三难（原子/可见/有序）→ 线程形态（Runnable/Callable）→ 状态机（BLOCKED/WAITING 分辨）→ 切换代价 → 贵 ⇒ 池化与虚拟线程两代解。
- **失效点与边界**：吞中断=失去停止能力；守护线程不保完成；jstack 的 RUNNABLE 含 IO 阻塞。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 创建形态、六状态机、切换代价、协作式中断 |
| Why | 并发三难 + 线程昂贵——是后续所有并发机制的问题定义 |
| When | 异步化设计、线程排障、优雅停机 |
| Where | 内核调度 + JVM 线程栈 |
| How | 池化提交任务 → 响应中断 → 命名线程 → 按状态机解读 jstack |

💡 **实战提示**：InterruptedException 必须处理；线程必命名；裸 new Thread 禁用；守护线程不做必须完成的事。

**开放问题**：虚拟线程让「线程贵」的前提崩塌——线程池（数量管控的艺术）会像手动内存管理一样逐步退出历史舞台吗？

**决策（何时用）**：一切生产并发用线程池/虚拟线程；推荐「线程命名规范 + 中断处理规范」进团队并发规范；推荐 jstack 状态机图贴在排障手册首页。

**Trade-off（代价与反方案）**：多线程用「复杂度与切换代价」换「吞吐与响应性」；反方案——单线程事件驱动（Node/Redis 模式：免切换，代价是阻塞即全停）、协程/虚拟线程（轻，代价是新心智模型）；线程数的权衡是「并行收益 vs 切换风暴」的曲线拐点。

**演进视角**：线程从「贵而稀缺」到虚拟线程「便宜到可以每个请求一个」——并发模型二十年最大的一次扩容正在发生（21 正式）；但三难（原子/可见/有序）不变，JMM 与同步机制（19-22 篇）依然是地基。

## 质疑者追问链

**质疑：线程基础 为什么设计成这样，不那样设计？**
线程基础 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——线程数量 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。
