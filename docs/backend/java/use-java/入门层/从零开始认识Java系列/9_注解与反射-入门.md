# 注解与反射

> **一句话摘要**：注解是「贴在代码上的元数据」，反射是「运行期打开类的能力」——两者组合（注解标记 + 反射读取 + 动态代理增强）构成了整个 Java 框架世界的机制底座（Spring/MyBatis/JUnit 全是这个三角）；理解「注解怎么被读到、代理怎么被生成」，框架的魔法就从黑盒变透明。

> **本文核心**：机制链 = **注解定义（@interface + 元注解）→ 保留策略（SOURCE/CLASS/RUNTIME）决定谁读它 → 反射 API 运行期读类/方法/字段 → 动态代理（JDK 接口代理 / CGLIB 子类代理）运行期生成增强类 → 框架 = 启动扫描注解 + 反射实例化 + 代理增强**——「注解驱动开发」的完整机制闭环。

前置阅读：[泛型](./8_泛型-入门.md)（反射读泛型签名的补充）。AOP 代理的完整展开归 Spring Boot 系列（本系列只讲机制地基）。

## 1. 背景：框架为什么依赖这个三角

手写世界的调用是编译期锁死的：`new UserService().doIt()`——换实现要改代码。框架世界的调用是运行期组装的：**你只写类 + 贴注解（@Service/@Transactional/@Test），框架在启动时扫描注解、反射实例化、动态代理增强**——你与框架的契约只剩注解。这套「声明式编程」范式让业务代码与框架逻辑解耦（事务/事务提交/测试注册全由框架代理注入），代价是运行期反射的性能与可读性成本——理解机制才能管好代价。

## 2. 核心机制：注解保留策略与反射 API

```mermaid
flowchart TD
    A[@interface 定义 + 元注解] --> R1[RetentionPolicy.SOURCE<br/>仅源码: @Override 编译后丢弃]
    A --> R2[CLASS: class 文件在 运行期不可见<br/>默认值 少用]
    A --> R3[RUNTIME: 运行期可反射读<br/>框架注解的必选]
    R3 --> REF[反射 API 运行期能力]
    REF --> F1[读类: Class 对象/构造器/方法/字段/注解/泛型签名]
    REF --> F2[建对象: Constructor.newInstance<br/>绕过编译期类型检查]
    REF --> F3[调方法: Method.invoke<br/>突破 private(setAccessible)]
    REF --> P[动态代理: 运行期生成增强类<br/>JDK 接口代理 / CGLIB 子类代理]
```

- **元注解（注解的注解）**：`@Retention`（保留策略——框架注解必 RUNTIME）、`@Target`（能贴哪里：类/方法/字段/参数）、`@Inherited`（子类可继承）、`@Repeatable`（可重复贴）——四件套决定注解的「生命周期与附着面」。
- **反射的成本与缓解**：`Method.invoke` 比直调慢一个数量级量级（参数装箱/访问检查/无法内联）——框架的缓解三板斧：启动期一次性反射并缓存 Method 对象（运行期不再查找）、`setAccessible(true)` 关访问检查、高热路径用 MethodHandle/LambdaMetafactory（ invokedynamic 生成直调句柄，性能逼近直调）。
- **动态代理两派**：**JDK 代理**（`Proxy.newProxyInstance`，运行期生成实现同一组接口的 `$Proxy` 类，方法调用统一转发 InvocationHandler）——只能代理接口；**CGLIB 子类代理**（生成目标类的子类覆写方法）——能代理类但不能代理 final 类/方法。Spring 的规则：有接口默认 JDK 代理（可配置强制 CGLIB），无接口走 CGLIB。
- **反射与模块化**：JDK 9+ 强封装（模块系统）下反射访问非导出包需要 `--add-opens`——框架（Spring/Hibernate）大量反射与新版 JDK 的兼容性主战场（第 2 篇升级暗坑在此的机制细节）。

## 3. 落地实践：手写一个迷你注解框架

```java
// 1. 定义注解
@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD)
public @interface ScheduledTask { int intervalSeconds(); }

// 2. 业务贴注解
class ReportJob {
    @ScheduledTask(intervalSeconds = 60)
    void generateReport() { ... }
}

// 3. 框架侧: 启动扫描 + 反射读取 + 调度执行
for (Method m : reportJobClass.getDeclaredMethods()) {
    ScheduledTask t = m.getAnnotation(ScheduledTask.class);
    if (t != null) {
        scheduler.scheduleAtFixedRate(() -> {
            try { m.invoke(instance); }
            catch (Exception e) { log.error("task fail", e); }   // 反射异常必包装
        }, t.intervalSeconds(), TimeUnit.SECONDS);
    }
}
```

这个 30 行的迷你框架就是 Spring @Scheduled 的机制原型——**注解定义 → 扫描读取 → 反射执行**三步；理解它，@Autowired/@Transactional 的「魔法」都还原为同一套流程（加代理增强一步）。

## 4. 生产视角：反射体系的事故形态

- **反射异常的连锁**：`InvocationTargetException` 包着真实异常（`getCause()` 才是根因）——排障时只看外层全是误导。反射调用方的异常解包是框架日志质量的关键。
- **setAccessible 的两难**：绕过 private 访问是框架能力的来源，也是封装的击穿点——JDK 9+ 模块化收紧后成为升级阻塞（--add-opens 清单要随依赖管理）。
- **代理失效的经典三坑**：① 同类内部自调用（`this.method()` 不走代理——this 是原对象不是代理对象）；② final 方法 CGLIB 无法覆写；③ private 方法不被代理——三者共同根因是「代理是另一个对象，不是字节码改写」。事务注解在内部调用上失效是最高频的代理事故。
- **扫描成本**：启动期全 classpath 注解扫描——类多时启动秒级变十秒级；Spring 的组件索引（META-INF/spring.components）与 GraalVM 的构建期扫描都是「把运行期扫描前置」的优化路线。

## 5. 主流系统怎么做：三角的生态应用

| 框架 | 注解 | 反射用途 | 代理用途 |
|---|---|---|---|
| Spring | @Service/@Transactional/@Autowired | Bean 扫描实例化/依赖注入 | 事务/AOP 增强 |
| MyBatis | @Select/@Param | 接口方法 → SQL 绑定 | Mapper 接口的动态代理实现 |
| JUnit/JMH | @Test/@Benchmark | 测试方法发现与调用 | 无（直调为主） |
| Jackson | @JsonProperty/@JsonIgnore | 字段发现与读写 | 无 |

规律：**「注解标记 + 反射组装」是标配，「代理增强」只在需要横切能力（事务/AOP）时出场**——看框架文档时先分辨它用到三角的哪几角。

## 6. 典型场景

- **声明式事务**（横切级）：@Transactional 注解 + 代理环绕（开启/提交/回滚）——三角全用的旗舰场景。
- **配置绑定**（集成级）：@ConfigurationProperties + 反射字段赋值——配置与代码的解耦。
- **RPC 接口代理**（通信级）：Dubbo/Feign 的接口代理——调方法实为发请求（机制同 Mapper 代理）。

## 7. 与相邻概念的区别

- **注解 vs 注释**：注解是机器可读的元数据（编译进 class，可处理）；注释是给人看的（编译后消失）——@Override 是 SOURCE 注解（编译器检查用），@Transactional 是 RUNTIME（框架读）——保留策略决定用途。
- **反射 vs 字节码增强**：反射是「运行期调用既有类」；字节码增强（ASM/Agent）是「改写类定义本身」（JPA 懒加载增强/链路追踪 Agent）——能力更重，门槛更高。
- **JDK 代理 vs CGLIB**：接口代理（只能接口，生成快）vs 子类代理（能代理类，final 除外）——选择由「目标有没有接口」与「框架配置」决定。
- **本篇 vs AQS（第 22 篇）**：无直接机制关联——但「框架扩展点」的视角相通：AQS 用模板方法（继承），Spring 用注解 + 代理（组合），两种扩展范式（第 4-5 篇）在框架层的各自落地。

## 8. 常见误区与不适用

- **「注解自己会干活」**：注解只是数据——没有任何机制时贴了也白贴（必须有处理器读它）；「加了 @Transactional 怎么没事务」的第一问是「代理生效了吗」。
- **「反射很慢所以不能用」**：反射「首次」慢（查找/校验），缓存 Method 后的 invoke 与直调差距在现代 JVM 已收窄（且可 MethodHandle 消除）——框架路径的反射是成本可控的工程决策，不是禁忌。
- **「代理能增强一切方法」**：self-invocation/final/private 三坑（第 4 节）——代理语义的边界必须在团队规范里显式声明。
- **「RUNTIME 注解随便贴」**：RUNTIME 注解常驻元空间且被扫描——定义注解也要有治理（保留策略/Target 精确化），不是「越多越灵活」。
- **不适用**：编译期可定的配置（常量/枚举——注解是运行期机制，能编译期定就编译期定）；性能纳级热点（反射调用路径绕开或用 MethodHandle）。

## 9. 你们可能会问

- **注解怎么实现继承语义？** 接口层面 @Inherited 只让「类上的注解」被子类继承（方法上的不继承）——注解「继承」是弱化的；组合扫描（框架沿类层次向上找）是常见的替代实现。
- **为什么内部调用事务失效？** 事务由代理对象实现——`this.update()` 走的是原对象引用，绕过代理的开启事务逻辑；解法：自注入代理/AopContext/拆类——本质是「让调用经过代理对象」。
- **反射能拿到泛型信息吗？** 字段/方法/父类声明的泛型能（签名属性保留，见泛型篇）；运行期实例的泛型不能（擦除）——「声明处可读、实例处无」的分界。
- **JDK 动态代理为什么只能代理接口？** 生成的 $Proxy 类已被设计为「继承 Proxy + 实现接口」——Java 单继承占用了父类名额，只能走接口；CGLIB 用「生成子类」绕开此限制。
- **怎么排查「注解不生效」？** 三步：注解保留策略是 RUNTIME 吗（SOURCE/CLASS 反射读不到）→ 目标对象是代理还是原对象（AopContext/isProxyClass）→ 处理器真的扫描到了吗（启动日志/断点扫描方法）——三步覆盖九成案例。

- **链条复述**：贴注解 → 启动扫描 → 反射实例化 → 代理增强；三角缺一，框架魔法即失效。
- **失效点与边界**：保留策略非 RUNTIME 读不到；self-invocation/final/private 三坑绕过代理。

**开放问题**：GraalVM 原生镜像要求「反射信息构建期封死」（reflection-config），运行期反射范式被 AOT 押注反转——框架会持续向「编译期处理」（注解处理器/编译时织入）迁移吗？

**决策（何时用）**：自定义注解 + 处理器用于「横切与声明式」场景；热路径反射用 MethodHandle/缓存；推荐「代理三坑」与「异常解包」进框架使用规范。

**Trade-off（代价与反方案）**：注解 + 反射用「运行期成本与隐式性」换「声明式解耦与框架能力」；反方案——显式配置/编码（直白，代价是样板与耦合）、编译期字节码增强（性能，代价是构建复杂与调试难）；反射深度与 AOT 兼容性是新时代的权衡维度。

**演进视角**：从 XML 配置（显式但冗长）到注解驱动（本篇三角）到编译期处理（GraalVM 时代回潮）——「配置与代码的边界」二十年在钟摆；反射范式不会消失，但「运行期做的事」正被持续前移。

## 质疑者追问链

**质疑：注解与反射 为什么设计成这样，不那样设计？**
注解与反射 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——反射调用 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。
