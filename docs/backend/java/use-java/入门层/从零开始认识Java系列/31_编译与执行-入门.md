# 编译与执行

> **一句话摘要**：Java 的「编译 + 执行」是双引擎——**javac 前端编译（源码→字节码，做语法糖脱糖）+ JVM 后端执行（解释器逐条跑 + JIT 热点编译成本地码）**；分层编译（C1 快速出码 + C2 深度优化）是「启动速度 × 峰值性能」的调和方案；本篇讲穿脱糖、热点探测、内联与去虚化——JIT 是「越跑越快」的全部秘密。

> **本文核心**：机制链 = **javac（脱糖：泛型擦除/自动装箱/foreach/Switch-String/字符串拼接 StringBuilder）→ 字节码指令集（栈式：load/store/invoke 系）→ 解释器逐条执行 → 热点探测（方法调用计数器/回边计数器）→ 触发 JIT：C1（快速出码，轻优化）→ C2（深度优化：内联/去虚化/逃逸分析/循环展开）→ OSR（栈上替换：正在执行的方法热替换为编译版）**——理解「脱糖 + 内联」两件事，字节码与性能问题都看得懂。

前置阅读：[Java 全景与运行机制](./1_Java全景与运行机制-入门.md)。JMM/锁升级/virtual 调用等机制的物理实现都在本篇闭环。

## 1. 背景：为什么需要两个编译器（C1/C2）

编译成本地码需要时间（编译本身是重计算）；立即编译则启动慢、晚编译则早期跑解释。**分层编译（Tiered Compilation，JDK 8 默认）的调和**：C1 客户端编译器——快速出码、做轻优化（方法内联基础版），让程序尽快离开解释模式；C2 服务端编译器——长时间后台深度优化（内联/逃逸分析/循环优化），产出峰值性能。执行路径：解释 → C1（1→2→3 层）→ C2（4 层）——**「分级升舱」让程序在每个阶段都接近当前可得的最优性能**。

## 2. 核心机制：脱糖、热点探测与 JIT 优化

```mermaid
flowchart TD
    JAVAC[javac 前端编译] --> SUG[脱糖 Dessugar:<br/>泛型擦除+强转插入/foreach转迭代器<br/>字符串拼接转SB/switch-String转两次switch]
    SUG --> BC[字节码: 栈式指令集<br/>load/store/invokevirtual/static/dynamic]
    BC --> INT[解释器: 逐条执行 快启动]
    INT --> HOT[热点探测: 方法调用计数器+回边计数器<br/>超阈值(可调)触发编译]
    HOT --> C1[C1: 快速出码 轻优化]
    C1 --> C2[C2: 深度优化<br/>方法内联/去虚化/逃逸分析/循环优化]
    C2 --> OSR[OSR: 栈上替换<br/>正在执行的循环体热替换为编译版]
```

- **脱糖（desugar）解释一切「语法糖」**：`foreach` 还原为迭代器循环（数组则是下标循环）；字符串 `+` 还原为 StringBuilder（单表达式）/invokedynamic（JDK 9+ 的 StringConcatFactory）；Switch-String 还原为「hashCode switch + equals 确认」——**javap -c 看字节码，语法糖全部现形**（第 6 篇的方法论在此的机制依据）。
- **热点探测**：方法调用计数器（调用频次）+ 回边计数器（循环体回跳次数——长循环在方法未退出时也能触发编译，即 OSR）；阈值可调（-XX:CompileThreshold 等）且分层编译下阈值是「相对值」（按时间衰减——避免冷代码累积计数）。
- **方法内联（JIT 之母）**：把被调方法体直接复制进调用点（消除调用开销 + 为后续优化打开局面——不内联则无法跨方法优化）；**内联的偏好是小方法**——「写小方法」的性能意义从 JVM 机制获得解释； getter/setter 类必然内联到消失。
- **去虚化**：动态绑定的调用点若运行期只有一个实现（单态），JIT 直接内联具体实现 + 乐观假设（类层次变化时用去优化退回）；第 4 篇「多态开销被 JIT 消化」的机制闭环在此。
- **去优化（deoptimization）**：乐观假设失效（新实现类出现/参数类型变化）→ 从编译码退回解释——「性能突然回退」类问题的机制根源之一（JIT 编译日志可见 Full优化/去优化事件）。

## 3. 落地实践：与 JIT 打交道的工程纪律

1. **基准测试用 JMH**：预热轮次让 JIT 完成编译与内联；裸循环测「小方法」测到的是未优化假数据（27 篇逃逸分析的呼应）。
2. **热点代码写「JIT 友好」的形态**：小方法（内联友好）、避免超大方法（超 8KB 字节码不内联）、避免高频路径的反射/动态调用（invokedynamic 已大幅改善但仍有首次成本）。
3. **观测 JIT 行为**：`-XX:+PrintCompilation`（编译事件流水）/ `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining`（内联决策）/ JFR 的编译事件——「代码为什么快/慢」的 JIT 视角证据。
4. **同代码不同时机的性能差异要预期**：冷启动期（解释+C1）与热身后（C2）的 RT 曲线不同——启动敏感场景（Serverless）看 GraalVM AOT 路线（第 2 篇联动）。
5. **编译器视角读「性能玄学」**：for-each vs 下标 for 的性能差异在 JIT 后消失；「手动内联」反而阻止 JIT 内联优化——迷信「底层写法更快」在 JIT 时代大多失效。

## 4. 生产视角：JIT 相关的形态

- **压测的「热身后下降」曲线**：启动初期解释执行 RT 偏高 → C1 → C2 稳定——「前几分钟慢」不是故障是编译爬坡；基线对比要用「热身后」的数据。
- **去优化引发的性能突刺**：单态假设被新实现打破（新实现类首次加载）→ 去优化回解释再重新编译——偶发 RT 尖刺的暗因之一（JFR 编译事件可证）。
- **大方法不内联的优化天花板**：千行大方法「整体」无法内联进调用方——内部热点循环自己成为编译单元——「大方法」的性能惩罚从内联视角再+1。
- **C2 编译线程占 CPU**：后台编译消耗 CPU（-CICompilerCount 可调）——容器 CPU 限额紧时「编译线程与业务抢核」；压测容量要算上编译期消耗。

## 5. 主流系统怎么做：编译执行的生态位

| 场景 | 执行路线 | 机制要点 |
|---|---|---|
| 长跑服务 | 分层编译 C1+C2 | 峰值性能主场 |
| 快速启动 | GraalVM AOT / CDS 类数据共享 | 编译前移，牺牲动态性 |
| 动态语言/框架 | invokedynamic + BSM | 调用点延迟绑定（Lambda/动态代理的新机制——第 9 篇联动） |
| 极致微基准 | JMH（感知 JIT） | 死代码消除/常量折叠的反制 |

规律：**「解释-JIT-AOT」是执行策略的三段谱系**——同一份字节码按场景选择起跑线与终点线；Java 9 的 AOT（jaotc）到 GraalVM Native Image 的路线成熟化正在拉宽谱系两端。

## 6. 典型场景

- **性能问题归因**（排障级）：「代码没改为什么变慢」——去优化/重新编译/编译线程争抢的 JIT 视角归因（与 GC 归因并列）。
- **启动速度优化**（云原生级）：CDS/AppCDS（类数据共享）+ 分层编译参数 + AOT 评估——启动曲线的分层优化。
- **框架性能设计**（框架级）：热路径避开反射（缓存 MethodHandle）、小方法化（内联友好）——框架作者对 JIT 的主动配合。

## 7. 与相邻概念的区别

- **javac vs JIT**：前端编译（字节码，脱糖）vs 后端编译（本地码，优化）——都叫「编译」，职责两半。
- **解释器 vs JIT**：逐条翻译立即执行 vs 批量翻译深度优化——启动与峰值的调和（分层编译缝合两者）。
- **内联 vs 去虚化**：内联是「复制方法体」（消除调用）；去虚化是「确定唯一实现」（内联的前置条件）——因果链上的两步。
- **本篇 vs JVM 篇其他成员**：类加载（30）是入口，内存（26-29）是舞台，本篇是「执行引擎」——JVM 三层（加载/内存/执行）在此合龙。

## 8. 常见误区与不适用

- **「字节码看懂了就是优化后逻辑」**：字节码是「优化前的中间表示」——JIT 的内联/消除/重排全发生在之后；按字节码推性能是错位。
- **「手写 StringBuilder 一定比 + 快」**：单表达式 + 已是 invokedynamic 优化（JDK 9+）——「老优化经验」要按版本重新验证（第 6 篇的版本纪律在此的技术依据）。
- **「测试代码与生产代码跑得一样快」**：代码路径/数据形态/JIT 时机全不同——基准与生产的差距是常态，结论以生产观测收口。
- **「JIT 优化让锁/并发无所谓」**：锁消除只对「证明无共享」生效——真共享的同步语义一点不少（19-22 篇的纪律不豁免）。
- **不适用**：AOT 原生镜像（无 JIT——运行期优化让位于构建期全量优化）；纳级硬实时（非确定性 JIT 是障碍）；一次执行的短命进程（JIT 来不及回本——AOT 更优）。

## 9. 你们可能会问

- **invokedynamic 是什么，为什么重要？** JDK 7 引入的「延迟绑定」指令：调用点把「如何调用」委托给引导方法（BSM）在首次执行时决定——Lambda（第 36 篇）与字符串拼接都用它；「字节码指令的插件化」机制。
- **怎么知道某个方法被 JIT 编译了/内联了？** `-XX:+PrintCompilation`（编译事件列表：层级与耗时）/ PrintInlining（内联决策与原因：「hot」「too big」「already inlined」）——JIT 的可观测三件套之一。
- **OSR（栈上替换）解决什么？** 长循环在「方法未退出」时无法等编译版替换——OSR 把循环体在「栈上」热替换为编译版（回边计数器触发）——长循环性能爬坡的机制。
- **C2 的「循环展开/向量化」能依赖吗？** 能存在不能依赖——触发条件苛刻（边界可证/对齐）；写代码追求「清晰的循环」让 JIT 有机会优化，而不是手写展开。
- **AOT 与 JIT 的最终关系？** AOT 管「启动与确定性」，JIT 管「峰值与自适应」——分层编译本身就是两者的内部调和；Native Image 与传统 JVM 将长期互补。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：编译与执行 = javac 脱糖出字节码 + JVM 分层编译（解释→C1→C2）——热点探测触发，内联与去虚化是优化之母，OSR 热替换长循环；「越跑越快」的全部机制在此。
- **链条复述**：脱糖清单 → 字节码指令集 → 热点探测双计数器 → C1/C2 分级升舱 → 内联/去虚化/逃逸分析 → 去优化的回退 → JMH/PrintCompilation 的观测。
- **失效点与边界**：字节码≠优化后逻辑；AOT 场景无 JIT；纳级实时非主场；JIT 优化不豁免同步纪律。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 脱糖 + 分层编译 + 热点探测 + 内联/去虚化/OSR |
| Why | 「越跑越快」与性能玄学的机制解释器 |
| When | 基准测试、性能归因、启动优化、框架热路径设计 |
| Where | javac + JVM 的解释器与编译线程 |
| How | JMH 基准 → PrintCompilation/Inlining 观测 → JIT 友好写法 |

💡 **实战提示**：基准必 JMH 预热；大方法拆小（内联友好）；CF/热路径少反射；冷启动场景评估 AOT；「老性能经验」按版本复核。

**开放问题**：Project Loom 与 Valhalla 把越来越多的语义交给 JVM 原生实现——未来「应用层性能技巧」会不会大面积失效于「JVM 自动优化」，性能工程的重心彻底转向「架构与数据」？

**决策（何时用）**：性能归因、基准设计、启动优化全场景；推荐「PrintCompilation + JFR 编译事件」进性能排障工具箱；推荐「新性能结论先问 JDK 版本」进评审习惯。

**Trade-off（代价与反方案）**：分层编译用「后台编译 CPU」换「逐级逼近峰值」；内联用「代码体积膨胀」换「调用消除与优化空间」；去优化机制用「性能突刺可能」换「乐观假设的高收益」——JIT 的每一项优化都是「编译期投入 vs 运行期收益」的投资决策，分层组合后即整个 Java 的性能形态。

**演进视角**：从纯解释（1.0）到分层编译（8）到 Graal JIT/AOT（10+ Native Image）——执行引擎三十年从「一次编译」进化为「全生命周期自适应优化」；终点方向是「程序不知道编译器存在」——而机制理解的价值，恰恰在优化失效的那些时刻兑现。

## 质疑者追问链

**质疑：编译与执行 为什么设计成这样，不那样设计？**
编译与执行 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——JIT 编译 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。

## 量级分档视角

| 量级 | 编译与执行的形态变化 | 关注点 |
|---|---|---|
| 10 万级 | 入门阶段，JIT 编译默认配置即可 | 语法正确性 |
| 千万级 | 需要关注 分层编译 的取舍 | 性能瓶颈与参数调优 |
| 亿级 | JIT 编译 成为架构决策的核心变量 | 架构选型与底层机制 |

量级每上一档，对 JIT 编译 的容忍度就降一级——**同样的代码在十万级没问题，在亿级就是事故预备役**。
