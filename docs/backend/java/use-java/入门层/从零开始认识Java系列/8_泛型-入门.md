# 泛型

> **一句话摘要**：泛型 = 编译期类型检查的参数化类型——但 Java 泛型是「编译期温柔、运行期不存在」的**类型擦除**实现：`List<String>` 与 `List<Integer>` 运行时都是 `List`；理解擦除才能解释一切泛型怪象（不能 `new T()`、不能泛型数组、通配符的捕获）；通配符 `? extends/super` 的 PECS 原则是读写边界的表达。

> **本文核心**：机制链 = **泛型在编译期做类型检查与插入强转 → 擦除后运行期只剩原始类型 → 擦除导致运行期无类型信息（T 不可 new/instanceof 不可用）→ 需要运行期类型时传 `Class<T>` 字面量 → 通配符按 PECS 定读写边界 → 桥方法保证多态不破**——泛型的全部「不能」都从擦除推导。

前置阅读：[继承与多态](./4_继承与多态-入门.md)（vtable 与桥方法的机制地基）。

## 1. 背景：为什么 Java 泛型要「擦除」

C# 的泛型是真泛型（运行期 `List<int>` 与 `List<string>` 是不同类型）；Java 选择擦除是**兼容性决策**：泛型（Java 5）必须与海量存量非泛型代码（raw type 时代）无迁移共存——擦除后 `List<String>` 与 `List` 运行时同一类型，老字节码与新泛型代码互相调用无障碍。代价是运行期类型信息的丢失，换来的是无割裂的生态迁移。这个取舍解释了 Java 泛型的全部怪癖——怪癖不是 bug，是兼容性方案的边界。

## 2. 核心机制：擦除、通配符与桥方法

```mermaid
flowchart TD
    SRC[编译期: List&lt;String&gt; 完整类型检查] --> ERA[擦除: 运行期 List&lt;String&gt; 变 List<br/>get 处自动插入 String 强转]
    ERA --> LOST[运行期丢失: T 不可 new/instanceof T 不可用<br/>泛型数组不可创建]
    LOST --> FIX[需要运行期类型: 传 Class&lt;T&gt; 字面量<br/>supplier 工厂 / 超类型令牌]
    W[通配符与边界] --> EXT[? extends T: 上界 只读生产者 Producer]
    W --> SUP[? super T: 下界 只写消费者 Consumer]
    EXT & SUP --> PECS[PECS 原则: 生产者用 extends 消费者用 super]
    BR[桥方法] --> BM[泛型父类被继承时编译器生成合成方法<br/>保住多态分派(擦除后签名冲突的解法)]
```

- **擦除的两个补偿**：① 编译器在调用处自动插入强转（你写的 `String s = list.get(0)` 编译后是 `(String) list.get(0)`）；② 桥方法——泛型父类被继承时（`class MyComp implements Comparator<String>`），擦除后父接口方法是 `compare(Object,Object)`，与子类 `compare(String,String)` 签名冲突，编译器生成一个合成桥方法（参数 Object，内部强转后委托）保住多态。`getClass()` 输出里偶见的 `bridge` 方法标记即它。
- **PECS（Producer Extends, Consumer Super）**：`copy(List<? extends T> src, List<? super T> dst)`——源是「生产 T」的（只读它）用 extends 上界（能放进 src 的是 T 或子类，读出来安全当 T 用）；目标是「消费 T」的（只写它）用 super 下界（T 或父类的引用能指向写入值）。**一次只读一次只写的边界设计**，把「集合可变性」从类型签名上表达出来。
- **需要运行期类型的标准解**：传 `Class<T>`（`<T> T parse(String s, Class<T> type)`）——把类型信息作为参数显式携带；进阶是超类型令牌（`TypeReference<List<User>>`，Jackson/Fastjson 的匿名子类技巧——泛型信息其实存在「父类签名」里，编译期保留、反射可取）。
- **泛型数组为什么禁**：擦除后数组协变检查（存取时按数组实际类型校验）与泛型静态类型检查错位——`new List<String>[10]` 若合法，数组校验按 `List` 执行，塞入 `List<Integer>` 不报错，取出强转 ClassCastException 发生在「远离肇事点」的位置（堆污染）。禁令的本质是把堆污染挡在编译期。

## 3. 落地实践：泛型 API 的设计惯例

```java
// 1. 通用方法: <T> 声明在方法级, 类型由实参推断
public static <T> T firstOrNull(List<T> list) {
    return list.isEmpty() ? null : list.get(0);
}
// 2. 边界: T 必须可比较(多边界 & 连接)
public static <T extends Comparable<T> & Serializable> T max(List<T> list) { ... }
// 3. PECS 实战: 从 src 读(生产)往 dst 写(消费)
public static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T t : src) dst.add(t);
}
// 4. 需要运行期类型: Class<T> 显式携带
public <T> T fromJson(String json, Class<T> type) { ... }
```

四条纪律：① 通用方法优先于「泛型化整个类」（作用域最小化）；② 无界通配 `<?>` 用于「只关心是 List 不关心元素」的场景（与 raw type 区分——raw type 关闭全部检查，`<?>` 保留检查）；③ 类型参数命名约定 T/E/K/V/R（类型/元素/键/值/返回），多参数可读性优先；④ 桥方法与擦除知识用于「读源码与排查」，不用于炫技。

## 4. 生产视角：泛型失误的形态

- **raw type 的检查静默关闭**：`List list = new ArrayList<String>()`——编译器警告但能跑，之后 `list.add(1)` 塞入 Integer、取出强转炸在千里之外。raw type 是「堆污染」的门票，评审红线。
- **泛型单例的误判**：`static <T> T identity(T x)` 的「泛型单例」能服务所有 T——因为擦除后运行期只有一个方法；有人据此认为「泛型可以缓存」，但一旦需要 T 的运行期行为（new/反射字段）立刻崩。
- **JSON 反序列化的类型丢失**：`fromJson(json, List.class)` 拿到的 List 元素全是 LinkedHashMap——没传泛型信息，反序列化器只能按 Object 映射。解法：TypeReference/TypeToken 显式携带完整泛型签名。
- **通配符编译错误的迷惑**：`List<? extends Number> l` 的 `l.add(1)` 编译不过——extends 上界集合「只读」（编译器不知道该放哪种 Number 子类），新人误当编译器 bug；PECS 理解后自然明白。

## 5. 主流系统怎么做：泛型的生态用法

| 场景 | 惯例 | 机制要点 |
|---|---|---|
| 容器 | List/Map 的泛型化 | 类型安全 + 免强转 |
| 框架回调 | `Function<T,R>`/`Supplier<T>` | 函数式接口 + 泛型参数化行为 |
| 反序列化 | TypeReference/TypeToken | 超类型令牌保留编译期泛型签名 |
| Builder | `Builder<T, R>` 自类型递归 | 泛型表达链式构建的类型流动 |
| MR 兼容 | 泛型与 raw 混用期 | @SafeVarargs/@SuppressWarnings 的显式豁免标注 |

规律：**泛型的生态用法都围绕「编译期把类型契约写死」**——运行期缺失的信息用「显式携带」（Class/TypeToken）补齐。

## 6. 典型场景

- **通用工具方法**（工具级）：firstOrNull/max/copy——一次编写类型安全复用。
- **框架扩展点**（框架级）：`Converter<S,T>`/`Validator<T>`——框架泛型化扩展点 + 容器推断注入。
- **序列化边界**（集成级）：JSON/ORM 的类型绑定——`Class<T>`/TypeReference 的标准位置。

## 7. 与相邻概念的区别

- **泛型 vs 重载**：泛型一份逻辑多类型（编译期统一）；重载多份逻辑（各类型定制行为）——逻辑相同用泛型，行为不同用重载。
- **泛型 vs Object**：`List<Object>` 不是「万能 List」——`List<String>` 不是 `List<Object>` 的子类型（不变性），塞不进去；这正是不变性保护类型安全（协变需求用通配符显式表达）。
- **extends vs super 直觉**：extends 收窄读取、super 放宽写入——「读用 extends 写用 super」而非「子类用 extends」的机械记忆。
- **本篇 vs Stream（第 37 篇）**：Stream 的泛型推断（`<T> Stream<T>` 链式流动）是泛型推断机制的最大用户——泛型学好了 Stream 的类型推导才看得懂。

## 8. 常见误区与不适用

- **「`List<String>` 运行时知道自己是 String 列表」**：擦除后只知道是 List——运行期类型判断一律失效，需要就显式传。
- **「泛型字段 new T()」**：擦除后 T 不存在——需要实例传 `Supplier<T>`/`Class<T>` 工厂。
- **「`<?>` 等价于 `<Object>`」**：`List<?>` 是「某种未知类型的 List」（只读安全视角），`List<Object>` 是「明确 Object 的 List」（可写）——`List<?>` 反而**不能 add 任何东西**（除 null），比「裸 `<Object>`」更严格。
- **「@SuppressWarnings("unchecked") 加了就安全」**：它只关闭编译器警告——确认「确实安全」才能加（并注释理由），盲目压制 = 关掉烟雾报警器。
- **不适用**：基本类型不能作类型参数（`List<int>` 不行——用包装类或专门库如 fastutil）；运行期类型分派密集的场景（擦除下要用 Class 参数绕行，设计上避免）。

## 9. 你们可能会问

- **泛型信息真的全没了吗？** 编译期保留在 class 文件的「签名属性」里（反射 `getGenericType` 可读）——字段/方法/父类声明的泛型可反射获取，运行期「实例上」没有（擦除的是实例的类型参数）；TypeReference 正是利用「匿名子类把泛型写进父类签名」的残留信息。
- **为什么数组是协变的而泛型是不变的？** 数组协变是历史设计（运行期校验兜底，代价是 ArrayStoreException 可能延迟爆）；泛型吸取教训选不变（编译期堵死）+ 通配符显式表达变型需求——「编译期堵死优于运行期爆」的设计哲学。
- **桥方法会在什么场景坑到我？** 反射枚举方法时可能拿到桥方法（`isBridge()` 过滤）；框架做方法解析时要处理——应用层极少直接遇到，写框架/工具必知。
- **`<T extends Comparable<T>>` 和 `<T extends Comparable<? super T>>` 哪个对？** 后者更通用（T 的父类实现了 Comparable 也能比较——如 `class A extends Base implements Comparable<Base>`）；Effective Java 第 31 条的标准结论。
- **怎么快速判断一段泛型代码的擦除结果？** `javap -c` 看字节码：强转插入点、raw 类型调用——擦除不是玄学，是可反汇编的编译行为。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：Java 泛型 = 编译期类型检查 + 运行期擦除——全部「不能」（new T/instanceof/泛型数组）从擦除推导，全部「补法」（Class 参数/TypeReference）是显式携带类型信息；通配符按 PECS 表达读写边界。
- **链条复述**：编译期检查与强转插入 → 擦除（兼容性决策）→ 运行期无 T → 显式携带补偿 → PECS 边界 → 桥方法保多态。
- **失效点与边界**：基本类型不可作参数；raw type 红线；运行期类型分派场景需绕行设计。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 擦除机制 + 通配符 PECS + 桥方法 + 类型显式携带 |
| Why | 与存量生态无迁移共存是擦除的历史决策 |
| When | 工具方法、框架扩展点、序列化边界、通配符编译错误排查 |
| Where | 编译期（检查/插入强转/桥方法）与运行期（只剩 raw） |
| How | 编译期写死契约 → 运行期显式携带 → PECS 定边界 |

💡 **实战提示**：raw type 红线；反序列化必带泛型信息（TypeReference）；extends 读 super 写；SuppressWarnings 必附理由。

**开放问题**：Valhalla 项目（值类型/特化泛型）若落地，「擦除」将被重构为可特化实现——二十年的擦除知识体系哪些会失效，哪些仍是地基？

**决策（何时用）**：通用逻辑一律泛型化；需要运行期类型的 API 强制显式携带参数；推荐「PECS + 禁 raw type」进评审清单。

**Trade-off（代价与反方案）**：擦除用「运行期类型能力」换「生态无割裂迁移」；反方案——具化泛型（C#/Valhalla 路线，代价是迁移割裂与字节码膨胀）、Object + 强转（前泛型时代，代价是全部检查失效）；通配符的权衡：类型表达力 vs 可读性——PECS 命名让表达力不再牺牲可读。

**演进视角**：泛型从 Java 5 的兼容性妥协到 Valhalla 的特化重构在途——「擦除」这个二十年的「临时方案」正在走向终点；但「编译期契约优先」的设计哲学贯穿始终，工具再变，方法论不变。

## 质疑者追问链

**质疑：泛型 为什么设计成这样，不那样设计？**
泛型 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——类型擦除 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。
