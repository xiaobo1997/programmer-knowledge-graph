# 运行时内存区域

> **一句话摘要**：JVM 运行时数据区按「线程私有 vs 线程共享」二分——**私有区：程序计数器、虚拟机栈、本地方法栈（随线程生灭）；共享区：堆（对象实例）、方法区/元空间（类元数据）+ 直接内存（NIO 堆外）**——每个区域都有专属的 OOM 长相，内存问题排查的第一步是「对号入座：哪块区域爆了」。

> **本文核心**：机制链 = **线程私有区随线程创建/销毁（栈帧入栈出栈）→ 共享区随 JVM 存亡（堆 GC 管、元空间类加载管）→ 栈的 OOM（StackOverflowError 递归过深/线程过多）与堆的 OOM（GC 后仍不够）长相不同 → 元空间 OOM（类元数据堆积，动态类生成场景）→ 直接内存（堆外，受 MaxDirectMemorySize 限）**——区域定位是内存排障的第一分诊台。

前置阅读：[Java 全景与运行机制](./1_Java全景与运行机制-入门.md)。堆内的 GC 行为见[垃圾回收算法](./28_垃圾回收算法-入门.md)。

## 1. 背景：为什么按「私有/共享」划分

划分的唯一依据是**并发安全边界**：线程私有的数据（正在执行的字节码位置、局部变量、方法参数）天然线程封闭（不共享则无竞争——ThreadLocal 的封闭思想是它的应用层版本）；线程共享的数据（对象实例、类信息）需要 GC 与同步机制治理。这个划分直接回答两个高频问题：局部变量要不要加锁（私有区——不要）；类变量存在哪（共享区——方法区）。

## 2. 核心机制：五区域与各自的 OOM 长相

```mermaid
flowchart TD
    R[运行时数据区] --> P[线程私有]
    R --> SH[线程共享]
    P --> PC[程序计数器: 当前字节码行号<br/>唯一不 OOM 的区域]
    P --> VS[虚拟机栈: 栈帧的入栈出栈<br/>局部变量表/操作数栈/动态链接]
    VS --> SO[StackOverflowError: 递归过深/栈深度超 -Xss]
    VS --> SO2[OutOfMemoryError: 线程过多 栈内存总量超限]
    SH --> HEAP[堆: 对象实例 GC 主战场<br/>分代: 新生代 Eden+S0+S1 / 老年代]
    HEAP --> HO[OutOfMemoryError: Java heap space<br/>GC 后仍不足]
    SH --> META[方法区/元空间: 类元数据/常量池(JDK7+串池在堆)<br/>JDK8 起落地 native 内存]
    META --> MO[OutOfMemoryError: Metaspace<br/>动态类生成堆积]
    NAT[直接内存: NIO DirectByteBuffer 堆外] --> NO[OutOfMemoryError: Direct buffer memory]
```

- **虚拟机栈与栈帧**：每个方法调用生成一个栈帧（局部变量表 + 操作数栈 + 动态链接 + 返回地址）入栈，方法返回出栈——递归无出口 = 栈帧堆到 `-Xss` 上限 = StackOverflowError（**这是 Error 不是 OOM**——栈空间耗尽的两副面孔之一）；线程数过多时「每个线程 × 栈大小」超物理内存则是另一副（OOM: unable to create thread）。
- **堆的分代结构**：新生代（Eden + 两个 Survivor）+ 老年代——对象先在 Eden 出生，熬过 Minor GC 进 Survivor，年龄够大晋升老年代（分代假设：多数对象朝生夕死）；**堆是 GC 的主战场**（28 篇专讲）。`-Xmx/-Xms` 控制堆大小。
- **方法区的落地演进**：JDK 7 前是「永久代」（堆的一部分，大小受限臭名昭著）；**JDK 8 起改为元空间（Metaspace）**——落地 native 内存（默认无上限，受 `-XX:MaxMetaspaceSize` 限制）。存类元数据、运行时常量池；**注意字符串常量池 JDK 7 起在堆**（第 6 篇的演进）——「常量池在方法区」的老图要标注版本。
- **直接内存（堆外）**：NIO 的 DirectByteBuffer 在堆外分配（省去堆内到内核的一次拷贝）——不受 `-Xmx` 管而受 `MaxDirectMemorySize` 限；Netty 的堆外内存池是它的工业级应用。堆外 OOM 的排查盲区：堆 dump 里看不到它的主体（只看到引用）。

## 3. 落地实践：OOM 的分诊流程

```text
第一步: 读 OOM 信息本身(它是分诊台)
  "Java heap space"       -> 堆: dump 分析 MAT 找大对象/泄漏
  "GC overhead limit"     -> 堆: GC 空转(回收率极低) 同上
  "Metaspace"             -> 元空间: 动态类生成排查(CGLIB/反射类/Groovy 脚本)
  "unable to create native thread" -> 线程数或系统限制: 数线程/调 -Xss/查 ulimit
  "Direct buffer memory"  -> 直接内存: 堆外分配未释放
  StackOverflowError      -> 栈: 递归/调用链过深(定位递归点)

第二步: 拿证据
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...  (OOM 自动 dump)
  -Xlog:gc*                                             (GC 行为)
第三步: MAT/JProfiler 分析 -> 定位持有链 -> 修代码或调参
```

三条纪律：① **OOM 参数常开**（HeapDumpOnOutOfMemoryError——事故现场自动留存）；② **分清 Error 与 OOM 的两副面孔**（StackOverflow 是栈不是堆）；③ **调参前先定位**（盲目调大 -Xmx 掩盖泄漏，只是推迟爆炸）。

## 4. 生产视角：内存事故的形态

- **堆泄漏的慢性增长**：static 集合/ThreadLocal/缓存无淘汰——老年代水位缓慢爬升，Full GC 频率渐进加密，最终 OOM。特征曲线（每次 Full GC 后的基线抬升）是泄漏 vs 压力大的判据（压力大的 GC 后基线回落）。
- **元空间泄漏（动态类的暗坑）**：CGLIB/Groovy/反射生成类不回收（类加载器未释放）——重部署不重启的容器场景高发。表现：Metaspace 水位持续涨、Full GC 由 Metaspace 触发。
- **直接内存的排查盲区**：堆外 OOM 时 dump 堆「看起来健康」——DirectByteBuffer 的 Cleaner 未执行（引用队列机制）或分配过多。`-XX:MaxDirectMemorySize` 显式设限 + NMT（NativeMemoryTracking）定位。
- **线程栈的隐性总量**：每个线程 1MB 量级栈——500 线程 = 500MB 栈内存（在 -Xmx 之外！）；「堆没满却 OOM unable to create thread」指向这里。

## 5. 主流系统怎么做：内存区域的运维锚点

| 区域 | 关键参数 | 监控锚点 |
|---|---|---|
| 堆 | -Xms/-Xmx（建议等值）/ 新生代比例 | 堆使用率、各代水位、GC 频率与耗时 |
| 元空间 | -XX:MaxMetaspaceSize | Metaspace 水位、类加载数 |
| 栈 | -Xss | 线程数、StackOverflow 告警 |
| 直接内存 | -XX:MaxDirectMemorySize + NMT | DirectBuffer 用量 |
| 全局 | HeapDumpOnOutOfMemoryError | OOM 事件 |

规律：**每块区域「参数 + 监控锚点」成对配置**——只配参数不配监控，OOM 时只有堆 dump 一条线索。

## 6. 典型场景

- **接口内存泄漏排查**（堆级）：MAT 支配树找最大保留对象 → 持有链定位代码。
- **容器元空间上涨**（元空间级）：频繁热部署/脚本引擎——类加载器治理。
- **网关堆外内存治理**（直接内存级）：Netty 池化参数与 NMT 联合定位。

## 7. 与相邻概念的区别

- **虚拟机栈 vs 本地方法栈**：Java 方法 vs native（C/C++）方法的栈——HotSpot 两栈合一（实现层）；语义上分属 JLS 与规范两章。
- **方法区 vs 永久代 vs 元空间**：方法区是规范概念（存什么）；永久代/元空间是 HotSpot 的实现（放哪）——「方法区 = 接口，永久代/元空间 = 实现版本」。
- **堆 vs 直接内存**：GC 治理 vs 手工管理（DirectByteBuffer 的 Cleaner）——「GC 管不着的地方」是直接内存的事故区。
- **本篇 vs 对象的一生（27 篇）**：本篇讲「区域地图」，27 篇讲「单个对象在区域间的完整旅程」（创建/布局/晋升）——地图与行程。

## 8. 常见误区与不适用

- **「OOM 就是堆满了」**：五块区域五种 OOM——盲目调 -Xmx 掩盖元空间/直接内存/线程栈的真凶；OOM 信息本身是分诊台。
- **「JDK 8 还有永久代」**：JDK 8 起元空间替代——老文章的 `-XX:PermSize` 在新版本无效（参数被忽略并告警）。
- **「-Xmx 设大就安全」**：堆外/元空间/栈都不在 -Xmx 预算内——容器内存预算要算「堆 + 堆外 + 元空间 + 线程栈 + JVM 自身」的总账（容器 OOMKilled 的常见根因）。
- **「程序计数器会 OOM」**：规范明确它是唯一不会 OOM/不会 GC 的区域——小的「知识边界题」。
- **不适用**：对象生命周期与晋升的细节（27 篇）；GC 算法与收集器（28-29 篇）——本篇只管「有哪些区域、每个区域 OOM 长什么样」。

## 9. 你们可能会问

- **对象一定在堆上吗？** 不一定——JIT 的逃逸分析可做标量替换/栈上分配（未逃逸的小对象拆成标量在栈帧里，「对象」从未真实创建）——第 27 篇的机制细节。
- **字符串常量池到底在哪？** JDK 7 起在堆（JDK 6 在永久代）——版本演进知识（第 6 篇详表）。
- **怎么算容器的 JVM 内存总账？** 堆(-Xmx) + Metaspace + 每线程栈×线程数 + 直接内存 + JVM 自身（码表/线程/编译器）——容器限额 = 总账 × 安全系数；「容器内 JVM 的 OOMKilled」多因总账超限。
- **元空间为什么会 OOM？动态类不该被回收吗？** 类回收条件苛刻（类加载器死亡 + 无实例 + 无引用）——动态生成的类挂在「活着的加载器」上就永远活着；泄漏的是「加载器 + 它加载的全部类」。
- **怎么定位「unable to create native thread」？** 数线程（jstack/系统级 `ls /proc/pid/task | wc -l`）→ 查 -Xss 与系统 ulimit → 降线程数或减栈——三步定位是线程过多还是系统配额。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：运行时数据区 = 线程私有（计数器/栈）+ 线程共享（堆/元空间）+ 直接内存（堆外）——每块区域的 OOM 长相不同，OOM 信息是排障的分诊台。
- **链条复述**：私有/共享二分的并发依据 → 栈两副面孔（SOE/线程 OOM）→ 堆分代与 GC 主战场 → 元空间替代永久代（JDK 8）→ 直接内存的排查盲区 → 容器内存总账。
- **失效点与边界**：对象未必在堆（逃逸分析）；字符串池在堆不在元空间；总账思维替代单参数思维。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 五区域地图 + 各区域 OOM 长相 + 分诊流程 |
| Why | 内存排障的第一步是区域定位 |
| When | OOM/内存增长排查、容器内存预算、JVM 参数配置 |
| Where | JVM 进程内存（堆内外） |
| How | 读 OOM 信息 → 开 dump 与日志 → MAT/NMT 定位 → 修因再调参 |

💡 **实战提示**：HeapDumpOnOutOfMemoryError 常开；-Xms=-Xmx；容器预算算总账；元空间上限显式设；盲目调大 -Xmx 是掩盖不是治疗。

**开放问题**：GraalVM 原生镜像把「堆 + 元空间 + JIT」大幅折叠（AOT 无运行时类生成）——运行时数据区的教科书地图会按「JIT JVM vs AOT 镜像」分成两张吗？

**决策（何时用）**：一切 JVM 内存问题的排障入口；容器化部署的预算评审；推荐「OOM 分诊流程图」进排障手册第一页。

**Trade-off（代价与反方案）**：堆调大换「GC 频率下降」付「容器预算与 GC 单次耗时上升」；栈调小换「可容纳线程数上升」付「递归深度上限下降」；直接内存用「管理成本」换「IO 零拷贝性能」——区域参数的每一项都是「容量 × 稳定性 × 性能」的三方结算。

**演进视角**：永久代 → 元空间（JDK 8）→ 堆内字符串池（JDK 7）→ 统一日志与 NMT 的可观测增强——内存区域的「实现层」持续翻新，「私有/共享 + 分诊」的概念层三十余年稳定；学概念地图（耐久），查实现版本（易变）。

## 质疑者追问链

**质疑：运行时内存区域 为什么设计成这样，不那样设计？**
运行时内存区域 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——堆大小 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。

## 量级分档视角

| 量级 | 运行时内存区域的形态变化 | 关注点 |
|---|---|---|
| 10 万级 | 入门阶段，堆大小默认配置即可 | 语法正确性 |
| 千万级 | 需要关注 元空间 的取舍 | 性能瓶颈与参数调优 |
| 亿级 | 堆大小 成为架构决策的核心变量 | 架构选型与底层机制 |

量级每上一档，对 堆大小 的容忍度就降一级——**同样的代码在十万级没问题，在亿级就是事故预备役**。
