# Java 17 新特性

> **一句话摘要**：Java 17（2021 LTS）是「语法现代化集大成」——**record（不可变数据载体一行定义）、sealed（封闭继承树）、switch 表达式（返回值+模式匹配前身）、文本块、instanceof 模式匹配**五件套 + 强封装（内部 API 封锁）；它把 Java 从「样板代码最多的主流语言」改写为「数据导向与类型安全兼备的现代语言」——这是 8 之后最大的一次写法换代。

> **本文核心**：机制链 = **样板代码的痛点（POJO 十几行/继承树敞开/switch 漏 break/多行字符串拼接）→ record 一次声明（构造/访问/equals/hashCode/toString 全自动 + 语义承诺不可变）→ sealed 收编继承（permits 白名单 + 穷举检查的编译期保证）→ switch 表达式（箭头语法无 fall-through + 返回值 + 穷举检查与 sealed 联动）→ instanceof 模式匹配（类型判断 + 变量绑定一步）**——record + sealed + switch 模式化 = 「代数数据类型」（ADT）思想的 Java 落地。

前置阅读：[Java 版本演进](./2_Java版本演进与LTS节奏-入门.md)。旧文《17 的亮点》素材已按本篇机制化重写。

## 1. 背景：为什么是「写法换代」

Java 8 到 17 之间积累的语法演进（9 集合工厂/10 var/13-15 文本块/16 record+模式匹配）在 17 LTS 汇合成「现代 Java」形态。这次换代的共同主题：**让编译器承担更多机械与校验**——record 让编译器生成数据类样板、sealed 让编译器检查穷举、switch 表达式让编译器检查遗漏分支、instanceof 模式让编译器管类型转换——「从人工纪律到编译器保证」是本代演进的统一哲学。

## 2. 核心机制：五件套的机制与联动

```mermaid
flowchart TD
    REC[record: 数据载体一行定义<br/>Point(int x int y) 自动生成<br/>构造/访问器/equals/hashCode/toString<br/>不可变 final + 无 setter]
    SEA[sealed: 封闭继承<br/>permits 白名单 子类必须 final/sealed/非密封之一]
    SW[switch 表达式: 箭头语法 无fall-through<br/>有返回值 穷举检查]
    PAT[instanceof 模式: 类型判断+变量绑定<br/>if obj instanceof String s]
    REC & SEA & SW & PAT --> ADT[联动 = 代数数据类型 ADT:<br/>sealed 接口 + record 实现集 + switch 穷举处理<br/>新增实现 => 编译器指出所有遗漏的 switch]
```

- **record 的语义承诺**：`record Point(int x, int y)` 一行生成——不可变字段、规范构造器、访问器（`x()` 而非 `getX()`）、基于全字段的 equals/hashCode/toString；**不可继承（隐式 final）、无 setter、字段不可变**——它不是「省代码的 POJO」，是「不可变数据载体的语义声明」（第 3 篇的 record 定位在此展开）。可加紧凑构造器做参数校验。
- **sealed 的穷举保证**：`sealed interface Shape permits Circle, Rect`——继承白名单制（子类必须 final/sealed/non-sealed 三选一）；与 switch 模式匹配联动后，**switch 覆盖所有 permits 分支则无需 default**——新增一个实现类，所有相关 switch 编译报错——「加类型不改调用方」从纪律变成编译器强制。
- **switch 表达式的现代化**：箭头语法（`case X -> ...` 无 fall-through 无 break）；有返回值（`return switch(day) { case ... -> ...; }`）；多标签合并（`case MON, TUE ->`）；null 检查可入 case（JDK 21 完善为模式化 switch）。
- **instanceof 模式匹配**：`if (obj instanceof String s) { s.length(); }`——类型判断与变量绑定合并（消除「判断后强转」的两步样板）；与 record 解构（JDK 21 记录模式）联动可实现递归解构。
- **强封装（JEP 403）的另一面**：内部 API（sun.misc.* 等）默认封锁——升级暗坑（第 2 篇）与「API 治理」的双刃；`--add-opens` 是临时通道非归宿。

## 3. 落地实践：ADT 风格的领域建模

```java
// 领域结果的代数数据类型建模
public sealed interface PayResult permits Success, Failure, Pending {}
public record Success(String tradeNo, long amount) implements PayResult {}
public record Failure(String code, String reason) implements PayResult {}
public record Pending(String tradeNo) implements PayResult {}

// 消费端: switch 穷举 编译器保证不漏
public String describe(PayResult r) {
    return switch (r) {
        case Success s -> "成功: " + s.tradeNo();
        case Failure f -> "失败: " + f.code() + " " + f.reason();
        case Pending p -> "处理中: " + p.tradeNo();
        // 无 default! 新增 PayResult 实现时这里编译报错 强制处理
    };
}
```

这组代码是 17 现代化的精髓：**支付结果的「成功/失败/处理中」三态用类型表达**——不再是「一个对象 + 状态字段 + if 判断」，而是「封闭类型 + 穷举处理」；新增状态（如 Refunded）时，编译器找出所有必须更新的 switch——状态机维护从「人肉记忆」升级为「编译器护航」。

## 4. 生产视角：17 换代的事故与收益形态

- **升级的强封装阻塞**：老依赖反射调内部 API——IllegalAccessError（第 2 篇升级暗坑）。--add-opens 止血 + 依赖升级治本。
- **record 误用的三态**：① record 里塞行为逻辑（record 是数据载体不是领域逻辑家）；② record 字段是可变对象（浅不可变——List 字段内部仍可改，防御性拷贝或 List.copyOf）；③ record 当 JPA 实体（JPA 需要可变与无参构造——实体仍用普通类）。
- **sealed 的 API 演进约束**：sealed 是「接口演进权收缩」——permits 清单的变更影响所有调用方的穷举检查（这是特性也是契约责任）；对外 API 用 sealed 前想清楚「新增分支的迁移窗口」。
- **文本块缩进的解析事故**：结束引号位置的缩进决定剥离量——JSON 模板对不齐导致解析失败（38 篇同款细节）。

## 5. 主流系统怎么做：现代语法的生态采纳

| 特性 | 生态采纳 | 机制要点 |
|---|---|---|
| record | DTO/值对象/Map 键全面采用 | 不可变 + 天然做键（equals/hashCode 全字段） |
| sealed + switch | 状态机/结果类型/AST 处理 | 穷举保证的状态处理范式 |
| 文本块 | SQL/JSON/HTML 模板标配 | 可读性革命 |
| 强封装 | 依赖矩阵治理的硬约束 | --add-opens 治理清单化 |

规律：**17 语法的采纳与「数据导向设计」（DDD 的值对象/结果类型）天然契合**——语言特性终于追上了领域驱动的设计思想。

## 6. 典型场景

- **DTO/VO 重写**（数据级）：POJO → record——十几行变一行，不可变防御免费。
- **结果类型建模**（领域级）：sealed Result + switch 穷举——错误处理的类型化（对齐理论系列 Optional/异常的分界）。
- **AST/规则引擎**（编译器级）：表达式树的 sealed 建模 + 递归 switch 求值——ADT 的教科书场景。

## 7. 与相邻概念的区别

- **record vs Lombok @Value**：语言内建（语义承诺 + JVM 级优化空间）vs 库生成（灵活但编译依赖）——record 的「不可变语义」是语言契约；Lombok 是代码生成。
- **sealed vs final**：final 禁一切继承；sealed 允许可控的有限继承集——「全禁」与「白名单」的粒度差。
- **switch 表达式 vs if-else 链**：穷举检查与返回值 vs 自由但易漏——类型化分支的现代选择。
- **本篇 vs Kotlin data class/sealed**：思想同源（Kotlin 先行）——Java 的追赶式演进印证「语法现代化」是竞争驱动的行业趋势。

## 8. 常见误区与不适用

- **「record 只是省代码」**：它是「不可变数据载体」的语义声明——把 record 当「快捷 POJO」塞可变逻辑，语义就碎了。
- **「sealed 限制了扩展性」**：它限制的是「未受控扩展」——换取穷举检查的编译期保证；扩展点应走接口 + 注册机制（第 9 篇 SPI），而非开放继承。
- **「switch 箭头语法必须配 yield」**：箭头右侧单表达式无需 yield；块体（`case X -> { yield v; }`）才需要——语法细节混用是编译错误高发点。
- **「强封装关掉就好（--add-opens=ALL-UNNAMED）」**：全开放等于放弃模块化的安全收益——精确 opens 到具体模块/包，加退出计划。
- **不适用**：JPA/JDBC 实体（需要可变与代理——record 不适用）；需要大量继承扩展的框架点（接口+组合）；JDK 8 运行时（语法不支持——语法糖不存在降级编译）。

## 9. 你们可能会问

- **record 能继承别的类吗？** 不能（隐式 final，且已继承 Record）——但可以实现接口；「数据载体的继承需求」应重新审视为接口契约。
- **sealed 能修饰类和接口吗？** 都能——sealed 类/接口 + permits 子类型；子类三选一（final 断代/sealed 继续封闭/non-sealed 重新开放局部）。
- **record 的 equals 为什么是全字段？** record 的语义是「值的载体」——相等性 = 值相等（与 String 不可变值语义一致）；「按引用比较」的 record 需求意味着它不该是 record。
- **模式匹配 switch 与传统 switch 能混用吗？** 同一 switch 内不能混箭头与冒号风格；模式化 switch（21 增强）与传统 switch 是语句与表达式的分代——新代码全用表达式形式。
- **存量 POJO 怎么迁 record？** 三查：是否被 JPA/代理框架管理（是则不迁）、字段是否可变语义（是则不迁）、调用方是否依赖 getX 风格（迁移成本）——「查完再迁」防为迁而迁。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：Java 17 = 语法现代化集大成——record（不可变数据载体）+ sealed（封闭继承）+ switch 表达式（穷举检查）+ 模式匹配 + 文本块；record+sealed+switch 联动落地 ADT，「加类型改所有 switch」从纪律变编译器强制。
- **链条复述**：样板痛点 → 五件套各自机制 → ADT 联动（sealed 接口 + record 实现 + 穷举 switch）→ 强封装的另一面 → 迁移三查。
- **失效点与边界**：record 不是 JPA 实体；sealed 是演进契约责任；强封装 --add-opens 是止血非归宿。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | record/sealed/switch 表达式/模式匹配/文本块五件套 |
| Why | 样板与漏检从人工纪律转编译器保证 |
| When | DTO 重写、状态机建模、结果类型、AST 处理 |
| Where | 17 LTS 的语言层（JDK 8 不可用） |
| How | record 数据 → sealed 类型族 → switch 穷举 → 文本块模板 |

💡 **实战提示**：record 配 List.copyOf 防浅不可变；sealed+switch 不写 default（穷举就是防线）；文本块注意缩进基准；--add-opens 清单化治理。

**开放问题**：record 与 Valhalla 值类型会合流吗——「不可变数据载体 + 平铺内存 + 无对象头」的组合（值 record）会让 Java 的数据建模性能与表达力同时到位吗？

**决策（何时用）**：DTO/值对象/结果类型全面推荐现代五件套；JPA 实体与可变领域对象保持普通类；推荐「ADT 建模范式（sealed+record+switch）」进新项目的状态机与结果处理设计标准。

**Trade-off（代价与反方案）**：record 用「不可变约束」换「样板归零与线程安全」；sealed 用「扩展封闭」换「穷举编译保证」；强封装用「升级摩擦」换「内部 API 边界清晰」；switch 穷举用「新增类型的全链修改」换「遗漏即编译错」——现代 Java 的哲学：**把不变量交给编译器，把自由留给接口**。

**演进视角**：从「样板最多」到「现代语言」——17 的五件套是 Java 25 年语法债的一次集中清偿；它与 8 的 Lambda 呼应成两大分水岭（行为范式/数据范式），21 的虚拟线程再补并发范式（41 篇）——三代分水岭构成「现代 Java」的完整拼图。

## 质疑者追问链

**质疑：Java 17 新特性 为什么设计成这样，不那样设计？**
Java 17 新特性 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——Sealed 类 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。

## 量级分档视角

| 量级 | Java 17 新特性的形态变化 | 关注点 |
|---|---|---|
| 10 万级 | 入门阶段，Sealed 类默认配置即可 | 语法正确性 |
| 千万级 | 需要关注 Record 模式 的取舍 | 性能瓶颈与参数调优 |
| 亿级 | Sealed 类 成为架构决策的核心变量 | 架构选型与底层机制 |

量级每上一档，对 Sealed 类 的容忍度就降一级——**同样的代码在十万级没问题，在亿级就是事故预备役**。
