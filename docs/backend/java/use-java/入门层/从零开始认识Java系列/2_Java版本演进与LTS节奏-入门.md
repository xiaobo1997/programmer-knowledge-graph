# Java 版本演进与 LTS 节奏

> **一句话摘要**：Java 的版本史是一条「大步慢跑的 LTS + 小步快跑的中间版」双轨线——8（Lambda 与流的分水岭）→ 11（模块化成熟）→ 17（语法现代化集大成）→ 21（虚拟线程）→ 25（下一个 LTS）；选型的核心判断是「业务要哪个分水岭特性、依赖生态是否就位」。

> **本文核心**：机制链 = **2018 年起每半年一版 → 只有 LTS（每两年）值得生产驻留 → 三大分水岭（8 函数式 / 9 模块化+集合工厂 / 17 语法现代化 / 21 虚拟线程）定义代际 → 升级路径 = 跳跃式到下一个 LTS + 依赖矩阵核查**——版本演进的本质是「语法减负、并发革命、GC 蜕变」三条线的接力。

前置阅读：[Java 全景与运行机制](./1_Java全景与运行机制-入门.md)。版本细节（17 语法/21 虚拟线程）在本系列第 7 组（38-41 篇）逐个展开。

## 1. 背景：发布节奏为什么变了

2018 年之前 Java 按大版本发布（Java 6→7 隔 5 年、7→8 隔 3.5 年）——企业等得久，但新特性落地慢。2018 年（Java 9 起）改为**每 6 个月一个版本**，其中每两年一个 **LTS（长期支持版）**：8、11、17、21、25。节奏变化的设计意图：特性小步快跑进中间版验证，企业只驻留 LTS——「创新与稳定」的解耦。

对工程师的实际意义：**中间版当尝鲜场，LTS 才是选型坐标**——谈「Java 21 的虚拟线程」之前，先确认生产驻留在 21。

## 2. 核心机制：三大分水岭与版本地图

```mermaid
flowchart LR
    V8[Java 8 (2014 LTS)<br/>Lambda+Stream+新日期<br/>函数式分水岭] --> V9[Java 9 (2017)<br/>模块化+集合工厂+私有方法]
    V9 --> V11[Java 11 (2018 LTS)<br/>HTTP Client+var+ZGC实验]
    V11 --> V17[Java 17 (2021 LTS)<br/>record+sealed+switch表达式<br/>语法现代化集大成]
    V17 --> V21[Java 21 (2023 LTS)<br/>虚拟线程正式+pattern matching<br/>并发革命]
    V21 --> V25[Java 25 (2025 LTS)<br/>下一代驻留点]
    style V8 fill:#e8f5e9
    style V17 fill:#fff3e0
    style V21 fill:#e3f2fd
```

三大分水岭（每一处都是编程范式的切换）：

- **Java 8（2014）——函数式分水岭**：Lambda + Stream + Optional + 新日期时间——「命令式集合遍历」转向「声明式数据流」。至今大量存量代码停在 8，就是这一步的迁移成本与生态验证周期（组 7 的 36-39 篇全是 8 的遗产深化）。
- **Java 17（2021）——语法现代化集大成**：record（不可变数据载体）、sealed（封闭继承）、switch 表达式、文本块、instanceof 模式匹配——样板代码的大规模减负。这是 8 之后最大的一次「写法换代」，也是 8 → 17 升级动力最足的一档。
- **Java 21（2023）——并发革命**：虚拟线程（轻量并发，百万级线程成为可能）正式化 + 记录模式——并发编程的心智从「线程池配额」转向「每个任务一个线程」（第 41 篇专讲）。GC 线上 ZGC/G1 也在 8→21 间完成了代际更替（第 29 篇）。

追问链：**为什么企业还停在 Java 8？**——存量依赖（老框架版本不支持新字节码）、升级验证成本、无强驱动力；**8 到 17 最大的暗坑是什么？**——不是语法是「内部 API 封锁」（JEP 403 强封装 sun.misc.* 等，老框架重度依赖的内部类被锁）、以及默认 GC 从 Parallel 变 G1（行为差异）；**为什么要跳着升（8→17 而非逐版）？**——中间版无需驻留，直接对齐目标 LTS + 依赖矩阵核查是成本最低路径。

## 3. 落地实践：升级路径的方法论

1. **选驻留点**：新项目直接 17 或 21（推荐 21——虚拟线程红利）；存量 8 的升级目标按「跳到 17」规划（11 作为中间验证站可选）。
2. **依赖矩阵核查**：列全依赖（框架/中间件客户端/JDBC 驱动），逐个核对「支持的目标 JDK 版本」——升级失败 80% 死在依赖而非语言（Spring Boot 2→3 的 Jakarta 命名空间切换是标志性联动成本）。
3. **编译先于运行**：先用目标 JDK 的 `javac` 编译（暴露语法/内部 API 封锁问题——`--release 17` 参数让老 JDK 也能产出目标字节码），再整体切换运行时。
4. **行为差异清单**：默认 GC 变化（G1）、内部 API 封锁、安全策略收紧、弃用项移除（Nashorn/永久代等历史概念）——逐项过一遍官方迁移指南。
5. **灰度验证**：压测对齐 GC 与 JIT 行为差异（新 JDK 的性能曲线是另一条线），不能假设「升级=免费性能提升」。

## 4. 生产视角：版本演进的事故形态

- **内部 API 封锁的升级阻塞**：`sun.misc.Unsafe`、`sun.misc.BASE64Encoder` 这类内部 API 在 16+ 强封装——老依赖（老版 ORM/序列化库）直接 IllegalAccessError。解法：升级依赖版本为主，`--add-opens` 参数为临时止血（有退出时限）。
- **GC 默认值变化的性能误判**：从 8（Parallel 默认）升 17（G1 默认），低延迟场景变好、吞吐场景可能持平甚至波动——「升级后性能变化」先看 GC 默认值再谈代码。
- **Jakarta 命名空间切换**：Java EE → Jakarta EE（javax.* → jakarta.*）——Spring Boot 2→3 的联动大坑，所有 javax 导入与第三方兼容一次性切换。
- **LTS 之外的驻留**：生产驻留在非 LTS 版本（如 Java 20）——半年后失去补丁支持，安全与稳定性双风险；驻留点只在 LTS 是铁律。

## 5. 主流系统怎么做：版本驻留的行业现状

| 阵营 | 驻留现状 | 机制原因 |
|---|---|---|
| 云原生新项目 | 17/21 起步 | 新项目无历史包袱，直接吃现代语法与虚拟线程 |
| 互联网存量 | 8→11/17 迁移进行时 | 迁移成本与业务节奏的权衡，17 为当前主目标 |
| 传统企业 | 8 大量驻留 | 存量依赖深、变更窗口少——升级以「换代项目」形态推进 |
| 中间件生态 | 多版本兼容矩阵 | Kafka/Netty 类基础件必须同时支持 8 与 21（字节码多版本发布） |

规律：**行业呈「8 与 17/21 双峰」分布**——新与旧共存是长期现实，这决定了「多版本兼容」是基础库的必修课（也是升级方的依赖核查重点）。

## 6. 典型场景

- **新项目立项**（绿地级）：直接 21 LTS + 现代语法起步——record/sealed/虚拟线程全量红利。
- **存量升级**（迁移级）：8→17 的方法论五步（本篇第 3 节）——以「依赖矩阵」为核心工程。
- **框架/组件研发**（基础库级）：字节码多版本发布（multi-release jar）——同时服务 8 驻留者与 21 驻留者。

## 7. 与相邻概念的区别

- **LTS vs 中间版**：LTS 是「驻留点」（长期支持），中间版是「特性预告片」（半年后失修）——生产坐标只在 LTS。
- **JDK 版本 vs Spring Boot 版本**：Spring Boot 3 要求 JDK 17+（强绑定）；Boot 2 停留在 8/11——选 Boot 版本时 JDK 是前置约束（联动矩阵）。
- **语法演进 vs 运行时演进**：17 的 record/sealed 是语法层（写法减负）；G1/ZGC/虚拟线程是运行时层（行为革命）——两条线并行，升级时分开评估。
- **本篇 vs 组 7 各篇**：本篇是版本地图，组 7（36-41）是各分水岭特性的机制展开——地图与景点。

## 8. 常见误区与不适用

- **「新版本一定更快」**：语法更快（写起来）、GC 分场景、虚拟线程改并发模型——「性能提升」不是版本升级的自动结论，压测对齐才是。
- **「LTS = 免费长期支持」**：Oracle 的 LTS 商业支持收费；社区发行版（Temurin）的 LTS 支持由社区节奏定——「LTS」是版本语义，支持服务要单独确认。
- **「Java 8 的代码在 17 直接能跑」**：绝大多数能跑，但内部 API 封锁、弃用移除、GC 行为差异会让「绝大多数」之外的部分爆雷——升级是工程不是开关。
- **「必须升级到最新」**：驻留点选 LTS 而非最新——最新中间版的价值是尝鲜与反馈，生产驻留另算。
- **不适用**：强绑定老生态的遗留系统（升级即大工程，按换代项目管理）；JVM 语言项目（Kotlin 等有自己的版本节奏，但 JVM 层结论同样适用）。

## 9. 你们可能会问

- **8 → 17 升级大概什么工作量？** 取决于依赖矩阵：依赖全兼容时以「内部 API 替换 + 编译修错」为主（人周级）；牵涉 Spring Boot 2→3 时按换代项目计（人月级）——先跑依赖扫描再估。
- **虚拟线程要不要等升级到 21 才学？** 机制概念现在就可以学（第 41 篇）——它是并发模型的理解升级，落地可在 21 驻留后。
- **多版本字节码（MR-JAR）是什么？** 同一个 jar 携带多版本 class（META-INF/versions），运行时按 JDK 选加载——基础库「两头通吃」的标准机制。
- **怎么跟踪版本动态？** OpenJDK 官网 JEP 索引 + 各 LTS 的 release notes——JEP（JDK Enhancement Proposal）是版本演进的官方提案体系，重要特性都有编号。
- **为什么不建议逐版本升级（8→9→10…）？** 每个中间版都是独立工程量且无需驻留——「跳跃到目标 LTS」是官方支持的路径（兼容性以 LTS 对 LTS 验证为主）。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：版本演进 = 半年节奏 + LTS 驻留的双轨；三大分水岭（8 函数式/17 语法现代化/21 虚拟线程）定义代际，升级 = 跳跃 LTS + 依赖矩阵核查。
- **链条复述**：节奏变化（2018 半年制）→ 分水岭定位 → 升级五步（驻留点/依赖矩阵/编译先行/行为清单/灰度）→ 双峰共存的行业现实。
- **失效点与边界**：非 LTS 驻留是风险；「新=快」不成立；内部 API 封锁是升级最大暗坑。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 版本地图（8/11/17/21/25）+ 三分水岭 + 升级方法论 |
| Why | 选型与升级是每个 Java 团队的周期性工程 |
| When | 新项目立项、存量升级规划、依赖冲突排查 |
| Where | JDK 选型、框架联动（Boot 3 要求 17+） |
| How | 依赖矩阵先行 → --release 编译 → 行为差异清单 → 灰度压测 |

💡 **实战提示**：驻留只在 LTS；升级先扫依赖；--add-opens 是止血不是归宿；GC 默认值变化先看再谈性能。

**开放问题**：虚拟线程会像 Lambda 一样成为下一个「分水岭驻留动力」吗——21 能否复现 8 时代的换代效应？

**决策（何时用）**：新项目推荐 21 起步；存量按「跳 17/21」规划；推荐「依赖矩阵扫描」作为一切升级动作的第一步。

**Trade-off（代价与反方案）**：升级用「迁移工程与验证成本」换「语法红利 + 运行时性能 + 支持周期」；反方案——驻留 8（稳定，代价是特性断层与支持收窄）、追最新中间版（尝鲜，代价是失去支持）；驻留点选择本质是「特性收益 × 迁移成本 × 支持周期」的三方定价。

**演进视角**：版本史从「五年一代」到「半年一版 + LTS 驻留」——节奏革命本身就是演进（2018 JEP 320 系列的发布模式改革）；下一分水岭（虚拟线程之后的并发/语法演进）仍在 JEP 流水线上滚动。
