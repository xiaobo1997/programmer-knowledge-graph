# 继承与多态

> **一句话摘要**：继承 = 「is-a」的机制复用与类型统一，多态 = 同一调用在运行期落到不同实现（动态绑定）——它是框架扩展点（模板方法/策略/回调）的全部机制基础；但继承是**最强的耦合**，Effective Java 的裁决是「组合优先于继承」——本篇讲清多态怎么实现、继承什么时候该用、什么时候用组合替代。

> **本文核心**：机制链 = **虚方法表（vtable）支撑动态绑定：调用点按引用的静态类型查方法签名，运行期按实际类型落到 vtable 条目 → 重写（override）替换实现、重载（overload）编译期静态分派是两回事 → 继承的三重代价（封装破坏/脆弱基类/绑定实现）→ 判据：真 is-a 用继承，否则组合委托**。

前置阅读：[对象与类](./3_对象与类-入门.md)（static 与 this 的机制定位）。接口与抽象类的取舍见下一篇。

## 1. 背景：多态在解决什么问题

没有多态的世界：`if (shape.type == CIRCLE) drawCircle(s); else if (type == RECT) drawRect(s); ...`——每加一种图形，所有分支点都要改（调用方被实现绑架）。多态把「按类型分派」反转成「按类型自描述」：`shape.draw()`——调用方只面向抽象（Shape），新增图形不改调用方（开闭原则的机制根基）。**框架设计的本质就是多态**：框架定义骨架与扩展点（抽象方法），业务填空（实现类），框架运行时通过动态绑定调用你的实现——Spring/SpringMVC/JUC 全是这个模式。

## 2. 核心机制：动态绑定怎么实现

```mermaid
flowchart TD
    CALL[shape.draw() 调用点] --> COMP[编译期: 按引用静态类型 Shape<br/>确定方法签名 唯一一次方法解析]
    COMP --> RUN[运行期: 按对象实际类型查 vtable]
    RUN --> VT1[Circle 的 vtable: draw->Circle实现]
    RUN --> VT2[Rect 的 vtable: draw->Rect实现]
    VT1 & VT2 --> JIT[_invokevirtual 指令: 运行期动态分派<br/>JIT 对单实现点做内联去虚化]
```

机制要点（追问链）：

- **重写（override）vs 重载（overload）**：重写是运行期动态分派（签名相同，子类替换 vtable 条目）；重载是编译期静态分派（同名不同参，按引用的**静态类型**在编译期就选定）——`void f(Object)` 与 `void f(String)` 对 `f("abc")` 的选择在编译期完成，这是重载谜题的根源。
- **重写三规则**：签名一致、访问权限不能更窄、异常不能更宽——协变返回（返回更具体类型）允许。`@Override` 注解必写：拼写错误（想重写写成重载）编译器立即报错。
- **重写与隐藏的区别**：实例方法重写（动态绑定）；**static 方法与字段是隐藏**（静态绑定，按引用类型选择）——「子类重写父类 static 方法」是幻觉，那只是定义了一个同名新方法。父类引用调 static 字段拿到父类值，是新人最常踩的静态绑定陷阱（呼应第 3 篇：static 无 this 无动态分派）。
- **super 的语义**：显式调用父类实现（跳过动态绑定一层）——构造器里 `super(...)` 必须首行（父类先于子类完成初始化）。
- **JIT 的去虚化**：单实现热点（接口只有一个实现类在跑）会被内联成直调——多态的运行期开销在生产中常被 JIT 消解（第 31 篇编译与执行展开）。

## 3. 落地实践：继承与组合的选择

```java
// 继承的合理形态: 真 is-a + 抽象骨架(框架扩展点)
public abstract class BaseOrderHandler {
    public final void handle(Order o) {     // 骨架 final 锁定流程
        validate(o); process(o); notify(o); // 模板方法模式
    }
    protected abstract void process(Order o); // 扩展点: 业务填空
    protected void validate(Order o) { /* 默认实现 可覆写 */ }
}

// 组合优先: 行为委托而不是类型继承
public class CountingList<E> {              // 不继承 ArrayList(脆弱基类)
    private final List<E> delegate;         // 组合: 委托给实现
    private final AtomicLong count = new AtomicLong();
    public boolean add(E e) { count.incrementAndGet(); return delegate.add(e); }
    public long totalAdded() { return count.get(); }
}
```

判据三问：① **真 is-a 吗？**（「订单处理器是一种处理器」是；「计数列表是一种 ArrayList」不是——它只是要用列表的能力）；② **会向上转型多态调用吗？**（不需要多态，继承的类型统一价值归零）；③ **父类会演进吗？**（自己可控的封闭层次才安全）。三问全过才用继承，否则组合。

## 4. 生产视角：继承滥用的事故形态

- **脆弱基类**：继承 JDK 类重写方法（如继承 ArrayList 重写 add/get 记录数量）——父类内部实现变化（`addAll` 内部走 add）导致计数翻倍：**父类的自用细节成为子类的隐含契约**。这是 Effective Java 第 18 条的经典论证。
- **构造器调用可覆写方法**：父类构造器调用了可覆写方法，子类覆写版本在「子类字段未初始化」时被执行——读到 null/0 的灵异 bug。纪律：构造器只调 private/final 方法。
- **深层继承树的考古成本**：七八层继承链改一个父类方法，行为变化沿树扩散——「改一行，崩一片」。现代代码评审对「超过两三层的继承」直接要求给出理由。
- **重载混淆的线上误分派**：方法重载 + null 实参（`f(null)` 匹配最具体类型）——线上行为与预期不符；规避：重载间避免「继承关系的参数类型」并列。

## 5. 主流系统怎么做：多态的生态用法

| 模式 | 载体 | 机制要点 |
|---|---|---|
| 模板方法 | Spring 的 JdbcTemplate/AbstractController | final 骨架 + abstract 扩展点——继承的正确主场 |
| 策略 | 排序 Comparator / 路由策略 | 接口 + 组合注入——运行期可切换，比继承灵活 |
| 回调/监听 | 各种 Listener | 接口多态的事件分发 |
| SPI | JDK ServiceLoader / Dubbo SPI | 接口 + 实现注册——生态扩展的标准协议（Dubbo 特性层专讲） |

规律：**框架对外的扩展点几乎全走「接口 + 组合」**（策略/回调/SPI），继承收敛到「框架内部的抽象骨架」——生态演进投票给了组合。

## 6. 典型场景

- **抽象骨架**（框架级）：流程固定、步骤可变的场景（模板方法）——继承的合理主场。
- **策略注入**（业务级）：计价规则/风控规则多实现切换——接口 + 组合 + 容器装配。
- **默认方法演进**（接口级）：接口加默认方法扩展能力而不破坏实现类（下一篇的接口演进主题）。

## 7. 与相邻概念的区别

- **重写 vs 重载**：运行期动态分派 vs 编译期静态分派——中文一字之差，机制两层世界。
- **继承 vs 实现（implements）**：类继承带走实现（强耦合）；接口实现只承诺行为契约（无实现耦合）——「面向接口编程」把耦合降到契约层。
- **组合 vs 聚合**：组合=生命周期绑定（订单删除则明细无意义）；聚合=可独立存在——UML 语义层面的强弱区分。
- **本篇 vs AQS（第 22 篇）**：AQS 是「模板方法 + 模板模式的并发级应用」——钩子方法由子类实现（tryAcquire），骨架锁定排队与唤醒——继承机制在并发框架的旗舰应用。

## 8. 常见误区与不适用

- **「继承就是复用代码」**：复用可以组合实现；继承买的是「类型统一 + 多态」，拿代码复用当继承理由必然造出「 pumpkin 不该 is-a 容器」的错继承。
- **「private 字段子类也有」**：private 不被继承（子类不可直接访问）——「所有字段和方法都被继承」是误传；可见性与继承是两个维度。
- **「父类引用一定调父类方法」**：实例方法按实际类型动态绑定——父类引用调用的是子类实现（多态的本质）；static/字段才是按引用类型。
- **「final 方法不能被重载」**：final 禁的是重写（换实现），不禁重载（同名不同参新方法）——两个概念再次混用。
- **不适用**：跨模块暴露的父类（继承树成为对外 API 的一部分，演进即违约风险）；纯工具复用场景（静态工具/组合委托更轻）。

## 9. 你们可能会问

- **为什么 Java 是单继承？** 多继承带来菱形冲突（两个父类有同名实现听谁的）——Java 用「单继承 + 多接口（default 冲突必须显式解决）」的组合规避；接口的 default 冲突规则要求子类显式 `InterfaceA.super.method()` 仲裁。
- **多态的性能代价大吗？** invokevirtual 的查表开销极小，且 JIT 对单态调用点做内联去虚化——生产热点路径的多态开销常被优化掉；设计决策不必为性能牺牲多态。
- **什么情况必须用继承而不是组合？** 需要「被框架动态绑定调用」（模板方法扩展点）、需要向上转型进类型体系（如所有异常继承 Exception 获得 catch 语义）——「类型体系成员资格」是继承的不可替代价值。
- **final 类（String 等）为什么设计成不可继承？** 安全（防恶意子类替换行为）与不变量守护——不可变类一律 final 是 Effective Java 的纪律。
- **怎么判断存量继承树要不要重构？** 三信号：子类大量覆写却调 super（假复用）、父类为迁就子类加开关参数（脆弱基类征兆）、跨模块共享父类（耦合扩散）——出现即评估「组合化改造」。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：继承买「类型统一 + 多态」（vtable 动态绑定），组合买「解耦与灵活」——真 is-a 才继承，其余组合。
- **链条复述**：编译期按静态类型定签名 → 运行期按实际类型查 vtable → 重写动态绑定/重载静态分派/static 与字段隐藏 → 继承三代价 → 三问判据。
- **失效点与边界**：脆弱基类是继承的结构性风险；构造器禁调可覆写方法；多态开销已被 JIT 大幅消化。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 动态绑定机制 + 重写/重载/隐藏三辨 + 组合优先判据 |
| Why | 多态是框架扩展点的机制基础；继承是最强耦合 |
| When | 框架扩展点设计、行为多变场景、代码评审 |
| Where | vtable（方法区/元空间）、调用点字节码 |
| How | 三问判据 → 真继承假组合 → final 骨架 + 抽象扩展点 |

💡 **实战提示**：@Override 必写；构造器只调 private/final；扩展点优先接口+组合；继承树不跨模块暴露。

**开放问题**：record（不可继承）与 sealed（封闭继承）的普及，会不会让「自由继承」逐步退出主流设计——开放继承的适用域还剩多少？

**决策（何时用）**：框架骨架推荐「模板方法继承」；业务多实现推荐「接口 + 组合策略」；推荐「三问判据」进评审 checklist。

**Trade-off（代价与反方案）**：继承用「最强耦合 + 脆弱基类风险」换「类型统一 + 骨架复用」；反方案——组合委托（解耦，代价是委托样板）、接口 + default（契约复用，无状态耦合）——组合的样板成本正被 Lombok/record 类工具持续摊薄，天平持续向组合倾斜。

**演进视角**：从「继承复用」的早期 OOP 教学（1990s）到「组合优先」的行业共识（Effective Java 2001 起持续强化）再到 sealed 对继承的收编——继承的角色三十年从「主角」收缩为「受控的框架机制」，多态则通过接口与组合持续繁荣。
