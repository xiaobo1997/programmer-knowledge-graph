# 类加载机制

> **一句话摘要**：类加载 = 把 class 文件变成可执行的方法区结构——**五阶段（加载 → 验证 → 准备 → 解析 → 初始化）+ 双亲委派（加载请求逐级上交：Application→Platform→Bootstrap）**；双亲委派保证「同一个类只会被加载一次、核心类不被篡改」，打破它（SPI/热部署/容器）的场景都遵循「父加载器看不到子类路径」的同一原理——NoClassDefFoundError 与依赖冲突的根因全在这里。

> **本文核心**：机制链 = **类的生命周期（加载→验证→准备→解析→初始化→使用→卸载）→ 初始化的触发条件（主动引用六条：new/反射/静态字段/父类初始化/main 类…）→ 双亲委派（先委托父加载器，父加载不了才自己加载）→ 打破双亲委派的三场景（SPI 的线程上下文类加载器/热部署/容器隔离）→ 唯一性 = 「类 + 加载器」共同决定**——「类冲突」问题的全部机制根源在「同一个类被两个加载器加载 = 两个不同的类」。

前置阅读：[运行时内存区域](./26_运行时内存区域-入门.md)（类元数据在方法区/元空间）。

## 1. 背景：类加载为什么复杂

编译期 java 只认识 jar 包里的 class；**运行期 class 从哪来、谁加载、什么时候初始化**——这三个问题的机制决定了：依赖冲突怎么发生的（不同 jar 的同名类谁被加载）、热部署怎么实现（重新加载就是新类）、SPI 怎么工作（父加载器加载的接口要找到子路径的实现）。类加载是「Java 的动态性」与「Java 的依赖地狱」的同一枚硬币。

## 2. 核心机制：五阶段、双亲委派与打破场景

```mermaid
flowchart TD
    LC[类生命周期] --> L1[加载: 读 class 字节流 生成 Class 对象]
    L1 --> L2[验证: 字节码格式/语义/符号引用校验]
    L1 --> L3[准备: 静态字段分配内存 设零值<br/>注意: 此时是零值不是代码赋值]
    L3 --> L4[解析: 符号引用转直接引用]
    L4 --> L5[初始化: clinit 执行<br/>静态字段赋值+static块 按序合并]
    L5 --> USE[使用]
    USE --> UN[卸载: 加载器死亡+无实例+无引用]
    DEL[双亲委派: 请求逐级上交] --> D1[Application(类路径)] -->|委托| D2[Platform/Extension] -->|委托| D3[Bootstrap(核心类)]
    D3 -->|加载不了 逐级下放| D1
    BRK[打破双亲委派] --> B1[SPI: 父加载器的接口要加载子路径实现<br/>线程上下文类加载器]
    BRK --> B2[热部署: 重新加载=新加载器新类]
    BRK --> B3[容器隔离: 每应用独立加载器]
```

- **五阶段中的两个易错点**：① **准备阶段是零值**——`static int a = 1` 在准备阶段 a=0，赋值 1 发生在初始化阶段的 `<clinit>`；「准备阶段拿到的值」是零值——所以 `static int a = getSomething()` 的执行时机在初始化。② **初始化的触发是「主动引用」**——new/读写静态字段/反射调方法/初始化子类（触发父类先行）/main 类等六条；**被动引用不触发**（通过子类引用父类静态字段——只初始化父类；数组定义；引用常量——编译期已入常量池）。
- **双亲委派的机制**：加载请求先委托父加载器（Application→Platform→Bootstrap），父加载不了才自己加载——两个保证：**唯一性**（核心类只被 Bootstrap 加载一次，无论谁请求）与**安全**（自定义 java.lang.String 不会被加载——上交后被 Bootstrap 的核心版本拦截）。
- **打破双亲委派的共同原理**：**「父加载器看不到子加载器的 classpath」**——① SPI（JDBC Driver 接口在 Bootstrap 加载的核心库，实现在应用 classpath——父找不到子，用「线程上下文类加载器」反向委托）；② 热部署（新加载器加载新 class = 「新类」，旧类卸载靠旧加载器死亡）；③ Web 容器（每个应用独立加载器实现隔离，且容器常违反委派——先加载应用类再委托）。
- **类的唯一性 = 类 + 加载器**：`Class.forName` 拿到的 Class 对象，**不同加载器加载的「同一个类文件」是两个不同的 Class、实例互不兼容**（cast 抛 ClassCastException「同一类」的灵异错误）——依赖冲突（不同 jar 的同名类被两个加载器各加载一次）的机制解释。

## 3. 落地实践：类加载问题的排查

1. **看类从哪加载**：`Class.getResource("/X.class")` 或 `-XX:+TraceClassLoading`（日志）或 Arthas 的 `sc -d X`（加载器与来源 jar 一次看全——32 篇工具）。
2. **依赖冲突定位**：`ClassNotFoundException`（编译在运行不在——依赖缺失/被 exclusion）与 `NoSuchMethodError`（同名类不同版本——**冲突**：加载到了旧版本的类）。排查用 `mvn dependency:tree` 找冲突路径 + Arthas 确认实际加载源。
3. **初始化顺序的验证**：static 字段赋值与 static 块按书写顺序合并进 `<clinit>`——「父类静态 → 子类静态 → 父类实例构造 → 子类实例构造」的顺序可写代码验证。
4. **自定义加载器**：覆写 `findClass`（遵循委派）或 `loadClass`（打破委派）——优先重用 `URLClassLoader`；打破委派要给足理由（隔离/热部署）。

## 4. 生产视角：类加载的事故形态

- **NoSuchMethodError 的依赖冲突**：两个 jar 携带同一库的不同版本——「离 classpath 优先者胜」；本地开发通过（IDE 顺序）生产爆炸（打包顺序不同）是经典翻车。根治：dependency:tree + exclusion 收敛到单版本；Arthas 确认运行时实际加载的 jar。
- **热部署的内存泄漏**：反复热部署 = 反复新建类加载器——旧加载器只要有「类实例/静态对象/注册回调」存活就无法卸载（卸载三条件：加载器死亡+无实例+无引用，26 篇）——Metaspace 持续上涨（26 篇的元空间 OOM 主场景）。
- **SPI 加载失败的三连**：驱动类没注册（META-INF/services 文件缺失）、线程上下文加载器被污染（容器/框架改了 TCCL 忘恢复）、Uber-Jar 合并丢服务文件——SPI 排查的三个固定检查点。
- **多加载器互不兼容的 ClassCastException**：跨加载器传对象 cast 失败——容器隔离/热部署场景的「同 class 不同世界」；解法是「接口类由共同父加载器加载」（接口在父、实现在子——SPI 的正道）。

## 5. 主流系统怎么做：类加载的生态应用

| 场景 | 加载器实践 | 机制要点 |
|---|---|---|
| JDBC SPI | DriverManager 用 TCCL 加载驱动实现 | 父接口 + 子实现的反向委托 |
| Web 容器 | 每应用 WebappClassLoader | 应用隔离 + 本地优先打破委派 |
| 热部署 | 新建加载器重载 + 旧加载器废弃 | 「新类」语义 + 卸载三条件 |
| OSGi/模块化 | 网状委派/JPMS 模块 | 委派模型的精细化改造 |
| 阿里 Arthas | 自定义加载器热更新类 | 诊断工具的动态性基础 |

规律：**「委派模型是默认，打破是能力」**——打破的场景全部服务「隔离/演进/扩展」三大需求；打破的正确姿势都保持「接口在父、实现在子」的兼容层。

## 6. 典型场景

- **依赖冲突排查**（高频级）：NoClassDefFound/NoSuchMethod 三件套（tree/exclusion/Arthas）——后端工程师的日常必修。
- **隔离需求**（容器级）：多应用共容器互不干扰——加载器隔离的标准应用。
- **插件化架构**（架构级）：插件 jar 动态加载/卸载——自定义加载器的架构级应用（插件框架的机制地基）。

## 7. 与相邻概念的区别

- **Class 对象 vs 类实例**：Class 是「类的元数据对象」（方法区结构的入口）；实例是「类的具体对象」——反射操作 Class，业务操作实例。
- **加载 vs 初始化**：加载只「读入并建档」；初始化才执行 `<clinit>`（静态赋值/块）——「类已加载但未初始化」的状态存在（懒加载的间隙）。
- **双亲委派 vs 单一加载器**：委派解决「唯一性与安全」；打破委派解决「隔离与动态」——不是对错关系，是两种能力需求。
- **本篇 vs 运行时数据区（26 篇）**：类加载的产物落在方法区/元空间（26 篇的共享区）——机制与容器的上下游。

## 8. 常见误区与不适用

- **「类的卸载 = GC 掉 Class 对象」**：卸载三条件苛刻（加载器死亡 + 所有实例回收 + Class 无引用）——Bootstrap/Platform 加载的类永不卸载；「类泄漏」是元空间 OOM 的机制根源。
- **「static 字段赋值发生在类加载时」**：发生在**初始化阶段**（加载之后）——「准备阶段零值」的时序细节（本篇第 2 节易错点）。
- **「ClassNotFoundException 和 NoClassDefFoundError 一回事」**：前者是 Exception（运行期显式加载失败——forName/loadClass）；后者是 Error（编译期在、运行期缺——依赖缺失）——两个异常两条排查路径（异常篇的语义分层）。
- **「打破双亲委派是高级玩法随便用」**：打破 = 放弃唯一性与安全保证——没有隔离/热部署/扩展的真实需求，委派是唯一正确姿势。
- **不适用**：单 classpath 简单应用（默认委派无需理解太深——但排查冲突时它是根因解释器）；JPMS 模块化项目（模块系统有自己的可见性规则，委派模型被模块可见性替代）。

## 9. 你们可能会问

- **为什么准备阶段先赋零值？** 把「分配内存」与「初始化逻辑」解耦——内存分配是 JVM 机械动作（零值是安全默认），业务初值必须由 `<clinit>`（可编程逻辑）统一执行；两步分离让「静态初始化」成为可分析的确定代码块。
- **线程上下文类加载器（TCCL）到底怎么工作？** 每线程携带一个「当前类加载器」引用（默认 Application）——父加载器代码里用 `Thread.currentThread().getContextClassLoader()` 反向取「子路径」的加载器来加载实现——「借道线程传加载器」的委派打破标准姿势；用完恢复原值是纪律（污染 TCCL 是容器事故源）。
- **怎么判断两个「同名类」是不是同一个？** `class1.getClassLoader() == class2.getClassLoader()` 且全限定名相同——加载器不同的同名类是两个类（cast 必炸）。
- **Spring Boot fat jar 的类加载有什么特殊？** 自定义 LaunchedURLClassLoader 从嵌套 jar（BOOT-INF/lib/*.jar）加载——理解它才能解释 fat jar 的依赖顺序与冲突行为（与普通 classpath 的差异）。
- **怎么实现一个热更新？** 新 URLClassLoader 加载新版本 → 通过接口（父加载器加载的共同契约）切换引用 → 丢弃旧加载器 → 等 GC 卸载——「共同接口 + 新加载器 + 旧器可死」三件套；成熟方案用 OSGi/Arthas 类工具不自研。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：类加载 = 五阶段生命周期 + 双亲委派（唯一性与安全）——打破委派的三场景（SPI/热部署/容器）共享「父看不到子」的原理；类的唯一性由「类 + 加载器」共同决定，依赖冲突与热部署的一切怪象由此解释。
- **链条复述**：五阶段（准备零值/初始化触发）→ 委派两级 → 三种打破场景与 TCCL → 唯一性二元组 → 卸载三条件 → 冲突排查三件套。
- **失效点与边界**：Bootstrap/Platform 类永不卸载；打破委派必须有隔离/动态需求；TCCL 污染要恢复。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 五阶段 + 双亲委派 + 打破场景 + 唯一性二元组 |
| Why | Java 动态性与依赖地狱的同一机制根源 |
| When | 依赖冲突排查、SPI 开发、热部署/插件化、NoClassDefFoundError |
| Where | 方法区/元空间（类元数据）+ 各级加载器 |
| How | Arthas 看加载源 → dependency:tree 找冲突 → TCCL 规范使用 |

💡 **实战提示**：NoClassDefFound 与 NoSuchMethod 两路排查；SPI 的 META-INF/services 三检查；TCCL 用完恢复；冲突收敛单版本。

**开放问题**：JPMS（模块系统）与 GraalVM AOT 正在把「类加载」前移到构建期——运行时类加载的动态性会收缩到「插件/热更新」两个场景吗？动态性的护城河在哪？

**决策（何时用）**：依赖冲突排查、SPI 开发、插件化/热部署设计全场景适用；推荐「Arthas sc -d」作为类加载问题的一键诊断入口；推荐「同名类冲突收敛到单版本」进构建治理。

**Trade-off（代价与反方案）**：双亲委派用「灵活性受限」换「唯一性与安全」；打破委派用「唯一性放弃」换「隔离/动态能力」；热部署用「Metaspace 风险」换「不停机更新」——加载器的每次选择都在「静态安全」与「动态能力」之间定价；卸载三条件的苛刻就是动态性的价签。

**演进视角**：从双亲委派（1.2）到 SPI 的 TCCL 打破、OSGi 的网状、JPMS 的模块可见性——类加载模型的演进史就是「Java 平台从单一黑盒走向模块化动态化」的历史；AOT 化是最新一章（运行期加载被构建期部分取代）——动态性的范围在收缩，机制理解的价值在排障与架构设计里不降反升。
