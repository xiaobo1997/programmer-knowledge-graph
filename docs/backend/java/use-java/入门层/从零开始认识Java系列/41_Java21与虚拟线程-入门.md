# Java 21 与虚拟线程

> **一句话摘要**：虚拟线程（JDK 21 正式，JEP 444）是 Java 并发三十年最大的一次范式扩容——**JVM 调度的轻量线程（M:N 映射），阻塞时「卸载」内核线程而非占住它——百万级线程成为可能，「一个请求一个线程」的简单模型重新可行**；配套的模式匹配增强让类型处理再进一步；本篇是全系列收官：讲穿虚拟线程的机制、适用边界，并把 41 篇的知识地图收束。

> **本文核心**：机制链 = **平台线程的贵（1:1 内核映射 + 1MB 栈 + 切换代价）→ 虚拟线程的轻（JVM 托管：阻塞时栈从内核线程「卸载」到堆，继续时再「装载」）→ 「一任务一线程」回归简单模型 → 限额需求从「限线程数」转为「信号量限下游」→ 卡车与货运的类比：平台线程=卡车，虚拟线程=小盒子，仍需限重（下游容量）**——池化线程的艺术不再必要，但「有界资源保护」的工程思想永生。

前置阅读：[线程池与异步编程](./25_线程池与异步编程-入门.md)（池化的对照系）、[线程基础](./17_线程基础与生命周期-入门.md)（状态机）。

## 1. 背景：为什么「简单模型」曾经不可行

服务端开发的理想模型是「一个请求一个线程」：代码顺序书写（接收→处理→响应），阻塞调用自然等待——**可读性满分**。但平台线程太贵（内核线程 1:1 映射 + MB 级栈），万级并发请求就是万级线程——切换风暴 + 内存爆炸。于是行业发明了两代 workaround：**异步回调**（CompletableFuture/Reactor：省线程但栈断链难调试）与**响应式**（声明式但心智重）。虚拟线程让「昂贵」变「便宜」——**同步写法 + 异步吞吐**，两全在 JDK 21 兑现。

## 2. 核心机制：挂载、卸载与调度

```mermaid
flowchart TD
    VT[虚拟线程: Thread.ofVirtual().start] --> M[载体线程 Carrier: 少量平台线程<br/>ForkJoinPool FIFO 调度]
    VT --> RUNN[运行: 挂载在载体线程上执行]
    RUNN --> BLK[遇到阻塞点: IO/sleep/锁等待]
    BLK --> UNM[卸载: 栈内容复制到堆<br/>载体线程释放去跑别的虚拟线程]
    UNM --> RDY[就绪后: 重新挂载到任意载体线程继续]
    BLK --> PIN[钉住 Pinning: synchronized 块内阻塞/Native 调用<br/>无法卸载 占住载体!]
    PIN --> FIX[规避: 热点 synchronized 换 ReentrantLock<br/>JDK 24 已大幅改善(JEP 491)]
```

- **挂载/卸载的机制**：虚拟线程的栈存在堆上（可增长）；运行时「挂载」到载体线程（carrier，少量平台线程）；遇到阻塞点时 JVM 把栈内容复制到堆、载体线程释放去执行其他虚拟线程；就绪后再「装载」回某个载体继续执行——**「阻塞」从占用内核资源变成一次堆内存操作**。这就是为什么百万虚拟线程可行：同一时刻真正「在跑」的仍然只有核数个载体线程。
- **Pinning（钉住）的边界**：两种情况无法卸载——**synchronized 块内阻塞**（早期 JDK 21，监视器与载体绑定）与 native 方法内阻塞——此时虚拟线程「钉」在载体上，等于退化成平台线程占用。规避：热点阻塞路径用 ReentrantLock（JDK 24 的 JEP 491 已让 synchronized 也可卸载——大改善）；pinned 的观测：`jcmd Thread.dump_to_file`（含虚拟线程）或 JFR 的 pinned 事件。
- **与线程池的关系重定义**：虚拟线程「便宜到不该池化」（复用的收益归零）——新范式是**每个任务新建虚拟线程**（`Thread.ofVirtual().start` 或 `Executors.newVirtualThreadPerTaskExecutor()`）；但「限流」需求仍在：并发打下游的容量保护改用 **Semaphore**（限「同时在途请求数」而非「线程数」）——25 篇「有界资源治理」思想的新载体。
- **模式匹配增强（JDK 21 同批）**：record 模式（解构 record 字段：`case Circle(Point center, double r) ->`）+ switch 模式匹配正式化（40 篇 ADT 的完全体）——类型处理与虚拟线程同为 21 的两大旗舰。

## 3. 落地实践：虚拟线程的工程姿势

```java
// 1. 每任务一线程: 服务端新范式
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var req : requests) {
        executor.submit(() -> handle(req));   // 万级任务直接提交
    }
}   // try-with-resources: 等全部任务完成

// 2. 限流: 信号量限下游(代替线程池的数量管控)
Semaphore downstreamPermits = new Semaphore(50);   // 下游只承受 50 并发
executor.submit(() -> {
    downstreamPermits.acquire();
    try { callDownstream(); }
    finally { downstreamPermits.release(); }
});

// 3. 注意: 虚拟线程内避免长时间 CPU 计算(挤占载体)与池化虚拟线程(反模式)
```

五条纪律：① **虚拟线程不池化**（复用收益归零，池化反模式）；② **CPU 密集任务仍走平台线程池**（虚拟线程的优势是 IO 等待密集——挂起释放载体；CPU 密集只是换壳竞争）；③ **ThreadLocal 用量重估**（百万线程 × ThreadLocal 大对象 = 内存乘数——41 篇的 ThreadLocal 与 ScopedValue 演进在此交汇）；④ **pinned 检测常态化**（JFR pinned 事件 + synchronized 热路径审视）；⑤ **下游保护从「池」转「信号量」**（限并发不改模型）。

## 4. 生产视角：虚拟线程的事故形态

- **synchronized 热点钉住**：老代码的 synchronized 静态资源访问在虚拟线程内阻塞——载体线程被钉住，载体池耗尽全应用卡死（JDK 21 时代的头号事故形态）。整改：换 ReentrantLock 或升级 24+。
- **ThreadLocal 内存乘数**：每请求一个虚拟线程 × 每个 ThreadLocal 持大对象——「百万线程 × 1MB 值」的隐性内存放大。整改：值瘦身/显式传递/ScopedValue 迁移评估。
- **CPU 密集任务误入**：视频转码塞进虚拟线程——不挂起则占住载体，并发收益归零且互相挤压。「IO 密集用 VT、CPU 密集用平台池」的分野纪律。
- **池化虚拟线程的误用**：把虚拟线程池化（ Executors.newFixedThreadPool 包虚拟线程工厂）——重新引入数量管控，且丧失「每任务一线程」的简单性；池化治理心智在 VT 时代应整体退役。
- **无信号量的下游打爆**：「线程便宜了」错觉下无限并发打下游——线程不炸了，下游炸了（连接池/下游容量）。「限流对象从线程迁移到下游容量」的意识转换。

## 5. 主流系统怎么做：虚拟线程的生态采纳

| 层 | 采纳形态 | 机制要点 |
|---|---|---|
| Spring Boot 3.2+ | `spring.threads.virtual.enabled=true` 一键开启 | Tomcat 虚拟线程执行器——Web 请求全 VT 化 |
| JDBC/JDBC 驱动 | 阻塞调用天然适配 | 阻塞即卸载——同步 JDBC 代码获得高并发 |
| HTTP 客户端 | 同步 API + VT | 简单写法 + 高并发 |
| Netty | 仍用 EventLoop（NIO 事件驱动） | 网络事件层 VT 收益有限——NIO 与 VT 的边界（34 篇） |
| 框架内部 | synchronized 热点排查与整改 | 生态适配期（pinned 治理） |

规律：**虚拟线程的最大受益者是「同步阻塞式」的传统代码**——JDBC/REST 调用/文件 IO；事件驱动框架（Netty/Reactor）与 VT 是并行的两种范式（各有主场）。

## 6. 典型场景

- **高并发 IO 服务**（旗舰级）：网关/聚合服务——每请求一 VT + 信号量限下游，代码同步、吞吐异步。
- **存量系统渐进**（迁移级）：线程池参数调优停做，切 `newVirtualThreadPerTaskExecutor` + pinned 排查——存量收益最大路径。
- **CPU/IO 混合**（混合级）：IO 部分虚拟线程 + CPU 部分固定平台池——按任务性质分流的完整形态。

## 7. 与相邻概念的区别

- **虚拟线程 vs 线程池**：新原语 vs 旧治理——VT 让「线程数量管控」退役，但「下游容量保护（信号量）」「隔离」「监控」全部保留；25 篇的思想清单逐项过检。
- **虚拟线程 vs Reactor/响应式**：同步写法 + 平台调度 vs 异步声明式 + 应用层调度——VT 的口号「写同步代码，得异步吞吐」直接瞄准响应式的复杂度痛点；响应式在背压/流控场景仍有主场。
- **虚拟线程 vs Go 协程**：同为轻量并发（M:N 调度）——语义差异：goroutine 是语言级 channel 协作，VT 是 Thread 兼容（存量代码零改造获收益）。
- **本篇 vs 系列全部**：25 篇线程池的「数量管控」、24 篇 ThreadLocal 的「内存乘数」、34 篇 NIO 的「事件驱动主场」——虚拟线程与它们逐一划界；它不是替代所有并发机制，是「线程贵」这个前提的终结者。

## 8. 常见误区与不适用

- **「虚拟线程更快」**：单线程执行速度完全相同——VT 提升的是「并发承载量」（多任务场景），不是「单任务速度」；基准测单任务速度测不出差异。
- **「虚拟线程不需要任何并发知识」**：三难（原子/可见/有序）不变、共享状态纪律不变、下游保护不变——VT 只改「线程的成本模型」；19-25 篇全部依然有效。
- **「所有场景都换虚拟线程」**：CPU 密集（无挂起无收益）、NIO 事件驱动层（已是异步）、池化数万个对象的场景——三个不适域要显式排除。
- **「synchronized 在 VT 里必须全换 ReentrantLock」**：只改「热点阻塞路径」（阻塞频繁的 synchronized）；低竞争短临界区无需动——按 pinned 事件数据驱动整改。
- **不适用**：CPU 密集计算（平台池）；需要线程亲和的场景（ThreadLocal 重度依赖且值大）；JDK 21 以下运行时（语法能力不存在）。

## 9. 你们可能会问

- **虚拟线程什么时候挂起，什么时候不挂起？** JDK 的阻塞 API（IO/sleep/BlockingQueue/ReentrantLock/JDBC 等）都支持卸载；不卸载的：synchronized 块内阻塞（21，24 改善）与 native 调用——pinned 清单随版本收缩。
- **虚拟线程的数量上限？** 无硬限（受内存约束）——百万级可行（每 VT 初始栈几百字节到 KB 级 vs 平台线程 MB 级）；上限治理从「限线程」转为「限内存与下游」。
- **怎么排查虚拟线程卡死？** `jcmd <pid> Thread.dump_to_file -format=json`（含虚拟线程的 dump；传统 jstack 不含）——排查工具新形态；配合 JFR 的 pinned/submitted 事件。
- **ThreadLocal 在虚拟线程里的正确姿势？** 重估用量（内存乘数）+ 值瘦身 + 异步透传用「作用域值 ScopedValue」（预览演进中——不可变 + 作用域自动清理，24 篇的演进方向在此合龙）。
- **存量系统怎么渐进采纳？** 三步：JDK 21 升级 → IO 密集服务开 VT（Spring 一键开关）→ pinned 与 ThreadLocal 专项治理——先低风险服务试点，指标（吞吐/pinned 事件/内存）达基线后推广。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：虚拟线程 = JVM 托管的轻量线程（阻塞卸载载体、就绪再装载）——「一任务一线程」的简单模型在百万并发下重新可行；数量管控退役、下游信号量接棒、pinned 与 ThreadLocal 是两大新治理项。
- **链条复述**：平台线程贵 → 挂载/卸载机制 → 简单模型回归 → 信号量替代池管控 → pinned 边界与规避 → 模式匹配增强 → IO 密集主场 + CPU 密集边界。
- **失效点与边界**：单任务速度不变；CPU 密集不适用；synchronized pinning（21）需治理；ThreadLocal 内存乘数重估。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 挂载/卸载机制 + Pinning + 新工程范式 |
| Why | 「线程贵」前提终结，简单模型与高并发两全 |
| When | IO 密集高并发服务、存量渐进采纳 |
| Where | JVM 托管（堆上栈）+ 少量载体平台线程 |
| How | VT per task → Semaphore 限下游 → pinned 治理 → 分级灰度 |

💡 **实战提示**：VT 不池化；CPU 密集走平台池；pinned 事件进监控；ThreadLocal 值瘦身；下游信号量必配。

**开放问题**：虚拟线程 + 结构化并发 + 作用域值（ScopedValue）构成「新一代并发三件套」——当「每任务一线程」成为默认，「并发编程」会从专项技能退化为「框架自动行为」吗？剩下的专项会是什么？

**决策（何时用）**：IO 密集高并发服务推荐 VT（Spring 一键开启起步）；CPU 密集保留平台池；推荐「pinned 事件监控 + ThreadLocal 用量审计」作为 VT 采纳的两个前置检查项。

**Trade-off（代价与反方案）**：VT 用「调度与内存的新治理项（pinned/ThreadLocal 乘数）」换「简单模型回归 + 连接级并发」；保留 synchronized 用「pinned 风险」换「免改存量」；每任务一线程用「创建开销（虽小但存在）」换「无限管理的简单」——范式迁移的成本不在代码，在「治理清单的换代」。

**演进视角**：从 green thread（Java 1.0 的失败尝试）到平台线程一统（1.3+）到虚拟线程回归（21）——「轻量线程」在 Java 历史上走了一个圆环；这一次带着 25 年的工程积累（内存模型/并发工具/可观测性）回来，思想终于能落地。全系列 41 篇的终点恰是 Java 下一个二十年的起点：**语法与并发都已现代化，接下来轮到用它们重新书写整个生态**。
