# 异常体系与最佳实践

> **一句话摘要**：异常体系是一张「失败语义的分类表」——Throwable 分 Error（JVM 级不可救）与 Exception；Exception 分 checked（编译期强制处理：调用方必须面对的外部失败）与 unchecked/Runtime（编程缺陷：不该发生的发生）；最佳实践的核心是**语义分层（谁来处理谁抛）+ 不吞异常 + 不丢因果链**。

> **本文核心**：机制链 = **Throwable 树（Error/Exception/RuntimeException）→ 处理责任分配（checked 强制声明=契约、runtime=编程缺陷上抛）→ try-with-resources 管资源关闭 → 异常链（cause）保根因 → 全局兜底（线程未捕获异常处理器）**——异常设计的本质是「失败信息的路由设计」。

前置阅读：[对象与类](./3_对象与类-入门.md)。线程未捕获异常与线程池异常的联动见[线程池与异步编程](./25_线程池与异步编程-入门.md)。

## 1. 背景：checked 与 unchecked 的设计意图之争

Java 是少数有 checked 异常的主流语言——设计意图：**可恢复的外部失败**（文件不存在/网络断）必须被调用方显式面对（catch 或声明），编译器强制。实践二十年后行业形成修正共识：

- **checked 适合**：调用方能真正处理（重试/换路径/提示用户）的外部失败——文件 IO、部分业务校验失败；
- **unchecked（RuntimeException）适合**：编程缺陷（空指针/非法参数/状态非法）——这类失败的正确处理是「修代码」不是「catch」；
- **现代框架的选择**：Spring 的数据访问统一为 DataAccessException 体系（unchecked）——理由：调用方多数处理不了（catch 了也只敢记日志重抛），强制声明只制造签名噪音。**新项目默认 unchecked + 全局兜底**，checked 留给「调用方真能处理」的少数场景。

## 2. 核心机制：异常树、抛出与异常链

```mermaid
flowchart TD
    T[Throwable] --> ER[Error: JVM 级不可救<br/>OutOfMemoryError/StackOverflowError/NoClassDefFoundError]
    T --> EX[Exception]
    EX --> CK[checked: 编译期强制 catch 或 throws<br/>IOException/SQLException/业务校验异常]
    EX --> RUN[RuntimeException unchecked<br/>NPE/IllegalArgument/IllegalState/越界]
    THROW[throw 抛出] --> CAP[try-catch-finally / try-with-resources]
    CAP --> CHAIN[异常链: new XxxException(msg, cause)<br/>根因不断链]
    CHAIN --> GL[全局兜底: Thread.uncaughtExceptionHandler<br/>线程池场景见篇25]
```

- **异常链（cause）是最易丢的一环**：`catch (IOException e) { throw new BusinessException("失败"); }`——根因 e 被丢弃，线上只能看到「失败」不知道「为什么失败」。必须 `new BusinessException("失败", e)`——**包装不丢链**是最常用的保根因纪律。
- **try-with-resources**：实现 AutoCloseable 的资源（流/连接/锁）自动关闭（编译器生成关闭与抑制异常逻辑）——替代手写 finally 关闭（老写法还容易把 close 的异常覆盖业务异常）。
- **finally 的执行语义**：除非 JVM 退出，finally 必走——但 finally 里 return 会吞掉 try/catch 的返回与异常（禁手）；关闭资源请用 try-with-resources 而不是 finally 手写。
- **Error 不要 catch**：OOM/StackOverflow 是 JVM 级状态不可信——catch 了也只会让系统在损坏状态下继续跑。

## 3. 落地实践：业务异常的设计模板

```java
// 业务异常基类(unchecked): 带机器可读错误码 + 人可读信息
public class BizException extends RuntimeException {
    private final String code;                      // 错误目录的码(对照错误目录治理)
    public BizException(String code, String message) { super(message); this.code = code; }
    public BizException(String code, String message, Throwable cause) {
        super(message, cause); this.code = code;    // 保根因
    }
    public String getCode() { return code; }
}
// 抛出: 语义分层 -- 底层抛技术异常, 服务层翻译成业务异常, 顶层(全局处理器)统一出参
throw new BizException("ORDER_NOT_FOUND", "订单 " + orderId + " 不存在");
// 全局兜底: @RestControllerAdvice / Thread.uncaughtExceptionHandler 统一收口
```

五条纪律：① **异常分层抛**——底层抛技术异常（IO/SQL），服务层翻译为业务异常（含错误码），接口层全局处理器统一出参；② **包装必带 cause**；③ **错误信息带上下文**（「订单 123 不存在」远强于「查不到」）；④ **catch 里要么处理要么包装上抛，不空吞**（空 catch 是线上排障的头号公敌）；⑤ **不要用异常做流程控制**（异常构造含填栈成本，且语义污染——预期内的分支用返回值/Optional）。

## 4. 生产视角：异常体系的事故形态

- **空 catch 的静默失败**：`catch (Exception e) {}`——消息没发送、数据没落库，系统表面正常。排查时日志里什么都没有（异常根本没记录）。code review 对空 catch 一票否决。
- **e.printStackTrace() 的失控输出**：打到 stdout 而非日志框架——日志收集不到、线程交错混乱。统一走日志框架（带堆栈作为参数传入）。
- **异常吞掉根因的排障泥潭**：多层包装不传 cause——线上只有顶层「业务失败」，底层为什么失败成谜（只能靠时间点猜）。异常链纪律是排障效率的第一决定因素。
- **catch (Exception e) 的过宽捕获**：把编程缺陷（NPE）也捕获包装成业务异常——缺陷被业务语义掩盖，该修的代码 bug 被「业务失败」话术遮蔽。捕获范围按「能处理的最小集」收敛。
- **线程池里的异常消失**：submit 的任务抛异常被 Future 静默吞掉（不 get 就没人知道）——线程池场景的异常必须显式处理（25 篇专讲）。

## 5. 主流系统怎么做：异常的生态惯例

| 层 | 惯例 | 机制要点 |
|---|---|---|
| 框架异常翻译 | Spring DataAccessException 体系 | 底层 checked 异常统一翻译成 unchecked 层次体系——调用方按需捕获 |
| 全局兜底 | @RestControllerAdvice + @ExceptionHandler | 接口层统一出参（错误体对照 REST 篇 RFC 9457） |
| 业务错误码 | 错误目录 + BizException(code,msg) | 错误码全局治理（REST 篇错误目录机制） |
| 资源关闭 | try-with-resources / AutoCloseable | 编译器生成关闭逻辑 + 抑制异常处理 |
| 日志记录 | log.error("ctx {}", id, e) | 上下文 + 异常对象作最后一个参数（堆栈完整） |

规律：**行业收敛到「unchecked 为主 + 全局兜底 + 错误码体系」**——checked 的使用收缩到「调用方真能处理」的窄域。

## 6. 典型场景

- **接口层**（对外级）：全局异常处理器统一出参（错误体 + 错误码 + 请求标识）——REST 篇的错误设计闭环。
- **资源操作**（IO 级）：try-with-resources 包流/连接——关闭零遗漏。
- **异步任务**（并发级）：线程池任务显式 try-catch + 兜底处理器——异常不失踪。

## 7. 与相邻概念的区别

- **异常 vs 返回值/Optional**：异常是「非预期失败的通道」，Optional/返回值是「预期内可能为空/失败」的表达——预期内失败（查询可能没结果）用返回值，非预期失败（连接断了）用异常。
- **Error vs Exception**：JVM 级不可救 vs 程序可处理——catch Error 是禁区（除极特殊的捕获诊断框架）。
- **业务异常 vs 技术异常**：业务失败（余额不足）走业务异常+错误码给用户；技术失败（DB 断连）走技术异常+告警给运维——两类失败的「读者」不同，出口也不同。
- **本篇 vs 全局兜底（线程池篇）**：本篇是异常的「单线程语义」，线程池场景的异常传递有独立机制（Future 吞异常/UncaughtExceptionHandler）——25 篇专讲。

## 8. 常见误区与不适用

- **「checked 异常更安全所以尽量用」**：强制声明只在「调用方能处理」时有价值——处理不了的声明是签名噪音（现代框架的投票已说明）。
- **「catch (Exception e) 更保险」**：过宽捕获掩盖编程缺陷——按能处理的最小集捕获，兜底交给全局处理器。
- **「异常信息给用户看就行」**：用户要的是「可行动的话术」（错误码+提示），排障要的是「根因与上下文」（日志）——两个读者两层出口，别混。
- **「finally 里做清理 + return」**：finally return 吞异常与返回值——清理用 try-with-resources，finally 只做纯清理不 return。
- **不适用**：异常不做流程控制（性能与语义双输）；高频可预期分支（用返回值）——异常成本高（填栈），只服务真正的失败。

## 9. 你们可能会问

- **throw 与 throws 的区别？** throw 是动作（抛出实例）；throws 是声明（方法签名标注可能抛的 checked 异常）——一个管行为一个管契约。
- **finally 一定执行吗？** 几乎一定（System.exit/JVM 崩溃/线程被强杀除外）——但 finally 里的 return/抛异常会改变控制流，纪律是 finally 只放清理。
- **自定义异常该继承哪个？** 业务失败继承 RuntimeException（现代主流）；要强制调用方处理的外部失败继承 Exception——按「调用方能否处理」定。
- **为什么异常构造慢（填栈）？** 构造时抓当前线程栈快照供 getStackTrace——高频路径可用「禁填栈」的自定义异常（重写 fillInStackTrace）但属优化特例，先确认真的是热点。
- **全局处理器和局部 catch 什么关系？** 局部 catch 处理「此处能处理的」，其余上抛到全局兜底——局部处理是例外，全局兜底是默认；反过来（层层 catch）是噪声源。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：异常 = 失败语义的路由设计——checked 面向可处理的外部失败、runtime 面向编程缺陷、业务异常带错误码、全局兜底统一出参、异常链保根因。
- **链条复述**：Throwable 树 → 处理责任分配 → try-with-resources 管资源 → 包装必带 cause → 全局兜底 + 错误目录。
- **失效点与边界**：异常不做流程控制；Error 不 catch；线程池场景异常有独立传递机制（25 篇）。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | Throwable 树 + checked/unchecked 分工 + 异常链 + 全局兜底 |
| Why | 失败信息的路由质量决定排障效率与用户体验 |
| When | 异常体系设计、code review（空 catch 一票否决）、排障 |
| Where | 底层技术异常 → 服务层业务异常 → 接口层全局出参 |
| How | 分层抛 → 包装带 cause → 上下文进 message → 错误码进目录 |

💡 **实战提示**：空 catch 与 printStackTrace 一票否决；包装必带 cause；message 带上下文参数；异常不做流程控制。

**开放问题**：Kotlin/Swift 等新语言全部放弃 checked——Java 会在未来版本软化 checked 语义吗，还是保持「历史选择」永不回头？

**决策（何时用）**：新项目推荐「unchecked 业务异常 + 错误目录 + 全局兜底」现代组合；checked 留给调用方真能处理的窄域；推荐「空 catch/printStackTrace」进评审红线清单。

**Trade-off（代价与反方案）**：checked 用「签名噪音」换「强制面对」；unchecked 用「编译器不保」换「签名干净 + 全局兜底灵活」；详细错误信息用「轻微性能与信息暴露风险」换「排障效率」——脱敏红线（不外泄内部细节）是详细化的边界。

**演进视角**：从 Java 1.0 的 checked 理想（所有失败显式面对）到现代框架的 unchecked 实践——异常哲学二十年完成一次范式转向；RFC 9457 式的结构化错误体又把「失败的表达」标准化回协议层——语言与协议两层正在合流。

## 质疑者追问链

**质疑：异常体系 为什么设计成这样，不那样设计？**
异常体系 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——异常处理 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。

## 量级分档视角

| 量级 | 异常体系的形态变化 | 关注点 |
|---|---|---|
| 10 万级 | 入门阶段，异常处理默认配置即可 | 语法正确性 |
| 千万级 | 需要关注 异常链路 的取舍 | 性能瓶颈与参数调优 |
| 亿级 | 异常处理 成为架构决策的核心变量 | 架构选型与底层机制 |

量级每上一档，对 异常处理 的容忍度就降一级——**同样的代码在十万级没问题，在亿级就是事故预备役**。
