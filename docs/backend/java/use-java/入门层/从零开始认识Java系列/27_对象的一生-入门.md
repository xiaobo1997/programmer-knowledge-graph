# 对象的一生

> **一句话摘要**：`new Object()` 的完整旅程——**类加载检查 → 堆分配（指针碰撞/TLAB）→ 零值初始化 → 构造器 → 对象头（Mark Word + 类型指针）落位 → 引用上手 → 被引用图收养 → 不可达 → GC 回收**；沿途的 JIT 优化（逃逸分析/标量替换/栈上分配）可能让「对象从未真正出生」——本篇把对象生命周期与优化机制一次讲穿。

> **本文核心**：机制链 = **创建五步（检查/分配/零值/构造/引用）→ 对象在堆上的三段布局（对象头/实例数据/对齐填充）→ Mark Word 的多态复用（hash/GC 年龄/锁状态——20 篇锁升级的物理载体）→ 逃逸分析三件套（栈上分配/标量替换/锁消除）→ 死亡判定（可达性分析而非引用计数）→ 引用四强度（强软弱虚）决定存活宽限**——「对象的一生」是内存区域（26 篇）与 GC（28 篇）之间的旅程叙事。

前置阅读：[运行时内存区域](./26_运行时内存区域-入门.md)。死亡判定的下游（回收算法与收集器）见 28-29 篇。

## 1. 背景：为什么「对象的旅程」值得单独一篇

对象是 Java 世界的最小公民，它的旅程串起 JVM 的全部机制：创建走类加载与内存分配（30/26 篇）、布局决定锁与 GC 的物理载体（20 篇 Mark Word）、死亡判定决定 GC 的算法设计（28 篇）。「对象的一生」是把这些散点串成一条线的叙事骨架——面试高频（对象创建几步/为什么需要可达性分析）的背后全是机制理解。

## 2. 核心机制：创建五步与对象布局

```mermaid
flowchart TD
    NEW[new Object] --> K1[1 类加载检查: 类已加载否则先走类加载流程]
    K1 --> K2[2 分配内存: 指针碰撞/空闲列表<br/>TLAB 线程私有缓冲优先 免竞争]
    K2 --> K3[3 零值初始化: 字段清零 内存提前划分的理由]
    K3 --> K4[4 设置对象头: Mark Word+类型指针<br/>hash 分代年龄 锁状态 | 指向类元数据]
    K4 --> K5[5 构造器执行: 按代码逻辑初始化字段]
    K5 --> USE[引用到手 对象可及]
    LAYOUT[堆上布局三段] --> LY1[对象头: Mark Word+Klass Pointer]
    LAYOUT --> LY2[实例数据: 各字段值]
    LAYOUT --> LY3[对齐填充: 8 字节整数倍]
```

- **TLAB（Thread Local Allocation Buffer）**：堆本身是共享区（并发分配要竞争）——JVM 给每个线程预划一小块私有缓冲，TLAB 内分配只是指针移动（无竞争无锁）；TLAB 用完再申请新缓冲。「共享区的私有化切片」与号段模式（ID 篇）、LongAdder 的 Cell 分散是同一思想的第 N 次重演。
- **对象头 Mark Word 的多态复用**：64 位里塞了 hash（25 位）、GC 分代年龄（4 位）、锁状态位（2 位）与锁信息——**同一字段的位布局随锁状态切换**（20 篇锁升级的物理载体）；GC 年龄也在这——「对象头是对象与 JVM 的通信总线」。
- **逃逸分析三件套**（JIT 优化）：① **栈上分配/标量替换**——未逃逸出方法的小对象，拆成标量直接在栈帧分配（「对象」从未在堆上诞生，GC 负担直接消失）；② **锁消除**——未逃逸对象上的 synchronized 被证明无共享 → 直接去掉（20 篇提到的 JIT 锁优化）；③ **同步省略**同理。逃逸分析是「JIT 对 Java 抽象的免费补偿」——写代码时不必为它改变风格，但要知道它存在（微基准不预热测的就是「没被优化前」的假数据）。
- **死亡判定：可达性分析**——从 GC Roots（栈引用/静态字段/JNI 引用等）出发，引用图可达即活、不可达即死。**为什么不用引用计数**：互相引用的孤岛（A↔B 无外部引用）计数永不为零——可达性分析天然解决循环引用；代价是 STW 的根扫描（并发收集器把它优化为并发标记）。

## 3. 落地实践：减少对象负担的工程手法

1. **对象复用**：高频短命对象（SimpleDateFormat 类）用池/ThreadLocal；但**现代 JVM 的短命对象分配极快**（TLAB 指针移动）——「对象池滥用」反而在老年代留垃圾，复用前先确认「分配真的是瓶颈」。
2. **大对象警惕**：超 Eden 的大对象直接进老年代（免来回拷贝）——大数组/大集合的频繁创建直接顶爆老年代；流式处理替代一次性大对象。
3. **引用强度选型**：缓存用软引用（内存不足才回收）/元数据用弱引用（GC 即清）/资源释放钩子用虚引用（Cleaner 机制——直接内存的回收通道，26 篇）。
4. **finalize 早已废弃**：执行时间不保证、 resurrect 对象、性能杀手——清理用 try-with-resources 或 Cleaner（Java 9+）。

## 4. 生产视角：对象生命周期的形态

- **短命对象的健康形态**：TLAB 快速分配、Young GC 快速回收——「朝生夕死」是 GC 最爱的形态（复制算法专治）；接口每请求分配几百个对象完全健康。
- **中命对象的晋升之路**：Survivor 区年龄递增到阈值晋升老年代——「该死的没死」对象（缓存/会话）撑大老年代，Full GC 频率上升。调参视角：Survivor 太小导致提前晋升。
- **永不死对象的堆积**：static 集合/缓存的慢性泄漏（26 篇形态）——老年代基线抬升不回落；MAT 支配树定位。
- **逃逸分析的「没出生」**：日志占位符、小迭代临时对象在 JIT 优化下可能从未进堆——「分配了 10 亿对象」的压测报告与「堆很干净」的监控同时成立，就是它。

## 5. 主流系统怎么做：生命周期的 JVM 实现演进

| 环节 | 现代实现 | 演进要点 |
|---|---|---|
| 分配 | TLAB + 指针碰撞 | 分配「接近免费」（数十 ns 量级） |
| 布局 | 压缩指针（4GB→32GB 可指）+ 字段重排 | 对齐与访问效率的平衡 |
| 存活判定 | 并发标记（G1/ZGC） | STW 根扫描最小化 |
| 引用 | Reference 四族 + Cleaner | finalize 的现代替代 |

规律：**分配越来越快、判定越来越并发**——「对象便宜」的现代结论（分配与年轻回收）是「池化滥用」反思的技术基础。

## 6. 典型场景

- **GC 调优的对象视角**（调优级）：先看「对象的分配速率与生命周期分布」（GC 日志/分配剖析），再选收集器参数——对象的生死分布决定 GC 形态。
- **内存泄漏排查**（泄漏级）：MAT 的不可达/可达分析 + 支配树——对象旅程的「验尸报告」。
- **微基准陷阱识别**（基准级）：未预热测的是「逃逸分析未生效前」的行为——JMH 的 warmup 是对 JIT 优化的尊重。

## 7. 与相邻概念的区别

- **可达性分析 vs 引用计数**：后者有循环引用死锁、前者无——主流 JVM 全选可达性；Python 用引用计数 + 补充循环检测的混合路线。
- **强/软/弱/虚引用**：强（永不回收）/软（内存不足才收——缓存）/弱（下次 GC 必收——元数据）/虚（回收通知——资源清理钩子）——四档「存活宽限期」。
- **对象头 vs 类元数据**：对象头在对象上（Mark Word/类型指针）；类元数据在元空间（方法区）——对象通过类型指针「知道自己是谁」。
- **本篇 vs GC 篇（28 篇）**：本篇到「不可达」为止；28 篇讲「不可达之后怎么回收」——生死分界。

## 8. 常见误区与不适用

- **「对象创建很慢所以要池化一切」**：现代 TLAB 分配接近免费、Young GC 对短命对象极快——池化的前提是「构造确实昂贵」（连接/线程）或「对象确实长寿」，否则负优化。
- **「手动置 null 能帮 GC」**：仅在「长方法中后续不再使用的大对象」上有意义（帮助提前不可达）——方法短小/局部作用域的常规场景，JIT 与作用域已足够；「处处置 null」是仪式性代码。
- **「System.gc() 能救内存急」**：只是「建议」Full GC（可能被禁用 -XX:+DisableExplicitGC）——且 Full GC 全停顿；生产禁用调用方使用。
- **「StackOverflow 说明内存不足」**：栈深超限不是内存不够（调大 -Xss 只能治递归，治不了无限递归）——两个问题两副药（26 篇的分诊）。
- **不适用**：GC 算法细节（28 篇）；JIT 编译细节（31 篇）；对象持久化序列化（另一域）。

## 9. 你们可能会问

- **对象的 hashCode 存在哪？** Mark Word（无锁态）——但被计算过且对象进入偏向/轻量态后会被迁移（对象头空间被锁信息征用）——「hash 会搬家」是锁升级与 hashCode 的联动细节。
- **TLAB 是什么，会浪费内存吗？** 线程私有分配缓冲（Eden 的一小块）——有浪费（TLAB 剩余不足以放新对象时剩余空间成「空洞」，用哑元填充）但换来无锁分配，值得。
- **为什么 finalize 被废（JEP 421）？** 执行无保证（可能永不执行）、 resurrect（finalize 里复活 this）、性能拖累（带 finalizer 的对象至少两次 GC 才回收）——Cleaner（显式注册 + 幻象引用）是替代。
- **逃逸分析怎么观察？** `-XX:+PrintEliminateAllocations`（诊断模式）或 JITWatch 看 JIT 决策——「标量替换」成功时该对象不出现堆分配事件。
- **怎么知道一个对象「多大」？** 浅大小（自身：对象头+字段）vs 保留大小（自身+独占引用的下游）——MAT 的 shallow/retained heap 区分是泄漏分析的核心概念。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：对象的一生 = 创建五步（类检查/TLAB 分配/零值/对象头/构造）→ 引用图中的存活 → 不可达 → 回收；Mark Word 是锁与 GC 的物理载体，逃逸分析可能让对象「从未出生」。
- **链条复述**：创建五步 → 布局三段 → Mark Word 多态复用 → 逃逸分析三件套 → 可达性分析 → 引用四强度 → finalize 废弃与 Cleaner 接棒。
- **失效点与边界**：未逃逸对象可能不进堆；分配便宜不等于池化无害；finalize 别用（Cleaner 替代）。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | 创建五步 + 布局三段 + 逃逸分析 + 可达性判定 |
| Why | 对象旅程串起类加载/内存/锁/GC 全部 JVM 机制 |
| When | GC 调优、泄漏排查、微基准、锁机制深挖 |
| Where | 堆（TLAB→Eden→Survivor→老年代）与栈（标量替换） |
| How | 看分配与生死分布 → 定位泄漏持有链 → 尊重 JIT 预热 |

💡 **实战提示**：短命对象是健康形态；大对象警惕直进老年代；finalize 换 Cleaner；微基准用 JMH 尊重 JIT。

**开放问题**：Valhalla 值类型如果落地，「无对象头、无引用、平铺内存」的值对象会改写本篇的「一生」（无 Mark Word、无可达性标记、显式生命周期）——值类型时代的「对象的一生」会变成「值的一生」吗？

**决策（何时用）**：GC 调优先看对象生死分布；泄漏排查用 dump 验尸；推荐「对象分配速率与生命周期分布」作为 JVM 健康度的第一视角（先于任何参数）。

**Trade-off（代价与反方案）**：TLAB 用「小浪费（空洞填充）」换「无锁分配」；逃逸分析用「JIT 编译成本」换「堆零负担」；可达性分析用「标记成本」换「循环引用免疫」——JVM 在对象生命周期的每一步都做了微观权衡，理解权衡才能理解参数。

**演进视角**：分配从「全堆锁」到 TLAB，判定从「全程 STW」到并发标记，逃逸分析从无到标配——「对象的一生」的每个环节都在持续加速；终点方向的极致是 ZGC 的亚毫秒停顿与 Valhalla 的值类型平铺——「对象」这一抽象的成本曲线仍在下行。
