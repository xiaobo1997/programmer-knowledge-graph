# 枚举与金额精度

> **一句话摘要**：两个「金融级代码」的地基件——**枚举（enum）是类型安全常量的终极形态**（编译期穷举 + 单例天然保证 + 自带行为），**BigDecimal 是金额的唯一正确载体**（double 的二进制浮点误差在钱上不可接受）；本篇把两个「金融刚需」合在一篇：枚举管状态与类型、BigDecimal 管钱，加「舍入模式」这个最容易翻车的点。

> **本文核心**：机制链 = **enum 本质是 final 类的语法糖（继承 java.lang.Enum、实例即单例、values/valuesOf 编译生成）→ 不可变 + 枚举内行为方法 = 类型安全状态机 → 金额：double 的二进制误差（0.1 表不出来）→ BigDecimal(string 构造/不可变/精度与标度分离) → 每次运算必须显式舍入模式 → 除不尽不定标度必炸**——枚举与 BigDecimal 的组合（币种枚举 + 金额计算）是交易系统的地基件。

前置阅读：[对象与类](./3_对象与类-入门.md)（不变量守卫）。事务与对账的金额流转见[分布式事务系列](../../../../../architecture/system-design/distributed-transaction/入门层/从零开始认识分布式事务系列/13_金融场景实战-入门.md)。

## 1. 背景：为什么这两件放一篇

 Java 里「金额算错」与「状态写歪」是资金类系统最高频的两类缺陷，根因也一致：**用了默认的便利方案**（double 与魔法数字/字符串状态）。行业约束下的正确姿势：状态用枚举（编译器穷举 + IDE 补全 + 遗漏即报错）、金额用 BigDecimal（十进制精确）+ 每次运算显式舍入。两件都是「多写三行代码，换掉一类资损事故」的投资。

## 2. 核心机制一：enum 的本质与能力

```mermaid
flowchart TD
    E[enum OrderStatus] --> M[本质: final class extends Enum<br/>实例 public static final 单例]
    M --> C[编译生成: values()/valueOf(String)<br/>name()/ordinal()/compareTo 按 ordinal]
    E --> B[可带字段与行为: 构造器/方法/覆写<br/>抽象方法各实例实现(实例级多态)]
    E --> U[工程用法: EnumMap/EnumSet 高性能容器<br/>switch 穷举编译期检查 + 单例最佳实践]
    R[ordinal 陷阱] --> X[依赖 ordinal 存储/传输 = 顺序变更即错乱<br/>持久化用 name/code 不用 ordinal]
```

- **枚举是单例的最佳实践**：实例由 JVM 保证唯一（反射也无法创建——构造器受语言层保护，反射 clone/序列化路径均被 Enum 基类封死），比「私有构造器 + 静态实例」的手写单例更完备（Effective Java 的单例首选）。
- **枚举可带行为**：每个实例覆写抽象方法（`APPROVED { public boolean payable() { return true; } }`）——枚举从「常量集合」升级为「类型安全的状态机」；配套 EnumMap/EnumSet（内部数组实现，比 HashMap 快且省）。
- **ordinal 陷阱（高频事故）**：枚举的序号随定义顺序变化——数据库存 ordinal、接口传 ordinal、排序依赖 ordinal，任何「中间插入一个枚举值」都引发历史数据错乱。**持久化与传输永远用 name 或自定义 code 字段**，ordinal 只用于内存内临时排序。
- **switch 穷举检查**：对枚举的 switch（表达式形式）漏一个分支编译器告警（配合 sealed 的穷举检查是同族机制）——新增枚举值时编译器替你找出所有遗漏点，这是枚举相对字符串常量的核心工程红利。

## 3. 核心机制二：BigDecimal 的精度与舍入

```mermaid
flowchart TD
    D[double 二进制浮点] --> X[0.1 无法精确表示<br/>0.1+0.2 = 0.30000000000000004]
    X --> BD[BigDecimal: 不可变 任意精度十进制<br/>value(unscaledValue) x 10^-scale]
    BD --> R1[构造: new BigDecimal(0.1) 错! 继承 double 误差<br/>new BigDecimal('0.1') 或 BigDecimal.valueOf(0.1) 对]
    BD --> R2[运算: 不可变 每次运算返回新对象]
    BD --> R3[除法: 除不尽必须指定 scale + RoundingMode<br/>否则 ArithmeticException]
    R3 --> RM[舍入模式: HALF_UP 四舍五入 / HALF_EVEN 银行家<br/>DOWN/UP/Ceiling/Floor 场景各异]
    RM --> CMP[比较: equals 含 scale 判定(1.0 != 1.00)<br/>数值比较用 compareTo]
```

- **double 为什么错**：二进制浮点无法精确表示多数十进制小数（0.1 = 二进制无限循环）——「加起来差一分钱」的对账事故全是它的锅；double 只用于「不涉及钱的量」（比例展示、科学计算）。
- **构造纪律**：`new BigDecimal(double)` 把 double 的误差原样带入（0.1 变 0.1000000000000000055511…）——**必须用字符串构造或 `BigDecimal.valueOf`**（valueOf 内部走 Double.toString 的十进制表示）。这是 BigDecimal 第一戒律。
- **不可变与链式**：加减乘除都返回新对象（`a.add(b)` 不改 a）——「以为 add 改了自己」是新人高频 bug；除法除不尽（1/3）不指定精度直接抛 ArithmeticException（防你静默丢精度——强制显式舍入是机制级保护）。
- **舍入模式的选择即业务规则**：HALF_UP（常规四舍五入）、HALF_EVEN（银行家舍入，统计场景减少累积偏差）、DOWN（截断，佣金分摊向商户不利/有利方向要明确业务规则）——**舍入模式不是技术选择，是业务与合规决策**，必须落文档。
- **equals 与 compareTo 的坑**：`new BigDecimal("1.0").equals(new BigDecimal("1.00"))` 为 false（scale 不同）——**数值比较永远 compareTo**；配合 `stripTrailingZeros()` 统一展示。

## 4. 生产视角：精度与状态的事故形态

- **double 累计误差的对账差异**：金额用 double 逐笔累加，日终对账差几分钱且不可复现——二进制误差随累加显形。整改：全链路 BigDecimal + 单位统一为「分」（long）是更彻底的方案（无小数则无舍入问题——电商行业主流是「分」为单位的 long）。
- **ordinal 入库的错乱**：状态枚举按序插入新值后，历史记录的「已完成」变「已取消」——ordinal 持久化的经典翻车；修复要数据迁移，代价远高于当初用 name/code。
- **舍入方向不一致的资损**：手续费计算 A 服务 HALF_UP、B 服务 DOWN——同一笔钱两边算出不同结果，对账差异常态化。舍入模式全局统一进规范。
- **BigDecimal 字段被 JSON 序列化成 double**：框架默认把 BigDecimal 过一道 double（精度又丢回去了）——序列化配置要保留 BigDecimal 原样（或字符串化）。

## 5. 主流系统怎么做：金额的行业惯例

| 环节 | 行业惯例 | 机制要点 |
|---|---|---|
| 金额存储 | long 分（整数）/ BigDecimal | 整数无舍入问题；BigDecimal 留给需要小数位的展示与折算 |
| 币种 | 枚举 + 币种精度表 | 不同币种小数位不同（日元 0 位/美元 2 位）——精度随币种 |
| 状态流转 | 枚举状态机 | 穷举 + switch 检查 + EnumMap 转移表 |
| 汇率计算 | BigDecimal + 显式舍入模式 | 舍入方向是业务合规决策 |
| 对账 | 逐笔 compareTo + 总额核对 | 见对账篇（分布式事务系列） |

规律：**「long 分 + 枚举状态 + 显式舍入」三件套覆盖绝大多数资金场景**——BigDecimal 是「必须小数」场景的兜底，不是默认起点。

## 6. 典型场景

- **交易订单**（资金级）：金额字段 long 分 + 订单状态枚举状态机——本篇组合的标准应用。
- **计费与分摊**（合规级）：手续费/佣金按比例分摊——BigDecimal + 舍入模式 + 「分摊差额归尾笔」的行业惯例。
- **配置开关**（工程级）：枚举定义开关状态 + EnumMap 存配置——类型安全的配置管理。

## 7. 与相邻概念的区别

- **枚举 vs 常量类（int 常量）**：类型安全（不能传任意 int）vs 常量可任意传——枚举把「合法取值」变成编译器可检查的类型；常量接口/常量类是历史方案（Effective Java 明确否决）。
- **BigDecimal vs long 分**：小数表达力 vs 无舍入问题——「能整数就整数」；BigDecimal 服务汇率/比例/展示这类必须小数的场景。
- **scale vs precision**：scale 是小数位（标度），precision 是总有效位——`1.230` 的 scale=3；stripTrailingZeros 改 scale 不改数值；「精度问题」多数时候是「标度问题」。
- **本篇 vs 金融实战（事务系列）**：本篇是「单机计算正确性」，金融实战篇是「跨系统资金一致性」——先保证算得对，再保证对得上。

## 8. 常见误区与不适用

- **「BigDecimal 用了就精确」**：`new BigDecimal(double)` 照样带误差；除法不指定舍入照样炸——BigDecimal 的正确性是「用对构造 + 显式舍入」换来的，不是类名自带的。
- **「枚举想加就加」**：枚举值是「类型契约」——删除/重排枚举值是破坏性变更（name 持久化场景删除即历史数据悬空）；枚举变更要走与 API 变更同级的管理。
- **「compareTo 为 0 就相等」**：对 BigDecimal 正确（compareTo 忽略 scale）；对枚举 compareTo 是 ordinal 比较——「比较语义」逐类型确认，不跨类型套用。
- **「金额展示直接 toString」**：`1E+2` 这类科学计数法会出现（stripTrailingZeros 后）——展示用 `toPlainString()` 或 setScale 固定位数。
- **不适用**：科学计算（double/浮点库才是主场）；高频游戏数值（性能敏感的内部数值可用 long/浮点，出口再换）——精度纪律服务于「钱与合规」。

## 9. 你们可能会问

- **为什么枚举能防反射与反序列化创建实例？** Enum 基类在构造/clone/readObject/readResolve 各路径都做了语言层封禁——反射的 `newInstance` 对 enum 直接抛异常；这是「单例最佳实践」结论的机制依据。
- **金额到底用 long 分还是 BigDecimal？** 判据：业务是否需要小数位语义——纯交易收付用 long 分（无舍入），汇率折算/费率计算/展示层用 BigDecimal；两者并存时边界清晰（内部分、出口换算）。
- **HALF_EVEN（银行家舍入）为什么存在？** 四舍五入对「5」恒向上，统计累积有系统性偏差——HALF_EVEN 向最近偶数舍入使偏差中性；统计与清分场景的行业惯例。
- **枚举序列化到 JSON 用什么？** name（默认）或自定义 code + @JsonValue——与持久化口径一致；反序列化要处理「未知值」（新增枚举值在老消费方）——容错策略进规范。
- **怎么审计代码里的金额精度风险？** 静态扫描（double/float 出现在金额字段命名附近即标记）+ 评审规则（金额运算必查构造与舍入）——用「字段命名规范」让机器可查。

## 10. 一句话总结 + 5W 速记卡 + 自测三问

**🎯 核心带走**：

- **核心一句话**：枚举 = 类型安全的状态机（单例保证 + 穷举检查 + 禁 ordinal 持久化）；BigDecimal = 金额唯一载体（字符串构造 + 不可变 + 显式舍入 + compareTo）——两者是资金类代码的地基件。
- **链条复述**：double 二进制误差 → BigDecimal 十进制精确 → 构造与舍入两戒律 → 枚举穷举与 ordinal 陷阱 → long 分 + 枚举状态 + 显式舍入的行业三件套。
- **失效点与边界**：科学计算不适用；枚举变更按破坏性管理；「能整数就整数」优先于 BigDecimal。

**5W 速记卡**：

| 维度 | 内容 |
|---|---|
| What | enum 机制 + BigDecimal 精度/舍入 + 行业三件套 |
| Why | 默认便利方案（double/魔法数）在资金场景必然出错 |
| When | 金额/状态/币种的设计与对账差异排查 |
| Where | 交易、计费、清结算、配置状态 |
| How | long 分优先 → BigDecimal 兜底 → 枚举状态机 → 舍入全局统一 |

💡 **实战提示**：字符串构造 BigDecimal；除法必带舍入；compareTo 判等；持久化用 name/code 禁 ordinal；金额字段命名规范让扫描器可查。

**开放问题**：Java 值类型（Valhalla）落地后，「long 分」与「金额 record」的 expressing 力量对比会变化吗——金额类型会不会被标准化进语言/标准库？

**决策（何时用）**：资金场景全量适用（行业既定答案）；非资金高频数值场景可用 double；推荐「金额字段命名规范 + 静态扫描」作为精度风险的前置防线。

**Trade-off（代价与反方案）**：BigDecimal 用「对象开销与显式舍入成本」换「十进制精确」；long 分用「表达力受限」换「零舍入问题」；枚举用「变更管理成本」换「类型安全与穷举检查」——三者的共同反面都是「默认便利方案」，而默认方案的钱账最终都由对账差异与资损来结。

**演进视角**：从 double 时代的「测试时才发现差一分」到 BigDecimal 静态扫描进 CI——精度纪律正在从「老工程师经验」变成「机器可查规范」；枚举从常量集合到 sealed/穷举检查的配套——类型安全的地基件仍在持续加固。

## 质疑者追问链

**质疑：枚举与金额精度 为什么设计成这样，不那样设计？**
枚举与金额精度 的设计是在「易用性、安全性、性能」三者之间做取舍——没有完美的选择，只有场景匹配的选择。理解取舍比记住结论更有价值。

**追问一层：如果换个场景，这个设计还成立吗？**
不完全成立——枚举实例数 从十万级涨到千万级时，很多默认假设失效；理解设计边界，才能判断「什么时候需要换方案」。

**再深一层：底层原理和上层 API 之间是什么关系？**
上层 API 是底层机制的抽象封装——机制不变，API 可以演进；反过来，机制变了 API 必须跟着变。这就是为什么「理解机制」比「记住 API」更保值。
